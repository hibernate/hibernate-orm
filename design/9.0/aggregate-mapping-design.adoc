= Aggregate Runtime Model Design
:toc:

The boot-time aggregate mapping redesign is complete.

The binding pipeline distinguishes aggregate storage before binding component
members, targets those members to an `AggregateMemberContainer`, and records a
data-only `AggregateComponentBinding` for ordered materialization. Aggregate
members are not temporarily registered as physical table columns, and aggregate
metadata completion is not a callback-style second pass.

The resulting boot handoff is:

[source]
----
ComponentSource
    -> AggregateValuePlan
    -> ComponentMemberTarget / AggregateMemberContainer
    -> AggregateComponentBinding
    -> AggregateMappingFinalizer
    -> Component / AggregateColumn / database aggregate metadata
----

`Component` and `AggregateColumn` remain the compatibility projection consumed
by the existing runtime and schema model. This document does not propose
reopening the boot-time mapping design without a concrete unsupported mapping
shape.

The remaining work is runtime-focused:

* represent aggregate storage explicitly in the runtime mapping model;
* make that representation authoritative for runtime consumers;
* centralize dialect-specific aggregate access behavior;
* migrate SQL selection, result assembly, mutation, JDBC access, and query-path
  handling away from inference based on boot mapping details.

== Problem Statement

The boot model knows that an embeddable is stored as one aggregate column, but
the runtime model still reconstructs that fact from `Component`,
`AggregateColumn`, JDBC type information, child selectable expressions, and
dialect hooks.

This spreads aggregate decisions across:

* runtime embeddable initialization;
* SQL AST path and selectable construction;
* domain-result and fetch assembly;
* aggregate JDBC type resolution;
* partial and whole-value mutation;
* schema and database aggregate support;
* special handling for nested aggregates and aggregate arrays.

The existing behavior supports SQL `STRUCT` / UDT, JSON, XML, nested aggregates,
aggregate arrays, collection elements, and map keys and values. The problem is
not a missing boot representation for those shapes. The problem is that runtime
consumers do not share one explicit description of aggregate storage and access.

== Goals

The runtime design should:

* let a model part answer directly whether it is aggregate-backed;
* identify the aggregate selectable and aggregate format without inspecting
  child column placement;
* preserve the embeddable member model independently from how the value is
  selected or bound;
* describe nested aggregate members and aggregate-array elements explicitly;
* centralize dialect-specific read, assignment, construction, extraction, and
  binding decisions;
* support both whole-aggregate and decomposed-member access;
* give SQL selection, result assembly, mutation, dirty checking, and query-path
  consumers the same authoritative runtime contract;
* keep format-specific behavior visible instead of treating every aggregate as
  a SQL `STRUCT`;
* remove duplicated inference only after each migrated consumer can use the new
  contract exclusively.

== Non-Goals

This work does not:

* redesign aggregate source discovery or component-member binding;
* replace `Component` as the boot representation of an embeddable;
* introduce parallel mutable state on `Component`;
* require one JDBC access mode for every aggregate format or dialect;
* require every database to support partial aggregate mutation;
* broaden the set of supported aggregate mapping shapes without a separate use
  case and test;
* remove `AggregateSupport`; it is the dialect foundation from which the
  runtime access strategy should be built.

== Runtime Storage Descriptor

The runtime model needs an immutable descriptor for aggregate storage.

The following names are provisional:

[source,java]
----
interface AggregateStorageDescriptor {
    AggregateStorageKind kind();

    SelectableMapping aggregateSelectable();

    JdbcMapping aggregateJdbcMapping();

    EmbeddableMappingType embeddableType();

    List<AggregateMemberDescriptor> members();

    AggregateAccessStrategy accessStrategy();
}

enum AggregateStorageKind {
    STRUCT,
    JSON,
    XML,
    ARRAY
}

interface AggregateMemberDescriptor {
    ModelPart modelPart();

    SelectablePath selectablePath();

    List<SelectableMapping> selectables();

    AggregateStorageDescriptor nestedAggregate();
}
----

The descriptor is a runtime product. It should be created while the runtime
mapping model is initialized from the completed boot projection. It should not
be another independently mutable boot representation.

The descriptor must be authoritative for:

* the physical selectable containing the aggregate value;
* the aggregate value JDBC mapping;
* the ordered embeddable members represented inside the value;
* parent/child relationships for nested aggregates;
* the element aggregate description for aggregate arrays;
* the dialect access strategy used by runtime consumers.

The embeddable mapping type remains authoritative for the domain structure:
attribute names, Java types, instantiation, decomposition, and member model
parts. The aggregate storage descriptor describes how that domain structure is
stored and accessed.

=== Ownership

The descriptor should be exposed by the aggregate-valued runtime model part.
Whether that is a new model-part subtype or an extension of an existing
embeddable-valued model part is an implementation choice.

Conceptually:

[source,java]
----
interface AggregateEmbeddableValuedModelPart extends EmbeddableValuedModelPart {
    AggregateStorageDescriptor aggregateStorage();
}
----

Consumers should not need to inspect a boot `Component` or test whether one of
its columns is an `AggregateColumn`.

=== Scalar and Array Values

Scalar aggregate embeddables and arrays of aggregate embeddables share an
aggregate storage concept but not necessarily the same result-assembly route.

For scalar aggregates:

* the descriptor represents one aggregate-backed embeddable;
* the embeddable member model remains available for path navigation;
* selection may use the whole aggregate or decomposed member expressions.

For aggregate arrays:

* the aggregate value has a plural Java and JDBC mapping;
* the element descriptor represents the embeddable structure of each element;
* whole-array result assembly must not treat array indexes as embeddable
  attribute positions;
* query support for indexed element paths may still use the element
  embeddable model.

The runtime descriptor must make this distinction explicit instead of relying
on an `Object[]`-shaped interpretation of both concepts.

=== Nested Aggregates

A nested aggregate is both:

* a member of its parent aggregate; and
* an aggregate storage boundary with its own format, selectable path, member
  order, and access behavior.

The runtime model should represent that relationship directly. SQL AST path
construction should walk descriptor relationships rather than reconstructing
parent aggregate paths from custom read expressions.

== Aggregate Access Strategy

`AggregateSupport` supplies dialect capabilities and expression renderers.
Runtime consumers should use a strategy resolved from the storage descriptor
and dialect support rather than independently combining:

* the aggregate column;
* member selectables;
* JDBC type codes;
* custom read expressions;
* assignment expressions;
* dialect preference flags.

A possible contract is:

[source,java]
----
interface AggregateAccessStrategy {
    AggregateSelectionMode selectionMode();

    AggregateBindingMode bindingMode();

    Expression readAggregate(...);

    Expression readMember(AggregateMemberDescriptor member, ...);

    JdbcValueExtractor<?> aggregateExtractor();

    JdbcValueBinder<?> aggregateBinder();

    AggregateMutationPlan mutationPlan(List<AggregateMemberDescriptor> dirtyMembers);
}

enum AggregateSelectionMode {
    WHOLE_VALUE,
    DECOMPOSED_MEMBERS
}

enum AggregateBindingMode {
    WHOLE_VALUE,
    MEMBER_ASSIGNMENTS
}
----

This contract is illustrative. It should expose decisions and reusable runtime
operations, not merely rename every method on `AggregateSupport`.

The strategy should cover:

* reading the complete aggregate value;
* reading a member from the aggregate value;
* extracting a complete aggregate as one JDBC value;
* extracting members as separate JDBC selections;
* binding a complete replacement value;
* assigning one or more changed members;
* rendering constructors when a database requires them;
* composing nested aggregate access;
* accessing aggregate-array values and, where supported, array elements.

=== Capability Decisions

Selection and mutation capabilities are related but independent. A dialect may:

* prefer whole-value selection but require member-based mutation;
* support member extraction but only whole-value replacement;
* support partial updates for JSON but not XML;
* require an explicit constructor for SQL `STRUCT`;
* expose an aggregate array as one JDBC value while supporting SQL access to an
  individual element.

These decisions belong in the resolved access strategy. Call sites should not
recompute them from JDBC type codes.

== Runtime Consumers

=== SQL Selection and Query Paths

SQL AST creation should use the storage descriptor to decide whether a path:

* selects the aggregate column;
* renders a member extraction expression;
* traverses into a nested aggregate;
* indexes an aggregate array and then navigates its element embeddable;
* requires a dialect-specific constructor or cast.

The SQM path remains a domain-model path. The storage descriptor determines how
that path is represented in SQL.

=== Result and Fetch Assembly

Result creation must distinguish:

* one JDBC aggregate value assembled by an aggregate JDBC type;
* separate member selections assembled as an embeddable;
* a plural aggregate value whose elements have an embeddable descriptor;
* nested aggregate values with their own assembly boundary.

The selected access mode and result assembler must come from the same strategy
decision. An initializer should not infer the mode again from the Java class or
number of child fetches.

=== Mutation

Mutation planning should ask the strategy whether changed members can be
assigned individually.

The mutation contract needs to account for:

* whole-value replacement;
* partial assignment of one or more members;
* nested-member changes;
* dynamic update;
* dirty tracking granularity;
* generated aggregate columns or generated members;
* optimistic-lock participation;
* insertability and updateability of individual member mappings;
* dialect limits on combining member assignments.

If partial assignment is unsupported or unsafe, the plan must fall back to a
whole-value replacement using the embeddable decomposition contract.

=== JDBC Extraction and Binding

Aggregate JDBC type resolution should occur once while the descriptor and
strategy are built.

Runtime extraction and binding should not repeat decisions about:

* scalar versus plural aggregate Java types;
* aggregate-array element types;
* converters applied to aggregate elements;
* STRUCT type names;
* JSON/XML serialization;
* whole-value versus member-wise access.

=== Dirty Checking and Optimistic Locking

Domain dirty checking remains based on the embeddable member model. The storage
descriptor translates the resulting dirty member set into a legal database
mutation.

Optimistic-lock behavior must be defined for both mutation modes:

* whether predicates compare the whole aggregate or selected members;
* how nested member dirtiness is represented;
* how generated or non-updateable members affect replacement;
* whether a dialect limitation forces a broader assignment or predicate.

== Format-Specific Requirements

The common contract is aggregate-valued embeddable storage. Format behavior
remains specialized.

SQL `STRUCT` / UDT::
Preserve the qualified type name and ordered database members. Support
dialect-specific member access, constructors, and STRUCT JDBC extraction.
`UserDefinedObjectType` may remain the schema projection even if the runtime
uses a more general descriptor.

JSON::
Preserve serialization type information and JSON path semantics. The strategy
must distinguish dialects supporting partial JSON mutation from those requiring
whole-document replacement.

XML::
Preserve XML serialization and path semantics independently from JSON. XML
mutation capabilities must not be inferred from JSON support.

Aggregate arrays::
Preserve plural Java/JDBC typing and the embeddable element descriptor. Array
construction, extraction, indexed access, and mutation remain dialect-specific.

Nested aggregates::
Allow the nested format to participate in path and mutation composition. Do not
assume that every nested aggregate uses the same format as its parent unless the
mapping rules explicitly require it.

== Relationship to the Boot Model

The completed boot pipeline remains responsible for:

* classifying aggregate source roles;
* resolving aggregate column placement;
* resolving scalar and plural aggregate JDBC codes;
* collecting ordered aggregate members;
* validating supported mapping shapes;
* contributing UDT and auxiliary database metadata;
* projecting the mapping into `Component` and `AggregateColumn`.

Runtime-model creation should consume that completed projection to build one
immutable storage descriptor. During migration, existing boot properties may
still be read to construct the descriptor. After construction, migrated runtime
consumers should use only the descriptor.

The boot model should not retain the runtime access strategy. The strategy may
depend on runtime `JdbcMapping`, model parts, and dialect capabilities that are
not final during boot binding.

== Migration Plan

=== Stage 1: Characterize Existing Runtime Decisions

Identify every runtime call site that independently decides:

* whether a mapping is aggregate-backed;
* which aggregate selectable contains the value;
* scalar versus plural aggregate handling;
* whole-value versus decomposed selection;
* whole-value versus member mutation;
* nested aggregate paths;
* aggregate JDBC type resolution.

Record the required inputs and observable behavior. Existing passing aggregate
suites establish compatibility; add a focused reproducer only where a consumer
decision is not already observable.

=== Stage 2: Materialize the Storage Descriptor

Build the immutable descriptor during runtime mapping-model initialization.

Initially:

* derive it from the completed `Component` / `AggregateColumn` projection;
* retain existing runtime behavior;
* expose it through the aggregate-valued model part;
* verify scalar, nested, array, collection-element, map-key, and map-value
  placement;
* verify descriptor identity and parent/element relationships.

At this stage the descriptor may coexist with legacy inference, but it must be
complete enough to replace that inference consumer by consumer.

=== Stage 3: Introduce the Access Strategy

Resolve one immutable access strategy for each storage descriptor from:

* aggregate kind;
* aggregate and member JDBC mappings;
* dialect `AggregateSupport`;
* nesting and array shape;
* selection and binding capabilities.

Characterize strategy decisions independently from SQL rendering.

=== Stage 4: Migrate Read Consumers

Move these consumers in order:

1. aggregate selectable and table ownership;
2. SQL member-path rendering;
3. whole-value and decomposed SQL selection;
4. domain-result and fetch assembly;
5. nested aggregate and aggregate-array query paths;
6. JDBC extraction.

After each move, remove the replaced inference from that consumer.

=== Stage 5: Migrate Mutation Consumers

Move:

1. whole-value binding;
2. aggregate member assignment rendering;
3. partial and nested mutation planning;
4. dynamic-update integration;
5. generated-value and optimistic-lock handling;
6. JDBC binding.

Mutation migration is complete only when the selected mutation mode, SQL
renderer, and JDBC binder all come from the same descriptor and strategy.

=== Stage 6: Remove Runtime Boot-Model Inference

Once all runtime consumers use the descriptor:

* remove runtime checks for `AggregateColumn` where they only infer storage;
* remove duplicated JDBC-code normalization;
* remove repeated dialect preference calculations;
* remove custom-expression state that is only an intermediate runtime cache;
* keep boot properties still required by schema tooling or compatibility APIs;
* reassess whether schema consumers should share a format-neutral descriptor or
  continue using `UserDefinedObjectType` and `AggregateColumn`.

== Validation Matrix

Each runtime migration stage should retain observable coverage for:

[cols="1,3"]
|===
|Shape |Required behavior

|Scalar STRUCT
|Ordered UDT members, whole/member selection, construction, extraction, and mutation

|Scalar JSON/XML
|Serialization, path selection, whole replacement, and supported partial mutation

|Nested aggregates
|Parent/child selectable paths, assembly boundaries, and nested mutation fallback

|Aggregate arrays
|Plural Java/JDBC typing, whole-array assembly, element descriptors, and indexed paths

|Collection elements
|Aggregate selectable ownership by the collection table and correct element assembly

|Map values
|Value-side aggregate typing, collection-table ownership, and value assembly

|Map keys
|Key-side aggregate typing, collection-table ownership, key assembly, and equality semantics

|Associations inside aggregates
|Member selectable paths and mutation without physical owner-table member columns

|Converters
|Correct scalar or element domain type during extraction, binding, and assembly

|Generated and locked state
|Defined whole/member behavior for generated values and optimistic-lock predicates
|===

Tests should assert runtime descriptors, generated SQL, JDBC/result behavior, and
mutation behavior where applicable. Successful metadata or SessionFactory
creation alone is insufficient evidence for a migrated runtime consumer.

== Open Design Decisions

These decisions should be made while implementing the corresponding migration
stage, using a focused runtime consumer rather than speculative boot changes.

Model-part ownership::
Should the descriptor be exposed by a distinct aggregate embeddable-valued
model-part type, or by an optional contract on the existing embeddable-valued
model part?

Member representation::
Should `AggregateMemberDescriptor` wrap existing model parts and selectables, or
should aggregate-aware selectable paths be added directly to those model parts?

Strategy granularity::
Should one strategy own selection, extraction, binding, and mutation, or should
an immutable aggregate access plan contain separate read and write strategies?

Schema sharing::
Can `UserDefinedObjectType` remain the SQL STRUCT schema product while runtime
uses the general descriptor? Introduce a shared schema/runtime aggregate
descriptor only if both sides can make it authoritative.

Mutation fallback::
When one dirty member cannot be assigned individually, should the entire
aggregate always be replaced, or may a strategy combine partial assignments
with reconstruction of a nested value?

Optimistic locking::
When member-level predicates are unavailable, should optimistic locking compare
the complete aggregate value, and how should unsupported aggregate equality be
reported?

Nested formats::
Should mixed nested aggregate formats be supported, rejected during boot
validation, or limited by dialect capabilities?

== Completion Criteria

The runtime redesign is complete when:

* every aggregate-valued runtime model part exposes an immutable storage
  descriptor;
* scalar, nested, collection/map, and array aggregates use the same descriptor
  contract;
* read and mutation consumers obtain aggregate behavior from a resolved access
  strategy;
* SQL AST path handling no longer reconstructs aggregate parentage from custom
  expressions;
* result and fetch assembly do not infer scalar-versus-array behavior from Java
  container shape;
* aggregate JDBC mapping decisions are resolved once;
* mutation planning has explicit partial-update and whole-replacement behavior;
* dynamic update, generated values, dirty tracking, and optimistic locking have
  defined aggregate semantics;
* runtime consumers no longer inspect boot mapping details solely to discover
  aggregate storage;
* schema-only compatibility projections are clearly separated from runtime
  contracts;
* the validation matrix passes with assertions at the migrated consumer
  boundaries.
