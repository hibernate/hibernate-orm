= Binding Extension SPI Design
:toc:

This document defines the ORM 9 direction for
`org.hibernate.binder.AttributeBinder` and
`org.hibernate.binder.TypeBinder`.

The binders remain incubating extension SPIs.  They are not deprecated and are
not treated as legacy adapters awaiting removal.  Incubation reflects that ORM
9 must stabilize the shape and timing of the contracts around the new
categorization, binding, and materialization pipeline.

== Decision

`AttributeBinder` and `TypeBinder` are post-materialization boot-mapping
customization SPIs.

Each invocation correlates:

* a read-only semantic description produced by categorization and binding;
* the concrete application of that description at a managed-type or attribute
  usage site;
* mutable `org.hibernate.mapping` objects produced for that application; and
* the boot services needed for broader metadata contributions.

The binders continue to mutate `PersistentClass`, `Component`, `Property`,
`Value`, `Column`, and related mapping objects directly.  This broad mutation
surface is intentional: the binders exist for customizations which cannot be
anticipated as a closed list of options.

The public contract must not expose ORM's mutable internal working state.
Categorized and binding-model contracts exposed to a binder are supported,
read-only SPI.  Internal builders, resolvers, contribution records, value
intents, materializers, and coordinator state remain internal.

== Why The Facet Model Is Not The Public Contract

Earlier ORM 9 work rehearsed a capability/facet-based attribute contributor
for `@TenantId`, `@NaturalId`, and `@Collate`.  It proved that ORM-owned
annotations can be translated into structured internal contributions, but the
facade itself duplicated the binder pipeline without defining a useful public
contract.  It was therefore removed.

The useful implementation pieces remain internal: semantic contribution
records preserve facts in the boot binding model, and focused materializers
apply those facts to `org.hibernate.mapping`.

`AttributeBinder` and `TypeBinder` are deliberately broad escape hatches.  A
public facet model would either:

* enumerate most mutations supported by `org.hibernate.mapping`, becoming a
  second mapping API; or
* expose only common operations and prevent the unusual customizations which
  justify the extension point.

The existing uses demonstrate the range:

* attribute access-strategy and insert/update/optional flags;
* basic-value converters and type configuration;
* collection batch sizing;
* selectable and column decoration;
* entity mutation expectations and discriminator behavior;
* metadata-wide filter definitions; and
* dialect-sensitive database initialization.

Targets, optional facets, contribution commands, conflict rules, and
materialization adapters would make these operations more complicated while
remaining less capable than direct mapping customization.

Internal semantic contributions and public custom binders therefore have
different purposes:

* ORM-owned annotations may use contribution records when that improves
  pipeline correctness.
* Public binders customize the materialized mapping with read-only access to
  the semantic facts which produced it.

An ORM-owned annotation migrated to an internal contribution path must not also
run through the public binder dispatcher.

== Boundary

The binder invocation sits at the semantic-to-materialized mapping boundary:

[source,text]
----
categorized domain model
        |
declaration / usage / application binding
        |
org.hibernate.mapping materialization
        |
AttributeBinder / TypeBinder
        |
value resolution and mapping finalization
----

The semantic side is observational.  The materialized side is mutable.

Binders do not receive mutation access to `BootBindingModel` or to the
categorized domain model.  Arbitrary categorized-model mutation would require
recategorization, extension ordering, conflict handling, fixed-point semantics,
and archive rules.  That is a distinct early source/categorization extension
problem and is not hidden inside these annotation binders.

== Semantic Model SPI And Internal Split

Binder contexts must not leak types from
`org.hibernate.boot.mapping.internal.*`.  ORM 9 should promote a coherent
read-only semantic model under:

[source,text]
----
org.hibernate.boot.mapping.spi
----

Implementations, construction, resolution, and mutable state remain under:

[source,text]
----
org.hibernate.boot.mapping.internal.categorize
org.hibernate.boot.mapping.internal.model
org.hibernate.boot.mapping.internal.context
org.hibernate.boot.mapping.internal.materialize
----

Existing internal interfaces are inputs to the supported design, not contracts
which are automatically promoted unchanged.  Some mix descriptive state with
internal operations and must be split.

=== Boundary Rules

The supported semantic model obeys these rules:

* No supported signature imports `org.hibernate.boot.mapping.internal.*`.
* Contracts are read-only and ORM-produced.
* Returned collections are immutable.
* Categorization services, builders, resolvers, and mutable registries remain
  internal.
* Binding contributions, `ValueIntent`, materializers, and binding/coordinator
  state remain internal.
* Internal marker contracts such as `TableOwner` do not become public
  supertypes merely because an implementation needs them.
* An internal interface is introduced only for genuine internal polymorphism,
  not merely to mirror a supported contract. Otherwise, an internal concrete
  or abstract class implements the supported contract directly and owns any
  additional internal operations.
* Concrete internal implementations use an `Impl` suffix where using the SPI
  simple name would create ambiguity.
* Hibernate Models SPI types may be exposed deliberately where they describe a
  source member or resolved Java type.
* Every exposed type has a closed supported transitive signature.

=== Categorized Contracts

The initial closure should cover the descriptive contracts needed to navigate
from a binder invocation to its source declaration and containing type:

* `CategorizedDomainModel`;
* `ManagedTypeMetadata`;
* `IdentifiableTypeMetadata`;
* `EntityTypeMetadata`;
* `MappedSuperclassTypeMetadata`;
* `EmbeddableTypeMetadata`;
* `EmbeddableUsageMetadata`;
* `AttributeMetadata`;
* `SingularAttributeMetadata`;
* `PluralAttributeMetadata`;
* `ValueMetadata`;
* `EmbeddedValueMetadata`;
* `ValueNature`; and
* a read-only entity-hierarchy view.

The closure is use-case driven.  Persistence-unit registrations, key-resolution
working state, generator-resolution state, and categorization services remain
internal unless a binder requirement independently justifies supporting them.

For example, the public embeddable contract may describe the declaration:

[source,java]
----
public interface EmbeddableTypeMetadata {
	ClassDetails getClassDetails();
	AccessType getExplicitAccessType();
}
----

The operation which resolves a usage remains on the internal implementation:

[source,java]
----
final class EmbeddableTypeMetadataImpl
		implements org.hibernate.boot.mapping.spi.EmbeddableTypeMetadata {
	EmbeddableUsageMetadata resolveUsage(
			MemberDetails sourceMember,
			TypeVariableScope scope,
			AccessType inheritedAccessType,
			CategorizationContext context);
}
----

Likewise, public `AttributeMetadata` does not extend the internal `TableOwner`
marker. The internal `AttributeMetadataImplementor` intersection remains
useful because multiple unrelated attribute implementations need both the
supported descriptive contract and the internal table-owner role.

The first implementation slice uses supported read-only superinterfaces and
internal implementations. `CategorizedDomainModel` exposes source
classes, mapped-superclass classes, entity hierarchies, and embeddable
declarations; persistence-unit `GlobalRegistrations` remains on the internal
`CategorizedDomainModelImpl`. The supported `EntityHierarchy` exposes root, absolute root,
inheritance strategy, and default access.  Key, generator, cache, listener, and
categorizer working state remain on `EntityHierarchyImpl`.
+
`ManagedTypeMetadata`, its identifiable/entity/mapped-superclass
specializations, attribute/value metadata, embeddable declarations/usages, and
collection-id metadata follow the same pattern. Internal concrete classes and
records implement the supported contracts directly. Shared implementation
behavior lives on `AbstractManagedTypeMetadata` and
`AbstractIdentifiableTypeMetadata`; embeddable usage resolution lives on
`EmbeddableTypeMetadataImpl`. Data-only implementations such as
`ValueMetadataImpl` likewise implement their supported contracts directly.

=== Declaration, Usage, And Application Contracts

The supported binding-side view follows the durable ORM 9 model:

Declaration::
Where a persistent attribute originates.

Usage::
How that declaration is interpreted in a contextual usage, including generic
type resolution and an embeddable or inherited path.

Application::
The concrete occurrence of that usage in the mapping graph.

The initial shape is:

[source,java]
----
public interface AttributeDeclaration {
	DeclarationRole getRole();
	String getName();
	ManagedTypeMetadata getDeclaringType();
	MemberDetails getMember();
	AccessType getAccessType();
	AttributeNature getNature();
}

public interface AttributeUsage {
	AttributeDeclaration getDeclaration();
	MemberDetails getMember();
	TypeDetails getResolvedType();
	String getSourceRole();
	String getAttributePath();
	AttributeNature getNature();
}

public interface AttributeApplication {
	AttributeUsage getUsage();
	MappingRole getRole();
}
----

These names and JavaBean versus concise accessor style remain subject to the
package/API consistency pass.  The three concepts and their read-only
relationship are the contract.

The existing internal types adapt to this SPI.  Internal contracts may add
working information:

[source,java]
----
interface AttributeUsageBinding extends AttributeUsage {
	AttributeUsageContainer usageContainer();
	ValueIntent valueIntent();
}
----

`AttributeUsageContainer`, `ValueIntent`, contribution records, and mutable
registration methods remain internal.

=== Stable Roles

`DeclarationRole` and `MappingRole` are immutable semantic identities for a
source declaration and a concrete mapping application.  They are not
`org.hibernate.mapping` compatibility objects.  They are supported values in
`org.hibernate.boot.mapping.spi`, shared by the read-only semantic model and
the mutable boot mapping model.  The public closure of `MappingRole.RootKind`,
`PartKind`, and `Part` is limited to stable identity and navigation vocabulary.

The implementation places both immutable values in
`org.hibernate.boot.mapping.spi`.  Their typed root/part vocabulary,
construction, navigation, canonical rendering, equality, and serialization
are tested as stable value semantics.  Mutable `org.hibernate.mapping` objects
carry these SPI-owned identities when they represent a concrete application or
a projection of a source declaration.

== Attribute Binder Shape

The binder shape is:

[source,java]
----
public interface AttributeBinder<A extends Annotation> {
	void bind(A annotation, AttributeBindingContext context);
}
----

The implemented context correlates the semantic application with the mutable materialized
mapping:

[source,java]
----
public interface AttributeBindingContext {
	CategorizedDomainModel getDomainModel();
	AttributeApplication getAttribute();

	PersistentClass getPersistentClass();
	Property getProperty();

	MetadataBuildingContext getMetadataBuildingContext();
}
----

`getPersistentClass()` identifies the ultimate containing entity.  For an
embeddable member it may differ from `Property#getPersistentClass()`.

`AttributeApplication` supplies the information which cannot be reconstructed
reliably from the mapping objects:

* declaration owner versus concrete containing type;
* declaration member versus contextual member interpretation;
* resolved generic type;
* nested or embedded usage path; and
* stable declaration and mapping roles.

Whether `CategorizedDomainModel` is exposed directly or reached through a
narrow read-only navigation service depends on the final categorized-model
closure.  The binder must at minimum see its local declaration, usage,
application, and containing-type graph.

== Type Binder Shape

`TypeBinder` follows the same boundary but retains strongly typed entity and
embeddable callbacks.  A single target with optional entity/embeddable facets
is not needed.

The implemented shape is:

[source,java]
----
public interface TypeBinder<A extends Annotation> {
	default void bind(A annotation, EntityBindingContext context) {
		context.unsupportedAnnotationPlacement( annotation );
	}

	default void bind(A annotation, EmbeddableBindingContext context) {
		context.unsupportedAnnotationPlacement( annotation );
	}
}
----

An entity context correlates categorized entity/hierarchy metadata with its
`PersistentClass`.  An embeddable context correlates the embeddable declaration
and particular usage/application path with its `Component` and ultimate
containing entity.

Default rejecting methods allow a binder to support only its legal target
without every implementation repeating an exception-only overload.
`unsupportedAnnotationPlacement(Annotation)` on each type context produces
the standard `AnnotationException`, naming the annotation and categorized
target type.

== Execution Semantics

The stabilized contract must specify and test phase timing, not merely Java
method signatures.

The ORM 9 pipeline currently establishes the intended order:

. Managed-type structures and members are materialized.
. Entity `TypeBinder`s run against structurally complete managed-type mapping
  objects.
. Embeddable `TypeBinder`s run against structurally complete components.
. `AttributeBinder`s run after `Property` and structural `Value`
  materialization.
. Basic-value resolution runs after attribute customization.
. Mappings created by later association and identifier phases drain through the
  same component, attribute, and value-resolution phases.
. Table-key, inverse-association, foreign-key, aggregate, and finalization
  phases complete afterward.

The precise state guaranteed for associations, collection keys, table keys,
and foreign keys must be stated from focused use cases.  A binder must not
depend on state which the documented invocation phase has not completed.

Each discovered custom annotation results in one binder invocation for each
concrete application.  Metadata restoration preserves the materialized result;
it does not rediscover and rerun binders.

== Broader Boot Contributions

`MetadataBuildingContext` remains available on binder contexts.  This is an
intentional escape hatch for metadata-wide behavior which cannot be expressed
by mutating the local mapping object.

The supported semantic model does not absorb configuration services, dialect
access, type registries, filter registration, or database mutation merely to
make the local source view appear self-contained.  Capability-level narrowing
of `MetadataBuildingContext` may be considered independently after real binder
use cases identify a coherent smaller contract.

== Implementation Sequence

. Define the exact read-only closure required by representative binder cases.
. Split operational methods and internal marker inheritance from the
  categorized interfaces.
. Introduce supported declaration, usage, and application contracts.
. Relocate or stabilize the declaration and mapping role value types.
. Adapt existing internal implementations and bindings to the supported SPI.
. Define `AttributeBindingContext`, `EntityBindingContext`, and
  `EmbeddableBindingContext` using only the closed SPI.
. Migrate built-in and test binder implementations.
. Lock down timing, once-only invocation, diagnostics, and archive restoration
  with focused tests.
. Reconcile API Javadocs, the user guide, compatibility guidance, and Stage 5
  design status.

The semantic-model slice is implemented under `org.hibernate.boot.mapping.spi`.  Focused
tests consume categorization results through `CategorizedDomainModel`,
`EntityHierarchy`, and `IdentifiableTypeMetadata`, and consume applied binding
results through `AttributeApplication`, `AttributeUsage`, and
`AttributeDeclaration`.  The public package has no dependency on
`org.hibernate.boot.mapping.internal.*`.
+
The binder-context slice is also implemented.  `AttributeBinder` receives an
`AttributeBindingContext`; `TypeBinder` receives typed entity or embeddable
contexts with default unsupported-placement rejection.  The dispatcher
correlates registered attribute applications where available and supplies a
semantic application adapter for identifier, version, tenant-id, and other
special properties which bypass the ordinary attribute application index.
Embeddable callbacks retain the particular categorized
`EmbeddableUsageMetadata`, including the source member, generic-resolution
scope, effective access, and selected attributes.  Built-in and test binders
use the stabilized signatures.  Focused tests cover all three contexts,
standard unsupported-target diagnostics, once-only invocation, special
version-property correlation, and archive restoration without binder
re-execution while preserving binder mutations.

== Remaining Shape Decisions

The following are bounded decisions within this design, not reasons to return
to the facet model:

* the final package split within `org.hibernate.boot.mapping.spi`;
* the exact public subset of `CategorizedDomainModel` and `EntityHierarchy`;
* JavaBean versus concise accessor naming;
* whether role part construction or only role observation is supported;
* whether `MetadataBuildingContext` remains directly visible or is later
  replaced by a separately justified boot-customization context.

== Recommendation

Stabilize `AttributeBinder` and `TypeBinder` around a supported semantic-to-
materialized boundary:

* supported categorized and applied-model contracts for reading;
* mutable `org.hibernate.mapping` targets for customization;
* explicit boot context for broader contributions; and
* documented invocation timing before value resolution and mapping
  finalization.

Do not publish the internal facet rehearsal as the binder SPI, and do not allow
binders to mutate the categorized or internal binding models.
