== Latest Categorized-Model Closeout

The final semantic-model slice extends the categorized domain model without
turning it into a binding or runtime model:

* global identifier-generator declarations are immutable, class-bearing
  `IdentifierGeneratorRegistration` values with explicit sequence, table,
  UUID, and custom kinds;
* strict JPA generator scoping is the only supported model, with unnamed
  declarations implicitly named from the owning JPA entity name;
* entity identifier-generator resolution is attached to `EntityHierarchy`;
  collection ids retain scoped lookup because they have no entity hierarchy;
* embeddables and collection elements/indexes are represented as categorized
  values;
* `AttributeMetadata` describes the persistent Java attribute and its
  declaration/usage type context, while `ValueMetadata` describes the mapped
  value shape independently of whether that value is itself an attribute;
* binding consumes this split and resolves concrete generic embeddable usages
  at the application site.

The full Core suite exposed and closed compatibility regressions involving
generic embeddables, composite user types, time-zone component projections,
generator resolution, repeated global annotations, and validation settings.

The first Stage 2 mapped-superclass cleanup stores role-bearing
`AppliedAttributeMapping` values directly in each
`MappedSuperclassContribution`.  Contribution registration no longer tests
copied `Property` membership by object identity, and the unused contribution
view which filtered categorized consumers by identity has been removed.
Mapped-superclass declarations also remain declaration-owned when an attribute
names a secondary table.  The concrete entity application is placed in the
secondary-table `Join` as inherited compatibility state and is retained in the
contribution by its stable `MappingRole`.
The first embeddable cleanup similarly makes `EmbeddableContribution` the
direct binder/materializer exchange product and removes its pass-through view.
Polymorphic subtype members are now part of that contribution before
materialization; the contribution, `AppliedEmbeddableMapping`, and legacy
`Component` projection therefore consume one ordered member plan.
Polymorphic discriminator discovery has likewise moved into the data-only
`EmbeddableDiscriminatorSource` owned by each contribution.  Singular embedded
attributes and collection elements materialize their discriminator
`BasicValue`, value map, and subtype-supertype links from that source.
Nested polymorphic components now follow the same path during recursive
materialization, with boot-model and persist/load regressions covering the
nested contribution and runtime subtype instantiation.
Explicit `@Embedded` and implicit embeddable attributes have also been verified
as one semantic path: they share categorized member declarations and the
`EMBEDDED_ATTRIBUTE` contribution kind, while retaining distinct path-specific
contributions, applied mappings, member usages, roles, and runtime handoff
results.
The mixed generic/polymorphic case is covered as well: a generic
mapped-superclass member resolves to its concrete application type while
subtype-local members and discriminator source remain in the same contribution
and role-based handoff.
The Stage 2 identifier audit verified all four whole-target derived-identity
combinations across `@IdClass` and `@EmbeddedId` parents and dependents.
Whole-target association identifiers now retain
`IdentifierExtractionKind.WHOLE_TARGET_ID` rather than being misclassified as
`DIRECT`, and focused boot tests assert the ordered selectables and compatibility
mapping shape.  `EntityIdentifierHandoff` is now indexed by the stable
identifier `MappingRole`; its `RootClass` and `KeyValue` lookups derive that role
as compatibility adapters.  Because the focused runtime matrix passes, no
parallel multi-part boot correspondence product is retained.  Association
values convert through the target `EntityIdentifierMapping`, while selectable
correspondence independently owns JDBC expansion and order.  A future
unsupported identifier shape should drive an executable runtime conversion
plan rather than a speculative boot DTO.
Deterministic attribute ordering is also closed.  Semantic contribution and
selectable order remain binding products; component, mapped-superclass, and
entity alphabetical ordering is an explicit compatibility projection completed
before runtime metamodel creation.  The reduced final-state note now lives
under `finished/`, with focused boot/runtime, native-query inheritance, and
polymorphic embeddable ordering guardrails.
The final Stage 2 context audit is closed as well.  `SimpleValue` does not
retain or expose `MetadataBuildingContext`, and `Value` no longer provides a
broad context-recovery contract.  Its remaining reflection hook now receives
`ClassLoaderService` explicitly from binding state.  Value-resolution and
custom-user-type compatibility receive phase-owned inputs directly; empty
context-taking mapping constructors are compatibility signatures rather than
retained state.  Naming-source and `UserTypeCreationContext` SPI narrowing are
routed to follow-up.

The first Stage 3 slices now produce the JPA static
metamodel injection plan during semantic binding and mapping materialization.
`BootBindingModel` accumulates managed-type, hierarchy, declared-attribute,
identifier, and version field references as those facts are registered.
`RuntimeMappingHandoffSnapshot` carries the resulting immutable plan directly
for both live bootstrap and metadata restoration instead of reconstructing it
from the completed binding model.

Embeddable declarations now contribute explicit
`EMBEDDABLE_DECLARED_ATTRIBUTE` entries.  Id-class representation members are
added even when they bypass ordinary component-member binding.  Runtime
injection follows embeddable descriptor finalization and resolves
mapped-superclass declarations through the applied embeddable hierarchy where
necessary.  Focused plan and runtime tests cover ordinary embeddables,
mapped-superclass inheritance, and id-class embeddables.

Concrete generic field hiding is now implemented across generation and runtime
population.  The annotation processor resolves inherited generic members in
the concrete subtype and emits a same-named declared field.  Applied
mapped-superclass and embeddable usages add
`CONCRETE_GENERIC_ATTRIBUTE` plan entries, whose runtime resolution uses the
declared concrete-generic attribute and requires exact subtype-field lookup.
The superclass declaration field remains independently populated.  Focused
processor, boot-plan, runtime injection, and typed Criteria tests cover the
contract.

The Stage 3 aggregate runtime-consumer audit is complete.  Scalar aggregates,
aggregate arrays, nested aggregates, and UDT/STRUCT order retain the existing
intent/member-container/value-plan handoff and its legacy-compatible projection.
Focused SessionFactory coverage now also verifies JSON/XML collection elements,
map values, and map keys.  That coverage exposed one runtime projection bug:
the aggregate selectable used the component owner's entity table.  It now uses
the materialized aggregate column's table, preserving collection-table
ownership and eliminating the table-group recursion without a new aggregate
product.  The aggregate `ComponentBinding` callback phase has also been retired:
binders now record data-only `AggregateComponentBinding` products, and the
coordinator invokes a single explicit `AggregateMappingFinalizer` after member
value resolution.  Basic, to-one, and `@Any` aggregate member columns target the
logical member container without temporary physical-table registration, so no
late column-removal repair remains.

The Stage 3 state-management runtime audit is complete.  The existing runtime
model is already explicit: `AuxiliaryMapping` owns query restrictions and
auxiliary-table selection, specialized `TemporalMapping` and `AuditMapping`
expose feature state, and `StateManagement` selects graph and legacy mutation
integrations.  Focused new-pipeline SessionFactory and execution coverage now
verifies entity and collection runtime mappings plus temporal/audit insert,
update, current-state query, and collection mutation.  No additional
`StateManagementDescriptor` or whole-model handoff is needed.

The Stage 3 generator descriptor migration is complete.  ORM 9 no longer makes
`IdentifierGenerator` an `ExportableProducer`; schema-producing implementations
declare that capability explicitly.  `SimpleValue` and `Property` now retain
the common declarative `GeneratorDescriptor`, while the deprecated
`GeneratorCreator` name remains only as a compatibility alias.

Annotation-based identifier and value descriptors expose their effective
generator class before instantiation and prepare generators through a
noncached `ManagedBean` lookup with Hibernate fallback construction.
Nonexportable before-execution identifier generators remain deferred.
Exportable identifier and value generators are prepared during relational
model finalization and handed to runtime construction as the same
construction-scoped `PreparedGenerator`; identified collections use the same
identifier handoff.  The live registries are transient, so metadata archives
retain descriptors and relational state but never managed beans or generator
instances.  On-execution identifier generators remain an explicit early-access
compatibility case because identity-column requirements affect the relational
model.

Focused tests cover deferred nonexportable identifiers, single-instance
identifier export/runtime use, and single-instance value-generator
export/runtime use.
+
The legacy named-strategy form is now class-bearing, resolves its effective
generator class during binding, retains immutable parameters, and preserves
the managed reference used for export/runtime handoff.  Identity and UUID are
direct descriptors: identity applies column semantics without early
instantiation, while UUID stores normalized style and algorithm facts.
Sequence and table now use direct class-bearing descriptors with normalized
JPA settings and construction-scoped managed references.  Managed references
are stabilized when obtained so the configured/exported instance is
necessarily the instance handed to runtime construction.  Derived identifiers
now use a direct, archive-safe descriptor in both binding pipelines; its
nonexportable runtime generator remains deferred until SessionFactory
construction.  UUID and `@Generated` value generation in the compatibility
materializer now also retain direct descriptors with normalized declaration
facts.  Custom annotation-backed identifier and value descriptors now retain
serializable snapshots of their localized declarations.  Archive restoration
reconstructs annotation interfaces, classes, enums, nested annotations, and
arrays through the construction environment's class loader, and no longer
reattaches `ModelsContext` to generators.  Binding-time precedence remains
member, entity, declaring type, then package, including mapped-superclass
`@GenericGenerator` overrides.
+
`@NativeGenerator` now exposes the effective dialect-selected generator class
for phase scheduling while retaining the existing `NativeGenerator` runtime
wrapper.  Sequence, table, and identity selections therefore participate in
relational preparation as required, while UUID remains deferred.  Direct JPA
binding no longer translates `GenerationType` through `GeneratorStrategies`;
the remaining strategy-name interpretation is confined to XML,
programmatic/named-definition, and other legacy compatibility inputs.
`IdentifierGeneratorDefinition` itself is now class-bearing, so those source
strings are resolved before entering the retained metadata model.

The first Stage 4 constructor-slimming slice prepares
`SqlStringGenerationContext` in `SessionFactoryRuntimeComponentsBuilder`.
`SessionFactoryConstructionPlanBuilder` now prepares standard-service
components first and supplies their `JdbcServices` to runtime-component
preparation.  Resolved-settings and legacy-options paths preserve their
respective default catalog/schema inputs, while `SessionFactoryImpl` only
assigns the prepared context.

The second Stage 4 slice removes `BootstrapContext` from
`RuntimeModelCreationContext`.  Runtime-model creation now names its
`ModelsContext`, class-loading, managed-bean, and managed-type representation
dependencies directly.  `SessionFactoryRuntimeComponentsBuilder` captures
those capabilities during preparation and `SessionFactoryImpl` passes them
into its narrowed model-creation context.

The third Stage 4 slice first made factory-scoped service-registry creation an
explicit pre-construction phase.  The later sixth slice removed that child
registry altogether.  The construction plan now carries its delayed
`SessionFactoryAccess` directly, and `SessionFactoryImpl` completes the handle
after receiving the plan.

The fourth Stage 4 slice replaces the `BootstrapContext` argument of
`Integrator#integrate` with `Integrator.Context`, while retaining the fully
bound `Metadata` and in-flight `SessionFactoryImplementor` arguments.  The narrow
context exposes `ManagedBeanRegistry`, covering the audited Hibernate
Search-style CDI use without carrying the full boot context.
`SessionFactoryIntegratorLifecycle` is now a prepared construction-plan product
and still owns integration bookkeeping and disintegration.  Consequently,
`SessionFactoryConstructionPlan` no longer stores or exposes
`BootstrapContext`.  Bean Validation no longer participates through
`Integrator`: its prepared plan contributes relational constraints before the
default producer orders and validates metadata, and later activates runtime
event listeners against the in-flight factory.  Integrators therefore receive
finalized metadata before runtime-model construction.

The fifth Stage 4 slice closes the `SessionFactoryOptions` boundary decision.
`ResolvedSessionFactorySettings` is the source-of-truth settings product for
the resolved pipeline.  `SessionFactoryOptions` remains a read-only
compatibility projection shared by `SessionFactoryProducer` invocations from
both resolved and legacy/native construction and retained by the completed
factory for runtime consumers.  The producer request intentionally does not
expose `ResolvedSessionFactorySettings`, since the legacy/native path has no
such product.

The sixth Stage 4 slice removes `SessionFactoryServiceRegistry` and its
builder, initiator, contributor, and factory infrastructure.  Factory-owned
cache, statistics, native-query, and extension-integration components are
prepared or selected explicitly and handed directly to `SessionFactoryImpl`.
`CacheFactory`, `StatisticsFactory`, `NativeQueryInterpreter`, and
`ExtensionIntegration` provide the Java-service extension points.  Integrator
disintegration now receives the same narrow `Integrator.Context` used during
integration, while `SessionFactoryImplementor#getServiceRegistry()` exposes
the standard registry without implying ownership by the factory.  The factory
registers as a lifecycle dependent of that standard registry, preserving
automatic registry shutdown and shared-registry reference counting without a
child registry.

The seventh Stage 4 slice audits runtime-model callbacks into the in-flight
factory.  `RuntimeModelCreationContext` no longer exposes a broad
`getSessionFactory()` shortcut; callers must use the deliberately named
`SessionFactoryAccess`.  Runtime-only consumers such as attribute mutability
plans and CTE mutation/insert strategies retain the access handle and defer
dereferencing it until execution.  The remaining construction-time
dereferences are explicit and limited to entity/collection persisters retaining
their runtime owner.  Proxy-factory creation no longer receives the factory:
`ProxyFactoryFactory#buildProxyFactory()` had an unused factory parameter in
both built-in implementations, so the eighth Stage 4 slice removes it.  The
ninth slice changes temporary-table strategy construction and preparation to
consume the selected `TemporaryTableStrategy` and `JdbcServices`; the old
factory-taking constructors remain compatibility bridges.  Runtime-owner
persister construction is therefore the only remaining deliberate
construction-time dereference rather than an implicit reason for every
model-construction consumer to see the factory.  The tenth slice audits that
persister boundary.  Persisters still retain the concrete factory as their
eventual runtime owner, but table-name formatting and filter alias/rendering
now consume `SqlStringGenerationContext`, `JdbcServices`, the mapping model,
`Dialect`, and `TypeConfiguration` directly.  The eleventh slice splits named
query resolution: HQL/native definitions resolve without a factory, while
stored-procedure definitions retain their genuinely factory-aware contract.
Persisters resolve and retain selection-only custom loader mementos through
the restricted `NamedLoaderQueryResolver` exposed by
`RuntimeModelCreationContext`; `NamedObjectRepository` implements that view,
but mutation and procedure registrations are excluded from it.  Their only
remaining construction-time factory dereference assigns the concrete factory
as their eventual runtime owner.

The final Stage 4 slice moves boot-model column ordering and validation into
`SessionFactoryConstructionState`, before either the default or a custom
`SessionFactoryProducer` receives the construction request.  It also prepares
the complete set of `DomainDataRegionConfig` values in
`SessionFactoryRuntimeComponentsBuilder`.  `SessionFactoryImpl` retains only
the genuinely factory-owned cache activation sequence: build the
`CacheImplementor`, prime it from those prepared configurations, and then
construct persisters which consume the resulting cache access strategies.
Runtime-model completion remains deliberately inside factory construction:
persisters retain the concrete factory as their runtime owner and complete
their loaders against the in-flight query and SQL infrastructure.

The first Stage 1 slice established function precedence in
`FunctionRegistryCoordinator`: dialect baseline, then all contributors by
ordinal, then explicit descriptors.  Equal-ordinal service contributors use
class-name order; equal-ordinal programmatic contributors retain registration
order and run after service contributors.  Focused tests cover dialect
override, ordinal ordering, equal-ordinal tie-breaking, and explicit descriptor
precedence.

The second Stage 1 slice established equivalent type precedence through
`TypeContributionCoordinator`: dialect baseline, all service/programmatic
contributors by ordinal, then explicit basic types, user types, and converters.
Contributors now run before source categorization, service discovery was
removed from `BindingCoordinator`, and archive restoration uses the same
coordinator.  Focused tests cover dialect override, ordinal ordering, and
equal-ordinal tie-breaking.  JPA entry points now normalize the retained
`hibernate.type_contributors` compatibility setting into the same contributor
input.

The third Stage 1 slice extracted `FunctionRegistryCustomizations` from
`MappingCustomizations` and made it an explicit `BootstrapPipelineRequest` and
mapping-resolution input.  `Configuration`, JPA entry points, metadata-only
bootstrap, schema generation, test bootstrap, and archive restoration now
route function population through that product.  A full `Configuration`
bootstrap guardrail verifies that a programmatic contributor is invoked once.

The fourth Stage 1 slice removed `MappingResolutionOptions` transport through
`BootstrapContext`.  Mapping resolution receives the options product
explicitly, resolved metadata retains it, and SessionFactory option adaptation
receives it from metadata.  `MappingResolutionOptionsImpl` now receives its
`TypeConfiguration` directly instead of using a circular
`setBootstrapContext(...)` link.  The function registry was already carried by
explicit mapping contributions and resolved metadata, so neither product is
now exposed by `BootstrapContext`.

The fifth Stage 1 slice replaced the late
`AdditionalMappingContributor` parameters `InFlightMetadataCollector` and
`MetadataBuildingContext` with the immutable `ProcessedMappings` snapshot and
the narrow `AdditionalMappingContributorContext`.  Mapped-entity presence and
dialect inspection are separated into processed-model and contextual concerns,
respectively; direct relational materialization is explicitly retained on the
`AdditionalMappingContributions` write side.
`ProcessedMappings` now also exposes a narrow `ProcessedEntity` view backed by
the primary categorized model.  Its names and lookups explicitly use Hibernate
entity names while JPA entity names and Java class names are exposed
separately.
The early source-level hook remains a triggered follow-up; its implementation
triggers and no-fixed-point rule are documented, so no speculative
recategorization machinery was added.

The final Stage 1 ownership audit confirmed `MappingResolutionPipeline` as the
single application owner for naming strategies, column ordering, shared cache
mode, cache definitions, and auxiliary database objects.  Entry points
normalize these into `MappingCustomizations`; binding and factory construction
do not rediscover or reapply them.

The old mapping/serialization branch split, rebase procedure, conflict policy,
and serialization "next step" are complete and have been removed from this
handoff.  Git history retains that implementation history.

== Completed Baseline

The following are implemented foundations, not pending design work:

* the supported bootstrap entry points route through the explicit bootstrap,
  mapping-resolution, and SessionFactory pipelines;
* `MetadataSources`, `MetadataBuilder`, `HibernateBootstrap`, the public
  `SessionFactoryBuilder` family, and `Metadata#buildSessionFactory()` have
  been removed;
* `Configuration` is a compatibility facade over the new pipeline;
* declaration, usage, and applied-mapping products use stable
  `DeclarationRole` and `MappingRole` identity;
* explicit mapping products and materializers cover primary, foreign, unique,
  dependent-table, and collection-table keys;
* mapped-superclass, embeddable, identifier, aggregate, state-management, and
  static-metamodel handoffs have implemented foundations;
* SessionFactory construction uses an explicit construction request,
  coordinator, producer SPI, construction plan, runtime components, and
  standard-service components;
* metadata archive production and restoration are factory-ready.

The metadata archive contract is canonical in
link:metadata-serialization-design.adoc[
`metadata-serialization-design.adoc`].  It includes:

* opaque `MetadataArchive` and factory-ready `RestoredMetadata`;
* exact archive-format and ORM-version checks;
* a trusted-build-artifact policy and payload bounds;
* declarative reconstruction of mapping resolutions, types, converters,
  generators, and runtime handoff products;
* stable role-based snapshot identity;
* rejection of mutable binding state, live services, contexts, and resolved
  type instances from the payload;
* no serialization-specific capture allocation when archive production is
  disabled.

The earlier boot-model snapshot proposal was deleted after its durable
stable-identity and validation decisions were folded into this implemented
contract.

== Guardrails

* Keep current status and immediate work only in this file.
* Keep durable decisions in focused design notes.
* Do not serialize `BootBindingModel`, `BindingState`, live services, bootstrap
  contexts, or derived mapping/type instances.
* Use stable semantic roles rather than mapping-object identity for handoffs
  and archive references.
* Keep new binding-model contracts free of `org.hibernate.mapping` types unless
  they are explicitly materializers or compatibility projections.
* Do not restore removed builder surfaces as compatibility shortcuts.
* Keep `Metadata` as the resolved mapping inspection view unless a concrete
  consumer proves it insufficient.
* Treat `AttributeBinder` and `TypeBinder` according to their supported
  semantic-to-materialized SPI boundary.  Treat `Configuration`,
  `AdditionalMappingContributor`, `Integrator`, `BootstrapContext`,
  `MetadataBuildingContext`, and `SessionFactoryOptions` according to their
  documented compatibility boundaries rather than as target pipeline products.
* Use `Identifier#matches(...)` semantics where identifier-aware comparison is
  required.
* Quoted JPA entity names are illegal; quote database identifiers through
  `@Table`, `@Column`, and related mapping annotations.
* New Java files require `@since 9.0` and `@author Steve Ebersole`.
