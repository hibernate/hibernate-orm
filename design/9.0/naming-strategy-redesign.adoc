== Problem And Goals

Steve identified inconsistent invocation and substantial room to improve the
implicit naming contract. Establish a concrete inventory before deciding which
callbacks to replace: a better interface alone will not correct missing calls
or inconsistent interpretation by callers.

* Define which naming decisions are customizable and exactly when they run.
* Give each decision complete, unambiguous inputs without broad boot access.
* Distinguish missing names, explicit names, defaults, logical identifiers,
  physical identifiers, and quoting responsibilities.
* Design extension points around current mapping requirements.
* Make generated-name behavior deliberate and testable; inventory existing names
  to understand changes without treating old contracts as requirements.

== Recorded Design Direction

Clean-room design::
If the redesign proceeds, compatibility with older naming contracts is not a
requirement. Do not preserve old interfaces, method shapes, source objects,
protected subclass hooks, invocation quirks, or provide legacy adapters to
constrain the new design. The current implementation is evidence of use cases
and pitfalls, not the blueprint for the replacement. This direction does not
constitute approval of a finished specification or implementation.

Mapping scope after hbm.xml removal::
Naming strategies originally grew from `hbm.xml`. With that support removed,
the new design must be based on the supported mapping model, including annotations
and supported mapping XML. Do not carry forward hbm-specific naming rules or
legacy strategy variants merely because they existed in the old contract.
Removal of `hbm.xml` does not mean removal of all XML mapping support.

Complete implicit naming coverage::
Steve's proposed baseline is that all implicit database-object naming flows
through the strategy: tables, columns, indexes, constraints, and other generated
database-object names. Tenant-id, discriminator, and primary-key join columns
are explicitly included. Existing bypasses do not establish exclusions.
Inventory additional object kinds, including sequences and generator tables,
before claiming coverage is complete. This does not yet prescribe a separate
Java method for each semantic role or define treatment of explicitly supplied names.

Name provenance::
Inputs must distinguish user-supplied names, mapping defaults, and generated
names wherever those distinctions affect the decision. A synthesized name must
not masquerade as a user-supplied identifier. The exact representation and the
precedence of these sources remain to be designed.

Logical and physical names::
The stage of referenced names and their quoting state must be unambiguous.
Steve favors investigating an end-to-end `LogicalName` / `PhysicalName` split.
His initial suggestion of a logical-only boot model, with physical naming during
runtime construction or schema tooling, remains an architectural possibility,
not an agreed lifecycle requirement. Distinct types also work with incremental
physical resolution during boot. Decide representation and resolution timing
separately.

Old-contract compatibility and generated database names are distinct questions.
The clean-room direction settles the former; the default naming rules and any
resulting schema-name changes must be made explicit in the new specification.
Do not infer either a blanket name-preservation requirement or permission to
change every generated name arbitrarily.

== Constraints

Naming strategies are SPI. Existing strategy interfaces remain in their current
package for the context-narrowing slice. Placement and roles for any replacement
must be decided explicitly. New naming inputs already use
`org.hibernate.boot.model.naming.spi`.

Resolve implicit logical names during mapping interpretation. The implemented
migration preserves finalized physical names on restoration. Any future separate
physical-name phase would require its own lifecycle design; it does not reopen
the agreed restoration rule for the current migration. Quarkus
preparation work remains deferred.

The physical strategy boundary is already redesigned: it receives
`PhysicalNamingContext` and returns `PhysicalName`. Expanding its object-kind
coverage, particularly for indexes and constraints, remains a separate decision.
The independent normalizer cleanup is complete: `ObjectNameNormalizer` handles
quoting/rendering through `IdentifierHelper` and `Dialect`; the unused
`NamingStrategyHelper` callback contract has been removed. This redesign should
define any needed dispatch mechanism from concrete naming requirements.

== Historical Proposal: Logical Boot Model And Physical Name Resolution

This records the earlier lifecycle proposal, not the implemented storage model.
The implementation uses distinct name types with incremental physical resolution
during boot. A logical-only boot model and separate physical phase remain deferred
architectural possibilities. The questions below apply to that alternative.

Steve proposes keeping only logical names in the boot model and applying
`PhysicalNamingStrategy` when constructing the runtime model or performing
schema tooling. Under this direction, implicit naming derives logical names
from mapping facts and other logical names. Explicit names are also represented
at the logical stage, with their provenance and quoting intent preserved.

This would resolve the implicit strategy's input-stage ambiguity by construction:
it would not consume names already transformed by the physical strategy.
Physical-name derivation must not overwrite the logical boot model. The current
boot model's use of physical identifiers is implementation evidence to inventory,
not a compatibility constraint on the replacement.

Recommended design consequences, subject to agreement:

* Runtime construction and schema tooling should use one defined physical-name
  resolution mechanism so the SQL they produce agrees. Whether they share a
  prepared physical model or resolve equivalent products independently remains open.
* A resolved physical name must not be fed back through physical naming as though
  it were logical. Prefer explicit representation of the stage to convention alone.
* Preserve explicit quoting intent in logical identifiers. Define where dialect
  rules, keyword quoting, length limits, and collisions are handled, distinguishing
  identifier resolution from rendering SQL text.
* Define physical naming for every relevant object kind. The old physical strategy
  method set must not silently limit the new design's treatment of indexes and
  constraints.
* Schema tooling must be able to resolve physical names without constructing a
  SessionFactory. Define the settings and target database information it requires.

Questions to investigate before specification:

* What representation holds resolved physical names and maps them back to the
  logical model, including foreign-key references and namespace identity?
* Should generated constraint names derive solely from logical names and then be
  physically transformed, or require a separate final-name rule using physical
  tables/columns? The latter would need an explicit stage outside implicit naming.
* How are database-dependent identifier collisions and length limits validated?
* What should metadata restoration retain or recompute under this model? The
  existing restoration requirements need review before assuming that logical-only
  archives and finalized physical names have the same lifecycle.

This separate-phase proposal has not been implemented. Subsequent sections record
the implemented type/storage migration, which retains the current resolution
timing. Quarkus preparation work remains deferred.

== Historical Investigation: Physical Names During Boot

This investigation motivated the type split. Source paths and next-step suggestions
in this section describe the pre-migration investigation, not the current work list.

Steve requested this investigation before committing to a separate physical
naming phase. The logical-only boot model above remains a candidate, not a
requirement. These findings are based on source inspection, not an experimental
implementation or exhaustive behavioral tests.

=== Where Physical Names Enter

`TableBinder` transforms table/catalog/schema names while building relational
references. `Namespace` also transforms names when creating tables and sequences.
`ColumnBinder.finalizeColumnName()` transforms and dialect-renders a logical name
before it is stored on `org.hibernate.mapping.Column`. These are the current
entry points, not evidence that their timing is intrinsically required.

=== Consumers And Reasons

[cols="2,4,4",options="header"]
|===
|Consumer |Observed dependency |Implication for later resolution

|Column identity and sharing
|`Table.getColumn()` and `addColumn()` key columns by canonical name. Adding an
existing column can merge nullability information. Those names are already
physical at this point.
|Replacing physical strings with logical strings alone could change which
columns are treated as the same. A logical model needs explicit relational
identity/sharing, plus a later physical collision check.

|Referenced-column matching and ordering
|`SelectableOrderResolver.findTargetColumn()` matches referenced identifiers
against `Column.getNameIdentifier(database)`. Association binding uses the result
to establish ordered foreign-key column correspondences.
|This is structural work, not SQL rendering. Later physical naming requires
logical/object references for structural binding, or deferring name-based
matching until physical names are available. The accepted meaning of supplied
referenced-column names must be specified and tested.

|Logical/physical correspondence and validation
|`InFlightMetadataCollectorImpl.TableColumnNameBinding` records both directions
and rejects inconsistent mappings or multiple logical names for one physical
name. `ColumnNameCorrespondence` maps logical names to physical columns and back.
|Physical collision checks genuinely require transformed names, but need not
necessarily happen during initial interpretation. Moving them changes validation
and failure timing and must precede use of the finalized relational model.

|Further implicit naming
|Association-table callbacks receive physical table names. Join-column binding
tries to recover logical target-column names, with a physical-name fallback.
Constraint naming consumes the existing relational columns.
|These dependencies are consequences of today's naming contract and mixed model.
They can be redesigned; they do not independently prove that implicit naming
requires physical names. Generated constraint-name semantics remain a decision.

|Identifier generators and database metadata
|`GeneratorBinder.callConfigure()` configures generators, registers exportables,
and initializes SQL. `SequenceStyleGenerator.validatedIncrementSize()` transforms
the sequence name to look up its increment in database metadata; the configured
mismatch policy may adjust the increment. `Namespace.createSequence()` creates a
sequence with its physical name.
|Database inspection genuinely needs the database name. Delaying physical naming
therefore requires separating generator configuration, exportable registration,
database-dependent validation, and SQL initialization as appropriate. This is
more than a naming-interface change.

|SQL/DDL preparation during boot
|`TemporalHelper.temporalTableDdlRequest()` supplies dialect-rendered table and
row-start/end column names to temporal DDL preparation. Generator initialization
also consumes `SqlStringGenerationContext`.
|These consumers genuinely need physical identifiers when producing executable
SQL, but the work could potentially move to a later preparation stage. Inventory
stored SQL and extension callbacks before assuming it can simply be delayed.

|Explicit physical references
|`@Synchronize(logical=false)` deliberately accepts physical table names; custom
SQL and subselect declarations are also opaque SQL inputs rather than logical
identifier declarations.
|A logical mapping representation still needs to retain explicitly physical
references and SQL fragments as such. They cannot all be converted into logical
names or sent through the physical strategy again.
|===

=== Assessment And Next Evidence Needed

A separate phase is not ruled out, but the current `org.hibernate.mapping` model
already combines mapping structure with physically named relational objects.
Postponing strategy calls until runtime construction or schema export would leave
existing boot consumers without the names they currently use.

A possible architecture is logical mapping interpretation followed by relational
finalization, followed by runtime construction or schema tooling. Physical naming,
physical collision validation, database-dependent generator checks, and SQL
preparation would have explicitly ordered places in that architecture. This is
an alternative to investigate, not an approved new phase.

For the naming redesign now, preserve the distinction between logical and physical
identity without requiring that physical names all appear at one late point.
Incremental physical resolution with explicit correspondences remains a viable
alternative to a separate phase.

The next useful feasibility case is a composite-key association with explicit
referenced-column names and a physical strategy that changes those names. Trace
whether the complete association structure can be resolved using logical identities
alone. Include shared columns and two logical names that transform to one physical
name. A second case should exercise a sequence increment mismatch, where the
physical name affects a database check and potentially generator configuration.
These examples would establish what must move and what can remain incremental.

== Worked Example: Composite-Key Association

The original characterization fixture, now converted to regression coverage, is
`hibernate-core/src/test/java/org/hibernate/orm/test/namingstrategy/CompositeReferenceNamingTest.java`.
It documents today's behavior, not acceptance criteria for the replacement.

=== Mapping And Transformation

A target entity has an embedded identifier with logical columns `country` and
`number`. A physical strategy prefixes every column name with `p_`, preserving
its quoted flag. The referencing entity declares its join columns in reverse
order to make name-based pairing observable:

[source,java]
----
@JoinColumns({
    @JoinColumn(name = "target_number", referencedColumnName = "p_number"),
    @JoinColumn(name = "target_country", referencedColumnName = "p_country")
})
----

The intended physical correspondence is:

[cols="2,2,2,2",options="header"]
|===
|Local logical name |Local physical name |Target logical name |Target physical name
|`target_country` |`p_target_country` |`country` |`p_country`
|`target_number` |`p_target_number` |`number` |`p_number`
|===

=== Source Path Before The Regression Fix

. Target column binding transforms the identifier column names before the
  association is bound; target `Column` objects hold `p_country` and `p_number`.
. `ToOneAttributeBinder.referencesPrimaryKeySources()` matches the supplied
  referenced names directly against those target columns. No physical naming
  transformation is applied to the referenced-name strings on this path.
. Successful matching classifies the association as a primary-key reference.
  `orderJoinColumnSources()` orders the declarations against target column order.
. Local `JoinColumn.name` values undergo normal column physical naming.
  The resulting foreign-key correspondences pair the local and target `Column`
  objects, independent of the reversed annotation declaration order.

Thus the two attributes of the same annotation currently have different name-stage
roles: `name` supplies a logical name to transform, while `referencedColumnName`
selects an already-physical target name in this example.

=== Initial Experimental Results

All three characterization tests passed:

* Physical references `p_number` / `p_country` with prefix naming produce the
  expected local-to-target column pairs and a primary-key association.
* Logical references `number` / `country` with prefix naming fail with
  `Could not resolve non-primary-key association target columns`. They fail the
  primary-key name match and subsequently fail non-primary-key target resolution.
* The same logical-reference mapping succeeds with identity physical naming.

The initial characterization validated completed metadata and actual foreign-key
column correspondences without building a SessionFactory or exercising database
SQL. Production behavior was unchanged during that investigation; the subsequent
fix is recorded below.

=== Upstream Verification: Logical Non-PK Reference

Steve supplied a simpler example: `Person.socialSecurityNumber` maps to logical
column `ssn`, and `Passport.person` uses
`@JoinColumn(name="person_fk", referencedColumnName="ssn")` on a one-to-one
association. A strategy prefixes columns with `p_`.

The exact mapping was tested in isolated checkouts of freshly fetched upstream
branches:

* `main` at `c3ef32170fa`: passed.
* `8.0` at `747e5b503b5`: passed.

On each branch, metadata construction and validation succeeded. Assertions
confirmed local column `p_person_fk`, target property column `p_ssn`, a non-PK
association, and an actual foreign-key mapping from `p_person_fk` to `p_ssn`.
The test did not build a SessionFactory or execute database SQL.

`AnnotatedJoinColumns` resolves referenced logical names through the metadata
collector's logical-to-physical column mapping on these upstream branches.
Therefore the physical-reference requirement observed in the 9.0 composite
fixture must not be described as established upstream behavior. The evidence
points to a regression in the new binding path, rather than an inherent need for
physical reference names in annotations. The subsequent regression fix also runs the exact Person/Passport fixture on
9.0, as recorded below.

The composite fixture was also executed on upstream `main` (`c3ef32170fa`) and

physical names can be computed later remains a separate architectural question;
these tests do not implement such a later phase.

=== Referenced-Column Regression Fix

Steve requested fixing the regression before deciding on end-to-end logical and
physical name types. Reference matching now consults the existing
`ColumnNameCorrespondence` registry for the target column's logical name rather
than comparing a logical reference against its physical spelling. This preserves
the target's resolved physical identity without invoking physical naming again.
Aliases and quoted-name matching are retained. Synthetic target columns without
registered correspondences retain their existing source-name matching fallback.

The lookup is used for primary-key classification, join-column ordering,
non-primary-key property resolution, and foreign-key correspondences, including
shared association-identifier and collection-key helpers. Physical-to-physical
comparisons unrelated to source references remain unchanged.

`CompositeReferenceNamingTest` now expects logical references to succeed with
identity and prefix naming and checks reversed composite-column pairings.
`LogicalSsnReferenceTest` covers Steve's Person/Passport example and verifies the
actual non-primary-key foreign key. `QuotedLogicalReferenceTest` covers quoted,
mixed-case target names and rejects an incorrectly cased quoted reference.
These tests establish the regression baseline; no logical/physical type split
or separate physical naming phase is implemented by this fix.

Validation: the naming-strategy, association-binding, identifier-binding, and
collection-binding regression selection passed 194 tests with no failures, errors,
or skips, including all six new referenced-name cases.

=== Logical-First Alternative

If `referencedColumnName` is defined to identify a logical column, the declarations
would instead use `number` and `country`. Mapping interpretation could find the
target columns by logical identity, establish that both belong to the identifier,
and record these object correspondences:

* local `target_country` column -> target `country` column;
* local `target_number` column -> target `number` column.

Physical resolution could then attach the four `p_` identifiers without redoing
the structural association matching. This example does not inherently require
physical names to determine the association shape; the current implementation
requires them because matching and identity use already-physical column names.

This depends on a deliberate semantic decision for referenced names. Preserving
physical-reference input would require resolving it after physical names exist,
or a separately represented physical-reference form. Applying the strategy to an
already-physical reference would produce `p_p_country`, illustrating why the stage
cannot safely be guessed. Inverting a physical strategy is not generally possible.

Physical validation remains necessary. A strategy could collapse two distinct
logical identifier columns to the same physical name; logical association pairing
cannot establish that such a physical model is valid. Likewise, intentional
shared columns should be represented by shared relational identity, not inferred
solely from an accidental collision after transformation. These cases remain
separate feasibility tests.

The example supports a logical-first association model but does not prove that
all boot processing can defer physical resolution. Generator database checks,
SQL preparation, quoting, and other association forms remain to be investigated.

== Impact Assessment: Logical And Physical Name Types

The assessment and proposals below record the reasoning behind the approved
slices. Their slice-local statements about unmigrated storage are historical;
the Status and Remaining Work sections describe current completion.

A source inventory found 234 Java files referencing the naming `Identifier`:
165 under production source roots, 67 under test roots, and two elsewhere.
These files contain approximately 1,730 `Identifier` tokens. This is an inventory
of direct references, not a predicted edit count: transitive callers and string
name flows are not captured, and stage-neutral uses may remain unchanged.
Of the 160 core production files, 86 are in boot, 29 in schema tooling, 13 in
dialect code, ten in mapping, eight in generators, and fourteen elsewhere.

A wholesale replacement is a substantial cross-cutting redesign. Concrete
pressure points include:

* `Namespace.createTable(Identifier, Function<Identifier, Table>)` accepts a
  logical name but passes a physical name to its callback. Its maps use logical
  keys while resulting tables contain physical names. This is a strong candidate
  for explicit stage types, not a mechanical type replacement.
* `QualifiedName` and qualified table/sequence names expose identifiers for all
  parts. Their callers must distinguish logical qualification from physical
  database qualification.
* `IdentifierHelper` combines parsing/quoting with JDBC metadata-name conversion.
  Some operations are stage-neutral; others specifically consume physical names.
* `Identifier` defines canonical equality, hashing, ordering, matching, and
  rendering, and is serializable. Distinct wrappers need deliberate equality and
  conversion rules; name-keyed collections must keep their intended semantics.
* `DatabaseIdentifier` already represents names obtained from the database, but
  extends `Identifier`. It does not distinguish logical from physical names in
  signatures. Observed database spelling and quoted mapping intent need care.
* `Column` stores name information as strings and creates identifiers on demand.
  Merely replacing direct `Identifier` uses would leave ambiguous string paths.
* Schema extraction, validation, generators, and dialect extension contracts also
  consume these identifiers. Removing old naming-contract compatibility does not
  make these adjacent changes cost-free or automatically settle their SPI scope.

Two implementation scopes should be evaluated separately:

Boundary distinction::
Keep `Identifier` as the common text/quoting value, and use `LogicalName` and
`PhysicalName` at new strategy and logical/physical correspondence boundaries.
This is less disruptive, with explicit conversion into existing relational and
schema code. Type safety ends where a wrapper is unwrapped; it must not be
advertised as end-to-end protection.

End-to-end distinction::
Carry the distinct types through relational storage, qualified names, lookup
maps, helper contracts, schema tools, and generators. This provides stronger
protection but constitutes a model-wide project with substantial semantic review
and regression coverage, not a small naming-SPI refinement.

Steve prefers the end-to-end direction. A boundary-only distinction is an
alternative evaluated here, not the proposed final scope. The referenced-column
regression has now been fixed and supplies coverage for investigating that
direction. The impact assessment itself did not approve implementation or a
schedule; subsequent approval of the first policy slice is recorded below.

=== Proposed End-to-End Representation

Use two immutable, noninterchangeable value types, `LogicalName` and
`PhysicalName`. Prefer composition over subclassing `Identifier`: inherited
methods returning `Identifier` and consumers accepting the common base would
erase the distinction. Shared internal text/quoting mechanics are possible,
but stage-specific contracts should not accept a common name supertype.

Each value carries identifier text and quoting state. Steve's direction is that
`LogicalName` also carries an explicit/implicit (generated) flag, available to
physical naming strategy suppliers. This flag does not participate in equality,
hashing, or ordering: two mappings can name the same logical name through
different origins. Preserve the flag through logical-name transformations and
delivery to physical naming; do not intern or deduplicate strategy inputs solely
by logical-name equality and thereby discard their origin. The treatment of
mapping defaults under this binary distinction remains to be specified; richer
source information may remain on the naming input.
Logical quoting expresses mapping intent; physical quoting also reflects
the strategy and database quoting policy. Missing optional names must remain
distinct from names whose text is empty; qualified-name defaults need explicit
resolution rules.

Physical naming is a directed operation from `LogicalName` to `PhysicalName`.
Even an identity strategy produces a value of the physical type. There should
be no general reverse conversion: multiple logical aliases may identify one
physical column, and physical transformations need not be reversible.
An explicitly physical input, such as `@Synchronize(logical=false)`, enters through
a physical-name parsing path without passing through the naming strategy.

The split does not require two independently built object graphs. Existing boot
relational references already retain logical and physical names together.
Preserve that option while typing their fields and accessors distinctly.
Mapping `Table` and `Column`, runtime SQL consumers, generators, and schema DDL
consume physical names; mapping declarations and referenced-column lookups
consume logical names. Correspondences connect those names to relational objects
within the appropriate table/namespace scope, not through a global name map.

For example, the conceptual signature of `Namespace.createTable` becomes
`createTable(LogicalName, Function<PhysicalName, Table>)`. The namespace's logical
lookup keys and the created table's physical name then have different types even
if physical naming still happens immediately. Column strings and ad hoc
reconstruction must also be addressed; replacing only `Identifier` signatures
would leave holes in the intended protection.

Qualified names must preserve the same distinction for catalog, schema, and
object name. Prefer separate logical and physical qualified-name contracts for
clarity; a generic qualified-name implementation is an alternative if it prevents
mixed-stage components without exposing stage-neutral consumers. This decision
does not require separate public types for every kind of database object.

=== Equality, Quoting, And Database Observation

Current `Identifier.equals()` and `compareTo()` compare canonical strings.
Consequently quoted `foo` and unquoted `foo` compare equal. In contrast,
`Identifier.matches(Identifier)` distinguishes quoted from unquoted names and
matches two unquoted names case-insensitively. Carrying both behaviors into new
types without a deliberate policy would preserve inconsistent map and lookup
semantics.

Agreed logical-name matching direction: quoted names compare exactly and only to
quoted names; a quoted and an unquoted name are never equal. Unquoted names
compare case-insensitively using one defined case-folding rule. Equality,
hashing, ordering, and lookup keys must agree. Preserve original spelling for
strategy inputs and diagnostics. Test non-ASCII case behavior explicitly rather
than assuming `equalsIgnoreCase()` and lowercased keys are interchangeable.
This is a proposed semantic change to existing collection keys, not a mechanical
rename justified solely by the clean-room strategy API.

Physical-name comparison uses the database naming rules defined for the system.
Steve's original suggestion of retaining a `Dialect` reference assumed one
dialect for that system, with all compared names using the same rules. The
comparison-policy direction has the same scope: one shared policy for the system,
not independently selected policies for individual names. Comparing names from
different systems is outside the intended use; cross-system policy compatibility
is not a design requirement or an outstanding decision for this work.

Steve accepted the comparison-policy direction: retain a shared immutable
name-comparison policy instead of the whole dialect. The exact contract remains
to be specified. A proposed implementation is for the policy to derive a
canonical comparison key while `PhysicalName` preserves its original text and
quoting state for rendering. Equality, hashing, and ordering must use consistent
policy semantics; independently customizable matching and hashing would risk
breaking collection contracts.

Steve requires enforcement of the shared-policy invariant: a custom physical
naming strategy must not supply an alternative comparison policy. This is an
extension-boundary constraint, not a requirement to support cross-system name
comparison.

Proposed construction contract:

* Hibernate owns the system's policy and supplies a factory through the physical
  naming context. Strategies choose text and quoting and ask that factory to
  create the `PhysicalName`; the factory attaches the policy internally.
* `PhysicalName` is final, with no public constructor or factory accepting a
  policy, and no operation for replacing the policy. Any name-copying operations
  preserve its association. Strategies cannot implement their own name subtype
  to override equality or hashing.
* The supplied factory establishes the policy association during construction.
  Names retain the policy and comparison key, not their factory. There are no
  factory-identity checks or result-ownership validation. Constructing another
  factory through internal APIs is outside the supported strategy contract;
  defending against that use is not a goal. Factories using the same policy
  produce names with the same equality, hashing, and ordering semantics.

An alternative is for strategies to continue returning `Identifier` as a
text/quoting result, with Hibernate wrapping it in `PhysicalName` afterward.
As Steve pointed out, this does not require inventing another result type and
would keep policy attachment entirely within Hibernate. Steve nevertheless
prefers the more elegant contract in which `PhysicalNamingStrategy` returns
`PhysicalName` directly. That is the preferred design direction; the
context-supplied factory above is the proposed means of enforcing policy
ownership. Exact signatures and internal construction access remain
working-specification details for the full migration. Steve subsequently approved
trying the policy/factory foundation, as recorded in the implementation slice.

Existing metadata conversion uses quoted/unquoted case strategies in
`IdentifierHelper`. Steve identified the overlap with `IdentifierSupport` and
`Dialect.getIdentifierSupport()`. Source inspection confirms that this is already
the dialect extension point for quoting, identifier limits, and construction of
the environment-specific helper. Its `buildIdentifierHelper()` initializes quoted
and unquoted case strategies from the supplied JDBC metadata snapshot and allows
provider overrides through the builder or a decorated helper.

Use this existing support/construction path as the proposed home for supplying
the comparison policy, rather than adding a parallel policy hook directly to
`Dialect`. The stable dialect-level `IdentifierSupport` and the configured,
system-level comparison policy have different responsibilities: the former
supplies database behavior, while the latter captures the effective comparison
rules. Specify how helper construction supplies that policy so that metadata
lookup and physical-name equality do not acquire independently configured casing
rules. Existing metadata case conversion alone is not proof of a complete
database-equivalence algorithm; verify its applicability before defining keys.
Continue auditing remaining column deduplication and database-observed name
matching against those rules. Restoration of migrated objects is now settled:
retain finalized spelling/quoting in data-only snapshots and reconstruct names
through the restored system factory. Apply that rule as remaining objects migrate.

JDBC metadata adds another distinction: observed database spelling does not
reliably retain the mapping's quoting intent. `DatabaseIdentifier` currently
signals that its text should bypass metadata case conversion. Preserve that
information explicitly in the metadata representation or lookup key; do not
reinterpret every observed name as an ordinary unquoted `PhysicalName`.
Whether that needs a separate public value type remains open.

`IdentifierHelper` currently mixes logical parsing, automatic quoting, metadata
case conversion, and column-definition SQL-fragment quoting. Separate those
responsibilities in the replacement contracts. Logical parsing preserves source
intent; physical finalization applies the agreed database policy; metadata
conversion consumes physical names. Column-definition SQL is not a logical or
physical name and should not be modeled as either. Define how global quoting
affects strategy inputs before specifying exact helper methods.

=== First Implementation Slice: Name Values And Comparison Policy

The trial adds `LogicalName`, `PhysicalName`, and `IdentifierComparisonPolicy`
in `org.hibernate.relational.naming.spi`. This shared package does not depend on
boot naming or dialect identifier support. `IdentifierSupport.render(PhysicalName)`
owns dialect-specific rendering; the name values validate their text locally
and report invalid constructor input with `IllegalArgumentException`.
`LogicalName` retains text, quoting, and explicit/implicit origin. Its identity
uses quoting plus a locale-independent lowercase key for unquoted names; quoted
names use exact text. The explicit flag does not affect equality, hashing, or
ordering. Non-ASCII behavior is defined by `Locale.ROOT` lowercase keys rather
than `String.equalsIgnoreCase()`.

`IdentifierSupport.buildIdentifierHelper()` remains the provider entry point.
`IdentifierHelperBuilder` derives the default `IdentifierComparisonPolicy` from
the final quoted/unquoted case strategies, after provider overrides. Providers
can supply a different immutable policy through `setComparisonPolicy()`.
The configured helper exposes the policy and one stable `PhysicalName.Factory`;
helper decorators and persistence-unit wrappers preserve that association.

The policy separates JDBC lookup spelling from comparison keys. Its default
comparison folds mapped text into database spelling and uses that as the key.
Already-observed database spelling is not folded again. A provider can override
database-name comparison keys when storage casing does not describe equality.
The existing helper's metadata conversion uses the same policy while preserving
the `DatabaseIdentifier` bypass. This trial does not establish that every dialect
can use storage-case rules as its final comparison semantics.

`PhysicalName` has a private constructor and is final. A supplied factory creates
names from finalized text and quoting and computes their keys. The factory's
policy-taking constructor is marked internal for Hibernate bootstrap; it is not
a supported naming-strategy operation. Names retain the policy directly, and
equality, hashing, and ordering use only the comparison key. Factory identity
does not affect comparison. `IdentifierComparisonPolicy.matchesDatabaseName()`
handles matching against JDBC-observed spelling. No factory ownership validation
is required.

The factory deliberately does not apply automatic or global quoting: that
responsibility still needs its pipeline decision. At this stage, name values were not yet
serializable; the namespace-key slice below adds serialization for `LogicalName`.
Physical-name serialization remains part of the subsequent model migration.
The subsequent strategy slice below migrates the callback signatures and context.
Relational storage and qualified-name consumers still use `Identifier` and retain
their existing identity semantics until the next model migration.

Validation: 40 tests passed across the identifier-provider contract tests, new
name/policy tests, naming-strategy regressions, and existing-foreign-key lookup
tests. Ten new tests cover logical origin and quoting, non-ASCII case keys,
physical equality/hash/order consistency, JDBC-observed spelling, provider case
overrides, custom comparison semantics, shared factories through wrappers, and
equality across distinct factories using the same policy, dialect rendering, and
shared name-text validation.

==== SPI Shape

Retain `PhysicalNamingStrategy` in `org.hibernate.boot.model.naming` for this
slice, with its USE/IMPLEMENT/SUPPLY roles. Define the supplied context in
`org.hibernate.boot.model.naming.spi` with USE role. The name values remain in
`org.hibernate.relational.naming.spi`; the shared package has no dependency on
these boot contracts.

[source,java]
----
interface PhysicalNamingContext {
    PhysicalName.Factory getPhysicalNameFactory();
}

interface PhysicalNamingStrategy {
    PhysicalName toPhysicalCatalogName(LogicalName name, PhysicalNamingContext context);
    PhysicalName toPhysicalSchemaName(LogicalName name, PhysicalNamingContext context);
    PhysicalName toPhysicalTableName(LogicalName name, PhysicalNamingContext context);
    PhysicalName toPhysicalSequenceName(LogicalName name, PhysicalNamingContext context);
    PhysicalName toPhysicalColumnName(LogicalName name, PhysicalNamingContext context);
    PhysicalName toPhysicalTypeName(LogicalName name, PhysicalNamingContext context);
}
----

The snippet omits annotations: catalog and schema inputs/results are nullable;
other inputs/results are non-null. Keeping nullable qualification callbacks lets
strategies supply physical qualification when mapping defaults leave it absent.
Missing table/column/sequence/type names are resolved before invoking the strategy;
a null result for those roles is a mapping error identifying the role and logical
input. Recommend making the type callback independent of table naming, with
identity behavior in the standard implementation instead of a default interface
method delegating to the table callback.

Start with the factory as the context's only capability. Identifier parsing,
metadata lookup, SQL rendering, services, and the whole dialect/JDBC environment
are not strategy responsibilities. Additional facts such as a database identifier
length limit may justify a focused capability when a concrete strategy needs it;
none is established by the current repository inventory.

An identity implementation creates a physical value using the supplied factory,
even when text and quoting do not change. Snake-case naming performs its text
transformation and creates a physical value through the same factory. There are
no legacy-signature overloads or public compatibility adapters. This method set
covers existing physical callbacks; expanding physical naming to constraints,
indexes, or other object kinds remains part of the broader coverage design.

==== Agreed Quoting Direction

The current factory consumes finalized text and quoting. Current boot helpers can
apply global and keyword quoting before the strategy, and some strategies apply
helper quoting again to their output while others bypass it. Simply replacing
helper calls with factory calls would silently lose that behavior.

Steve accepted this ownership: logical names retain mapping quoting intent; Hibernate
finalizes global/database automatic quoting against the strategy's resulting
physical text before storage. The strategy supplies spelling and requested
quoting via the factory; an internal finalizer can construct the effective quoted
physical name using that same factory. It must not invoke physical naming again.
Steve requires additive quoting: a strategy may request quoting but cannot remove
mapping-requested quoting. Finalization preserves the logical input's quoting
regardless of the boolean returned by the strategy. Conceptually:

[source,java]
----
finalQuoted = logicalQuoted || strategyQuoted || globallyQuoted || automaticallyQuoted;
----

Here `logicalQuoted` is false for an absent optional logical name, and automatic
quoting is determined from the resulting physical text. If a strategy returns an
unquoted value for a quoted logical input, finalization restores quoting rather
than treating the strategy's result as permission to unquote. This protects the
invariant without relying on every strategy implementation to preserve the flag.
The comparison key must correspond to the final quoting state. Per-mapping
quoting configuration stays with the caller/finalizer, not mutable state on the
shared system factory. SQL column-definition fragments remain outside this path.

The agreed placement applies global quoting after the strategy. For example, with logical `customerName`, snake-case naming, and global
quoting enabled:

* Applying global quoting before the strategy marks the logical input quoted,
  so the current snake-case rule leaves it as quoted `customerName`.
* Applying global quoting only after the strategy produces quoted `customer_name`.

Use the latter: global/database quoting governs the final database name,
while explicit source quoting remains visible to the strategy. Record resulting
schema-name changes rather than presenting this as a behavior-neutral refactor.
Mapping-level delimited-identifier defaults also need explicit classification
under this rule. Keyword quoting must inspect the transformed text, including a
strategy that turns an ordinary name into a reserved word.

=== Relational Storage Migration: Persisted Physical Namespace Names

Steve approved restoring names through the configured system factory, with no
comparison-policy change checks. This slice implements that behavior.

==== Goal And Constraints

Replace the physical catalog/schema names held by `Namespace` and the physical
implicit namespace held by `Database` with `PhysicalName` values. Preserve the
already-resolved spelling and quoting across a metadata archive round trip,
without repeating implicit naming, physical naming, global quoting, or keyword
quoting.

`PhysicalName` currently retains an immutable comparison policy. That policy is
supplied through the configured identifier helper and need not be serializable.
`MetadataArchiveImpl` archives a declarative `MetadataState` graph; its existing
restoration path recreates services and calls `Database.reattach()`. Serializing
a policy instance would introduce a new provider requirement and could capture
state belonging to the old system. This slice must not introduce factory ownership
checks or require policy implementations to implement `Serializable`.

==== Value And Archive Contracts

* Keep live `PhysicalName` immutable and constructed only through the supplied
  `PhysicalName.Factory`. Do not add a temporarily policy-less or mutable state
  to the value type.
* Introduce an internal data-only physical-name archive value holding finalized
  text and the quoted flag. Null optional qualifiers remain null; they are not
  represented by empty names. This archive value is not a strategy result or
  a logical name and carries no explicit/implicit origin.
* The internal archive value supports capture from a `PhysicalName` and
  reconstruction through a supplied factory. It does not parse delimiters,
  normalize quoting, apply naming strategies, or serialize the factory/policy.
* Introduce a physical namespace pair whose catalog and schema components are
  nullable `PhysicalName` values. `Namespace.getPhysicalName()` and
  `Database.getPhysicalImplicitNamespaceName()` expose this typed pair.
  `Namespace.LogicalNamespaceName` remains the logical lookup key.
* The owning database/namespace serial form stores the data-only name values.
  Restore all live physical values from the restored identifier helper's shared
  factory during reattachment, before exposing completed restored metadata.
  Do not let partially restored names escape through the archive API.
* Physical-key indexes, as they are migrated, must be reconstructed from restored
  values. Never mutate comparison keys on objects already used as map keys.
  The existing logical namespace/table/sequence indexes remain intact.

The first implementation migrates physical namespace storage and its consumers.
Consumers still requiring `Identifier` (mapping `Table`, sequences, UDT storage,
and unmigrated SQL formatting/extraction contracts) receive explicit internal
projections of the finalized physical values. These projections do not apply
physical naming or quoting again. No old public getter overloads are retained.
`QualifiedName` is not mechanically changed in this slice: its existing uses mix
logical generator/parser inputs with physical SQL names and require separate
contracts as those callers migrate.

==== Implementation Boundary

`PhysicalNameSnapshot` stores finalized text/quoting, and
`PhysicalNamespaceSnapshot` stores the two optional qualifier snapshots. Live
`PhysicalNamespaceName` values are transient on `Database` and `Namespace`;
reattachment reconstructs them through the restored identifier helper factory.
The snapshot is retained as data-only state for later archive round trips.
Physical namespace access before reattachment fails explicitly rather than
returning an incomplete live name.

Schema existence lookup consumes the typed namespace. Mapping tables, sequences,
UDTs, SQL defaults, and remaining extraction/rendering APIs use explicit
`physicalIdentifier()` projections until their own storage/contracts migrate.
No `PhysicalName` or policy is made Java-serializable. No physical-key indexes
are introduced in this slice; existing logical indexes survive unchanged.

=== Recommended Resolution Rules

. Resolve the applicable mapping declaration/override first. A supplied object name
  becomes an explicit `LogicalName` and bypasses implicit naming for every role,
  including indexes and constraints. Steve approved this uniform bypass.
. With no supplied object name, invoke implicit naming with the object's semantic
  role, relevant mapping facts, typed logical/physical dependencies, and effective naming defaults.
  A configured default is an input to that decision, not a fabricated explicit name
  which prevents the strategy from participating.
. Record the result as an implicit `LogicalName`. Explicit origin belongs to the
  naming decision, so strategy output must not relabel a generated result explicit.
  A copied/reused name for a distinct unnamed object is still implicit even when
  the referenced object's name was explicit.
. Resolve physical spelling at the existing materialization boundary. Naming
  requests should expose both `LogicalName` and `PhysicalName` for dependencies
  whose two names are available. Define availability per role; do not disguise a
  physical name as a logical name or use a string fallback. No global physical
  phase is required.
. Reusing an already named object, resolving its aliases, copying its finalized
  representation, and restoring an archive do not repeat its naming decision.
  Counts are per naming decision, not per source annotation or source contribution;
  intentional sharing and independently declared collisions need separate rules.

Preserve `LogicalName.isExplicit()` and its exclusion from equality. More detailed
source facts, such as an applied override versus a configured mapping default,
belong in the naming request/default input when useful to the provider. This does
not replace the explicit/implicit flag with a provenance enum in the name value.
Annotation default values must not automatically be classified as supplied object
names: the pipeline must distinguish an absent declaration from a naming default.

|Inventory each generated object and define role/default handling
|UDTs and temporary/internal objects
|Type or internal-object purpose and logical dependencies where applicable
|Define which objects are mapping names customizable by providers and which are internal allocations

Every implicit mapping database-object name should have an accountable naming role.
The matrix describes semantics, not one Java method per row. SQL expressions,
formula text, query aliases, and values stored in a generator table are not database
identifier names. Internal objects need an explicit scope decision rather than an
accidental omission or an automatic public callback.

=== Both Dependency Names And JPA Defaults

Steve prefers providing both dependency names where possible. This supersedes the
initial logical-only recommendation. The result of implicit naming remains an
implicit `LogicalName`; exposing physical inputs does not change the result type
or implicitly skip subsequent physical naming.

JPA default rules are role-specific:

* https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/jointable[JoinTable]
  combines the owning and inverse primary-table names, with the owner first.
* https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/joincolumn[JoinColumn]
  normally combines the relationship attribute name and referenced primary-key
  column name for a single defaulted join column; some cases use an entity name
  instead of an attribute name.
* https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/collectiontable[CollectionTable]
  derives its default table name from the entity and collection attribute names.

These rules refer to mapped tables and columns, but JPA does not define Hibernate's
logical/physical naming stages or the interaction with a custom physical strategy.
They justify retaining access to physical dependency names; they do not by
themselves settle where Hibernate-specific transformations enter every algorithm.
Do not mandate logical inputs for all default algorithms. Specify each default
against the applicable mapping rule and record the effect of physical naming.

For example, a join-table request could expose these pairs:

[cols="1,1,1",options="header"]
|===
|Dependency |Logical name |Physical name
|Owning table |`Person` |`p_Person`
|Inverse table |`Passport` |`p_Passport`
|===

A provider can deliberately combine the physical spellings into logical
`p_Person_p_Passport`. Applying a prefixing physical strategy to this new table
then yields `p_p_Person_p_Passport`. That repetition is not, by itself, evidence
that the same naming decision ran twice: the input tables and the new join table
are different objects. A provider choosing logical dependencies could instead
produce logical `Person_Passport`, then physical `p_Person_Passport`. Tests must
separate intentional composition from accidental replay on the same object.

Likewise, a join-column request should expose the referenced logical name and its
physical column name together. The default algorithm's choice does not change
logical `referencedColumnName` matching or the identity of the referenced column.
Constraints should receive typed dependencies appropriate to their role; generated
names must not hash comparison-policy keys. Explicit constraints still bypass
implicit naming; physical index/constraint handling remains an open SPI decision.

=== Initial Feasibility Findings

Association and collection table naming already receives materialized table
objects. Their physical names are available for named tables. `TableReference`
retains the logical name alongside that mapping object, so carrying both into
requests is feasible without delaying all physical naming.

Materialized columns expose `PhysicalName`; `ColumnNameCorrespondence` retains
logical aliases. A request must carry the logical dependency selected during
binding rather than arbitrarily reverse-looking up one alias for a physical
column. This is especially important for multiple logical aliases and composite
referenced-column pairings.

This is not yet proof that every naming role can promise both names. The working
specification must audit deferred/cyclic associations, derived identifiers,
generator objects, and auxiliary mappings. An inline view has a logical identity
and SQL expression, not a physical table name; it must not receive a fabricated
physical name. For roles requiring physical dependencies, arrange the dependency
before invocation or define a distinct supported case. Do not make all physical
inputs opportunistically nullable as a substitute for a lifecycle contract.

=== Defaults And Quoting To Resolve

Recommend preserving the current JPA discriminator default `DTYPE` in the new
default algorithm while making discriminator naming participate in the strategy.
Do not silently inherit `class` from the unused callback. The exact precedence of
configured defaults and the default strategy's role-specific rules still needs
approval, as does the tenant default. A custom strategy may select its own implicit
spelling using the effective defaults supplied to it.

Logical inputs carry their own quoting flags. Copying a referenced logical name
for another object and composing a new name from several inputs are different
operations. The specification must decide whether composition propagates quoting,
and how quote-by-default combines with provider-requested quoting. Preserve the
approved additive physical quoting rule: physical naming cannot unquote its input.
No proposed string concatenation may silently discard a logical input's quoting.

=== Alternatives And Tradeoffs For This Slice

Providing both stages lets default algorithms follow their role-specific mapping
rules and lets providers deliberately choose a dependency stage. Its cost is
retaining logical aliases and guaranteeing physical-name availability where the
request requires it. Logical-only inputs would simplify dependencies but exclude
physical-name-based algorithms; physical-only inputs would lose source identity.
The preferred direction is both, with explicit types and per-role guarantees.

Uniform explicit-name bypass gives implicit naming a single responsibility and
makes the explicit flag reliable. Continuing to pass explicit names to implicit
providers allows those providers to replace them, but makes the contract a general
name-selection policy. If that broader capability is needed, specify it deliberately
rather than preserving it only for constraints.

where feasible. Next verify per-role availability and resolve the concrete default
algorithms and quoting examples, generator/auxiliary coverage,

inputs, collision rules, and tests. Select Java contract shapes from those semantics.

== Alternatives And Tradeoffs

Serializing `PhysicalName` together with its policy is simpler mechanically but
would require every policy supplier to define a safe serial form and would
restore policy objects independently of the new system factory. It conflicts
with the intended shared-policy boundary.

Serializing text/quoting and rebuilding from the restored factory keeps the
archive declarative and preserves physical spelling, while requiring an explicit
restoration step and rebuilding any physical-key indexes. This is the recommended
approach.

Archiving comparison keys as well could conservatively reject a restore whenever
new keys differ. However, changed key encoding does not necessarily mean changed
comparison semantics, and matching keys for archived names do not establish
policy equivalence for every possible future name. This is not a substitute for
a defined archive environment-compatibility contract.

==== Approved Restored Comparison Rules

The restored system's policy governs reconstructed values.
Archive finalized spelling and quoting, not cached comparison keys. Retain the
existing environment-compatibility checks; do not add a policy identity or
factory identity check. Rebuild physical indexes under the restored policy and
report collisions where a uniqueness requirement would otherwise be violated.

Archived keys and policy identity checks are not part of this implementation.
Changing comparison rules does not itself reject restoration.

==== Acceptance Criteria

* Round-trip explicit, implicit, quoted, unquoted, and null catalog/schema values.
* Preserve physical text/quoting exactly, including a qualifier supplied by a

* Restore names using a nonserializable custom policy supplied by the restored
  environment; neither the old policy nor its services enter the archive.
* A strategy or quoting finalizer which would change names on a second invocation

* Exercise restoration under changed comparison rules according to the approved
  behavior above, with explicit coverage of physical-key index rebuilding as

* Preserve qualified SQL rendering and default catalog/schema behavior for
  existing table, sequence, UDT, schema creation/migration, and extraction paths.

=== Table Storage: Hierarchy Split

tables, named database views, and inline views, with shared relational mapping

The earlier proposal to keep all roles inside one `Table` representation is
superseded.

The approved hierarchy split is implemented and validated.
`TableReference` delegates physical naming to

=== Concrete Findings

Discriminator naming has an intentional bypass::
`ColumnBinder.bindDiscriminatorColumn()` supplies `DTYPE` directly when no name
is given. Its comment explicitly refers to HHH-20613 before routing through the
strategy. The default strategy instead obtains the effective discriminator
default. A redesign must decide the intended default and customization rule;
connecting the existing callback mechanically could change existing names.
The referenced issue has not been investigated in this pass.

Tenant naming follows basic-value materialization::
`BasicValueMappingMaterializer.materializeTenantIdBasicValue()` uses the shared
selectable processing path. The dedicated tenant naming callback has no production
caller. Decide whether tenant columns need a distinct naming role or should be
specified as ordinary basic columns; do not retain an apparently supported hook
that never participates.

Primary-key join naming has no production caller::
The callback's existence does not establish its coverage. Joined-inheritance,
secondary-table, and shared-primary-key association cases need separate behavioral
examples before deciding which belong to this role and how defaults are chosen.

Generated collection-index names are presented as explicit::
`TableKeyBinder.applyIndexes()` creates `idx_<table>_<column-list-hash>` for an
unnamed collection-table index, then passes it through `ResolvedIndex.explicit()`.
`IndexMappingMaterializer` still invokes `determineIndexName()`, but exposes that
generated name as `getUserProvidedIdentifier()`. The default strategy consequently
preserves it rather than generating its normal hashed index name. This is a
concrete mismatch between input provenance and the source contract, even though
the callback is invoked. Correcting it may change existing generated names.

Explicit-name policy varies by role::
Table callbacks are bypassed for explicit names, while constraint callbacks
receive a user-provided identifier and the default strategy elects to preserve
it. A custom constraint strategy can replace it. Uniformly bypassing callbacks
would therefore remove existing customization behavior.

Logical/physical identity and quoting need explicit input semantics::
Join-table inputs use physical table names as strings. Collection-table inputs
reconstruct an `Identifier` from `owningTable.getName()`, which does not explicitly
carry the table's quoted flag. Index naming attempts a logical table-name lookup
and falls back to a physical identifier on `MappingException`. These paths give
concrete reasons to specify name stage and quoting information. Behavioral tests
are still needed to establish affected cases and intended outcomes.

== Alternatives And Tradeoffs

New role-specific SPI::
Design callbacks and inputs around current naming decisions. Distinct callbacks
can expose precise facts for each role, but shared naming policies may require
repeated implementation. The method set is unconstrained by the old interface.

One generic naming request and dispatcher::
Represent naming kinds through a typed request hierarchy. Centralizes dispatch
and can make coverage visible, but moves branching into providers and makes
handling new request kinds a compatibility concern. An untyped property bag is
not an acceptable substitute for defined inputs.
