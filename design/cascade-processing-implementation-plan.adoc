== Purpose and Authority

This document describes how to implement the approved
link:cascade-processing-spec.adoc[Cascade Processing Specification].  The
specification remains authoritative for required behavior, compatibility, test
coverage, acceptance criteria, and permitted scope.  This plan records code
organization, sequencing, verification gates, migration mechanics, and current
implementation status.

Changing this plan does not change the approved specification.  Any discovered
need to change an observable behavior, compatibility requirement, or normative
`CPS-*` requirement MUST be disclosed and approved as a specification change
before implementation proceeds with that deviation.

The plan covers `CPS-STG-001` through `CPS-STG-004` and the benchmark-gated
`CPS-STG-006` workstream.  `CPS-STG-005` remains deferred until the Collection
Flush Processing Working Specification is approved.

== Implementation Principles

The implementation will follow these principles:

* Preserve the behavior and signatures of the `Cascade.cascade(...)` entry
  points and `CascadingAction` SPI except for the explicitly approved package
  relocation in `CPS-COM-005` through `CPS-COM-009`.
* Keep every completed stage buildable and behaviorally usable on its own.
* Keep the metadata walker as the production route until a compiled route has
  passed its complete differential and integration gates.
* Separate stable mapping structure from invocation-local traversal state.
* Apply runtime-sensitive action, style, cascade-point, lazy-state, and orphan
  decisions at traversal time unless a route profile has independently passed
  its parity gate.
* Introduce no public plan, traversal-context, route-selection, or diagnostic
  contract.
* Avoid changes to persister SPI solely to expose cascade plans.  Registry access
  will use an internal implementation boundary owned by the mapping metamodel.
* Treat behavioral parity as absolute.  Performance measurements may affect
  route selection but cannot excuse a parity failure.
* Make scoped context mutation exception-safe with `try`/`finally` restoration.
* Preserve action-specific contexts as the only authority for cross-invocation
  cycle and duplicate handling.

== Target Runtime Decomposition

The implementation is expected to converge on these internal responsibilities.
Names may be adjusted mechanically when the code makes a better name evident,
but responsibility changes require updating this plan.

[cols="2,4,3",options="header"]
|===
| Component | Responsibility | Initial location

| Cascade extension contracts
| Define action and style extension behavior and own the built-in action/style
  registries and singleton instances.
| `org.hibernate.cascade.spi`

| `CascadePoint`
| Identify the engine lifecycle point at which cascade traversal occurs.
| `org.hibernate.cascade.spi`

| `Cascade`
| Preserve the existing entry point, create an invocation context, apply or
  delegate root routing, and retain the metadata route during migration.
| `org.hibernate.cascade.internal`

| `CascadeTraversalContext`
| Carry invocation-local action, cascade point, session, root, action context,
  current parent, current node/metadata edge, and lazily materialized attribute
  path.  Provide scoped restoration operations.
| `org.hibernate.cascade.internal`

| `CascadePlan`
| Immutable entity-rooted ordered plan.
| Internal cascade-plan package selected during stage 2

| `CascadePlanNode`
| Immutable stable mapping facts for a property or relative element edge,
  including generic fallback information.
| Internal cascade-plan package selected during stage 2

| `CascadePlanCompiler`
| Compile persister metadata into plans after all referenced persisters are
  resolvable.
| Mapping-metamodel internal implementation

| `CascadePlanRegistry`
| Own entity plans by `EntityPersister` identity and reusable element subplans by
  `CollectionPersister` identity; become immutable for runtime lookup.
| Factory-scoped mapping-metamodel internal implementation

| Metadata walker
| Preserve the current traversal as the production and parity-reference route.
  It may initially remain in `Cascade` and later be extracted when dual walking
  requires a clean boundary.
| `org.hibernate.cascade.internal`

| Generic compiled walker
| Traverse plan nodes in mapping order while invoking the existing runtime
  predicates and behavior.
| `org.hibernate.cascade.internal`

| Route selector
| Select only routes that have passed migration gates; unknown/custom actions
  always select generic filtering.
| Internal implementation, with no public setting

| Normalized decision trace
| Record semantic decisions for differential tests without exposing a production
  diagnostic contract.
| Primarily test infrastructure, with only the minimum package-private hook
  required to observe both walkers

| `CascadeActionKind`
| Classify an exact built-in `CascadingActions` singleton once per root entry.
| Internal implementation introduced in stage 6
|===

The registry MUST be initialized after entity and collection persisters have
completed the mapping-model phases needed by the compiler.  Stage 2 will verify
the exact hook in `MappingMetamodelImpl.finishInitialization(...)`.  Access from
the walker MUST NOT add a plan accessor to `EntityPersister` or
`CollectionPersister`, and SHOULD avoid adding a new abstract method to an
existing public or SPI interface.  An additional internal access interface
implemented by the mapping-metamodel implementation is the preferred starting
point.

== `CPS-STG-001`: Traversal Context over the Metadata Walker

=== Intended result

Every public `Cascade.cascade(...)` entry creates one behaviorally independent,
thread-confined traversal context.  The current metadata iteration remains the
only walker and produces unchanged behavior.

=== Production work

`CPI-001-01`:: Add an internal `CascadeTraversalContext<T>` initialized with the
active `CascadingAction<T>`, root `CascadePoint`, `EventSource`, root
`EntityPersister`, root object, and action-specific context.

`CPI-001-02`:: Represent the mutable current parent, current metadata edge, and
current attribute path in the context.  Before plan nodes exist, the current
metadata edge is the property name/type/style/index needed to identify the
equivalent edge.  Stage 2 replaces or supplements this with a plan-node
reference.

`CPI-001-03`:: Route recursive component, association, to-one, collection, and
orphan processing through the context instead of repeatedly passing traversal
state as independent parameters.

`CPI-001-04`:: Lazily materialize the component path so root-level traversal does
not allocate a path list.  Preserve the `null` path supplied to existing actions
for root-level associations.

`CPI-001-05`:: Scope component-path, current-parent, current-edge, and temporary
collection cascade-point changes with `try`/`finally`.  Restore the caller's
state after both normal completion and exceptions.

`CPI-001-06`:: Preserve the translation from
`AFTER_INSERT_BEFORE_DELETE` to
`AFTER_INSERT_BEFORE_DELETE_VIA_COLLECTION` only while traversing collection
elements.

`CPI-001-07`:: Preserve persistence-context child/parent registration and its
existing `finally` cleanup around `CascadingAction.cascade(...)`.

`CPI-001-08`:: Confirm that a nested event-driven public cascade entry creates a
new traversal context while continuing to pass the action-specific context value
according to the existing action contract.

=== Test work

`CPI-001-T01`:: Add focused context tests for initial state, lazy path creation,
nested component paths, cascade-point translation, and restoration.

`CPI-001-T02`:: Add exceptional-exit coverage proving path, parent, edge,
cascade-point, and persistence-context child/parent restoration.

`CPI-001-T03`:: Add or adapt a nested-entry/cycle test proving that no generic
visited set changes action-specific duplicate suppression.

`CPI-001-T04`:: Run existing component, collection, orphan, enhanced-lazy,
database-cascade, and cascade-cycle regressions.

=== Exit gate

* `CPS-TST-008` and `CPS-TST-009` pass for the context behaviors available at
  this stage.
* Existing cascade tests selected by `CPI-000-01` pass.
* Public and SPI signatures are unchanged.
* The metadata walker remains the sole production route.
* No completed context is retained by factory, metamodel, persister, session, or

== `CPS-STG-004`: Production Route Migration

=== Intended result

Independently proven built-in and generic routes move to the compiled walker
without removing the metadata fallback prematurely.

=== Production work

`CPI-004-01`:: Define an internal route table using exact action identity,
cascade point, and any other stable discriminator required by the verified test
matrix.  Stage 6 may replace the built-in identity mapping with
`CascadeActionKind` classification.  Unknown/custom actions select the generic
compiled route only after the custom-action gate passes; otherwise they remain
on metadata traversal.

`CPI-004-02`:: Migrate one independently testable route group at a time.  Initial
ordering SHOULD favor a common, well-covered route with low orphan and lazy-state
complexity before moving persist-on-flush, check-on-flush, and remove routes.

`CPI-004-03`:: Retain per-node generic predicate evaluation in the compiled
walker.  Route migration does not imply use of a route profile.

`CPI-004-04`:: Retain the metadata walker until all supported and dormant routes
have a conforming generic compiled path and removal has been reviewed separately.

`CPI-004-05`:: Record each migrated route, its differential test coverage,
integration test set, benchmark result, and any explicitly accepted performance
exception.

=== Route gate

A route may switch only when:

* its normalized decision traces match exactly,
* its real-action integration tests pass,
* its existing regression tests pass,
* custom/registered styles encountered within the route retain generic behavior,
* the paired benchmark has been reviewed under `CPS-PRF-006`, and
* any traversal-time regression above 5% or allocation regression above 10% has
  been investigated and explicitly accepted.

=== Exit gate

All production routes selected for this implementation have an auditable route
gate record.  Routes not passing a gate continue to use metadata traversal and
do not block migration of independent routes.

== `CPS-STG-006`: Profiled Built-in Routes

Stage 6 follows the generic compiled walker and may proceed independently of the
deferred collection-delta stage.

=== Production work

`CPI-006-01`:: Introduce `CascadeActionKind` classification by exact identity of
known `CascadingActions` singleton instances.  Resolve it once per root entry.

`CPI-006-02`:: Add profile data only for stable built-in action/style/point facts
covered by differential tests.

`CPI-006-03`:: Permit profile use per node.  A registered style, unverified
composed style, or unproven node uses the generic runtime predicates without
disabling proven profiles elsewhere in the same plan.

`CPI-006-04`:: Keep unclassified and custom actions entirely on the generic
runtime-filtered path.

=== Profile gate

A profile is retained only when it has exact differential parity and demonstrates
a measurable benefit in at least one targeted workload.  A profile that fails
either condition is removed or left disabled without affecting the generic
compiled route.

== `CPS-STG-005`: Deferred Collection-Delta Integration

No production implementation of `CPS-COL-*` is authorized yet.  Until the
collection specification is approved:

* cascade continues to discover collection orphans using current initialized or
  queued-operation behavior,
* cascade does not depend on `CollectionDelta`, delta freezing, or a collection
  flush context,
* the plan compiler and walker may reserve no behavior that assumes a future
  delta representation, and
* `CascadeCollectionBoundaryTest` remains planned but is not an exit dependency
  for stages 1 through 4 or 6.

After the collection specification is approved, this section will be expanded
into concrete producer/consumer boundary work before stage 5 begins.

== Benchmark Implementation and Review

=== Artifact

Add `org.hibernate.cascade.internal.CascadeTraversalBenchmark` under
`hibernate-core/src/jmh/java`, or an equivalently named artifact preserving the
traceability stated by `CPS-TST-013`.

=== Development runs

Short local runs may be used while shaping the implementation, but they are not
approval evidence.  They SHOULD compare paired metadata and generic compiled
variants and expose counters for nodes, metadata scans, value resolutions, and
path allocations alongside JMH time and GC allocation.

=== Route-approval runs

Approval evidence MUST follow `CPS-PRF-003` through `CPS-PRF-006`: at least three
forks, ten warmups, twenty measurements, recorded JVM/machine/heap/profiler
settings, paired equivalent fixtures, and retained raw results.

For each route review, retain:

* the source revision,
* benchmark command and environment,
* raw JMH output or durable artifact reference,
* a concise metadata-versus-compiled comparison,
* allocation and traversal-time differences,
* the route decision, and
* the rationale for any explicitly accepted threshold exception.

The checked-in location and CI artifact policy for raw benchmark results will be
selected before the first production route migration.  That repository-layout
choice does not alter the benchmark requirements.

== Verification Strategy

Verification is layered so failures remain attributable to a stage.

[cols="1,3,3",options="header"]
|===
| Layer | When | Evidence

| Compile and focused unit tests
| Every implementation increment
| Changed production classes compile; new focused tests pass

| Focused cascade regressions
| Every stage exit
| Component, collection, lazy, orphan, database-cascade, and cycle cases pass

| Differential matrix
| Stages 3, 4, and 6
| Exact normalized traces from equivalent fresh state

| Real-action integration
| Stages 3 and 4
| Observable built-in action, orphan, lazy, ordering, and cleanup behavior

| Full `hibernate-core` tests
| Before a production route switch and final handoff
| No module regression attributable to cascade changes

| JMH characterization
| Before stage 4 route switches and for every stage 6 profile
| Paired time, allocation, and semantic work counters with retained results

The initial focused regression inventory will include existing tests for:

* cascades through components and nested components,
* managed and detached enhanced-lazy associations,
* uninitialized collections and queued operations,
* persist, merge, remove, refresh, evict, and check-on-flush routes,
* logical one-to-one and collection orphan removal,
* `OnDelete` database cascade,
* circular and multipath object graphs, and
* collection cascade ordering and FK constraints.

Exact Gradle selectors will be recorded with the implementation checkpoint once
the smallest representative set has been confirmed.

== Review Units and Checkpoints

Implementation should be presented in reviewable units in this order:

. traversal-context type and metadata-walker parameter refactor,
. traversal-context restoration and regression tests,
. immutable plan vocabulary,
. compiler and registry bootstrap integration,
. plan structural tests,
. walker boundary and normalized trace vocabulary,
. generic compiled walker,
. full differential and compatibility matrix,
. JMH benchmark suite,
. independently gated production route migrations, and
. independently gated built-in route profiles.

Each checkpoint report will state:

* completed work-item identifiers,
* tests and benchmarks run with results,
* remaining stage work,
* observed compatibility or performance risks,
* any implementation choice that materially refines this plan, and
* any proposed deviation requiring specification approval.
