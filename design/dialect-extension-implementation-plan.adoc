This document plans implementation of

facility defined and partially implemented through
`design/spi-implementation-plan.adoc` while keeping the

is complete.  If inventory work changes a normative decision, the working
specification must be amended before implementation proceeds.

== Objectives

The implementation must turn Dialect extension from an accidental collection
of public, protected, and internal contracts into an explicit provider SPI.
It must:

* classify `Dialect` for independent `USE`, `IMPLEMENT`, and `SUPPLY` roles;
* audit and deliberately reduce or retain its complete generated surface,
  currently roughly 420 reportable declarations;
* provide supported replacements for internals used by maintained Dialects;
* make the translator-visible SQL AST and model-mutation trees supported SPI;
* provide deliberate generic and SQL-family translator bases;
* separate database capabilities from global SQM and HQL integration;
* treat community Dialects and a standalone provider as external consumers;
* publish a Dialect compatibility test kit;
* analyze all of this through the general SPI report and explicitly invoked
  validators, with lifecycle enforcement reconsidered after remediation.

This is an incremental migration.  It is not a package-wide declaration that
everything under `org.hibernate.dialect` is SPI, and it is not a compatibility
promise for every built-in implementation class.

== Dependencies and sequencing

The general SPI annotation, canonical model, reports, and standalone validators
are implemented.  Dialect work therefore begins with read-only inventory and
proposed classification overlays.  Production classification depends on:

* canonical roles and classification origins;
* signature traversal and deduplication;
* report generation;
* explicitly invoked validation;
* reviewed readiness of each support commitment.

A populated migration allowlist, `check` integration, and role-sensitive
compatibility baseline are deliberately deferred.  They are not prerequisites
for Dialect remediation and must not be introduced merely to make the current
inventory pass.

Dialect-specific logic should be implemented as inputs, views, and rules over
the canonical SPI model.  It must not create a second classifier.

== Work products

The migration will maintain the following reviewable artifacts:

Dialect surface ledger::
One row for every public or protected declaration owned by `Dialect`, including
roles, usage evidence, disposition, replacement, and required Migration Guide
anchor.

Provider dependency ledger::
Every static dependency from `hibernate-community-dialects` to an upstream
Hibernate internal element, including a usage category, remediation batch, and
planned or completed Migration Guide anchor for its supported replacement.

Family evidence matrix::
Existing inheritance, copied behavior, compatibility modes, external-provider
evidence when available, and a recommendation for each potential SQL family.

Package-migration map::
Every translator-visible SQL AST and model-mutation package/type, its final SPI
classification or internal disposition, and any transition adapter.

Migration Guide coverage index::
A generated or validated mapping from each completed provider-facing removal,
relocation, narrowing, or replacement to a stable anchor in the versioned root
`migration-guide.adoc`.

Provisional Dialect provider report::
A representative provider-oriented view generated from the general canonical
SPI model and migration inventory.  Its adoption is a later review decision,
not a required publication at the start of migration.

These artifacts should be machine-readable where practical, with generated
AsciiDoc views for review.  Hand-maintained evidence such as a disposition or
tracking issue may be joined to generated declarations by stable element
identity.

== Deferred review decisions

The following decisions require evidence or a concrete API proposal from the
named phase and are not silently delegated to implementation:

* Phase 0: generated-inventory and checked-in decision-overlay format;
* Phase 0: selectability metadata and possible selector/resolver catalog;
* Phase 1: exact accepted Dialect and translator SQL-family bases;
* Phase 4: complete SQL AST translation request/context API;
* Phase 4: final translator result-construction helper boundary;
* Phase 7: optional Java service loading for HQL/SQM translators;
* Phase 9: adoption or rejection of a focused Dialect-provider report;
* Phase 9: removal of the migration inventory task or retention of a proven,
  reduced diagnostic subset.

The Phase 8 review also chooses the dedicated test-kit artifact name and its
complete public SPI.

== Execution strategy

The numbered phases are accountability checkpoints and completion buckets, not
a requirement to implement the migration as a strict waterfall.  After the
initial evidence and contract decisions, production work should proceed in
narrow vertical slices.  Each slice includes the supported contract, provider
migration, external-boundary tests, classification changes, documentation, and
Migration Guide coverage needed to make that slice complete.

=== Inventory foundation

Begin with a migration-scoped `generateDialectExtensionInventory` task.  The
task is not a new published report or permanent validation mechanism.  It must
remain reproducible and rerunnable throughout the migration so that decisions
and progress can be reviewed against current compiled artifacts.

The task must consume the outputs and inputs of `buildAggregatedIndex` through
Gradle providers rather than hard-coding paths under `documentation/target`.
Its analysis uses:

* the aggregated `jandex.idx` for declarations, signatures, annotations,
  hierarchy, and package structure;
* the aggregated artifact-provenance data for declaration ownership;
* the indexed compiled artifacts for method-body calls, field accesses, and
  other authoritative bytecode linkage.

Jandex does not describe method-body linkage, so the Jandex index alone is not
sufficient for the provider dependency ledger.  Source imports may supplement
but must not replace bytecode analysis.

The task should apply `JandexClassificationClassifier` to the same in-memory
index whenever category and role information is needed.  It must not introduce
a Dialect-specific classifier.  `classifications.json` is the published
interchange and reporting artifact, not the primary input to this inventory.
If classification is also requested in the same Gradle invocation, a
project-scoped extension may share the immutable classified model rather than
classifying or parsing it repeatedly.

All generated inventory projections should be produced from one analysis
execution and written beneath the configured build directory.  The complete
facts remain disposable generated output.  During this migration, a compact,
sparse decision overlay is checked in under `design/`; it records only human
decisions and rationale and is removed when the migration no longer needs it.

=== Decision tranche

Use the generated evidence to prepare three related decisions before the first
production support commitment:

. review every `Dialect` declaration in coherent review groups such as constructors
  and identity, capabilities, translation and factories, supplied strategies,
  DDL/schema/type/function support, and low-level engine helpers;
. review the SQL-family evidence matrix and select the initial supported
  families;
. review the SQL AST and model-mutation package-migration map and its staged
  subtree order.

Do not add the type-level `Dialect` SPI classification merely because inventory
is complete.  It waits until every exposed declaration has a disposition, as
required by Phase 2.

=== Provider walking skeleton

Establish the Phase 3 standalone provider fixture and explicit provider-boundary
diagnostics before the first production migration slice.  The fixture may
initially expose missing SPI and need not pass completely.  It provides the
real external consumer and measurable boundary against which each later slice
is completed.

=== Production migration slices

After the applicable review checkpoints, use select translation as the first
SQL AST vertical slice.  Select its representative community Dialect from the
inventory evidence, preferring one which exercises the central translator
contracts without pulling in many unrelated feature remediations.  Include the
semantic nodes and walkers, translation request/context, translator factory,
generic base, community consumer, standalone provider fixture, tests,
classification, documentation, and Migration Guide entries needed by that
path.

Continue with coherent slices for query mutation and model mutation, followed
by the Phase 5 feature-family priorities, accepted SQL-family bases, and SQM/HQL
decoupling.  A numbered phase may therefore have work in progress while an
earlier vertical slice is completed; its status becomes complete only when all
of that phase's acceptance criteria are satisfied.

Provider-facing tests should accumulate with these slices.  Phase 8 extracts
and stabilizes them as the compatibility test kit instead of designing the
entire kit only after all production migration has finished.

== Delivery sequence

Each phase carries an implementation status.  `NOT STARTED` means that design
text, existing classes, or general SPI tooling must not be mistaken for
Dialect-phase implementation.  `IN PROGRESS` means that reviewable phase work
exists but one or more acceptance criteria or review checkpoints remain.
Deferred review points are called out separately from phase completion.

Selection-policy decisions:

* `APPROVED`: `hibernate.dialect` intentionally accepts a constructed `Dialect`
  instance, a `Class<? extends Dialect>`, or a fully qualified Dialect class
  name.  These are application-facing configuration forms; they do not change
  the provider-SPI audience of a custom Dialect implementation.
* `APPROVED`: when `hibernate.dialect` is absent, standard automatic resolution
  from `DialectResolutionInfo` is intentionally supported and is the preferred
  application path for built-in Dialects.  The resolution information may come
  from JDBC metadata or explicitly supplied database-product metadata.
* `APPROVED`: `hibernate.dialect_resolvers` remains a supported application
  configuration mechanism for explicitly installing provider
  `DialectResolver` implementations.  Configured resolvers run before
  discovered and standard resolvers.
* `APPROVED`: Java-service-loaded `DialectResolver` implementations remain a
  supported provider-SPI discovery mechanism.  They run after explicitly
  configured resolvers and before standard resolution; this is also the
  mechanism used by `hibernate-community-dialects`.
* `APPROVED`: Java-service-loaded `DialectSelector` remains supported provider
  SPI for mapping explicit provider-defined names to Dialect classes.  It is
  complementary to automatic `DialectResolver` discovery; a possible shared
  metadata catalog remains deferred.
* `APPROVED`: named Dialect registration through `StrategyRegistrationProvider`
  remains supported as a consequence of the general named-strategy SPI, but it
  is not promoted as a separate preferred Dialect-provider mechanism.
  Dialect-specific provider guidance directs name contributions to
  `DialectSelector`.
* `APPROVED`: canonical, unversioned Dialect short names remain supported
  configuration values.  They provide stable names independent of an
  implementation FQCN, while automatic resolution remains the recommended path
  for built-in Dialects.
* `APPROVED`: version-qualified legacy aliases are removed instead of becoming
  supported selection names.  They no longer select version-specific behavior
  and misleadingly suggest support for obsolete database versions.  A
  versioned Migration Guide table maps each removed alias to automatic
  resolution or its canonical unversioned name, and obsolete names fail
  clearly rather than silently selecting a modern Dialect.
* `APPROVED`: the noncanonical `SAPDB`, `DB2400`, `DB2390`,
  `HANARowStore`, `HANAColumnStore`, and `HANACloudColumnStore` names are
  removed for the same reason.  None selects distinct behavior; their Migration
  Guide replacements are `MaxDB`, `DB2i`, `DB2z`, and `HANA`, respectively.
* `APPROVED`: inclusion in the generated Dialect support table is a supported
  database-and-version statement subject to the containing module's support
  policy.  It does not assign API or SPI category, promise subclassability, or
  imply a particular selection mechanism.  Conversely, an undocumented
  concrete Dialect subclass gains no supported-selection promise merely because
  reflective FQCN construction currently succeeds.
* `APPROVED`: individual concrete-Dialect Java category, supported
  subclassability and constructors, and configuration-selectability decisions
  are made in Phase 2 after Phase 1 establishes the supported family bases.
  Phase 0 supplies the evidence and does not infer those decisions from current
  visibility.

Capture:

* all public and protected declarations owned by `Dialect`;
* all in-repository overrides of each declaration;
* direct calls from Core and community Dialects;
* all direct and transitive type references in exposed signatures;
* every community-Dialect bytecode dependency on upstream internal elements;
* every built-in and community Dialect inheritance edge;
* every SQL AST, SQM, HQL, mutation, locking, DDL, schema, sequence, callable,

* current uses of `getSqlAstTranslatorFactory()`,
  `getSqmTranslatorFactory()`, and `getHqlTranslator()`;
* selection metadata and responsibilities in `DefaultDialectSelector`,

Bytecode/linkage analysis is authoritative for dependency counts.  A source
import report may be retained as a convenient secondary view, but must not be
the authoritative inventory because fully qualified references, inherited
signatures, and other bytecode dependencies can evade import scanning.

Consume `buildAggregatedIndex` through its declared Gradle providers.  Use the

Generate deterministic inventories with stable element identifiers and report

=== Phase 1: family inventory and decision checkpoint

Status:: `NOT STARTED`

Derive the initial family inventory from repository evidence.  No initial list
is required from the specification reviewer.

For each candidate Dialect or translator family, record:

* current superclass/subclass relationships in Core and community Dialects;
* substantial duplicated or copied translation behavior;
* compatible-database modes represented by the family;
* assumptions currently obtained through casts to concrete built-in Dialects;
* syntax differences which are better expressed as capabilities or rendering
  strategies;
* known maintained external subclasses, if evidence is available;
* the estimated protected surface of a supported base.

Recommend exactly one disposition:

Supported family base::
Introduce or retain an abstract `IMPLEMENT` base with a deliberate protected
contract.

Supported concrete provider base::
Classify an existing concrete Dialect as `IMPLEMENT` SPI because its identity
and construction are useful to providers.  Configuration selectability remains
an independent property and does not make the SPI ordinary API.

Composable capability or strategy::
Avoid inheritance and expose the varying behavior through a focused supported
contract.

No supported extension::
Keep a built-in class internal as a Java implementation because there is
insufficient provider evidence.  Its configuration selectability is decided
independently.

At minimum, evaluate PostgreSQL-compatible, MySQL-compatible, DB2-compatible,
and Transact-SQL relationships; these are candidates, not predetermined
outcomes.

Review checkpoint:

* review the evidence matrix and recommendations;
* amend the specification with the accepted initial family list;
* only then commit to the public/protected contract of a family base.

Discover publicly maintained external Dialects through source repositories,
artifact metadata, issue history, and documentation.  The reviewer may
supplement private or vendor-maintained providers, but exhaustive ecosystem
discovery is not required to begin.

=== Phase 2: classify and audit Dialect

Status:: `NOT STARTED`

Model the proposed type-level classification and roles in the surface ledger
before changing production annotations.  Production `@SPI` annotations are
support commitments, not migration markers.

Process the surface ledger declaration by declaration.  Assign:

* independent effective roles;
* evidence from Core, built-in, community, and surveyed external usage;
* one disposition: retain, make final, reduce visibility, move behind an
  internal collaborator, deprecate, or replace;
* a compatibility and migration action;
* the required Migration Guide entry or an explicit reason no provider-facing
  migration is involved;
* an owning remediation phase when other work is required first.

Separate target classification from physical removal.  A declaration excluded
from the intended SPI may receive a direct `@Internal` override while remaining
temporarily visible for compatibility.  Retention, bridging, deprecation,
visibility reduction, and direct removal are case-by-case decisions under the
release policy.  A method must not remain overridable only because changing it
requires a decision; commonly used accidental hooks should not be removed
without a supported replacement and migration note.

Supply points require explicit attention.  Methods returning a strategy,
factory, descriptor, or service supplied by the subclass should be explicitly
classified `SUPPLY`; type-level `SUPPLY` must not cause unrelated methods to be
reported as supply points.

Classify Java category, configuration selectability, and SPI roles
independently.  A concrete built-in Dialect defaults to internal as a Java
implementation.  Provider use or subclassing requires an affirmative SPI
decision; application Java use beyond selection requires an affirmative API
decision.  Selectability changes neither category nor roles.  Abstract family
bases default to non-selectable `IMPLEMENT` SPI.

After every exposed `Dialect` declaration has a reviewed disposition, add the
specified type-level classification and explicitly classify each supported
subclass constructor for `IMPLEMENT`.  Add `@Internal` overrides for transition
declarations deliberately excluded from the support surface.  Production
classification may proceed in coherent ready batches but must not promise an
unreviewed signature.

Acceptance for this phase:

* the generated inventory accounts for every exposed `Dialect` declaration;
* every retained overridable method is intentionally in the `IMPLEMENT`
  baseline;
* supported constructors and actual supply points are explicit;
* no whole-package `IMPLEMENT` classification is introduced;
* built-in Java category and SPI roles are canonical, while selectability is
  modeled independently;
* compatibility-sensitive reductions include deprecation or migration handling
  appropriate to the release policy;
* every applied provider-facing reduction has a valid Migration Guide anchor.

=== Phase 4: SQL AST and model-mutation SPI

Status:: `NOT STARTED`

Inventory the actual semantic trees used by provider translators.  Define a
package-migration map that keeps the coherent existing trees rather than
introducing parallel façade nodes.

For each package and node:

* classify translator-read semantic nodes as `USE` SPI;
* add `IMPLEMENT` only where providers implement or subclass a node;
* add `SUPPLY` only where providers contribute or construct instances for
  Hibernate;
* keep execution-result implementations internal where providers do not need
  to name them;
* place supported coherent subtrees beneath `.spi` package roots so the general
  subtree convention supplies their baseline `USE` classification;
* identify package moves, compatibility adapters, and eventual removals.

Use `org.hibernate.sql.ast.spi...` for semantic AST contracts, walkers,
request/context contracts, and generic engine-level translator SPI.  Use
`org.hibernate.dialect.sql.ast.spi...` for Dialect rendering and accepted
SQL-family bases, and corresponding `internal` trees for built-in leaves and
non-contract helpers.

Move coherent subtrees in staged vertical batches rather than one atomic
relocation.  Each batch updates Core, community Dialects, the standalone
fixture, classification, tests, and Migration Guide coverage together.

Make `SqlAstTranslatorFactory` implementable and classify the Dialect factory
method for `IMPLEMENT + SUPPLY`.  Introduce a supported translation request or
context when current factory inputs expose implementation detail.  Before
changing the factory, present the exact request/context interfaces, methods,
roles, ownership, and operation-specific relationships for focused review.

Refactor the generic translator base so provider translators can render select,
query-mutation, and model-mutation SQL while consuming only supported contracts.
Prototype supported helpers/factories for internal JDBC operations, selections,
bindings, and execution results instead of exposing their implementation
classes.  This is the preferred direction, but its final shape and requirement
remain deferred until the inventories show actual provider construction needs
and the helper surface is reviewed.

Include set-returning-function descriptors and anonymous-tuple leakage in this
phase, not as an unrelated later cleanup.

Acceptance for this phase:

* the standalone provider traverses representative select and mutation trees;
* supported walker and protected-hook signatures contain no internal types;
* the proposed result-construction boundary has received focused review before
  becoming a support commitment;
* the real semantic trees are the supported contracts; no duplicate façade tree
  exists;
* generic translator public/protected surface has been audited before its
  `IMPLEMENT` baseline is established;
* package moves have explicit migration adapters or release-policy handling;
* SQL AST and model-mutation relocations have versioned Migration Guide entries
  with before-and-after imports or usage examples.

=== Phase 5: feature-family remediation batches

Status:: `NOT STARTED`

Repair internal dependencies in small vertical batches.  Each batch must
include the supported contract, provider migration, tests, classification and
inventory changes, a versioned Migration Guide entry, and other provider
documentation.

Use this priority order:

. internal types leaked directly by supported signatures;
. SQL AST walker and translator requirements not completed in Phase 4;
. DDL type construction and temporary-table/CTE mutation strategies;
. locking support profiles and locking-clause rendering;
. schema exporters and sequence information extractors;
. callable statement support and function/type contribution;
. remaining provider conveniences and utilities.

The approved temporary-table batch uses the three independent Dialect strategy
getters for local, global, and persistent behavior.  Local and global results
are nullable to indicate unsupported kinds; the inherited persistent strategy
remains the non-null fallback.  Remove `getSupportedTemporaryTableKind()`
because one value cannot express simultaneous support for multiple kinds.

Move `TemporaryTableStrategy` and `TemporaryTableKind` to the temporary-table
`.spi` package.  Classify the strategy interface for provider implementation
and the kind enum for provider use.  Retain deliberate standard local and
global family bases, while keeping composition as the normal persistent path.
Migrate and remove `LegacyTemporaryTableStrategy` together with the related
deprecated Dialect methods.  The provider fixture must supply local and global
strategies simultaneously and also exercise the inherited persistent fallback.

For each observed external need, choose the narrowest appropriate shape:

* factory, builder, profile, or registry for constructing stock behavior;
* supported abstract base for deliberate subclassing;
* read-only interface for semantic inspection;
* request/context interface for state consumed by a base;
* helper/factory when the provider needs to create an internal engine result.

Do not promote an internal implementation class solely because community code
currently imports it.  First decide whether providers need to use, implement,
or supply the concept, then expose the smallest stable contract that satisfies
that role.

Each batch is accepted when:

* every changed contract has explicit roles;
* Core, community Dialects, and the standalone fixture use the supported path;
* no replacement signature leaks another internal type;
* before-and-after provider documentation exists;
* the corresponding versioned Migration Guide entry exists and its stable
  anchor is recorded in the affected ledgers;
* the complete Dialect-boundary diagnostics decrease or become more precise,
  with exact identities retained rather than a count-only gate;
* SQL-generation or database integration tests cover the behavior.

=== Phase 6: accepted SQL-family bases

Status:: `NOT STARTED`

Implement the family decisions accepted after Phase 1.

Treat acceptance as a family as a decision about shared behavior and
compatibility assumptions, not as a decision to expose every deviation through
subclass overriding or any other single customization mechanism.

For each supported family base:

* make it abstract unless direct construction is a deliberate use case;
* classify it `IMPLEMENT`;
* document its grammar family and assumptions;
* expose a reviewed, minimal extension surface which may combine protected
  hooks, abstract methods, capabilities, profiles, strategies, and delegates;
* replace concrete-Dialect casts with supported family support interfaces;
* choose the combination of template inheritance and composition which matches
  the family's actual invariant and variable behavior;
* migrate in-repository subclasses and copied implementations;
* keep built-in leaves internal unless independently approved for API or SPI.

Add a focused compatibility fixture per family.  The fixture should subclass
the family base outside Hibernate packages and override every intended hook at
least once across the fixture suite.

Acceptance for this phase:

* every family is justified by the accepted evidence matrix;
* each base depends only on supported API/SPI;
* its public/protected surface appears in the `IMPLEMENT` baseline;
* small syntax variants use capabilities/strategies rather than unnecessary
  subclasses, including within an otherwise justified family base;
* no maintained in-repository subclass is left extending an unsupported
  built-in leaf.

=== Phase 7: SQM and HQL decoupling

Status:: `NOT STARTED`

Replace database-specific full SQM converter selection with focused structural
capabilities.  Start with the repeated synthetic-table behavior in Informix,
Ingres, Sybase, and legacy Sybase:

* define a supported capability describing when the synthetic table group is
  needed and the semantic/rendering information required;
* teach the standard SQM converter to interpret it;
* migrate the four in-repository implementations;
* test grouping, ordering, partitioning, and table-less selection behavior.

Then inventory every `getSqmTranslatorFactory()` override and call site and
distinguish database capabilities from general query-engine replacement.  Keep
any general SQM translator integration outside Dialect and replace internal
request types, including `DomainParameterXref`, with supported request/context
contracts where that general integration remains supported.

Retain `QueryEngineOptions` as the canonical downstream source for global HQL
and SQM translator integration.  Preserve explicit settings.  Prototype, but do
not adopt without focused review, Java service-loadable contributions feeding
the same options; define precedence, ambiguity, multiplicity, and lifecycle.

After migrating all in-repository uses, remove
`Dialect#getSqmTranslatorFactory()` and `Dialect#getHqlTranslator()` directly.
Do not deprecate them, add forwarding hooks, or include them in the initial
Dialect SPI compatibility baseline.  Document migration toward focused Dialect
capabilities or the global query translator integration, as appropriate, and
reject new database-specific HQL parser selection.

Add a dedicated versioned Migration Guide entry in the same change as the
removal.  It must explain that there is no replacement hook on `Dialect` and
separately show the focused-capability and global-integration migration paths.

Acceptance for this phase:

* in-repository database structural differences use focused capabilities;
* normal Dialects do not replace the complete SQM converter for local syntax
  variation;
* remaining general integration signatures contain no internal types;
* both Dialect hooks are absent from `Dialect` and from its SPI compatibility
  baseline;
* no equivalent general query-translator selection hook has been added back to
  `Dialect`;
* the removal's Migration Guide entry covers both provider migration paths;
* tests prove equivalent query semantics and SQL for migrated Dialects.

Database-integration contract suite::

== Compatibility and migration policy

Establish compatibility baselines only after the relevant visibility audit,
not before.  Otherwise accidental public/protected methods become supported by
default.

For package moves and replacement contracts:

* apply normal compatibility policy to existing API and SPI;
* move internal contracts directly where practical while documenting supported
  replacements for known provider use;
* decide accidental public/protected contracts case by case from Javadoc,
  history, and provider evidence;
* use direct `@Internal` classification before later removal where a bridge or
  deprecation window is appropriate;
* add or update the versioned Migration Guide entry in the same change;
* document both the role being replaced and the supported replacement;
* keep internal adapters out of the new SPI report;
* remove adapters only according to the applicable release policy;
* update provider fixtures before updating a compatibility baseline.

The Migration Guide entry is required even where an accidental or internal
contract did not previously receive a formal compatibility guarantee.  The
entry explains the practical provider migration; it does not retroactively
classify the old contract as supported SPI.

Moving a real SQL AST node to an SPI-classified package may be more compatible
and maintainable than defining a parallel interface.  The package-migration map
must decide transitions per coherent tree area rather than through ad hoc
single-class moves.

== Risks and controls

Oversized Dialect contract::
Audit every declaration and reduce visibility/finality before baseline.  Track
unresolved entries explicitly; do not equate current exposure with intent.

Family-base overfitting::
Require multiple implementations, maintained external use, or a documented
compatibility mode.  Prefer capabilities for small variations.

Package-move churn::
Move coherent semantic tree areas, provide reviewed adapters, and avoid a
parallel façade tree that doubles translator maintenance.

Provider migration deadlock::
Use vertical feature batches so a supported replacement, migrated community
consumer, tests, documentation, and diagnostic reduction land together.

False confidence from source imports::
Use compiled linkage for the authoritative inventory and source scanning only
as supplementary evidence.

General SPI model drift::
Keep every Dialect inventory, report, and validator view on the canonical
classification model; do not establish unsupported one-off Dialect
classification logic.

Compatibility kit scope::
Separate SQL-generation from database integration and reuse the existing
database matrix rather than requiring all external databases for the normal
build.

== Review checkpoints

Implementation should pause for focused review at these points:

. reproducible inventory formats, selectability sources, and headline counts;
. family evidence matrix and exact initial family list;
. `Dialect` surface dispositions before its first SPI baseline;
. SQL AST/model-mutation package-migration map and staged subtree order;
. concrete translation request/context interfaces;
. translator result-construction helper boundary;
. first complete remediation batch and replacement-shape conventions;
. SQM/HQL removal, replacement contracts, optional service loading, and
  migration text;
. compatibility test-kit public surface;
. zero-boundary review, complete Migration Guide coverage, lifecycle
  integration decision, and provisional report disposition.

The recommended first Dialect implementation change is Phase 0 plus the family
evidence matrix from Phase 1, using the already implemented general SPI
annotation and canonical model.  The first production classification change to
`Dialect` waits until the surface ledger can show exactly what contract that
classification creates.

== Completion criteria

This plan is complete when every completion criterion in
`design/dialect-extension-specification.adoc` is satisfied, all required
provider tests are active, the defined Dialect provider boundary has zero
validation errors, the Migration Guide coverage index has no missing anchors,

uses the same canonical SPI model as validation and compatibility checking.
Whether general validation joins the normal build lifecycle remains the
separate post-remediation SPI decision.
