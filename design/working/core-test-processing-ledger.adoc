= Separate Core Test Annotation Processing

Status: Implementation and verification complete. Steve explicitly requested
implementation of option 1 as a second commit, after the extraction commit
`e3b8a60de4c`.

== Contract and implementation

* `generateTestSources` runs the current processor and its current core
  dependency over the original test Java sources with `-proc:only`.
* Generated Java and source-output indexes belong to
  `target/generated/sources/test-processor`.
* Processor class-output resources belong to
  `target/generated/resources/test-processor`, included in test runtime
  output and the test JAR. Source-output indexes remain with the generated
  sources, matching the previous pipeline.
* `compileTestJava` compiles original and generated Java with `-proc:none`
  and an empty processor path. Its ordinary compile classpath still includes
  current core and retains Gradle's ABI-sensitive normalization.
* Generation is nonincremental so changed/deleted inputs rebuild the complete
  generated tree rather than retaining obsolete metamodels or indexes.
  This also means a test-source edit reruns processing over the whole suite;
  optimizing that path is outside this initial implementation.
* Build-cache reuse is disabled for this generation task. A real enum index
  named `entity/index/._78729` (for `PostalArea._78729`) matches Gradle's
  metadata-file exclusions. Inspection of the cached output archive confirmed
  it was omitted, while ordinary hidden enum indexes were included. A cache
  restore therefore lost one of the 10,138 outputs. Normal up-to-date checks
  remain enabled; compiler outputs are not cached through this task.
* The generated-source path is registered without task provenance because
  Spotless inspects all SourceSets, and a dependency through its source
  collection would cycle back through main compilation. The test compiler
  explicitly depends on generation. Generated files remain excluded from
  formatting by the existing `target/**/*.java` exclusion.

== Why the processor path matters after extraction

Core is both a compile dependency of the tests and a transitive runtime
dependency of the processor. Gradle 9.9.1's
`CompileOptions.getAnnotationProcessorPath()` is annotated `@Classpath`,
which includes implementation changes, whereas `@CompileClasspath` ignores
body-only changes. A core JAR change therefore invalidated the former
combined compile task through its processor path even when core's ABI was
unchanged. This is legitimate: the processor executes core code, including
HQL semantic validation.

The separate generation task must still rerun in that case. The acceptance
condition is that unchanged generation results no longer force recompiling
the test suite. This does not claim to eliminate processing or all other
upstream compilation work (for example, processing in `hibernate-testing`).
