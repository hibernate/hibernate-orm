[[best-practices]]
== Performance Tuning and Best Practices

Tune a representative operation against its required results and consistency guarantees.
A change that helps one workload can add cost to another, so use measurements to choose among
Hibernate's mapping, fetching, and execution options.

:example-dir-best-practices: {core-project-dir}/src/test/java/org/hibernate/orm/test/bestpractices

[[best-practices-measurement]]
=== Measure and diagnose

. Define the operation, required results, transaction semantics, and latency or throughput target.
  Use representative data sizes, parameter distributions, and concurrency.
. Establish a baseline, separating setup and warmup from the work being measured.
. Observe application latency, generated SQL, database work and rows transferred,
  connection occupancy, and application allocation or retained state as appropriate.
. Identify the likely bottleneck, change one relevant choice, and repeat under comparable conditions.
. Verify equivalent results and semantics, and retain useful regression checks.

Use database execution plans to inspect the actual predicates, joins, cardinality estimates,
and index use. An index can improve relevant reads while increasing write and storage costs.
Hibernate statistics, JDBC instrumentation, database metrics, and connection-pool metrics
provide different observations; no single source supplies all of them.
Fewer statements alone do not establish lower latency, fewer transferred rows, or lower memory use.

Control persistence-context reuse and cache state when comparing alternatives.
Distinguish cold and warmed measurements, and keep database contents and concurrency comparable.
Statistics aggregate activity across the factory; resetting them does not clear persistence
contexts or caches. Avoid resetting a shared factory while other work is using it.
See <<statistics-general>> and <<statistics-measurement-example>> for counter scope and comparisons.

[[best-practices-worked-investigation]]
==== Worked investigation: a book-list operation

Suppose a book-list operation becomes slower as its result grows. It returns book titles and
author names in book-id order. Start by defining its latency or throughput target, required
transaction semantics, representative data and parameter distributions, and expected concurrency.
Measure the complete operation, including accessing author names, constructing the result,
and completing the transaction. Timing only the initial query can miss work done afterwards.

The following small reproduction demonstrates how to investigate its loading behavior.
It does not reproduce a measured production latency problem: use application measurements
under representative conditions to establish whether a change helps the real workload.

===== Establish a baseline

The fixture contains three books, each referencing a distinct author through a lazy,
nonoptional `@ManyToOne`. The model uses assigned identifiers.
Setup completes before observing either operation. Both operations use the same baseline settings:

* Second-level caching is disabled.

* Batch fetching is disabled.

===== Inspect the evidence

Enable SQL logging as described in <<best-practices-logging>> and inspect the complete operation.
For this fixture, expect one query for books followed by three queries for their authors.
This is an N+1 loading pattern: the initial query is followed by additional queries to obtain
required associated state. In other workloads, their number depends on distinct unresolved
references, persistence-context and cache reuse, and fetch configuration, rather than always
being one extra query per book.

The preparation count corroborates the expected loading pattern in this isolated fixture.
It records JDBC statement preparation attempts, not executions, network round trips, or elapsed
time; see <<statistics-jdbc>>. Combine SQL observations with application timing and database
measurements to assess whether repeated loading is contributing materially to the reported cost.

===== Follow the remaining evidence

If the operation still misses its target, choose the next investigation from the observations:

* If database execution remains costly, inspect the actual plan, predicates, joins, cardinality
  estimates, and relevant indexes. Consider write and storage costs before adding an index;
  an index does not remove an N+1 loading pattern.
* If unnecessary state is being loaded, consider a projection of the fields needed for these
  strings; see <<fetching-plan-selection>>. If the application can return a bounded portion
  of the results, consider <<jpql-pagination,pagination>> or <<query-key-pagination,key-based pagination>>.
  Returning a page changes the all-results contract and needs to fit the operation's requirements.
* If database observations do not explain the latency, investigate application processing,
  connection waits and occupancy, and concurrency. See <<database-managed-pools>> and
  <<database-connection-handling>> for connection-related guidance.

Retain the correctness and loading checks as regression tests, and use representative workload
measurements to judge whether each subsequent change improves the operation.

as described in <<batch-verification>>.

[[best-practices-mapping]]
=== Choose mappings

Choose mappings that express the domain's identity, ownership, and lifecycle requirements,
then inspect the database work for the operations the application actually performs.

[[best-practices-mapping-identifiers]]
==== Identifiers

A natural or business primary key derives from domain data; a synthetic primary key exists
for entity identity. An entity with a synthetic primary key can also expose a separate
<<naturalid,`@NaturalId`>>. Assigned identifiers are supplied by the application;
that choice is distinct from mapping a separate natural identifier. See <<identifiers>>.

For generated synthetic identifiers, consider numeric and UUID strategies in terms of key width,
generation coordination, and index locality. Their impact depends on database representation,
generation strategy, and workload; UUID generation is not necessarily random.
See <<identifiers-generators-uuid>>.

Where sequences are suitable, pooled allocation can reduce identifier-allocation round trips.
Keep the mapping's allocation size, optimizer, and database sequence increment compatible;
see <<identifiers-generators-sequence>> and <<identifiers-generators-optimizer>>.
For ordinary entity inserts, insert-generated identifiers, including `IDENTITY`, prevent JDBC
batching for the affected inserts. This does not disable batching for every statement or
processing API. See <<identifiers-generators-identity>> and <<batch-jdbcbatch>>.

The `TABLE` generator coordinates allocation using a table, with locking and additional
allocation work. Pooling can amortize that work, but does not make it equivalent to a native
sequence. Evaluate it against the available alternatives; see <<identifiers-generators-table>>.

[[best-practices-mapping-associations]]
==== Associations and collections

A `@ManyToOne` or owning `@OneToOne` maps a foreign-key reference directly.
An inverse collection can provide useful navigation, but is not required for every foreign-key
relationship: a filtered or paginated entity query might better fit a large collection.
Inverse `@OneToOne` loading depends on the mapping and enhancement; see <<fetching-association-constraints>>.
A shared-primary-key association using `@MapsId` is useful when that identifier design fits
the domain; see <<identifiers-derived-mapsid,derived identifier mapping with `@MapsId`>>.

`@ElementCollection` maps collections of basic or embeddable values, rather than associations
to independently persistent entities; see <<collections-elemental>>.
Bidirectional `@ManyToMany` mappings have owning and inverse sides.
A <<associations-many-to-many-bidirectional-with-link-entity,link entity>> is useful when the
relationship needs attributes, an independent lifecycle, or more explicit mutation control.
It is not necessary for every many-to-many relationship.

Collection costs depend on where the relationship is stored, which side controls updates,
and how individual rows can be identified. Consider collection size, ordering/index maintenance,
nullable component state, and the actual add, remove, and reorder operations.
Changing from a bag to a set or making a relationship bidirectional does not guarantee cheaper mutations.
For example, the <<collections-unidirectional-bag,unidirectional bag>> example recreates its
link-table entries when an element is removed. Inspect the owning mapping and mutation examples
in <<collections-semantics>> and <<associations-one-to-many-bidirectional>> instead of ranking
all sets, lists, and bags alike.

[[best-practices-inheritance]]
==== Inheritance

Choose an inheritance strategy using the expected concrete-type and polymorphic operations,
schema constraints, and read/write mix. Statement count alone does not capture the cost.

[cols="1,3,3",options="header"]
|===
|Strategy |Schema and constraints |Work to investigate
|<<entity-inheritance-single-table,`SINGLE_TABLE`>>
|One hierarchy table. Common required columns can use `NOT NULL`; subtype-dependent requirements
can use discriminator-aware `CHECK` constraints or another suitable database mechanism.
|Polymorphic access avoids hierarchy joins or unions, but row width and subtype-specific nullable columns still matter.
|<<entity-inheritance-joined-table,`JOINED`>>
|Separate subtype tables can express subtype constraints.
|Polymorphic loading may require several joins. A to-one reference to the root is not automatically cheap;
concrete-type resolution can also add work. See <<concrete-proxy>>.
|<<entity-inheritance-table-per-class,`TABLE_PER_CLASS`>>
|Concrete types have their own tables, including inherited state.
|Concrete-type access differs from polymorphic access, which commonly requires unions across subtype tables.
|===

[[best-practices-fetching]]
=== Choose fetch plans and query shapes

Request the state needed by the operation and measure both SQL statements and rows transferred.
Managed entities and scalar or DTO projections can both be useful for read-only work; choose
according to the required state and lifecycle semantics. See <<fetching-plan-selection>>.

Use bounded result sets where the operation permits them. See <<jpql-pagination>> and
<<query-key-pagination>> for pagination, and <<hql-query-plan-cache>> for query-plan reuse.
Query-plan caching and caching query results solve different problems.
Read-only entity options can reduce dirty-checking work, but do not remove all retained state
or prevent every database write; see <<hql-read-only-entities>> and <<pc-read-only>>.

[[best-practices-fetching-associations]]
==== Fetching associations

Prefer lazy association defaults and use operation-specific plans for required state.
See <<fetching-basics>> for timing versus method, <<fetching-mapping-defaults>> for defaults and overrides,
and <<fetching-query-limitations>> for row multiplication and collection-fetch pagination.

Load the state needed outside the persistence context before detaching it or closing the context.
See <<fetching-initialization>> for initialization checks and explicit loading, and <<pc-detach>> for detachment.

[[best-practices-workloads]]
=== Process larger workloads

Select a processing model according to the required managed-state, callback, cascade, and
transaction semantics; see <<batch-processing-models>>.
Bound persistence-context growth during managed processing with appropriate flush/clear intervals;
see <<batch-session-batch-insert>>. Clearing managed state does not itself end a transaction or
release its connection. Long transactions and connection occupancy need separate consideration;
see <<transactions>> and <<database-connection-handling>>.

Close streams, scrollable results, and other owned resources promptly; see <<jpql-api-stream>>
and <<hql-api-scroll>>. Splitting work into transaction chunks changes atomicity and recovery requirements.
<<batch-stateless,Stateless processing>> and <<query-mutations,bulk mutations>> have different
lifecycle and persistence-context semantics from managed entity processing; evaluate those
requirements before choosing them.

[[best-practices-jdbc-batching]]
==== JDBC batching

JDBC batching groups compatible statement executions and can reduce database round trips.
Its effectiveness depends on mappings, driver behavior, statement compatibility, and the workload.
See <<batch-jdbcbatch>> for configuration and eligibility, and <<flushing-settings>> for dependency planning.

Choose JDBC batch size, flush/clear interval, and transaction chunk size independently.
Measure batch additions and executions as well as statement and row counts; SQL logging alone does not establish that batching occurred.
See <<batch-verification>> for a controlled measurement approach.

[[best-practices-caching]]
=== Evaluate caching

The persistence context maintains managed identity and state; it does not establish the database's isolation level.
Its lifetime can span transactions. See <<pc-fundamentals>> and <<transactions>> for context and transaction boundaries.

A second-level cache can reduce database work when state is reused across contexts.
Its value depends on hit rates, mutation frequency, entry size, and consistency costs; caching is not a mandatory next step after database tuning.
See <<caching-scopes>> for the cache scopes and <<caching-mappings>> for eligibility and concurrency strategies.

Choose a strategy compatible with the application's consistency requirements and the cache provider's capabilities.
A cache strategy does not replace database isolation or optimistic locking, and stronger coordination can have a throughput cost.
Distributed cache topology and transactional integration depend on the provider.

Direct JDBC, external writers, and trigger side effects need deliberate invalidation or eviction.
See <<caching-invalidation>> for those boundaries, and measure representative workloads with <<caching-statistics>>.

[[best-practices-schema]]
=== Manage schema evolution

Hibernate can execute supported schema creation and alteration commands against a database or export them as scripts.
See <<schema-generation>> for the available operations and <<schema-generation-alteration-scripts>> for alteration scripts.

For evolution across application versions, consider dedicated schema versioning tools such as Flyway or Liquibase.
Keep reviewed migration scripts with the application source and test them against a representative existing schema and data.
Versioned migrations record the intended evolution, including data transformations that cannot be inferred from mappings.
