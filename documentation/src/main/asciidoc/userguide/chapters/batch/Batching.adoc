[[batch]]
== Batching
:example-dir-doc-batch: {core-project-dir}/src/test/java/org/hibernate/orm/test/batch
:example-dir-bulkid: {core-project-dir}/src/test/java/org/hibernate/orm/test/bulkid
:batch-extras-dir: extras

Processing many rows involves separate choices about persistence semantics, JDBC execution,
persistence-context memory, and transaction boundaries. Choose a processing model first,
then measure the batching and resource-management controls appropriate to it.

[[batch-processing-models]]
=== Choosing a processing model

[cols="1,3,2",options="header"]
|===
|Model |Behavior |Typical use
|Stateful entity operations |Managed identity, dirty checking, cascades, and lifecycle callbacks
  |Work requiring ordinary entity lifecycle semantics
|Stateless commands |Explicit operations on detached objects without a persistent first-level cache
  |Processing bounded groups with explicit inserts, updates, or deletes
|Bulk mutations |Set-based changes without loading each matching entity into the application
  |Applying a common change or predicate-based deletion to many entities
|===

_JDBC batching_ groups compatible SQL statement executions. It is an optimization of entity operations,
not the same operation as an HQL bulk update or delete.
It is also distinct from <<fetching,association batch fetching>>, multiple-id loading,
and JDBC _fetch size_, which concerns retrieving result rows.

Three independent controls matter for a stateful workload:

* JDBC batch size: how many compatible parameter sets are accumulated before executing a batch.
* Flush/clear interval: how much managed state is retained before writing pending changes and detaching objects.
* Transaction chunk size: how much work shares a commit or rollback boundary.

These values need not be equal. A large JDBC batch does not limit persistence-context memory,
and clearing the context does not commit a transaction.

[[batch-jdbcbatch]]
=== JDBC batching configuration and eligibility

A JDBC batch applies several sets of bound values to a compatible `PreparedStatement`.
It can reduce driver and network overhead, but the number of network round trips depends on the driver
and database. A batch does not guarantee one server call.

// suppress inspection "AsciiDocLinkResolve"
The setting <<settings-hibernate.jdbc.batch_size,`hibernate.jdbc.batch_size`>> supplies the stateful-session default.
Its default is zero; zero or a negative value disables batching. A size greater than one permits grouping
multiple executions. The configured size is an upper bound, not a promise that every batch is full.
Choose a starting size and measure representative workloads rather than assuming a universally optimal value.

The examples below use a small factory batch size of two to make full and partial groups easy to verify:

[source,xml]
----
<property name="hibernate.jdbc.batch_size" value="2"/>
----

A `Session` can override this default. `setJdbcBatchSize(null)` removes its override.
When changing the size temporarily, flush the intended work while the override still applies,

==== Transaction chunks

Flushing does not commit. Clearing does not release transaction locks, return the transaction's connection,
or reduce its rollback scope. Long transactions can hold locks and occupy connections for substantial periods.

If the application permits partial completion, process bounded groups in separate transactions.
This changes atomicity: a later failure does not undo earlier committed groups.
Define how the application records progress and resumes or handles failed groups before choosing this approach.
Do not confuse a flush/clear interval with a commit interval.

[[batch-stateless]]
=== Stateless processing and explicit groups

Jakarta Persistence 4 defines `EntityAgent` for explicit commands on detached entities.
Hibernate implements it through `StatelessSession`.
There is no persistent first-level cache, automatic dirty checking, or stateful transactional write-behind.
Repeated loads of the same identifier need not return the same object, so account for data aliasing.

Operations do not cascade to associated entities. Load required associations using a fetching plan
or an explicit `fetch()` operation; see <<fetching>>.
Current stateless operations invoke applicable lifecycle callbacks and Hibernate event listeners.
They do not use the stateful action queue, and are not identical to stateful entity operations.
See link:{doc-javadoc-url}org/hibernate/StatelessSession.html[`StatelessSession`] for operation-specific contracts.

[[batch-bulk-hql]]
=== Bulk mutation execution and context consequences

Bulk HQL and Criteria mutations change matching entities without loading and processing each entity instance.
They differ from a loop of `persist()`, managed updates, or `remove()` calls:
ordinary per-entity dirty checking, lifecycle callbacks, and cascades are not applied to every matching instance.
Database-side cascades or triggers are separate mechanisms.

Bulk mutations require an appropriate transaction and do not synchronize existing managed objects.
Flush first when pending entity changes must be included in the mutation's input.
Then deliberately clear, refresh, or use another context to obtain the resulting state.
Do not clear pending edits without preserving them.
See <<pc>> and <<caching>> for context state and cache invalidation.

[[batch-bulk-hql-strategies]]
=== Multi-table mutation and insert strategies

A logical operation on an entity mapped to several tables may require multiple SQL statements.
For update/delete operations, Hibernate may preserve matching identifiers before changing any affected tables,
so that later statements still target the originally selected entities.
Insert staging stores the values needed to populate the target tables and has different requirements.

The dialect selects fallback families through
link:{doc-javadoc-url}org/hibernate/dialect/Dialect.html#getMultiTableMutationSupport()[`Dialect.getMultiTableMutationSupport()`].
Its `MultiTableMutationSupport` profile selects update/delete and insert strategies independently.
Configured global or entity-specific strategies take precedence over the fallback.

// suppress inspection "AsciiDocLinkResolve"
The <<settings-hibernate.query.mutation_strategy,`hibernate.query.mutation_strategy`>> setting selects an update/delete strategy;
// suppress inspection "AsciiDocLinkResolve"
<<settings-hibernate.query.insert_strategy,`hibernate.query.insert_strategy`>> selects an insert strategy.
Defaults depend on the dialect and its capabilities, not just the database product name.

[cols="1,3",options="header"]
|===
|Family |Approach
|CTE |Uses data-modifying common-table expressions when supported by the dialect.
|Local temporary table |Uses staging local to a database connection, with dialect-specific creation/use actions.
|Global temporary table |Uses a globally defined table whose contents have database-specific temporary scope.
|Persistent table |Uses an ordinary auxiliary table and separates concurrent session work using a session discriminator.
|===

==== Auxiliary tables and database permissions

Identifier tables conventionally use an `HT_` prefix; insert staging tables conventionally use `HTE_`.
Their exact names and schemas depend on mapping, naming adjustments, strategy, and dialect.
Insert staging may require generated-key, row-number, or session-discriminator columns in addition to mapped attributes.
Creating one generic `HTE_<root>` table does not provision every update/delete and insert strategy.

Global temporary and persistent table implementations normally prepare their auxiliary tables during factory
initialization. Their `create_tables` settings default to `true`, and `drop_tables` defaults to `false`:

* `hibernate.query.mutation_strategy.global_temporary.create_tables`
* `hibernate.query.mutation_strategy.global_temporary.drop_tables`
* `hibernate.query.mutation_strategy.persistent.create_tables`
* `hibernate.query.mutation_strategy.persistent.drop_tables`

The corresponding insert strategies share these setting names in the current implementation.
Local temporary-table creation follows the dialect's before-use action during execution.
`hibernate.query.mutation_strategy.local_temporary.drop_tables`, defaulting to `false`, controls forced
post-use dropping; the dialect's own after-use action also matters.
Disabling global/persistent startup creation does not disable local execution-time creation.

For restricted database permissions, arrange for the exact auxiliary tables required by the selected strategy
to be provisioned by an authorized schema-management process, then configure Hibernate's creation/drop behavior
accordingly. Inspect the strategy's actual dialect-specific DDL rather than inferring columns from a prefix.
See <<schema-generation>> for ordinary schema tooling; do not assume its regular create/export scripts
include every mutation strategy's auxiliary table.

[[batch-bulk-hql-strategies-non-temporary-table]]
==== Inline update/delete alternative

`InlineMutationStrategy` selects matching identifiers into application memory and uses those values
in subsequent update/delete predicates, avoiding identifier staging tables for those mutations:

[source,xml]
----
<property name="hibernate.query.mutation_strategy"
          value="org.hibernate.query.sqm.mutation.internal.inline.InlineMutationStrategy"/>
----

This can increase memory consumption and SQL size and is subject to database statement-size limits.
Evaluate it for the expected affected set. It is an update/delete strategy, not an equivalent inline insert strategy;
selecting it does not eliminate tables needed by an independently configured insert strategy.

[[batch-verification]]
=== Measuring and verifying batching

SQL logging and affected-row counts alone do not prove JDBC batch execution.
Several statements may be added to one batch while still producing a log entry for each set of parameters.
Inspect batch additions, executions, and how fully batches are populated using suitable JDBC instrumentation.
Actual network behavior still depends on the driver.

Use <<statistics>> and SQL inspection as complementary evidence, and verify the final persisted values and versions.
Keep setup and cleanup outside the measured interval. Use known initial cache and context state so that reads
or cached data do not obscure the operations being measured.
For this chapter's controlled five-row insert/update examples, batch size two and flush interval two produce
five JDBC batch additions and three batch executions, including the final one-row group.
Those counts describe the fixture, not every entity mapping, driver, or workload.
