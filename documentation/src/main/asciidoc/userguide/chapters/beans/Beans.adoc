[[beans]]
== Managed Beans

:beans-guide-example: {core-project-dir}/src/test/java/org/hibernate/orm/test/cdi/guide/ManagedBeansGuideTests.java
:beans-guide-resources: {core-project-dir}/src/test/resources/beans-guide

Hibernate can obtain extension instances through CDI or another bean container, allowing
those instances to receive dependency injection and lifecycle callbacks. This support
applies to specific extension registration and acquisition paths; configuring a container
does not automatically register every extension implementation or make entities CDI beans.

The {doc-javadoc-url}org/hibernate/resource/beans/spi/ManagedBeanRegistry.html[`ManagedBeanRegistry`]
service acquires bean handles. A handle exposes the instance when it is needed.
The {doc-javadoc-url}org/hibernate/resource/beans/container/spi/BeanContainer.html[`BeanContainer`]
SPI connects the registry to an external container. When no external container is selected,
Hibernate uses fallback construction.

Hibernate's managed-bean abstraction is broader than a CDI contextual bean.
Injection, instance reuse, and destruction depend on the acquisition policy;
see <<beans-lifecycle>>.

`hibernate.cdi.extensions` defaults to `false`. It enables supported additional extension
lookups, not automatic discovery and registration of arbitrary implementations.
Despite its name, the flag also gates these additional acquisition paths when using a
custom non-CDI container. Explicit settings and each extension's default selection rules
still apply; for example, container lookup does not override an explicitly supplied tenant resolver.

[[beans-container-selection]]
=== Container selection and configuration

Hibernate selects its bean container in this order:

. Use an explicit `hibernate.resource.beans.container` value, if supplied.
. Otherwise, discover `BeanContainer` service implementations. One implementation is
  selected; multiple implementations cause an error unless a container is selected explicitly.
. If no service is found, use the CDI manager supplied through `jakarta.persistence.bean.manager`.
. If no external container is available, use Hibernate's fallback container and instance producer.

The settings are:

[cols="2,2,3",options="header"]
|===
|Setting |Default |Value and purpose
|{doc-javadoc-url}org/hibernate/cfg/ManagedBeanSettings.html#JAKARTA_CDI_BEAN_MANAGER[`jakarta.persistence.bean.manager`]
|Unset
|A `BeanManager` instance, or an <<beans-cdi-extended,`ExtendedBeanManager`>>. This is an object reference, not a class name.
|{doc-javadoc-url}org/hibernate/cfg/ManagedBeanSettings.html#BEAN_CONTAINER[`hibernate.resource.beans.container`]
|Unset
|A `BeanContainer` instance, implementation `Class`, or implementation class name. Class-based construction requires an accessible public no-argument constructor.
|{doc-javadoc-url}org/hibernate/cfg/ManagedBeanSettings.html#DELAY_CDI_ACCESS[`hibernate.delay_cdi_access`]
|`false`
|Delay ordinary CDI bean initialization until needed; see <<beans-cdi-delayed>>.
|{doc-javadoc-url}org/hibernate/cfg/ManagedBeanSettings.html#ALLOW_EXTENSIONS_IN_CDI[`hibernate.cdi.extensions`]
|`false`
|Allow the additional extension lookups listed in <<beans-manageable>>.
|===

Having CDI API classes on the classpath does not start CDI or automatically locate a
`BeanManager`. When no explicit or discovered `BeanContainer` takes precedence, supplying
a manager while CDI is unavailable to Hibernate's class loader causes bootstrap to fail.
The deprecated `javax.persistence.bean.manager` name remains a compatibility
alias; use the Jakarta name in new configuration.

[[beans-cdi]]
=== CDI integration

Hibernate adapts a supplied CDI `BeanManager` to its `BeanContainer` SPI.
In <<bootstrap-standardized-container,Jakarta EE bootstrap>>, the container normally
supplies the manager when CDI is enabled. For application-managed bootstrap, supply a manager
from the CDI container owned by the application or its environment; Hibernate does not create
that CDI container.

[[beans-cdi-access-modes]]
==== CDI access modes

[cols="1,2,3",options="header"]
|===
|Mode |Selection |When ordinary bean initialization occurs
|<<beans-cdi-default,Immediate>>
|A `BeanManager`, with `hibernate.delay_cdi_access=false`.
|During acquisition, which may happen during bootstrap.
|<<beans-cdi-delayed,Delayed>>
|A `BeanManager`, with `hibernate.delay_cdi_access=true`.
|When the instance is first needed, possibly still during bootstrap.
|<<beans-cdi-extended,Extended>>
|An `ExtendedBeanManager` supplied instead of a direct manager.
|Registered references can be initialized when the integration signals readiness; later acquisitions can initialize on access.
|===

Access mode and bootstrap-safe acquisition are separate choices. A bootstrap-safe handle
can be acquired without immediately obtaining its instance, but injection requires CDI to be
usable when that instance is needed. Not every extension uses bootstrap-safe acquisition.
See <<events-interceptor-cdi-readiness>> for the interceptor-specific behavior.

[[beans-cdi-default]]
==== Immediate access

With the default mode, ordinary acquisition initializes beans immediately. This often occurs
during bootstrap, but does not mean every eligible bean is instantiated when the factory is built.
Extensions using bootstrap-safe handles, including class-registered interceptors, can defer
instance acquisition. If CDI and persistence bootstrap depend on each other, consider delayed
access or an integration supplying extended access.

[[beans-cdi-delayed]]
==== Delayed access

Set `hibernate.delay_cdi_access=true` to defer ordinary CDI bean initialization until needed.
The manager must be ready at that point. An extension can need its instance during metadata
building, so delaying access does not guarantee that CDI will only be accessed after bootstrap.
Configuration problems may consequently be detected later than with immediate access.

This mode does not receive a readiness notification. When the integration can provide
reliable lifecycle callbacks, prefer <<beans-cdi-extended,extended access>>.

[[beans-cdi-extended]]
==== Extended access

An integration may supply
{doc-javadoc-url}org/hibernate/resource/beans/container/spi/ExtendedBeanManager.html[`ExtendedBeanManager`]
as `jakarta.persistence.bean.manager`. This selects extended access regardless of the delayed flag.

Hibernate registers a `LifecycleListener` through `registerLifecycleListener()`.
The integration calls `beanManagerInitialized()` with the usable manager and
`beforeBeanManagerDestroyed()` before destroying it. The initialization callback can
initialize registered bean references; the destruction callback releases Hibernate's tracked references.
This is a lifecycle callback protocol implemented by the integration, not a CDI container
that Hibernate starts or a standard `Future`.

Do not depend on using instances before CDI is ready. Some early acquisition paths can fall
back to direct construction, while others can fail; neither outcome guarantees injection.
The extension's acquisition and fallback policy determines the result.

[[beans-lifecycle]]
=== Lifetimes, caching, and fallback

Bean acquisition, reference caching, and instance lifetime are independent decisions.
A `ManagedBean` handle can exist before its instance is initialized. The container and
acquisition policy determine instance reuse and destruction.

[[beans-lifecycle-creation]]
==== Independent creation and CDI scopes

The built-in registry requests JPA-compliant creation: Hibernate controls independent
instance lifetimes while CDI supplies injection and lifecycle callbacks. The requested
class need not be returned as its existing CDI contextual instance. In particular,
`@ApplicationScoped` or `@Singleton` on that class does not guarantee that Hibernate uses
the application's existing contextual instance. Injected dependencies still follow their
own CDI resolution and scope rules.

Integrators calling `BeanContainer` directly can request container-managed creation by
returning `false` from `LifecycleOptions.useJpaCompliantCreation()`. Returning `true`
requests independent, Hibernate-managed lifetimes. That policy and the external container's
scope semantics are distinct from reference caching.

[[beans-lifecycle-caching]]
==== Caching and release

For integrations using `ManagedBeanRegistry`,
{doc-javadoc-url}org/hibernate/resource/beans/spi/BeanInstanceCaching.html[`BeanInstanceCaching`]
controls handle reuse:

* `ALLOW` permits a shared cached reference. Release it only after all its users have finished.
* `DISALLOW` bypasses Hibernate's reference cache. Release the returned handle with
  `ManagedBeanRegistry.releaseBean()` when finished. This does not override a custom
  container's contextual scope or guarantee a different underlying contextual object.

Registry/container shutdown normally releases outstanding owned references. Some consumers
release them earlier: automatically acquired <<events-interceptor-cdi,per-session interceptors>>
are released at their session-related boundary. Transaction completion is not a general
bean-release boundary, and registry shutdown need not coincide with closing one factory
when the service registry has a different owner.

A custom adapter receives `stop()` from Hibernate's bean infrastructure. It should release
the references it owns without assuming it owns the entire external container. Supplying
a `BeanManager` does not transfer ownership of the CDI container to Hibernate.

[[beans-fallback]]
==== Fallback construction

Without an external container, Hibernate's default producer normally invokes a no-argument
constructor. It does not provide CDI injection or CDI lifecycle callbacks. An extension
can supply a specialized fallback producer instead.

Some CDI resolution or creation failures also use the fallback producer. Do not assume
that successful bootstrap proves injection occurred, or that every CDI problem is converted
into fallback construction. Failures before the manager is ready can follow different paths.
Optional service lookups also retain their own absence/default behavior; the fallback registry
does not automatically supply every optional Hibernate service.
