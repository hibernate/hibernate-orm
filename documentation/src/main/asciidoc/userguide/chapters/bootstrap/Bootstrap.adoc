[[bootstrap]]
== Bootstrap

:bootstrap-guide-examples: {core-project-dir}/src/test/java/org/hibernate/orm/test/bootstrap/guide
:bootstrap-guide-resources: {core-project-dir}/src/test/resources/org/hibernate/orm/test/bootstrap/guide
:extrasdir: extras

Bootstrapping creates the factory used to access an application's persistent model.
When Hibernate is the persistence provider, the factory implements both `EntityManagerFactory` and `SessionFactory`.
Creating a factory is expensive. Usually, an application reuses one factory for each persistence unit until shutdown.

For individual configuration properties, see <<settings>>.
See <<database>> for datasource, JDBC connection, and pooling configuration.
See <<schema-generation>> for creating or validating schemas and exporting schema creation or supported alteration commands to scripts.
Build-time enhancement, metamodel generation, and other build services are covered in <<tooling>>.

[[bootstrap-standardized]]
=== Choosing a bootstrap approach

[cols="2,3,3",options="header"]
|===
|Entry point |Configuration |Ownership and portability
|<<bootstrap-standardized-container,JPA EE bootstrap>>
|A deployed persistence unit, normally declared in `META-INF/persistence.xml`.
|The container creates and owns the factory. Deployment details depend on the container.
|<<bootstrap-hibernate-persistence-configuration,HibernatePersistenceConfiguration>>
|A programmatic persistence unit with Hibernate-specific conveniences.
|The application owns the factory. Configuration code depends on Hibernate.
|<<bootstrap-persistence-configuration,PersistenceConfiguration>>
|A programmatic persistence unit using the standard API.
|The application owns the factory. Standard options are portable across compatible Jakarta Persistence providers.
|<<bootstrap-jpa-se-xml,JPA SE bootstrap with persistence.xml>>
|A named XML persistence unit, optionally overridden by a settings map.
|The application owns the factory. Standard configuration is portable across Jakarta Persistence providers.
|<<bootstrap-native,Other Hibernate bootstrap APIs>>
|`Configuration` or the metadata-builder pipeline.
|The application or integration owns the factory. These APIs are Hibernate-specific.
|===

Bootstrap mechanism, entity-manager ownership, and transaction management are separate concerns.
For example, an EE application can create an application-managed entity manager from a container-owned factory.
A programmatically configured persistence unit remains an SE-style unit even when the application runs in an EE environment;
it does not become a container-managed persistence unit.

[[bootstrap-settings-merging]]
==== How Hibernate merges settings

When Hibernate builds a factory through a JPA bootstrap entry point, it combines environment defaults,
persistence-unit properties, and any bootstrap overrides.
For an ordinary property supplied under the same key, the following sources are applied in order;
a later source replaces an earlier value:

[cols="1,3",options="header"]
|===
|Order |Source
|1 |The classpath resource `hibernate.properties`, if present.
|2 |JVM system properties, which override values from `hibernate.properties`.
|3 |Persistence-unit properties: those supplied by the EE container, declared in `persistence.xml`,
or collected in a `PersistenceConfiguration` or `HibernatePersistenceConfiguration`.
|4 |Properties from a Hibernate XML configuration resource explicitly selected using `hibernate.cfg_xml_file`, if present.
|5 |Bootstrap overrides: the map passed to `Persistence.createEntityManagerFactory(unitName, overrides)`
or supplied by the EE container to the provider.
|===

Environment defaults and the optional Hibernate XML configuration resource are Hibernate-specific sources;
Jakarta Persistence defines the persistence-unit configuration and bootstrap override contract.
Hibernate captures the environment defaults when its `Environment` class initializes.
Changing a JVM system property afterward does not update that captured baseline.
These defaults also apply when the application uses the standard Jakarta Persistence bootstrap APIs.

Programmatic configuration collects properties before bootstrap.
Each `property(name, value)` call replaces the previous value for that key;
`properties(map)` merges the supplied entries, replacing matching keys while retaining other entries.
Thus, the last configuration call for a key wins within the programmatic unit.
If that unit selects `hibernate.cfg_xml_file`, properties from the selected resource are applied afterward.
Naming a programmatic unit does not import a same-named unit from `persistence.xml`.

Connection settings need additional resolution because multiple keys can describe the same connection option.
For example, `hibernate.connection.url` and `jakarta.persistence.jdbc.url` are aliases rather than independent settings.
Within the merged properties, Hibernate prefers the Hibernate JDBC URL key when both are present,
even if the Jakarta key came from a later source.
A JDBC URL supplied in the bootstrap override map takes precedence over a URL in the persistence-unit properties,
including one supplied under another alias.
Hibernate also resolves datasource and JDBC connection settings together:
a datasource supplied in the override map takes precedence over a JDBC URL in that map,
and Hibernate removes conflicting connection settings after selecting the connection source.
Transaction type, validation mode, shared-cache mode, and schema-management options also have
specific rules for combining typed persistence-unit options and properties.
The table therefore describes ordinary same-key property merging, not a universal ordering of every configuration option.

Set application properties explicitly and use one spelling for each connection option.
See <<database-connectionprovider>> for connection sources, <<schema-generation>> for schema management,
and <<settings>> for individual configuration properties.

==== Registration and discovery

Explicit managed-class and mapping-file registration makes the configured model clear and avoids reliance on scanning.
`managedClass()` and `mappingFile()` are inherited standard methods; Hibernate adds conveniences such as `managedClasses()` and `mappingFiles()`.
For package- and module-level mapping metadata, the current standard API also provides `managedPackageDescriptor()` and `managedModuleDescriptor()`.
These metadata registrations are distinct from discovering entity classes.

To enable Hibernate scanning, add the `hibernate-scan-jandex` module or another implementation of the `ScanningProvider` service.
Hibernate scans locations identified by the following URL sources:

* An explicit persistence-unit root URL supplied to `new HibernatePersistenceConfiguration("CRM", rootUrl)`.
* A persistence-unit root URL inferred from a class reference supplied to `new HibernatePersistenceConfiguration("CRM", Document.class)`.
Hibernate uses the class's code-source location as the root URL.
* Explicit JAR URLs supplied using `jarFileUrl(url)` or `jarFileUrls(urls)`.
* JAR URLs inferred from class references supplied using `jarFileUrl(ModelClass.class)`
or `jarFileUrls(FirstModelClass.class, SecondModelClass.class)`.
Hibernate uses each class's code-source location as a JAR URL.

Class references used to identify scanning locations do not explicitly register those classes as managed classes.
The constructor taking only a name does not implicitly scan the application's whole classpath.


==== Configuration sources

Hibernate starts with environment defaults and applies the programmatic properties over them.
If `hibernate.cfg_xml_file` selects a Hibernate XML configuration resource, Hibernate then applies that resource's properties.
See <<bootstrap-settings-merging>> for precedence and connection-setting resolution.

Use this API when Hibernate-specific configuration conveniences are useful.
For portable bootstrap code, use <<bootstrap-persistence-configuration,PersistenceConfiguration>> instead.

=== Programmatic bootstrap with PersistenceConfiguration

Jakarta Persistence 3.2 introduced `jakarta.persistence.PersistenceConfiguration` as an alternative to defining a persistence unit in XML.
It provides methods for registering managed classes and mapping files, selecting a provider and transaction type,
and configuring standard options. Connection properties and vendor-specific settings may still be supplied using `property()`.

The example explicitly selects Hibernate as the provider but otherwise uses standard configuration methods and properties.
Omit `provider()` when provider discovery can select the intended provider unambiguously.
`managedClass()` identifies the mapped class; use `mappingFile()` for XML mapping resources.
Newer Jakarta Persistence versions add configuration methods, including package- and module-descriptor registration;
use only options supported by the API version deployed with the application.

`configuration.createEntityManagerFactory()` delegates to `Persistence.createEntityManagerFactory(configuration)`.
Both forms define the unit from the supplied configuration rather than looking up a same-named XML descriptor.
The default transaction type is `RESOURCE_LOCAL`; the example states it explicitly.
Other standard options include datasource names, validation mode, shared-cache mode, and schema-management actions.
When Hibernate is the provider, the settings-merging rules in <<bootstrap-settings-merging>> also apply.

This is application bootstrap even when invoked within an EE environment.
A CDI producer and disposer can expose an application-created factory and arrange its cleanup, but this does not give it the semantics of an injected container-managed persistence unit.

When Hibernate-specific access is needed after standard bootstrap, obtain the factory using:

[source,java]
----
SessionFactory sessionFactory = factory.unwrap(SessionFactory.class);
----

The unwrapped reference represents the same factory; it does not require a separate shutdown lifecycle.
See <<pc-unwrap>> for unwrapping persistence objects.

[[bootstrap-standardized-integrations]]
=== Bootstrap integrations

Service discovery lets extensions participate in factory bootstrap without making application code reproduce Hibernate's metadata pipeline.
Register a service implementation in `META-INF/services/<contract-class-name>` where the contract supports service loading.
The supported callback, lifecycle, and bootstrap path depend on the extension contract; not every native builder hook applies to every JPA bootstrap path.

[cols="1,3",options="header"]
|===
|Contract |Purpose and further reading
|`TypeContributor`
|Contributes types and descriptors. See <<basic-type-contributor>> for type contributions and <<basic-mapping-registries>> for the descriptor registries.
Service-loaded contributors run in ascending `ordinal()` order; see link:{doc-javadoc-url}org/hibernate/boot/model/TypeContributor.html[the ordering contract].
|`ServiceContributor`
|Contributes Hibernate services to the service registry. See link:{doc-javadoc-url}org/hibernate/service/spi/ServiceContributor.html[the contract documentation].
|`Integrator`
|Participates in factory initialization, for example to register listeners. See <<events-events>> and link:{doc-javadoc-url}org/hibernate/integrator/spi/Integrator.html[the current callback contract].
|===

[[example-bootstrap-event-listener-registration]]For event-listener behavior and examples, see <<events-events>>;
for interceptors, see <<events-interceptors>>. Use the current `Integrator` callbacks when registering listeners during bootstrap.
Do not assume that the factory is fully initialized inside its integration callback.

Older integrations may use `MetadataSourcesContributor` or `MetadataBuilderInitializer`, both marked for removal in Hibernate 9.0.
They are not recommended entry points for new integrations.
Consult the supported SPI contracts for additional mapping contributions rather than treating all builder callbacks as interchangeable.
