[[associations]]
=== Associations
:example-dir-association: {core-project-dir}/src/test/java/org/hibernate/orm/test/associations
:example-dir-any: {core-project-dir}/src/test/java/org/hibernate/orm/test/any
:domain-associations-extrasdir: extras/associations

Associations map relationships between entities.
The association reference is a value in the containing entity's state; the referenced entity has its own identity and lifecycle.
This distinction applies to `@ManyToOne`, `@OneToOne`, and Hibernate's `@Any` mapping, as described in <<categorization-value>>.
For a to-many association, the collection holds references to entities rather than owning the entities as embedded values.
A bidirectional association has an owning side and an inverse side identified by `mappedBy`.
The owning side determines the relationship written to the database.
Applications must keep both sides synchronized, either explicitly or using the automatic management described in <<auto-bidir-mgmt>>.

[NOTE]
====
Hibernate has historically relied on users managing both sides of bidirectional associations.  The examples in this chapter generally illustrate this manual management as it is the only portable approach, in the Jakarta Persistence sense.

However, starting in 8.0 Hibernate adds the option to automatically manage the inverse side of these bidirectional
associations.  See <<auto-bidir-mgmt>> for details.

====

[[associations-one-to-many]]
==== `@OneToMany`

The `@OneToMany` association links a parent entity with one or more child entities.
An association mapped with `@OneToMany` is bidirectional when its `mappedBy` attribute identifies the corresponding `@ManyToOne` attribute on the child entity.
The application can then navigate the relationship from either end.
Without this `mappedBy` declaration, the `@OneToMany` is unidirectional, even if the child has a separate `@ManyToOne` mapping back to the parent.

Unlike the unidirectional `@OneToMany`, the bidirectional association is much more efficient when managing the collection persistence state.
Every element removal only requires a single update (in which the foreign key column is set to `NULL`), and,
if the child entity lifecycle is bound to its owning parent so that the child cannot exist without its parent,
enable `orphanRemoval` so that dissociating the child also deletes its database row.

[[associations-one-to-one-bidirectional-lazy]]
====== Bidirectional `@OneToOne` lazy association

Even when the parent-side association is marked for lazy fetching,
Hibernate cannot honor this request since it cannot know whether the association is `null` or not.

The only way to figure out whether there is an associated record on the child side is to fetch the child association using a secondary query.
Because this can lead to N+1 query issues, it's much more efficient to use unidirectional `@OneToOne` associations with the `@MapsId` annotation in place.

For lazy fetching of the parent side of a bidirectional association, enable bytecode enhancement for lazy state initialization.

[[associations-not-found]]
==== `@NotFound`

When dealing with associations which are not enforced by a physical foreign-key, it is possible
for a non-null foreign-key value to point to a non-existent value on the associated entity's table.

[WARNING]
====
Not enforcing physical foreign-keys at the database level is highly discouraged.
====

Hibernate provides support for such models using the `@NotFound` annotation, which accepts a
`NotFoundAction` value which indicates how Hibernate should behave when such broken foreign-keys
are encountered -

EXCEPTION:: (default) Hibernate will throw an exception (`FetchNotFoundException`)
IGNORE:: the association will be treated as `null`

Both `@NotFound(IGNORE)` and `@NotFound(EXCEPTION)` cause Hibernate to assume that there is
no physical foreign-key.

`@ManyToOne` and `@OneToOne` associations annotated with `@NotFound` are always fetched eagerly even
if the `fetch` strategy is set to `FetchType.LAZY`.


[TIP]
====
If the application itself manages the referential integrity and can guarantee that there are no
broken foreign-keys, `jakarta.persistence.ForeignKey(NO_CONSTRAINT)` can be used instead.
This will force Hibernate to not export physical foreign-keys, but still behave as if there is
in terms of avoiding the downsides to `@NotFound`.
====

`@NotFound` also affects how the association is treated as "implicit joins" in HQL and Criteria.
When there is a physical foreign-key, Hibernate can safely assume that the value in the foreign-key's
key-column(s) will match the value in the target-column(s) because the database makes sure that
is the case.  However, `@NotFound` forces Hibernate to perform a physical join for implicit joins
when it might not be needed otherwise.

Using the `Person` / `City` model, consider the query `from Person p where p.city.id is null`.

Normally Hibernate would not need the join between the `Person` table and the `City` table because
a physical foreign-key would ensure that any non-null value in the `Person.cityName` column
has a matching non-null value in the `City.name` column.

However, with `@NotFound` mappings it is possible to have a broken association because there is no
physical foreign-key enforcing the relation.  As seen in <<associations-not-found-non-existing-persist-example>>,
the `Person.cityName` column for John Doe has been changed from "New York" to "Atlantis" even though
there is no `City` in the database named "Atlantis".  Hibernate is not able to trust the referring
foreign-key value ("Atlantis") has a matching target value, so it must join to the `City` table to
resolve the `city.id` value.

[[associations-any]]
==== `@Any` mapping

The `@Any` mapping defines a unidirectional to-one association whose target may belong to one of several entity types.
Each attribute value is a reference to a single entity, with the same reference-versus-entity distinction as `@ManyToOne` and `@OneToOne`.

Because the `@Any` mapping defines a polymorphic association to classes from multiple tables,
this association type requires the FK column which provides the associated parent identifier and
a discriminator which identifies the associated entity type.

[NOTE]
====
Use this form of polymorphic association only for special cases, such as audit logs or user session data.
====

This association mapping requires three pieces of information:

1. The column and mapping for the <<associations-any-discriminator,discriminator>>
2. The column and mapping for the <<associations-any-key,key>>
3. The mapping between discriminator values and entity types which may be <<associations-any-explicit-discriminator,explicit>>
<<associations-any-implicit-discriminator,implicit>> or <<associations-any-mixed-discriminator,mixed>>.

[[associations-any-discriminator]]
===== The discriminator

The discriminator is the value that indicates which entity is referred to by a row.

Its "column" can be specified with either `@Column` or `@Formula`.  The mapping type can be influenced by any of:

1. `@AnyDiscriminator` allows re-using the `DiscriminatorType` simplified mappings from Jakarta Persistence for the common cases
2. `@JavaType`
3. `@JdbcType`
4. `@JdbcTypeCode`


[[associations-any-key]]
===== The key

The key of an any-style association holds the matching key for the row

Its "column" can be specified with either `@JoinColumn` (`@JoinFormula` not supported).  The mapping
type can be influenced by any of:

1. `@AnyKeyJavaClass`
2. `@AnyKeyJavaType`
3. `@AnyKeyJdbcType`
4. `@AnyKeyJdbcTypeCode`

[[auto-bidir-mgmt]]
==== Automatic Bidirectionality Management

As mentioned earlier, Hibernate assumes that users will manually manage both sides of a bidirectional association keeping them in sync.  That approach was discussed throughout this chapter.

However, starting in 8.0 Hibernate also adds the option to automatically manage the *inverse* side of bidirectional associations.

[IMPORTANT]
====
It is important to note that users must still manage the *owning* side.  Changing just the *inverse* side will have no effect.
====

To opt in to this behavior, use

[source,properties]
----
hibernate.bidirectionality_management=true
----


Hibernate performs this management during flush preparation.
At that time, Hibernate inspects the managed persistence context, treats the *owning* side of each bidirectional association as authoritative, and applies the corresponding *inverse*-side changes for managed entities.
These changes are made before dirty checking and before SQL actions are scheduled.

In other words, enabling this feature effectively asks Hibernate to perform the inverse-side updates performed manually in the earlier examples.  For example, if a managed child entity is reassigned to a different parent by changing the owning `@ManyToOne`, Hibernate can remove the child from the old parent's initialized `@OneToMany` collection and add it to the new parent's initialized `@OneToMany` collection.
Similarly, when an owning bidirectional `@OneToOne` reference is reassigned, Hibernate updates the managed inverse reference, and when an owning `@ManyToMany` collection is changed, Hibernate updates initialized managed inverse collections.

Because these changes happen before dirty checking, they participate in normal flush processing.
That means collection dirtiness, entity dirtiness, versioning, callbacks, and second-level cache invalidation see the same kind of inverse-side changes they would have seen if application code had made those changes directly before flushing.

===== Lazy inverse collections

Automatic bidirectionality management does not initialize lazy inverse collections just to keep them synchronized in memory.
Only inverse collections which are already initialized in the persistence context are changed.

This boundary is intentional.
If an inverse collection is uninitialized, Hibernate leaves it uninitialized during flush.
When the collection is later initialized, it is loaded through the usual loading rules and reflects the database state visible to that session.

For example, changing the owning `Child.parent` association does not force initialization of `Parent.children`.
If `Parent.children` was already initialized, Hibernate updates it during flush preparation.
If it was not initialized, Hibernate leaves it alone.

===== Second-level cache considerations

The same loaded-versus-unloaded boundary is important when second-level caching is enabled.

If a cacheable inverse collection is initialized when bidirectionality management updates it, the collection is dirtied before normal flush processing.
Hibernate therefore applies the usual collection action and collection cache invalidation rules.
This does not depend on `hibernate.cache.auto_evict_collection_cache`.

If a cacheable inverse collection is not initialized, bidirectionality management does not dirty it and does not evict its collection cache entry by itself.
For owner-side-only changes where the inverse collection may remain unloaded, the existing automatic collection cache eviction setting is still relevant:

[source,properties]
----
hibernate.cache.auto_evict_collection_cache=true
----

This setting is especially important for cacheable inverse `@OneToMany` collections mapped by an owning `@ManyToOne`.
Without either an initialized inverse collection or appropriate collection cache eviction, a later session could read an outdated inverse collection entry from the second-level cache.

The setting does not change the core contract of bidirectionality management: Hibernate manages loaded inverse state during flush preparation, but it does not load every possible inverse collection just to update the in-memory graph.
