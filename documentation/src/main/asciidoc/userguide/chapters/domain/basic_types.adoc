A basic type is a mapping between a Java type and a single database column.

Hibernate can map many standard Java types (`Integer`, `String`, etc.) as basic
types.  The mappings for many types come from tables B-3 and B-4 in the JDBC specification<<jdbc>>.
Hibernate provides additional mappings, such as `URL` to `VARCHAR`.

Additionally, Hibernate provides multiple, flexible ways to indicate how the Java type
should be mapped to the database.

[TIP]
====
The Jakarta Persistence specification strictly limits the Java types that can be marked as basic to the following:

|===
| Category | Package | Types

| Java primitive types | | `boolean`, `int`, `double`, etc.
| Primitive wrappers | `java.lang` | `Boolean`, `Integer`, `Double`, etc.
| Strings | `java.lang` | `String`
| UUIDs | `java.util` | `UUID`
| Arbitrary-precision numeric types | `java.math` | `BigInteger` and `BigDecimal`
| Date/time types | `java.time` | `LocalDate`, `LocalTime`, `LocalDateTime`, `OffsetTime`, `OffsetDateTime`, `Instant`, `Year`
| Deprecated date/time types | `java.util` | `Date` and `Calendar`
| Deprecated date/time types from | `java.sql` | `Date`, `Time`, `Timestamp`
| Byte and character arrays | | `byte[]` or `char[]`
| Java enumerated types | | Any `enum`
| Serializable types | | Any type that implements ``java.io.Serializable``footnote:[Jakarta Persistence's support for Serializable types is to directly serialize their state to the database]
|===

Use these basic types for portability across Jakarta Persistence providers.

Jakarta Persistence's `AttributeConverter` provides support for handling types beyond those defined in the specification.
See <<basic-jpa-convert>> for more on this topic.
====

[[basic-annotation-implicit-example]]

====
[source, java, indent=0]
----
include::{example-dir-basic-mapping}/basic/ImplicitBasicTypeTest.java[tags=basic-annotation-implicit-example]
----
====

The `@Basic` annotation defines two attributes.

`optional` - boolean (defaults to true):: Defines whether this attribute allows nulls.  Jakarta Persistence defines
    this as "a hint", which means the provider is free to ignore it.  Jakarta Persistence also says that it will be
    ignored if the type is primitive.  As long as the type is not primitive, Hibernate will honor this
    value.  Works in conjunction with `@Column#nullable` - see <<basic-column-annotation>>.
`fetch` - FetchType (defaults to EAGER):: Defines whether this attribute should be fetched eagerly or lazily.
    `EAGER` indicates that the value will be fetched as part of loading the owner.  `LAZY` values are
    fetched only when the value is accessed.  Jakarta Persistence requires providers to support `EAGER`, while support for
    `LAZY` is optional meaning that a provider is free to not support it.  Hibernate supports lazy loading
    of basic values when using its <<chapters/pc/BytecodeEnhancement.adoc#BytecodeEnhancement,bytecode enhancement>>
    support.

====== Boolean

By default, `Boolean` attributes map to `BOOLEAN` columns, at least when the database has a
dedicated `BOOLEAN` type. On databases which don't, Hibernate uses whatever else is available:
`BIT`, `TINYINT`, or `SMALLINT`.

However, it is quite common to find boolean values encoded as a character or as an integer.
Such cases are exactly the intention of `AttributeConverter`.  For convenience, Hibernate
provides three built-in converters for the common boolean mapping cases:

- `YesNoConverter` encodes a boolean value as `'Y'` or `'N'`,
- `TrueFalseConverter` encodes a boolean value as `'T'` or `'F'`, and
- `NumericBooleanConverter` encodes the value as an integer, `1` for true, and `0` for false.

====== String

By default, Hibernate maps `String` to the `VARCHAR` JDBC type.

[[basic-string-example]]
.Mapping String
====
[source, java, indent=0]
----
include::{example-dir-basic-mapping}/basic/StringMappingTests.java[tags=basic-string-example]
----
====

Optionally, specify the maximum length of the string using `@Column(length=...)`,
or using the `@Size` annotation from Hibernate Validator.
For large strings, use one of the constant values defined by the class
`org.hibernate.Length`, for example:

[source, java, indent=0]
----
@Column(length=Length.LONG)
private String text;
----

Alternatively, explicitly specify the JDBC type `LONGVARCHAR`, which is treated
as a `VARCHAR` mapping with default `length=Length.LONG` when no `length` is explicitly
specified:

[source, java, indent=0]
----
@JdbcTypeCode(Types.LONGVARCHAR)
private String text;
----

When generating the schema, Hibernate selects a column type that accommodates the specified maximum length.

[TIP]
====
If the specified maximum length is too long to fit in the largest `VARCHAR` column supported
by your database, Hibernate's schema exporter will automatically upgrade the column type to
`TEXT`, `CLOB`, or whatever is the equivalent type for your database.
Do not use `@Lob` solely to request a `TEXT` column.
`@Lob` selects JDBC LOB handling rather than a DDL column type.
====

See <<basic-lob>> for details on mapping to a database CLOB.

[[basic-enums]]
==== Enums

Hibernate supports the mapping of Java enums as basic value types in a number of different ways.

[[basic-enums-Enumerated]]
===== `@Enumerated`

The original Jakarta Persistence-compliant way to map enums was via the `@Enumerated` or `@MapKeyEnumerated`
annotations, working on the principle that the enum values are stored according to one of two strategies indicated
by `jakarta.persistence.EnumType`:

`ORDINAL`:: stored according to the enum value's ordinal position within the enum class, as indicated by `java.lang.Enum#ordinal`
`STRING`:: stored according to the enum value's name, as indicated by `java.lang.Enum#name`

Jakarta Persistence also supports `@EnumeratedValue` on a final field of the enum to supply custom database values.
For `ORDINAL`, this field must have type `byte`, `short`, or `int`; for `STRING`, it must have type `String`.
The values must be distinct for each enum constant and must not be null.
For example:

[source,java]
----
enum Status {
    OPEN("O"), CLOSED("C");

    @EnumeratedValue
    final String code;

    Status(String code) {
        this.code = code;
    }
}
----

When neither `@Enumerated` nor an `AttributeConverter` is specified, an enum with a `String` field annotated `@EnumeratedValue` is inferred to use `STRING`; otherwise, `ORDINAL` is inferred.
The SQL column type depends on the dialect and mapping configuration.
Ordinal mappings generally use `TINYINT` or `SMALLINT`, while string mappings may use a native enum type or a character type.

[[basic-other-standard-types]]
==== UUIDs and other standard Java types

[[basic-uuid]]
===== UUID

Hibernate allows mapping UUID values in a number of ways.  By default, Hibernate will
store UUID values in the native form by using the SQL type `UUID` or in binary form with the `BINARY` JDBC type
if the database does not have a native UUID type.


[NOTE]
====
When the database does not support a native UUID type, the default mapping uses the binary representation for efficient storage.

However, many applications prefer the readability of the character-based column storage.

To switch the default mapping, set the `hibernate.type.preferred_uuid_jdbc_type` configuration to `CHAR`.
====

====== UUID as binary

The binary mapping is the default fallback when the database does not support a native UUID type.
It maps the UUID to a `byte[]` using `java.util.UUID#getMostSignificantBits` and `java.util.UUID#getLeastSignificantBits` and stores that as `BINARY` data.

====== UUID as (var)char

Maps the UUID to a String using `java.util.UUID#toString` and `java.util.UUID#fromString` and stores that as `CHAR` or `VARCHAR` data.

====== UUID as identifier

Hibernate supports using UUID values as identifiers, and they can even be generated on the user's behalf.
For details, see the discussion of generators in <<chapters/domain/identifiers.adoc#identifiers,_Identifiers_>>.

[[basic-temporal]]
==== Handling temporal data

Hibernate supports mapping temporal values to the following SQL date/time types:

DATE:: Represents a calendar date by storing years, months and days.
TIME:: Represents the time of a day by storing hours, minutes and seconds.
TIME WITH TIME ZONE:: Represents a time of day with a zone offset.
TIMESTAMP:: Represents both a DATE and a TIME plus nanoseconds.
TIMESTAMP WITH TIME ZONE:: Represents both a DATE and a TIME plus nanoseconds and zone id or offset.

The mapping of `java.time` temporal types to the specific SQL Date/Time types is implied as follows:

DATE:: `java.time.LocalDate`
TIME:: `java.time.LocalTime`, or `java.time.OffsetTime` when its offset is normalized
TIME WITH TIME ZONE:: `java.time.OffsetTime`, when supported and selected by the mapping
TIMESTAMP:: `java.time.LocalDateTime`, or `java.time.Instant`, `java.time.OffsetDateTime`, and `java.time.ZonedDateTime` when normalized
TIMESTAMP WITH TIME ZONE:: `java.time.Instant`, `java.time.OffsetDateTime`, or `java.time.ZonedDateTime`, depending on dialect support and storage configuration

Although Hibernate recommends the use of the `java.time` package for representing temporal values,
it does support using `java.sql.Date`, `java.sql.Time`, `java.sql.Timestamp`, `java.util.Date` and
`java.util.Calendar`.

The mappings for `java.sql.Date`, `java.sql.Time`, `java.sql.Timestamp` are implicit:

DATE:: `java.sql.Date`
TIME:: `java.sql.Time`
TIMESTAMP:: `java.sql.Timestamp`


[IMPORTANT]
====
Applying `@Temporal` to `java.sql.Date`, `java.sql.Time`, `java.sql.Timestamp` or any of the `java.time` types
is considered an exception
====

When using `java.util.Date` or `java.util.Calendar`, Hibernate assumes `TIMESTAMP`.  To alter that,
use `@Temporal`.

[[basic-java-time-direct-jdbc]]
===== Java time at the JDBC boundary

The _JDBC boundary_ is where Hibernate binds parameter values to a JDBC statement and extracts values from a JDBC result set.
The Java type exchanged with the JDBC driver at this boundary can differ from the type of the entity attribute.
For example, Hibernate can map a `LocalDate` attribute to a SQL `DATE` column either by passing the `LocalDate` directly to the driver,
or by converting it to a `java.sql.Date` for JDBC access and converting the retrieved value back to `LocalDate`.

The <<settings-hibernate.type.java_time_use_direct_jdbc,`hibernate.type.java_time_use_direct_jdbc`>> setting controls
whether Hibernate prefers to exchange `java.time` values directly with the driver using `PreparedStatement.setObject()`
and `ResultSet.getObject(..., Class)`.
It defaults to `true` since Hibernate 8.0; earlier versions defaulted to `false`.
This setting controls the Java representation at the JDBC boundary, independently of the SQL column type and time-zone storage strategy.

JDBC 4.2, included in Java 8, requires support for `LocalDate`, `LocalTime`, `LocalDateTime`, `OffsetTime`, and `OffsetDateTime`.
Despite this requirement, some JDBC drivers still do not support all of these types at the JDBC boundary.
Running on Java 8 or later therefore does not by itself guarantee that a driver can bind and extract these values directly.
Hibernate uses the configured dialect's knowledge of driver support to select direct access for each Java time type.
When direct access is requested but the dialect reports a type as unsupported, Hibernate uses the corresponding legacy JDBC representation
and logs the known limitation.

To disable this preference globally, for example when migrating an application that depends on the legacy conversions, set:

[source,properties]
----
hibernate.type.java_time_use_direct_jdbc=false
----

The entity attributes may still use `java.time` types; Hibernate performs the conversions needed for JDBC access.
For time-zone configuration when using legacy JDBC temporal types, see <<basic-datetime-time-zone>>.

[NOTE]
====
JDBC 4.2 does not require direct support for `Instant` or `ZonedDateTime`.
The `hibernate.type.java_time_use_direct_jdbc` setting does not enable direct `Instant` access.
That requires `hibernate.type.preferred_instant_jdbc_type=INSTANT` and dialect support for the driver's `Instant` handling.
For a `ZonedDateTime` attribute, Hibernate may exchange an `OffsetDateTime` at the JDBC boundary when the driver supports that type
but does not support `ZonedDateTime` directly.
====

[[basic-datetime-time-zone]]
===== Using a specific time zone

By default, Hibernate uses the https://docs.oracle.com/javase/8/docs/api/java/sql/PreparedStatement.html#setTimestamp-int-java.sql.Timestamp-[`PreparedStatement.setTimestamp(int parameterIndex, java.sql.Timestamp)`] or
https://docs.oracle.com/javase/8/docs/api/java/sql/PreparedStatement.html#setTime-int-java.sql.Time-[`PreparedStatement.setTime(int parameterIndex, java.sql.Time x)`] when saving a `java.sql.Timestamp` or a `java.sql.Time` property.

When the time zone is not specified, the JDBC driver uses the JVM default time zone. This can produce inconsistent results when application instances run in different time zones.
Use a consistent reference time zone, such as UTC, when saving and loading temporal data.

One alternative would be to configure all JVMs to use the reference time zone:

Declaratively::
+
[source,java]
----
java -Duser.timezone=UTC ...
----

Programmatically::
+
[source,java]
----
TimeZone.setDefault( TimeZone.getTimeZone( "UTC" ) );
----

However, as explained in https://in.relation.to/2016/09/12/jdbc-time-zone-configuration-property/[this article], this is not always practical, especially for front-end nodes.
For this reason, Hibernate offers the `hibernate.jdbc.time_zone` configuration property which can be configured:

Declaratively, at the `SessionFactory` level::
+
[source,java]
----
settings.put(
    AvailableSettings.JDBC_TIME_ZONE,
    TimeZone.getTimeZone( "UTC" )
);
----

Programmatically, on a per `Session` basis::
+
[source,java]
----
Session session = sessionFactory()
    .withOptions()
    .jdbcTimeZone( TimeZone.getTimeZone( "UTC" ) )
    .openSession();
----

With this configuration property in place, Hibernate calls the https://docs.oracle.com/javase/8/docs/api/java/sql/PreparedStatement.html#setTimestamp-int-java.sql.Timestamp-java.util.Calendar-[`PreparedStatement.setTimestamp(int parameterIndex, java.sql.Timestamp, Calendar cal)`] or
https://docs.oracle.com/javase/8/docs/api/java/sql/PreparedStatement.html#setTime-int-java.sql.Time-java.util.Calendar-[`PreparedStatement.setTime(int parameterIndex, java.sql.Time x, Calendar cal)`], where the `java.util.Calendar` references the time zone provided via the `hibernate.jdbc.time_zone` property.

[[basic-timestamp-with-time-zone]]
===== Handling time zoned temporal data

The default time zone storage strategy is `DEFAULT`.
For `OffsetDateTime` and `ZonedDateTime`, it uses `NATIVE` when the dialect supports preserving offsets in a `TIMESTAMP WITH TIME ZONE` column, and `NORMALIZE_UTC` otherwise.
This preserves the instant, but does not guarantee preservation of the original offset or zone.
The strategy can be configured using `hibernate.timezone.default_storage`:

[source,java]
----
settings.put(
    AvailableSettings.TIMEZONE_DEFAULT_STORAGE,
    TimeZoneStorageType.AUTO
);
----

`DEFAULT`:: Uses `NATIVE` when supported, or `NORMALIZE_UTC` otherwise.
`AUTO`:: Uses `NATIVE` when supported, or `COLUMN` otherwise, preserving the instant and offset.
`COLUMN`:: Stores the offset in a separate column.
`NATIVE`:: Uses a `TIMESTAMP WITH TIME ZONE` column. Hibernate fails at boot if the dialect does not support native time zone storage.
`NORMALIZE`:: Normalizes timestamps to `hibernate.jdbc.time_zone`, or to the JVM default time zone if that setting is absent. Values read back use the JVM default zone or offset.
`NORMALIZE_UTC`:: Normalizes timestamps to UTC and reads them back in UTC, without preserving the original offset or zone.

Hibernate determines native time zone support through `Dialect#getTimeZoneSupport()`.

===== `@TimeZoneStorage`

Hibernate supports defining the storage to use for time zone information for individual properties
via the `@TimeZoneStorage` and `@TimeZoneColumn` annotations.
The storage type can be specified via the `@TimeZoneStorage` by specifying a `org.hibernate.annotations.TimeZoneStorageType`.
When `@TimeZoneStorage` is absent, the configured default strategy applies.
When the annotation is present without an explicit value, its value defaults to `AUTO`.
The `@TimeZoneColumn` annotation can be used in conjunction with `AUTO` or `COLUMN` and defines
the column details for the time zone information storage.

[NOTE]
====
Storing the zone offset might be problematic for future timestamps as zone rules can change.
An offset alone does not retain the rules of a named time zone.
If future scheduling depends on those rules, store the zone identifier separately.
For values which represent only an instant, `DEFAULT` or `NORMALIZE_UTC` avoids relying on preservation of the original offset.

[[basic-lob]]
==== Handling LOB data

The `@Lob` annotation specifies that character or binary data should be written to the database
using the special JDBC APIs for handling database LOB (Large OBject) types.

[NOTE]
====
JDBC LOB handling varies between drivers. Hibernate accounts for these differences where possible,
but LOB mappings may require driver-specific configuration or handling beyond the scope of this guide.
====

[IMPORTANT]
====
For databases with no `CLOB` type, attributes of type `java.sql.Clob` are unsupported.
Use a materialized type like `String` or `char[]` instead.
====

A LOB can be represented in the Java domain model in two ways:

- using a special JDBC-defined _LOB locator type_, or
- using a regular "materialized" type like `String`, `char[]`, or `byte[]`.

===== LOB Locator

The JDBC LOB locator types are:

* `java.sql.Blob`
* `java.sql.Clob`
* `java.sql.NClob`

These types represent references to off-table LOB data.
In principle, they allow JDBC drivers to support more efficient access to the LOB data.
Some drivers stream parts of the LOB data as needed, potentially consuming less memory.

However, `java.sql.Blob` and `java.sql.Clob` can be unnatural to deal with and suffer
certain limitations.
For example, it's not portable to access a LOB locator after the end of the transaction
in which it was obtained.

===== Materialized LOB

LOB data can also be represented by `String`, `char[]`, or `byte[]`.
This requires loading the entire LOB into memory when the value is retrieved.
The performance cost depends on the data size and JDBC driver behavior.

[TIP]
====
A database column of type `BLOB` or `CLOB` does not necessarily require a `@Lob` mapping.
The `@Lob` annotation is a special-purpose tool that should only be used when a default
basic mapping to `String` would result in unacceptable performance characteristics.
====

[[basic-nationalized]]
==== Handling nationalized character data

How nationalized character data is handled and stored depends on the underlying database.

Most databases support storing nationalized character data through the standardized SQL
NCHAR, NVARCHAR, LONGNVARCHAR and NCLOB variants.

Others support storing nationalized data as part of CHAR, VARCHAR, LONGVARCHAR
and CLOB.  Generally these databases do not support NCHAR, NVARCHAR, LONGNVARCHAR
and NCLOB, even as aliased types.

Ultimately Hibernate understands this through `Dialect#getNationalizationSupport()`

To ensure nationalized character data gets stored and accessed correctly, `@Nationalized`
can be used locally or `hibernate.use_nationalized_character_data` can be set globally.

[NOTE]
====
`@Nationalized` and `hibernate.use_nationalized_character_data` can be used regardless
of the specific database support for nationalized data and allows the application to
work portably across databases with varying support.
====

[IMPORTANT]
====
For databases with no `NCLOB` data type, attributes of type `java.sql.NClob` are
unsupported. Use `java.sql.Clob` (which `NClob` extends) or a materialized mapping like
`String` or `char[]` instead.

See also <<basic-lob>> regarding similar limitation for databases which do not support
explicit `CLOB` data-type.

[[basic-document-representation]]
===== Choosing a document representation

`@JdbcTypeCode(SqlTypes.JSON)` or `@JdbcTypeCode(SqlTypes.SQLXML)` selects a JDBC document mapping.
The attribute's Java type and the format mapper determine how its value is represented.
A structured value, such as a map, is serialized to a document and reconstructed when loaded.
A `String` value containing an already serialized JSON or XML document is treated as document text, not as a string to be serialized again.
For a JSON `String` mapping, the database may normalize whitespace or object-key ordering, so the original textual formatting is not guaranteed to survive a round trip.
This differs from a plain `String` mapping to `VARCHAR`, even if that string happens to contain JSON.

[source,java,indent=0]
----
include::{root-project-dir}/hibernate-core/src/test/java/org/hibernate/orm/test/mapping/userguide/DomainModelGuideTests.java[tag=guide-json-mapping]

A basic document value is mapped as one value. An <<embeddable-mapping-aggregate,aggregate embeddable>> additionally exposes its mapped component attributes to Hibernate.
Choose an aggregate embeddable when the document represents a mapped component with persistent attributes;
choose a basic document value when the application handles it as a single value.
Database document types, aggregate operations, and JSON/XML query functions have different dialect requirements.

[[basic-converter-selection]]
===== Converter selection and applicability

An `AttributeConverter<X,Y>` converts between the domain Java type `X` and a relational Java type `Y` that Hibernate can bind through JDBC.
It does not directly implement JDBC binding or extraction.
Declare a converter using `@Converter` and ensure that it is discovered or registered as part of the persistence unit.
`@Converter(autoApply=true)` applies it automatically to eligible mappings of its domain type; primitive types and their wrappers are treated as equivalent for this purpose.

An explicit `@Convert(converter=...)` selects a converter for a particular mapping, overriding automatic selection.
Use `@Convert(disableConversion=true)` to suppress automatic conversion:

[source,java,indent=0]
----
include::{root-project-dir}/hibernate-core/src/test/java/org/hibernate/orm/test/mapping/userguide/converters/ConverterSelectionTests.java[tag=guide-converter-selection]
----

With the package registration shown below, `automatic` uses `YesNoConverter`, `explicit` uses `NumericBooleanConverter`,
and `disabled` uses the default Boolean mapping.

When multiple converters could apply to the same type, select one explicitly instead of relying on discovery order.
Automatic application does not mean that any converter on the classpath is necessarily discovered.

Conversion applies to basic attributes, basic element-collection values, and basic map keys and values.
On a map, use `attributeName="key"` or `attributeName="value"` to select the converted part.
For an attribute inside an embeddable, use its attribute path when declaring a conversion on the embedding attribute.
For example:

[source,java,indent=0]
----
include::{root-project-dir}/hibernate-core/src/test/java/org/hibernate/orm/test/mapping/userguide/converters/ConverterSelectionTests.java[tag=guide-converter-map]
----

Jakarta Persistence excludes identifier attributes, version attributes, associations, and attributes explicitly annotated with `@Enumerated` or `@Temporal` from automatic conversion.
Explicitly applying converters to these mappings is not portable.
The same restrictions apply to the corresponding map keys.

[[basic-converter-registration]]
====== Registering converters externally

Hibernate's link:{doc-javadoc-url}org/hibernate/annotations/ConverterRegistration.html[`@ConverterRegistration`]
registers a converter without requiring changes to its class.
Its `autoApply` member defaults to `true` and overrides the converter's declared automatic-application policy.
Use `domainType` to specify the domain type for which the registration applies; omitting it uses the converter's inferred domain type.
This is useful for third-party converters or for refining application to a particular subtype.

[source,java]
----
@ConverterRegistration(converter = YesNoConverter.class, autoApply = true)
package com.example.model;

import org.hibernate.annotations.ConverterRegistration;
import org.hibernate.type.YesNoConverter;
----

Place registrations in `package-info.java` or `module-info.java` so Hibernate processes them before resolving attributes.
They register converters for the persistence unit; package placement is not a restriction to attributes declared in that package.
Class-level registrations are supported, but affect only mappings processed after the registration is encountered and do not revise earlier resolutions.
Avoid relying on that processing order.

`@ConverterRegistration` is repeatable.
Use repeated annotations or the explicit link:{doc-javadoc-url}org/hibernate/annotations/ConverterRegistrations.html[`@ConverterRegistrations`] container:

[source,java,indent=0]
----
include::{root-project-dir}/hibernate-core/src/test/java/org/hibernate/orm/test/mapping/userguide/converters/package-info.java[tag=guide-converter-registrations]
----

Here, `YesNoConverter` is automatically applied, while `PeriodStringConverter` is registered for explicit selection.
These registration annotations are Hibernate extensions.

====== Choosing a customization mechanism

Use an `AttributeConverter` to translate a domain value to an existing relational Java representation.
Use <<basic-mapping-composition,compositional mapping annotations>> to select Java/JDBC descriptors or a mutability plan.
Use <<basic-mapping-custom,`UserType`>> when the mapping needs custom JDBC handling beyond a value conversion.
See <<basic-jpa-convert-mutability>> for converted-value dirty checking.

[[mapping-generated]]
==== Generated properties

NOTE: This section talks about generating values for non-identifier attributes.  For discussion of generated identifier values, see <<identifiers-generators>>.

Generated attributes have their values generated as part of performing a SQL INSERT or UPDATE.  Applications can generate these
values in any number of ways (SQL DEFAULT value, trigger, etc).  Typically, the application needs to refresh objects that
contain any properties for which the database was generating values, which is a major drawback.

Applications can also delegate generation to Hibernate, in which case Hibernate will manage the value generation
and (potentialfootnote:[Only in-DB generation requires the refresh]) state refresh itself.

[IMPORTANT]
====
Only `@Basic` and `@Version` attributes can be marked as generated.

Whether a generated attribute is written in an `INSERT` or `UPDATE` depends on its generator.
In-memory generators produce values which Hibernate writes to the database.
For database-generated values, `@Generated` normally omits the value from the SQL statement, but `@Generated(writable = true)` includes the assigned value and retrieves the generated result.
An attribute generated only on insert may still be updated later by the application unless it is marked `@Immutable`.
====

Hibernate supports both in-VM and in-DB generation.  A generation that uses the current JVM timestamp as the
generated value is an example of an in-VM strategy.  A generation that uses the database's `current_timestamp`
function is an example of an in-DB strategy.

Generators declare the events for which they generate a value using `org.hibernate.generator.EventType`:

`INSERT`:: The value is generated when the entity is inserted.
`UPDATE`:: The value is generated when the entity is updated.
`FORCE_INCREMENT`:: A version value is generated when its increment is forced.

An annotation with an `event` member may select multiple events, such as `event = {INSERT, UPDATE}`.
Without a generator, the application supplies the attribute value.

Hibernate supports multiple ways to mark an attribute as generated:

* Using the dedicated generators provided by Hibernate
    * `@CurrentTimestamp` - <<mapping-generated-CurrentTimestamp>>
    * `@CreationTimestamp` - <<mapping-generated-CreationTimestamp>>
    * `@UpdateTimestamp` - <<mapping-generated-UpdateTimestamp>>
    * `@Generated` - <<mapping-generated-Generated>>
* Using a custom generation strategy - <<mapping-generated-custom>>


[[mapping-generated-CurrentTimestamp]]
===== `@CurrentTimestamp`

The `@CurrentTimestamp` annotation generates a timestamp for the events selected by its `event` member.
By default, it includes `INSERT`, `UPDATE`, and `FORCE_INCREMENT`.
Its default `source = DB` uses the database's `current_timestamp` function; `source = VM` uses the current JVM timestamp.

[[mapping-generated-Generated]]
===== `@Generated` annotation

The `@Generated` annotation marks a value as generated by the database and causes Hibernate to retrieve it after the configured events.
The default is `event = INSERT`; use `event = {INSERT, UPDATE}` to retrieve the value after both operations.
Values may come from a column default, a trigger, or an expression supplied using `@Generated(sql = ...)`.
With `writable = true`, Hibernate includes the assigned value in the SQL statement, allowing the database to transform it before Hibernate retrieves the result.
