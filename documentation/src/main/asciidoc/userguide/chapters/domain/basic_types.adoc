A basic type is a mapping between a Java type and a single database column.

Hibernate can map many standard Java types (`Integer`, `String`, etc.) as basic
types.  The mappings for many types come from tables B-3 and B-4 in the JDBC specification<<jdbc>>.
Hibernate provides additional mappings, such as `URL` to `VARCHAR`.

Additionally, Hibernate provides multiple, flexible ways to indicate how the Java type
should be mapped to the database.

[TIP]
====
The Jakarta Persistence specification strictly limits the Java types that can be marked as basic to the following:

|===
| Category | Package | Types

| Java primitive types | | `boolean`, `int`, `double`, etc.
| Primitive wrappers | `java.lang` | `Boolean`, `Integer`, `Double`, etc.
| Strings | `java.lang` | `String`
| UUIDs | `java.util` | `UUID`
| Arbitrary-precision numeric types | `java.math` | `BigInteger` and `BigDecimal`
| Date/time types | `java.time` | `LocalDate`, `LocalTime`, `LocalDateTime`, `OffsetTime`, `OffsetDateTime`, `Instant`, `Year`
| Deprecated date/time types | `java.util` | `Date` and `Calendar`
| Deprecated date/time types from | `java.sql` | `Date`, `Time`, `Timestamp`
| Byte and character arrays | | `byte[]` or `char[]`
| Java enumerated types | | Any `enum`
| Serializable types | | Any type that implements ``java.io.Serializable``footnote:[Jakarta Persistence's support for Serializable types is to directly serialize their state to the database]
|===

Use these basic types for portability across Jakarta Persistence providers.

Jakarta Persistence's `AttributeConverter` provides support for handling types beyond those defined in the specification.
See <<basic-jpa-convert>> for more on this topic.
====

The `@Basic` annotation defines two attributes.

`optional` - boolean (defaults to true):: Defines whether this attribute allows nulls.  Jakarta Persistence defines
    this as "a hint", which means the provider is free to ignore it.  Jakarta Persistence also says that it will be
    ignored if the type is primitive.  As long as the type is not primitive, Hibernate will honor this
    value.  Works in conjunction with `@Column#nullable` - see <<basic-column-annotation>>.
`fetch` - FetchType (defaults to EAGER):: Defines eager or lazy timing for the basic attribute.
    `EAGER` requires the value to be available when the owner is loaded. `LAZY` is a hint permitting deferred loading,
    not a guarantee that the value is loaded only upon access. Hibernate needs enhancement to defer basic state;
    see <<fetching-lazy-basic,lazy basic attributes and groups>> and <<fetching-basics,fetch timing>>.

By default, `Boolean` attributes map to `BOOLEAN` columns, at least when the database has a
dedicated `BOOLEAN` type. On databases which don't, Hibernate uses whatever else is available:
`BIT`, `TINYINT`, or `SMALLINT`.

Such cases are exactly the intention of `AttributeConverter`.  For convenience, Hibernate
provides three built-in converters for the common boolean mapping cases:

====== String

By default, Hibernate maps `String` to the `VARCHAR` JDBC type.

[[basic-string-example]]
.Mapping String
====
[source, java, indent=0]
----
include::{example-dir-basic-mapping}/basic/StringMappingTests.java[tags=basic-string-example]
----
====

Optionally, specify the maximum length of the string using `@Column(length=...)`,
or using the `@Size` annotation from Hibernate Validator.
For large strings, use one of the constant values defined by the class
`org.hibernate.Length`, for example:

[source, java, indent=0]
----
@Column(length=Length.LONG)
private String text;
----

Alternatively, explicitly specify the JDBC type `LONGVARCHAR`, which is treated
as a `VARCHAR` mapping with default `length=Length.LONG` when no `length` is explicitly
specified:

[source, java, indent=0]
----
@JdbcTypeCode(Types.LONGVARCHAR)
private String text;
----

When generating the schema, Hibernate selects a column type that accommodates the specified maximum length.

[TIP]
====
If the specified maximum length is too long to fit in the largest `VARCHAR` column supported
by your database, Hibernate's schema exporter will automatically upgrade the column type to
`TEXT`, `CLOB`, or whatever is the equivalent type for your database.
Do not use `@Lob` solely to request a `TEXT` column.
`@Lob` selects JDBC LOB handling rather than a DDL column type.
====

See <<basic-lob>> for details on mapping to a database CLOB.

[[basic-enums]]
==== Enums

Hibernate supports the mapping of Java enums as basic value types in a number of different ways.

[[basic-enums-Enumerated]]
===== `@Enumerated`

The original Jakarta Persistence-compliant way to map enums was via the `@Enumerated` or `@MapKeyEnumerated`
annotations, working on the principle that the enum values are stored according to one of two strategies indicated
by `jakarta.persistence.EnumType`:

`ORDINAL`:: stored according to the enum value's ordinal position within the enum class, as indicated by `java.lang.Enum#ordinal`
`STRING`:: stored according to the enum value's name, as indicated by `java.lang.Enum#name`

Jakarta Persistence also supports `@EnumeratedValue` on a final field of the enum to supply custom database values.
For `ORDINAL`, this field must have type `byte`, `short`, or `int`; for `STRING`, it must have type `String`.
The values must be distinct for each enum constant and must not be null.
For example:

[source,java]
----
enum Status {
    OPEN("O"), CLOSED("C");

    @EnumeratedValue
    final String code;

    Status(String code) {
        this.code = code;
    }
}
----

When neither `@Enumerated` nor an `AttributeConverter` is specified, an enum with a `String` field annotated `@EnumeratedValue` is inferred to use `STRING`; otherwise, `ORDINAL` is inferred.
The SQL column type depends on the dialect and mapping configuration.
Ordinal mappings generally use `TINYINT` or `SMALLINT`, while string mappings may use a native enum type or a character type.

[[basic-other-standard-types]]
==== UUIDs and other standard Java types

[[basic-uuid]]
===== UUID

Hibernate allows mapping UUID values in a number of ways.  By default, Hibernate will
store UUID values in the native form by using the SQL type `UUID` or in binary form with the `BINARY` JDBC type
if the database does not have a native UUID type.


[NOTE]
====
When the database does not support a native UUID type, the default mapping uses the binary representation for efficient storage.

However, many applications prefer the readability of the character-based column storage.

To switch the default mapping, set the `hibernate.type.preferred_uuid_jdbc_type` configuration to `CHAR`.
====

====== UUID as binary

The binary mapping is the default fallback when the database does not support a native UUID type.
It maps the UUID to a `byte[]` using `java.util.UUID#getMostSignificantBits` and `java.util.UUID#getLeastSignificantBits` and stores that as `BINARY` data.

====== UUID as (var)char

Maps the UUID to a String using `java.util.UUID#toString` and `java.util.UUID#fromString` and stores that as `CHAR` or `VARCHAR` data.

====== UUID as identifier

Hibernate supports using UUID values as identifiers, and they can even be generated on the user's behalf.
For details, see the discussion of generators in <<chapters/domain/identifiers.adoc#identifiers,_Identifiers_>>.

[[basic-temporal]]
==== Handling temporal data

Hibernate recommends `java.time` types for temporal values. Use local types for calendar dates and local
clock readings, `Instant` for a point on the timeline, and offset- or zone-bearing types when that information
is part of the domain value. Hibernate also supports legacy `java.util.Date`, `java.util.Calendar`, and
`java.sql` date/time types, as well as related types such as `Duration`, `Year`, `TimeZone`, and `ZoneOffset`.

The Java type describes the value's meaning. Its physical representation depends on the dialect, the
selected mapping and the preservation requirements. Relevant SQL types include:

DATE:: A calendar date.
TIME:: A time of day, with fractional seconds where supported.
TIME WITH TIME ZONE:: A time of day with an offset.
TIMESTAMP:: A date and time, with fractional seconds subject to database and column precision.
TIMESTAMP WITH TIME ZONE:: A timestamp whose timezone information and interpretation depend on the database;
the name alone does not promise retention of the original offset or zone ID.

There is no universal one-to-one correspondence between these SQL types and Java types. For example,
Oracle's preserving `LocalTime` handling uses a timestamp carrier. Storage choices do not implicitly
request timezone adjustment or permission to discard information.

[[basic-temporal-preservation]]
===== Preservability Guarantees

Preservability guarantees define which parts of a Java time value Hibernate retains when the value is
stored and read back. The required guarantee depends on the Java type and any explicit representation
or timezone adjustment selected for the mapping.

[[basic-java-time-direct-jdbc]]
The <<settings-hibernate.type.temporal_preservation,`hibernate.type.temporal_preservation`>> setting
enables these guarantees and defaults to `true`.
Hibernate uses direct JDBC access when supported, or a preserving fallback conversion.
The guarantee follows the Java type, not the SQL type name or whether direct JDBC access is used.
Hibernate rejects a mapping when its resolved Java/JDBC handling cannot establish the required guarantee;
it does not silently substitute instant-only handling for an offset- or zone-preserving mapping.

[[basic-temporal-preservation-policy]]
====== Configurable preservation policies

`hibernate.type.temporal_preservation_policy` selects `domain_value` (the default) or `normalized`.
Preservation must remain enabled. `NORMALIZED` requires the same instant for `OffsetDateTime` and
`ZonedDateTime`, while allowing the original offset and zone ID to change. For `OffsetTime`, it requires
the same UTC-equivalent time of day modulo 24 hours: `00:30+02:00` and `22:30Z` are equivalent.
This explicitly discards day displacement and differs from `OffsetTime.isEqual()` across midnight.
It does not invent a date, require UTC output, select storage, or request timezone adjustment.
Local Java Time types and `Instant` retain their existing guarantees.

Each offset-bearing type may override the common default:

[source,properties]
----
hibernate.type.temporal_preservation=true
hibernate.type.temporal_preservation_policy=domain_value
hibernate.type.temporal_preservation_policy.offset_datetime=normalized
hibernate.type.temporal_preservation_policy.zoned_datetime=normalized
hibernate.type.temporal_preservation_policy.offset_time=domain_value
----

`@TemporalPreservationPolicy` overrides configuration on a member, declaring class, package or module.
Its `Type` enum contains `DOMAIN_VALUE` and `NORMALIZED`. For example, using static imports of these constants:

[source,java]
----
@TemporalPreservationPolicy(NORMALIZED)
OffsetDateTime occurredAt;

@TemporalPreservationPolicy(DOMAIN_VALUE)
OffsetDateTime enteredAt;
----

On a class, package or module, the annotation is repeatable and may select exact types:

[source,java]
----
@TemporalPreservationPolicy(value = NORMALIZED, types = { OffsetDateTime.class, ZonedDateTime.class })
@TemporalPreservationPolicy(value = DOMAIN_VALUE, types = OffsetTime.class)
----

Lookup uses the mapped member, its declaring class and superclass chain, exact declaring package,
module, per-type setting, then common setting. At one scope, a matching typed declaration wins over an
untargeted default. A nearer untargeted default wins over a farther typed declaration. Overlapping type
selectors or multiple untargeted declarations at one scope are invalid. On members, omit `types`.
For an application converter, selectors and validation use its relational Java type.
A broad normalized default leaves local types unchanged; directly requesting normalization on a local type is invalid.

The selected requirement must still be supported by the actual descriptors. Policy changes do not migrate
historical data or establish its interpretation. Equality, dirty checking and cache serialization remain
unchanged: an offset-only change may be dirty, and a cache hit may retain an offset that a database reload
normalizes. Both must meet the selected precision-qualified guarantee.

====== Guarantees by policy

[[basic-temporal-preservation-matrix]]
.Guarantees with temporal preservation enabled and no timezone adjustment
[cols="1,3,3",options="header"]
|===
|Java type |`DOMAIN_VALUE` (default) |`NORMALIZED`
|`LocalDate` |Calendar date. |Unchanged under a broad default.
|`LocalTime` |Local time of day. |Unchanged under a broad default.
|`LocalDateTime` |Local date and time. |Unchanged under a broad default.
|`Instant` |Instant on the UTC timeline. |Same instant.
|`OffsetTime` |Local time of day and offset. |UTC-equivalent time of day modulo 24 hours; original offset and day displacement need not survive.
|`OffsetDateTime` |Local date-time and offset, and therefore the same instant. |Same instant; original offset and local date-time need not survive.
|`ZonedDateTime` |Local date-time, zone ID and resolved offset, and therefore the same instant. |Same instant; original zone ID, offset and local date-time need not survive.
|===

The matrix defines guarantees for these seven Java Time types, including their supported version mappings,
and for Hibernate's synthetic `Instant` system-period boundaries. It does not introduce equivalent guarantees
for `java.util.Date`, `Calendar`, the `java.sql` temporal classes, `Duration`, `Year`, or standalone zone types.
Those retain their established mapping semantics. Enabling preservation can still affect shared validation:
for example, a `java.sql.Time` handler cannot satisfy requested precision beyond milliseconds.

These guarantees apply within the supported finite SQL range and column precision.
Fractional seconds may be rounded or truncated according to the supported driver/database handling and column precision;
these guarantees do not promise to retain all nine Java nanosecond digits in a lower-precision column. Java minimum/maximum sentinels are not a portable
way to store database infinity.

There is one explicit representation qualification: `@TimeZoneRepresentation(COLUMN)` stores an offset
separately, so a `ZonedDateTime` round trip preserves local date-time and offset but reconstructs a fixed-offset
zone, not the original region ID. A `WITH TIME ZONE` primary column does not restore a region discarded
by this decomposition. Choose this representation only when the offset-only contract is suitable.

Database support for `TIMESTAMP WITH TIME ZONE` alone does not establish zone-ID or offset preservation.
For example, H2's offset-only inline handling cannot meet the baseline `ZonedDateTime` guarantee, and
PostgreSQL's instant-preserving timestamp handling does not preserve an arbitrary original offset.
Provider limitations do not silently weaken the contract: choose a supported mapping, an explicit preservation
policy, or an explicit adjustment whose semantics match the application.

For an active application `AttributeConverter`, validation follows its relational Java type and JDBC mapping.
Thus, a non-Java-Time attribute converted to `Instant` receives the Instant guarantee at the JDBC boundary;
a Java Time attribute converted to `String` does not receive a guarantee about the application's encoding.
Hibernate does not guarantee that application conversion itself is lossless. An active whole-value converter
cannot be combined with synthetic COLUMN storage or with a non-NONE timezone adjustment.

This mode also applies to Java time version attributes and synthetic `Instant` system-period boundaries.
Version generation, optimistic-lock predicates, and historical queries use their resolved temporal mappings.
Enabled system periods require a preserving dialect contribution for their storage and generation strategy.
For example, an offset-only JDBC mapping cannot preserve a region-bearing `ZonedDateTime` version.

Applications that need the existing direct-disabled temporal interpretations can select compatibility mode:

[source,properties]
----
hibernate.type.temporal_preservation=false
----

The entity attributes may still use `java.time` types, for which Hibernate continues to offer no preservability guarantees.  This selects legacy handling, including timestamp versions and system periods; it does not convert existing data.

[IMPORTANT]
====
Assess existing schemas and encoded values as part of migrating applications using Java Time types in the domain model.

Schema validation and data migration script generation is planned as part of the `hibernate-migration-recipes` project.
====

.Temporal settings
[cols="2,3",options="header"]
|===
|Setting |Meaning
|`hibernate.type.temporal_preservation`
|Defaults to `true`. Enables the guarantees above, including Java time versions and supported system periods.
`false` selects the existing direct-disabled interpretation; it does not migrate data.
|`hibernate.type.java_time_use_direct_jdbc`
|Deprecated alias, used only when the new setting is absent.
|`hibernate.type.preferred_instant_jdbc_type`

The deprecated `hibernate.type.java_time_use_direct_jdbc` setting remains an alias when the new setting is absent.
An explicit `hibernate.type.temporal_preservation` value takes precedence over a conflicting alias.
With neither setting supplied, preservation is enabled.

Direct JDBC access and fallback conversion are ways to fulfill the guarantee. At the _JDBC boundary_,
Hibernate binds statement parameters and extracts result values. The Java type exchanged with the driver
may differ from the attribute type: a preserving conversion is acceptable if it retains the required value.
Choosing direct access alone does not establish preservation.

JDBC 4.2 requires direct support for several Java time classes but not `Instant` or `ZonedDateTime`;
actual driver support varies. The dialect selects direct access or the matching fallback.
Enabled preservation derives an `INSTANT` preferred JDBC type for `Instant`, with a `TIMESTAMP_UTC` fallback
when direct access is unavailable. Disabled preservation derives the legacy `TIMESTAMP_UTC` preference.
An explicit `hibernate.type.preferred_instant_jdbc_type` overrides that preference but does not waive an enabled guarantee.
Synthetic period layouts remain selected by the dialect's period contribution rather than the application Instant preference.
For legacy JDBC timezone configuration, see <<basic-datetime-time-zone>>.

[[basic-timestamp-with-time-zone]]
===== Storage representation and timezone adjustment

With preservation enabled, storage representation and timezone adjustment are separate decisions.
`@TimeZoneRepresentation(INLINE)` (the default) uses the primary column; `COLUMN` stores an offset in an
additional column, customizable with `@TimeZoneColumn`. Neither choice by itself requests timezone adjustment.

`@TimeZoneAdjustment("America/New_York")` explicitly expresses a value in that target zone on both write and read.
For `OffsetDateTime` and `ZonedDateTime`, adjustment retains the instant while changing local fields and the
offset/zone as required. For `OffsetTime`, the target must be a fixed offset, since there is no date with
which to resolve a region's rules. `@TimeZoneAdjustment(TimeZoneAdjustment.NONE)` cancels an inherited
adjustment. It does not disable preservation or an application converter.

[source,java,opts=novalidate]
----
@TimeZoneRepresentation(TimeZoneRepresentation.Type.COLUMN)
OffsetDateTime recordedAt; // retains local date-time and offset

@TimeZoneRepresentation(TimeZoneRepresentation.Type.INLINE)
@TimeZoneAdjustment("UTC")
OffsetDateTime publishedAt; // deliberately reads and writes in UTC
----

Declarations may be placed on supported mapped members, their declaring classes and superclass chain,
the exact declaring package, or the declaring module. The nearer declaration wins for each decision.
These annotations require enabled preservation; they are not a way to alter compatibility mode.
They apply to supported basic attributes and basic set/list/bag elements, not identifiers, version attributes,
map keys/values, arrays or aggregate mappings such as JSON, XML and SQL structs. Explicit declarations on
excluded roles are rejected; broader defaults do not alter those roles. Java time version attributes still
receive preservation validation through their version mappings.

The deprecated `@TimeZoneStorage` and `TimeZoneStorageType` combine these decisions.
Prefer the separate annotations for new mappings. In enabled mode, legacy `COLUMN`, `NATIVE`, and
`NORMALIZE_UTC` declarations retain compatibility translations and their constraints; they do not waive
the guarantees. Member-level `AUTO`, `DEFAULT`, and `NORMALIZE` require an explicit replacement or
compatibility mode. An explicitly configured global legacy policy may also require narrower declarations;
setting adjustment to NONE alone does not replace its storage choice.

[[basic-temporal-query-precision]]
===== Precision in queries and the query cache

On supported precision-preserving mappings, assignments use the target column's fractional-second
precision. Query comparisons keep the supplied comparison boundary. For example, a timestamp ending
in `.122900` and one ending in `.123100` might both round to `.123` when written to a millisecond
column, but `stamp < :boundary` must still distinguish them. Being equivalent for dirty checking
therefore does not imply being equivalent in a query predicate.

HQL and Criteria assignment parameters use each target mapping independently. Whole-value COLUMN
assignments prepare the primary timestamp and companion offset together, including when rounding
crosses a transition in an explicitly configured timezone. Database expressions and explicit casts
retain their SQL semantics; they are not Java-side assignment conversion. An adjusted COLUMN
path copy between different precision or adjustment contracts is rejected when its companion offset
would require recomputation; bind a whole temporal value instead. Copies already using the same
fixed offset, such as UTC, retain SQL precision conversion without needing offset recomputation.
Native SQL does not infer
an attribute's precision from its parameter's Java class.

The query cache preserves the results of the query, including scalar and converted projections.
It does not round comparison parameters merely to obtain a cache key or reduce a projection to an
unrelated attribute's precision. For converted temporal parameters, key construction reuses the
relational values prepared for that execution. A cache hit can still require conversion to identify
that execution; application converters must not rely on queries bypassing conversion.

Bulk updates and deletes retain their usual persistence-context behavior: invalidate affected cached
results, but do not refresh already managed objects or invoke entity callbacks. Use a fresh persistence
context or explicit refresh to inspect the new values. Native mutations must register their affected
query spaces when cache invalidation is required. Evict affected entity, collection and query-cache
regions when changing temporal mapping contracts or migrating stored interpretations; cache entries
are not a migration mechanism.

[[basic-temporal-period-precision]]
===== Precision of temporal history periods

With `hibernate.type.temporal_preservation=true`, timestamp periods declared using
`org.hibernate.annotations.Temporal` share one Dialect-selected precision and storage contract
within a `SessionFactory`. This covers both endpoints of temporal entities and collections,
including collections on non-temporal entities. It does not change ordinary attribute,
`@Version`, or Envers revision timestamp precision.

Hibernate prepares a Java-generated changeset timestamp once before publishing it and reuses
that value throughout the transaction. A custom timestamp supplier may therefore see its
fractional nanoseconds adjusted to the supported period grid. This does not guarantee distinct
timestamps for different transactions. An application-owned `@Changelog` Instant identifier
must already be representable: Hibernate rejects an incompatible identifier instead of changing
its identity. Other identifier types retain their existing behavior.

`@Temporal.secondPrecision` is deprecated. Omit it to use the Dialect contract; a matching
explicit value remains accepted, while a conflicting value fails bootstrap. The selected
contract requires matching physical period columns. Resolution uses mapping information and
does not require JDBC metadata access at boot. Assess retained column precision separately; type-only schema validation does not prove fractional precision.

Supported database-generated timestamps must meet the same storage contract. Native period
values remain database-owned; support for a Java timestamp route alone does not establish
support for a server or native route. Custom Dialects may contribute an explicit period contract
through `TemporalTableSupport.getTemporalPeriodPrecisionSupport()`.

Historical query arguments are comparison boundaries and are not rounded to the period grid.
A temporal collection on a non-temporal owner supplies collection history only: its owner's
state is still current. For existing schemas, `temporal_preservation=false` retains legacy
per-mapping period precision and timestamp handling. This is a broad temporal compatibility
switch, not a precision-only override; see the migration guide before enabling preservation.

[[basic-temporal-custom-descriptors]]
===== Custom temporal descriptors

`@JavaType`, `@JdbcType` and `@JdbcTypeCode` select handling; they do not waive preservation
requirements. Hibernate assesses the actual resolved Java/JDBC descriptor pair. Extending a
supported built-in descriptor does not automatically establish that a replacement preserves
its conversions.

A custom `TemporalJavaType` may implement `PreservationAwareTemporalJavaType` to declare the
independent temporal parts needed to reconstruct its values. Its `getRequiredTemporalParts()`
returns a stable, nonempty set without null elements. For the seven Java Time classes in the
guarantee matrix, a participating replacement must declare the existing contract exactly:
for example, `OffsetDateTime` requires `INSTANT` and `OFFSET`. Other custom domain classes opt
into validation through this interface; existing `TemporalJavaType` implementations are unchanged.
This declaration alone does not certify a JDBC pairing or add COLUMN decomposition, timezone
adjustment, identifier/version generation, or system-period support for a custom domain.

A `JdbcType` may implement `TemporalJdbcType` to assess its actual pairing with a supplied
`JavaType` and `Dialect`. Its `getTemporalPreservation()` returns an `Optional<TemporalPreservation>`:

* `Optional.empty()` declines the pair and allows normal Dialect fallback.
* A present report is authoritative at this stage. Required parts must be `SUPPORTED`;
`UNKNOWN`, `UNSUPPORTED` and `IRRELEVANT` do not satisfy them. Hibernate does not fill gaps
with more optimistic fallback reports.

The Java-side declaration remains the domain contract even when a mapping selects `NORMALIZED`;
Hibernate applies the mapping's policy afterward. `NORMALIZED_TIME` is the separate assessment for
UTC-equivalent time of day modulo 24 hours. `TIME` alone does not establish it. Supported `TIME` and
`OFFSET` together imply it when no explicit normalized-time assessment is supplied. The original
five-argument report constructor remains available and leaves the new component unknown.

The report must account for wrapping/unwrapping, binding, extraction and reconstruction.
Recognize descriptor behavior that the implementation actually understands, not merely a
matching domain class or SQL type code. For example, a delegating JDBC adapter whose execution
uses an established pair can reuse that pair's assessment:

[source,java]
----
@Override
public Optional<TemporalPreservation> getTemporalPreservation(
        JavaType<?> javaType, Dialect dialect) {
    if ( javaType != supportedJavaType ) {
        return Optional.empty();
    }
    // Binding and extraction delegate using exactly these underlying descriptors.
    return Optional.of( dialect.getTemporalPreservation( delegateJavaType, delegateJdbcType ) );
}
----

Here the adapter must also establish that its conversion to and from `delegateJavaType` preserves
the required parts. Delegating an assessment does not prove that conversion. Delegation must
use a distinct pair; recursive assessment fails with a mapping diagnostic.

Built-in Dialects consult this SPI before their existing pair recognition. An application
Dialect override remains authoritative; delegating to `super` gives the descriptor its SPI
opportunity. The existing Dialect override mechanism therefore remains valid.

An explicitly adopted SPI contract may be inherited, but a subclass changing execution must
update or decline its assessment. Callbacks must be deterministic for the configured descriptor
instances, side-effect-free, and independent of boot metadata access. They must not acquire
connections or change execution. Reports do not certify arbitrary schemas, supported value
ranges, precision, or every callable operation; those remain separate responsibilities.
Active application converters are assessed using their relational Java descriptor, not a
requirement declaration on the converter's domain type. With `temporal_preservation=false`,
ordinary mapping and query execution does not invoke these new validation callbacks.

[[basic-datetime-time-zone]]
====== Legacy JDBC timezone conversion

The `hibernate.jdbc.time_zone` setting controls applicable JDBC conversions for legacy temporal mappings, including Java Time
attributes using compatibility mode. It does not select a domain adjustment target, set the database session
timezone, or rewrite existing values. Preserving JDBC handlers may instead use their own fixed conversion
protocol to satisfy the guarantee independently of this setting.

By default, Hibernate uses the https://docs.oracle.com/javase/8/docs/api/java/sql/PreparedStatement.html#setTimestamp-int-java.sql.Timestamp-[`PreparedStatement.setTimestamp(int parameterIndex, java.sql.Timestamp)`] or
https://docs.oracle.com/javase/8/docs/api/java/sql/PreparedStatement.html#setTime-int-java.sql.Time-[`PreparedStatement.setTime(int parameterIndex, java.sql.Time x)`] when saving a `java.sql.Timestamp` or a `java.sql.Time` property.

When the time zone is not specified, the JDBC driver uses the JVM default time zone. This can produce inconsistent results when application instances run in different time zones.
Use a consistent reference time zone, such as UTC, when saving and loading temporal data.

One alternative would be to configure all JVMs to use the reference time zone:

Declaratively::
+
[source,shell]
----
java -Duser.timezone=UTC ...
----

Programmatically::
+
[source,java,opts=novalidate]
----
TimeZone.setDefault( TimeZone.getTimeZone( "UTC" ) );
----

However, as explained in https://in.relation.to/2016/09/12/jdbc-time-zone-configuration-property/[this article], this is not always practical, especially for front-end nodes.
For this reason, Hibernate offers the `hibernate.jdbc.time_zone` configuration property which can be configured:

Declaratively, at the `SessionFactory` level::
+
[source,java,opts=novalidate]
----
settings.put(
    AvailableSettings.JDBC_TIME_ZONE,
    TimeZone.getTimeZone( "UTC" )
);
----

Programmatically, on a per `Session` basis::
+
[source,java]
----
Session session = sessionFactory()
    .withOptions()
    .jdbcTimeZone( TimeZone.getTimeZone( "UTC" ) )
    .openSession();
----

With this configuration property in place, Hibernate calls the https://docs.oracle.com/javase/8/docs/api/java/sql/PreparedStatement.html#setTimestamp-int-java.sql.Timestamp-java.util.Calendar-[`PreparedStatement.setTimestamp(int parameterIndex, java.sql.Timestamp, Calendar cal)`] or
https://docs.oracle.com/javase/8/docs/api/java/sql/PreparedStatement.html#setTime-int-java.sql.Time-java.util.Calendar-[`PreparedStatement.setTime(int parameterIndex, java.sql.Time x, Calendar cal)`], where the `java.util.Calendar` references the time zone provided via the `hibernate.jdbc.time_zone` property.

[[basic-legacy-timezone-storage]]
====== Legacy timezone storage

The following strategies describe compatibility mode (`hibernate.type.temporal_preservation=false`).
They may discard offsets or region IDs and must not be read as enabled-preservation guarantees.

The default time zone storage strategy is `DEFAULT`.
For `OffsetDateTime` and `ZonedDateTime`, it uses `NATIVE` when the dialect supports preserving offsets in a `TIMESTAMP WITH TIME ZONE` column, and `NORMALIZE_UTC` otherwise.
This preserves the instant, but does not guarantee preservation of the original offset or zone.
The strategy can be configured using `hibernate.timezone.default_storage`:

[source,java,opts=novalidate]
----
settings.put(
    AvailableSettings.TIMEZONE_DEFAULT_STORAGE,
    TimeZoneStorageType.AUTO
);
----

`DEFAULT`:: Uses `NATIVE` when supported, or `NORMALIZE_UTC` otherwise.
`AUTO`:: Uses `NATIVE` when supported, or `COLUMN` otherwise, preserving the instant and offset.
`COLUMN`:: Stores the offset in a separate column.
`NATIVE`:: Uses a `TIMESTAMP WITH TIME ZONE` column. Hibernate fails at boot if the dialect does not support native time zone storage.
`NORMALIZE`:: Normalizes timestamps to `hibernate.jdbc.time_zone`, or to the JVM default time zone if that setting is absent. Values read back use the JVM default zone or offset.
`NORMALIZE_UTC`:: Normalizes timestamps to UTC and reads them back in UTC, without preserving the original offset or zone.

Hibernate determines native time zone support through `Dialect#getTimeZoneSupport()`.

====== Legacy `@TimeZoneStorage`

Hibernate supports defining the storage to use for time zone information for individual properties
via the `@TimeZoneStorage` and `@TimeZoneColumn` annotations.
The storage type can be specified via the `@TimeZoneStorage` by specifying a `org.hibernate.annotations.TimeZoneStorageType`.
When `@TimeZoneStorage` is absent, the configured default strategy applies.
When the annotation is present without an explicit value, its value defaults to `AUTO`.
The `@TimeZoneColumn` annotation can be used in conjunction with `AUTO` or `COLUMN` and defines
the column details for the time zone information storage.

[NOTE]
====
Storing the zone offset might be problematic for future timestamps as zone rules can change.
An offset alone does not retain the rules of a named time zone.
If future scheduling depends on those rules, store the zone identifier separately.
For values which represent only an instant, `DEFAULT` or `NORMALIZE_UTC` avoids relying on preservation of the original offset.

With temporal preservation enabled (the default), an inline `ZonedDateTime` mapping

[[basic-lob]]
==== Handling LOB data

The `@Lob` annotation specifies that character or binary data should be written to the database
using the special JDBC APIs for handling database LOB (Large OBject) types.

[NOTE]
====
JDBC LOB handling varies between drivers. Hibernate accounts for these differences where possible,
but LOB mappings may require driver-specific configuration or handling beyond the scope of this guide.
====

[IMPORTANT]
====
For databases with no `CLOB` type, attributes of type `java.sql.Clob` are unsupported.
Use a materialized type like `String` or `char[]` instead.
====

A LOB can be represented in the Java domain model in two ways:

- using a special JDBC-defined _LOB locator type_, or
- using a regular "materialized" type like `String`, `char[]`, or `byte[]`.

===== LOB Locator

The JDBC LOB locator types are:

* `java.sql.Blob`
* `java.sql.Clob`
* `java.sql.NClob`

These types represent references to off-table LOB data.
In principle, they allow JDBC drivers to support more efficient access to the LOB data.
Some drivers stream parts of the LOB data as needed, potentially consuming less memory.

However, `java.sql.Blob` and `java.sql.Clob` can be unnatural to deal with and suffer
certain limitations.
For example, it's not portable to access a LOB locator after the end of the transaction
in which it was obtained.

===== Materialized LOB

LOB data can also be represented by `String`, `char[]`, or `byte[]`.
This requires loading the entire LOB into memory when the value is retrieved.
The performance cost depends on the data size and JDBC driver behavior.

[TIP]
====
A database column of type `BLOB` or `CLOB` does not necessarily require a `@Lob` mapping.
The `@Lob` annotation is a special-purpose tool that should only be used when a default
basic mapping to `String` would result in unacceptable performance characteristics.
====

[[basic-nationalized]]
==== Handling nationalized character data

How nationalized character data is handled and stored depends on the underlying database.

Most databases support storing nationalized character data through the standardized SQL
NCHAR, NVARCHAR, LONGNVARCHAR and NCLOB variants.

Others support storing nationalized data as part of CHAR, VARCHAR, LONGVARCHAR
and CLOB.  Generally these databases do not support NCHAR, NVARCHAR, LONGNVARCHAR
and NCLOB, even as aliased types.

Ultimately Hibernate understands this through `Dialect#getNationalizationSupport()`

To ensure nationalized character data gets stored and accessed correctly, `@Nationalized`
can be used locally or `hibernate.use_nationalized_character_data` can be set globally.

[NOTE]
====
`@Nationalized` and `hibernate.use_nationalized_character_data` can be used regardless
of the specific database support for nationalized data and allows the application to
work portably across databases with varying support.
====

[IMPORTANT]
====
For databases with no `NCLOB` data type, attributes of type `java.sql.NClob` are
unsupported. Use `java.sql.Clob` (which `NClob` extends) or a materialized mapping like
`String` or `char[]` instead.

See also <<basic-lob>> regarding similar limitation for databases which do not support
explicit `CLOB` data-type.

[[basic-document-representation]]
===== Choosing a document representation

`@JdbcTypeCode(SqlTypes.JSON)` or `@JdbcTypeCode(SqlTypes.SQLXML)` selects a JDBC document mapping.
The attribute's Java type and the format mapper determine how its value is represented.
A structured value, such as a map, is serialized to a document and reconstructed when loaded.
A `String` value containing an already serialized JSON or XML document is treated as document text, not as a string to be serialized again.
For a JSON `String` mapping, the database may normalize whitespace or object-key ordering, so the original textual formatting is not guaranteed to survive a round trip.
This differs from a plain `String` mapping to `VARCHAR`, even if that string happens to contain JSON.

----

A basic document value is mapped as one value. An <<embeddable-mapping-aggregate,aggregate embeddable>> additionally exposes its mapped component attributes to Hibernate.
Choose an aggregate embeddable when the document represents a mapped component with persistent attributes;
choose a basic document value when the application handles it as a single value.
Database document types, aggregate operations, and JSON/XML query functions have different dialect requirements.

[[basic-converter-selection]]
===== Converter selection and applicability

An `AttributeConverter<X,Y>` converts between the domain Java type `X` and a relational Java type `Y` that Hibernate can bind through JDBC.
It does not directly implement JDBC binding or extraction.
Declare a converter using `@Converter` and ensure that it is discovered or registered as part of the persistence unit.
`@Converter(autoApply=true)` applies it automatically to eligible mappings of its domain type; primitive types and their wrappers are treated as equivalent for this purpose.

An explicit `@Convert(converter=...)` selects a converter for a particular mapping, overriding automatic selection.
Use `@Convert(disableConversion=true)` to suppress automatic conversion:

[source,java,indent=0]
----
include::{root-project-dir}/hibernate-core/src/test/java/org/hibernate/orm/test/mapping/userguide/converters/ConverterSelectionTests.java[tag=guide-converter-selection]
----

With the package registration shown below, `automatic` uses `YesNoConverter`, `explicit` uses `NumericBooleanConverter`,
and `disabled` uses the default Boolean mapping.

When multiple converters could apply to the same type, select one explicitly instead of relying on discovery order.
Automatic application does not mean that any converter on the classpath is necessarily discovered.

Conversion applies to basic attributes, basic element-collection values, and basic map keys and values.
On a map, use `attributeName="key"` or `attributeName="value"` to select the converted part.
For an attribute inside an embeddable, use its attribute path when declaring a conversion on the embedding attribute.
For example:

[source,java,indent=0]
----
include::{root-project-dir}/hibernate-core/src/test/java/org/hibernate/orm/test/mapping/userguide/converters/ConverterSelectionTests.java[tag=guide-converter-map]
----

Jakarta Persistence excludes identifier attributes, version attributes, associations, and attributes explicitly annotated with `@Enumerated` or `@Temporal` from automatic conversion.
Explicitly applying converters to these mappings is not portable.
The same restrictions apply to the corresponding map keys.

[[basic-converter-registration]]
====== Registering converters externally

Hibernate's link:{doc-javadoc-url}org/hibernate/annotations/ConverterRegistration.html[`@ConverterRegistration`]
registers a converter without requiring changes to its class.
Its `autoApply` member defaults to `true` and overrides the converter's declared automatic-application policy.
Use `domainType` to specify the domain type for which the registration applies; omitting it uses the converter's inferred domain type.
This is useful for third-party converters or for refining application to a particular subtype.

[source,java]
----
@ConverterRegistration(converter = YesNoConverter.class, autoApply = true)
package com.example.model;

import org.hibernate.annotations.ConverterRegistration;
import org.hibernate.type.YesNoConverter;
----

Place registrations in `package-info.java` or `module-info.java` so Hibernate processes them before resolving attributes.
They register converters for the persistence unit; package placement is not a restriction to attributes declared in that package.
Class-level registrations are supported, but affect only mappings processed after the registration is encountered and do not revise earlier resolutions.
Avoid relying on that processing order.

`@ConverterRegistration` is repeatable.
Use repeated annotations or the explicit link:{doc-javadoc-url}org/hibernate/annotations/ConverterRegistrations.html[`@ConverterRegistrations`] container:

[source,java,indent=0]
----
include::{root-project-dir}/hibernate-core/src/test/java/org/hibernate/orm/test/mapping/userguide/converters/package-info.java[tag=guide-converter-registrations]
----

Here, `YesNoConverter` is automatically applied, while `PeriodStringConverter` is registered for explicit selection.
These registration annotations are Hibernate extensions.

Use an `AttributeConverter` to translate a domain value to an existing relational Java representation.
Use <<basic-mapping-composition,compositional mapping annotations>> to select Java/JDBC descriptors or a mutability plan.
Use <<basic-mapping-custom,`UserType`>> when the mapping needs custom JDBC handling beyond a value conversion.
See <<basic-jpa-convert-mutability>> for converted-value dirty checking.

[[mapping-generated]]
==== Generated properties

NOTE: This section talks about generating values for non-identifier attributes.  For discussion of generated identifier values, see <<identifiers-generators>>.

Generated attributes have their values generated as part of performing a SQL INSERT or UPDATE.  Applications can generate these
values in any number of ways (SQL DEFAULT value, trigger, etc).  Typically, the application needs to refresh objects that
contain any properties for which the database was generating values, which is a major drawback.

Applications can also delegate generation to Hibernate, in which case Hibernate will manage the value generation
and (potentialfootnote:[Only in-DB generation requires the refresh]) state refresh itself.

[IMPORTANT]
====
Only `@Basic` and `@Version` attributes can be marked as generated.

Whether a generated attribute is written in an `INSERT` or `UPDATE` depends on its generator.
In-memory generators produce values which Hibernate writes to the database.
For database-generated values, `@Generated` normally omits the value from the SQL statement, but `@Generated(writable = true)` includes the assigned value and retrieves the generated result.
An attribute generated only on insert may still be updated later by the application unless it is marked `@Immutable`.
====

Hibernate supports both in-VM and in-DB generation.  A generation that uses the current JVM timestamp as the
generated value is an example of an in-VM strategy.  A generation that uses the database's `current_timestamp`
function is an example of an in-DB strategy.

Generators declare the events for which they generate a value using `org.hibernate.generator.EventType`:

`INSERT`:: The value is generated when the entity is inserted.
`UPDATE`:: The value is generated when the entity is updated.
`FORCE_INCREMENT`:: A version value is generated when its increment is forced.

An annotation with an `event` member may select multiple events, such as `event = {INSERT, UPDATE}`.
Without a generator, the application supplies the attribute value.

Hibernate supports multiple ways to mark an attribute as generated:

* Using the dedicated generators provided by Hibernate
    * `@CurrentTimestamp` - <<mapping-generated-CurrentTimestamp>>
    * `@CreationTimestamp` - <<mapping-generated-CreationTimestamp>>
    * `@UpdateTimestamp` - <<mapping-generated-UpdateTimestamp>>
    * `@Generated` - <<mapping-generated-Generated>>
* Using a custom generation strategy - <<mapping-generated-custom>>


[[mapping-generated-CurrentTimestamp]]
===== `@CurrentTimestamp`

The `@CurrentTimestamp` annotation generates a timestamp for the events selected by its `event` member.
By default, it includes `INSERT`, `UPDATE`, and `FORCE_INCREMENT`.
Its default `source = DB` uses the database's `current_timestamp` function; `source = VM` uses the current JVM timestamp.

[[mapping-generated-Generated]]
===== `@Generated` annotation

The `@Generated` annotation marks a value as generated by the database and causes Hibernate to retrieve it after the configured events.
The default is `event = INSERT`; use `event = {INSERT, UPDATE}` to retrieve the value after both operations.
Values may come from a column default, a trigger, or an expression supplied using `@Generated(sql = ...)`.
With `writable = true`, Hibernate includes the assigned value in the SQL statement, allowing the database to transform it before Hibernate retrieves the result.
