Entity classes represent objects with persistent identity.
The following sections describe class requirements and how Hibernate accesses persistent attributes.
See <<identifiers>> for identifier mappings and <<domain-relational-mapping>> for table and column mappings.

[[entity-pojo]]
==== POJO Models

Section _2.1 The Entity Class_ of the _Jakarta Persistence specification_ defines its requirements for an entity class.
Applications that wish to remain portable across Jakarta Persistence providers should adhere to these requirements:

> - The entity class must be annotated with the `@Entity` annotation or declared as an `entity` in its XML descriptor.
>
> - The entity class must be a top-level class or a static inner class.
> An enum, record, or interface may not be designated as an entity.
>
> - The entity class must have a `public` or `protected` constructor with no parameters, which is called by the persistence provider runtime to instantiate the entity.
>
> - The entity class must be non-`final`. Every method and persistent instance variable of the entity class must also be non-`final`.
>
> An entity might be an abstract class, or it might be a concrete class.
> An entity may extend a non-entity class, or it may extend another entity class.
> A non-entity class may extend an entity class.
>
> The persistent state of an entity is represented by instance variables, which may correspond to JavaBeans properties.
> An instance variable may be directly accessed only within the methods of the entity, by the entity instance itself.
> An instance variable of an entity must _not_ be directly accessed by a client of the entity.
> The state of the entity is available to clients only through the methods of the entity--that is, via accessor (getter/setter) methods, or via other business methods.

Hibernate, however, is not as strict in its requirements. Differences from the list above include:

- Fields may be declared `final` in many cases; see <<entity-pojo-final-fields>> below.

- The constructor with no parameters may be declared with package visibility, or, when the <<chapters/pc/BytecodeEnhancement.adoc#BytecodeEnhancement,bytecode enhancer>> is used, it may be omitted completely.

- Final classes and classes with final methods are tolerated but not recommended unless the bytecode enhancer is used.


The following sections explain these requirements.

[[entity-pojo-final]]
==== Prefer non-final classes

A central feature of Hibernate is the ability to lazily load entity state via _proxies_.
This feature depends on:

- the entity class being non-`final` (or implementing an interface that declares the external operations of the entity), and
- the non-`private` methods and accessor methods being non-`final`.

Hibernate _can_ persist a `final` entity class that does not implement any interface, but it is then not able to use proxies for lazily fetching to-one associations to that entity type, limiting options for performance tuning.

The bytecode enhancer automatically makes any entity class non-`final`, along with all its methods.

[[entity-pojo-final-fields]]
==== Prefer non-final persistent fields

While the JPA specification requires persistent fields to be non-`final`, Hibernate tolerates `final` persistent fields.
However, `final` persistent fields are not guaranteed to work in every situation.

Hibernate typically instantiates entities using a no-argument constructor and then sets persistent fields individually through reflection.
Setting a `final` field through reflection is deprecated starting with JDK 26 and will be denied in a future JDK version.
When Hibernate detects `final` persistent fields that will need to be set through reflection, it logs a warning on boot.

The <<chapters/pc/BytecodeEnhancement.adoc#BytecodeEnhancement,bytecode enhancer>> automatically removes the `final` modifier from persistent fields,
resolving these warnings.
Alternatively, remove the `final` modifier from the persistent field declarations.

`final` fields are supported for types that use constructor-based instantiation:

* record types used as `@Embeddable` (including `@EmbeddedId`) or as `@IdClass`,
* embeddable or `@IdClass` types with an <<embeddable-instantiator,`@Instantiator`-annotated constructor>>,

since those are instantiated through their constructor without any reflective field mutation.

The configuration property `hibernate.mapping.final_persistent_fields` controls the behavior of this check.
Valid values are `warn` (the default), `error` (fail on boot), and `ignore` (suppress the check).

[[entity-pojo-constructor]]
==== Implement a no-argument constructor

The entity class should have a constructor with no parameters.
Both Hibernate and Jakarta Persistence require this.
Hibernate allows the constructor to be declared with `public`, `protected`, or package visibility.

The bytecode enhancer automatically adds a constructor with no parameters if it is missing.

Hibernate initializes and updates the version. Application code must not assign a new version to force an update.
An entity has at most one version attribute, declared on the entity or an inherited mapped superclass.
For an entity mapped to multiple tables, map the version to its primary table.

Jakarta Persistence supports `int`, `Integer`, `short`, `Short`, `long`, `Long`, `java.sql.Timestamp`, `java.time.Instant`, and `java.time.LocalDateTime` as version types.
Hibernate also supports additional version mappings, including custom `UserVersionType` implementations.
For conflict handling, timestamp versions, and lock modes, see <<locking>>.
For database-generated versions, see <<mapping-generated>> and the locking guidance.
