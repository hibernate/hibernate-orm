[[mapping-model-pojo-equalshashcode]]
==== Implementing `equals()` and `hashCode()`

[NOTE]
====
This section discusses managed, transient, and detached entities and their relationship to a Hibernate `Session`.
These concepts are explained in the <<chapters/pc/PersistenceContext.adoc#pc,Persistence Context>> chapter.
====

The need for `equals()` and `hashCode()` depends on how the domain model uses entities.
A user-defined identifier class, such as a composite identifier class, must implement these methods based on its identifier values.
For entity classes, the choice depends on whether instances representing the same database row need to compare as equal.

The default implementations inherited from `Object` use Java object identity.
Separate instances therefore compare as unequal even when they represent the same row.
Within a single `Session`, Hibernate guarantees that persistent identity and Java identity coincide.

The issue here is a conflict between the use of the generated identifier, the contract of `Set`, and the equals/hashCode implementations.
`Set` says that the equals/hashCode value for an object should not change while the object is part of the `Set`.
But that is exactly what happens when `equals()` and `hashCode()` are based on a generated identifier which is assigned after the entity is added to the set.
The timing of identifier assignment depends on the generation strategy: a sequence-generated identifier may be assigned during `persist()`, while an identity-generated identifier requires execution of the insert.

Note that this is just a concern when using generated identifiers.
Assigned identifiers avoid this problem if the identifier is set before the entity is added to the `Set`.

Another option is to force the identifier to be generated and set prior to adding to the `Set`:

[[domain-equality-proxies]]
===== Equality, proxies, and inheritance

An entity reference may be represented by a lazy proxy whose runtime class differs from the entity class.
An equality implementation using `getClass()` can therefore reject a proxy for the same entity.
Direct field access on a proxy can also observe uninitialized state; use accessor methods when comparing persistent values.
Accessing a business key may initialize the proxy and execute a database query, so equality evaluation is not necessarily free of database access.
An uninitialized detached proxy cannot be assumed to expose those values without an associated session.

----

`instanceof` accepts subclass proxies. In a mapped inheritance hierarchy, however, accepting every subtype can produce inappropriate equality or violate symmetry if subclasses define different rules.
Exact-type checks require a deliberate proxy-aware type strategy and may also require initialization.
See <<concrete-proxy>> for concrete proxies and subtype resolution.

The business key must be assigned before an instance is added to a hashed collection and remain stable while it is a member.
A database uniqueness constraint does not itself guarantee a stable Java hash code.
This example deliberately has no natural-id setter; it is not a universal equality implementation for every entity hierarchy.

The appropriate equality strategy depends on the entity's identifier and how the application uses its instances.

[TIP]
====
A natural id is a useful basis for `equals()` and `hashCode()`, but some entities have only a generated identifier.

Using a generated identifier for equality requires special handling:

- Return a constant from `hashCode()` so that assigning the identifier does not change the hash code.
- Compare identifiers for equality only for non-transient entities.
====
