[[events]]
== Interceptors and Events
:example-dir-event: {core-project-dir}/src/test/java/org/hibernate/orm/test/events
:example-dir-event-resources: {core-project-dir}/src/test/resources/org/hibernate/orm/test/events

Callbacks let an application react to entity lifecycle changes and database operations, inspect or adjust state, and integrate with Hibernate's event processing.
Choose the mechanism according to the information and control the application needs.

[[events-choosing]]
=== Choosing a callback mechanism

[cols="1,2,2",options="header"]
|===
|Mechanism |Use it for |Contract and scope
|Jakarta Persistence callbacks |Entity initialization, state validation, and lifecycle notifications |Standard annotations and listener registration; entity callbacks receive an entity, not Hibernate's previous-state arrays
|Hibernate `Interceptor` |Inspecting or adjusting entity state and observing collection changes |Hibernate callbacks with state arrays; shared across sessions or selected/created per session
|Native event listeners |Integrating with or extending Hibernate's event processing |Hibernate SPI; listeners participate in ordered event groups and may replace essential default behavior
|===

Start with persistence callbacks when they provide the required information.
An interceptor can also inspect the previous state supplied for dirty checking and observe collection changes.
Native listeners offer more control over Hibernate processing and require more knowledge of its internals.

A notification after an insert or delete does not establish that the transaction committed.
Logging changes is different from maintaining persistent revision history; see <<envers>> for revision auditing and <<transactions-completion>> for transaction completion and failures.

[[events-jpa-callbacks]]
=== Jakarta Persistence callbacks

Jakarta Persistence supports callbacks declared on entities and mapped superclasses, separate listener classes, and listeners registered programmatically.
The following groups distinguish managed-entity lifecycle operations from database operations.

[[events-callback-types]]
==== Callback events and timing

[cols="1,3",options="header"]
|===
|Callback |When it applies
|`@PrePersist` |Before an entity becomes persistent through `persist()` or creation during `merge()`
|`@PostPersist` |After the entity's database insertion; it may be deferred until flush
|`@PreRemove` |Before an entity is marked for removal
|`@PostRemove` |After the entity's database deletion; it may be deferred until flush
|`@PreMerge` |Before state is copied from the object supplied to `merge()`; the callback receives that object, not the managed result
|`@PreInsert`, `@PostInsert` |Before and after inserting entity data
|`@PreUpdate`, `@PostUpdate` |Before and after updating entity data
|`@PreDelete`, `@PostDelete` |Before and after deleting entity data
|`@PreUpsert`, `@PostUpsert` |Before and after the upsert operation, rather than separate insert/update notifications for its database outcome
|`@PostLoad` |After loaded or refreshed state has been assigned to the entity instance
|===

The insert/delete/upsert pairs and `@PreMerge` are additions in Jakarta Persistence 4.0.
Database-operation callbacks also apply to the corresponding stateless operations; they do not require a managed entity in a persistence context.
Hibernate also invokes the older persist/remove callback annotations for stateless insert/delete operations.
Use the operation-specific annotations when expressing database-operation intent, and see <<batch-stateless>> for stateless processing.

For a stateful persistence context, `@PrePersist` and `@PreRemove` run during the lifecycle operation, while SQL and its post-operation callbacks may run later during <<flushing,flushing>>.
Primary keys generated with `SEQUENCE`, `TABLE`, or `UUID` are available to `@PrePersist`; an `IDENTITY` key is available after insertion.
Do not depend on a universal ordering of callbacks relative to cascades to other entities.
See <<pc-persist>>, <<pc-remove>>, and <<pc-merge>> for those operations.

[[events-callback-contracts]]
==== Entity callback contracts

A callback method returns `void` and may have public, protected, package, or private access, but must not be static or final.
An entity or mapped-superclass method has no arguments.
A listener method has one argument whose type is the entity class or a compatible supertype, including `Object`.
Listener classes have a public no-argument constructor and can receive CDI injection when the container is configured; see <<beans>>.
This support does not make the entity instances themselves CDI-managed objects.

A callback may modify the entity's nonrelationship state, as the normalization example does.
Portable callbacks should not execute entity-manager or query operations, access other entities, or modify relationships within the same persistence context.
A runtime exception stops further callback processing and marks a joined transaction for rollback.
Catching it does not restore the transaction or persistence context to a usable state; see <<pc-exception-handling>>.

Listener instances can serve multiple entities and concurrent sessions.
Keep mutable operation-specific state out of shared listeners; immutable configuration and thread-safe injected dependencies are appropriate fields.
The invocation logs in these tests are fixtures, not examples of concurrent application storage.

Bulk HQL/Criteria mutations and direct SQL bypass ordinary per-entity lifecycle callbacks.
The database-operation callback annotations do not turn a listener into a database trigger.
See <<query-mutations>>, <<sql>>, and <<database-jdbc-work>> for these execution boundaries.

[[events-callback-ordering]]
==== Ordering and inheritance

For a given entity callback event, Hibernate invokes the following groups in order:

. XML persistence-unit default listeners, in declaration order.
. Discovered `@EntityListener` listeners; do not depend on a relative order among these listeners.
. Module-level listeners, followed by package-level listeners, in each declaration's order.
. Listeners associated with the entity hierarchy, with superclass registrations before subclass registrations and declaration order within each registration.
. Callback methods on the entity hierarchy, with superclass callbacks before subclass callbacks.
. Runtime callbacks registered through <<events-runtime-listener-example,`EntityManagerFactory.addListener()`>>, in registration order, after the declared callbacks above.

Overriding a callback method changes which inherited method is eligible; annotate the overriding method for the callback event it is intended to handle.
XML mappings may override annotation-based callback declarations and ordering.
See the Jakarta Persistence specification's
https://jakarta.ee/specifications/persistence/4.0/jakarta-persistence-spec-4.0-M4.html#a2251[callback ordering rules].

[[events-exclude-default-listener]]
===== Excluding listeners

{jpaJavadocUrlPrefix}ExcludeDefaultListeners.html[`@ExcludeDefaultListeners`] excludes default listeners declared in XML and on package/module descriptors.
It may be declared on an entity or mapped superclass, and the exclusion applies to its subclasses.
The equivalent XML element is `<exclude-default-listeners/>`.
Discovered `@EntityListener` registrations are separate from these defaults and are not suppressed by this exclusion.

{jpaJavadocUrlPrefix}ExcludeSuperclassListeners.html[`@ExcludeSuperclassListeners`] excludes listeners associated with superclasses.
It does not exclude package/module or XML default listeners, or callback methods declared on the entity hierarchy itself.
Neither annotation removes the entity's own explicitly associated listeners or callback methods.

[[events-unit-lifecycle]]
==== Persistence-unit lifecycle callbacks

Jakarta Persistence 4.0 also provides `@PostCreate` and `@PreClose` callbacks for the creation and closing of an `EntityManagerFactory`, `EntityManager`, or `EntityAgent`.
Declare these methods on a discovered `@EntityListener` class.
Each method returns `void` and takes one parameter of the specific type whose lifecycle it observes: `EntityManagerFactory`, `EntityManager`, or `EntityAgent`.
These callbacks observe persistence infrastructure, rather than changes to an entity or the completion of a transaction.

[[events-interceptors]]
=== Hibernate interceptors

link:{doc-javadoc-url}org/hibernate/Interceptor.html[`Interceptor`] provides stateful callbacks such as `onLoad()`, `onPersist()`, `onRemove()`, and `onFlushDirty()`, plus collection callbacks for recreation, removal, and updates.
Stateless operations use `onLoad()`, `onInsert()`, `onUpdate()`, `onUpsert()`, and the stateless `onDelete()` overload.
Use the current `onPersist()`/`onRemove()` methods instead of the deprecated stateful `onSave()`/`onDelete()` callbacks.

[[events-interceptor-contracts]]
==== Inspecting and adjusting state

The indexes of an interceptor's state, property-name, and type arrays correspond.
For callbacks returning a boolean, return `true` if the callback changes the mutable state array and `false` when it only observes state.
Do not modify `previousState`, and do not assume a previous-state snapshot is always available.

[[events-interceptor-registration]]
==== Registration, scope, and ownership

[cols="2,2,3",options="header"]
|===
|Registration |Values |Behavior
|`hibernate.session_factory.interceptor` |Instance, class, or class name |One shared interceptor; classes are resolved through managed-bean support
|`hibernate.session_factory.session_scoped_interceptor` |Class, class name, or `Supplier<Interceptor>` |Automatic per-session acquisition or a supplier call for each session; an instance is not accepted here
|Session/stateless-session builder `interceptor(instance)` |Instance |Explicit selection for that session, replacing the configured interceptor
|===

Both settings being nonnull causes `ConflictingInterceptorSettingsException`; they do not compose two interceptors.
Shared interceptors must be thread-safe and must not store mutable session-specific state.
A supplier should return appropriately separate instances when those instances hold session-specific state.

[[events-interceptor-cdi]]
==== CDI and managed interceptor lifecycles

Class and class-name registrations use Hibernate's managed-bean infrastructure.
With a configured CDI `BeanManager` or custom `BeanContainer`, this supports dependency injection and lifecycle callbacks.
Without an external container, Hibernate constructs the class itself; that fallback does not supply CDI injection.
Register the interceptor class explicitly: enabling CDI does not automatically select an `Interceptor` implementation.

[[events-interceptor-cdi-readiness]]
===== CDI readiness

See <<beans-cdi>> for `jakarta.persistence.bean.manager`, `hibernate.delay_cdi_access`, and extended access, or <<beans-custom-container>> for `hibernate.resource.beans.container`.
Class-based interceptor acquisition does not require `hibernate.cdi.extensions=true`.
The factory can retain a bootstrap-safe bean reference without immediately obtaining its interceptor instance.
This does not mean every access mode initializes all beans at the same time: extended access can initialize registered references when the manager signals readiness.

CDI must be usable before an interceptor instance is needed for reliable injection.
Do not depend on opening sessions before CDI readiness or on fallback construction producing an injected object.
The tests exercise immediate, delayed, and extended access with a real CDI container, verify shared and per-session identities, and check destruction at the appropriate lifecycle boundary.

[[events-events]]
=== Native event listeners

Native listeners implement interfaces such as `LoadEventListener` and participate in Hibernate's event processing.
`org.hibernate.event.spi.EventType` is a class exposing typed constants such as `LOAD`, `PERSIST`, `PRE_INSERT`, and `POST_LOAD`.
These include both requests, such as loading an entity, and notifications around database operations; they are not a one-to-one list of public session methods.

[[events-native-registration]]
==== Registration and ordering

Register listeners during bootstrap using an `Integrator` and the `EventListenerRegistry`.
`prependListeners()` adds listeners before the existing group, `appendListeners()` adds them after it, and `setListeners()` replaces the group.
If an integration may register a listener repeatedly, use the registry's duplication handling to define whether duplicate registrations are rejected, retained, or replaced.

[[events-mixing-events-and-interceptors]]
==== Preserving default event processing

Hibernate's default listeners implement persistence behavior and invoke interceptors and persistence callbacks where appropriate.
For example, save processing calls `Interceptor.onPersist()`, and `DefaultPreLoadEventListener` calls `Interceptor.onLoad()` before assigning loaded state.

Prefer adding listeners around the defaults when observing an event.
Replacing a group can remove loading, state-transition processing, and callback invocation.
A replacement must preserve every required contract; extending or delegating a default implementation can help, but does not automatically make arbitrary replacement behavior equivalent.
Do not manually invoke interceptor callbacks as an application notification API.
