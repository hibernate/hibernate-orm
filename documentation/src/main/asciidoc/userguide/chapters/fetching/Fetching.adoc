Fetching loads persistent state so the application can use it.
A fetch plan determines which state a particular operation needs and how Hibernate should retrieve it.
Loading unnecessary columns or rows increases transfer, processing, and memory costs;
loading too little state can lead to additional queries when the application navigates associations.

This chapter explains fetching behavior and the choices used to build and verify a fetch plan.
See <<associations>> and <<collections>> for mapping declarations, <<pc>> for entity lifecycle,
and <<hql>> for executing queries.

[[fetching-basics]]
=== Fetch timing, method, and scope

Fetch timing answers _when_ state is needed:

* `EAGER` requests that state be available when loading completes.
* `LAZY` permits loading to be delayed until the state is accessed or explicitly initialized.
  Jakarta Persistence defines lazy fetching as a hint, so it is not a guarantee that no state is retrieved early.

The fetch method answers _how_ Hibernate retrieves that state:

[cols="1,3",options="header"]
|===
|Method |SQL behavior
|Join |Retrieve associated state with the owner using a SQL join.
|Individual select |Retrieve an entity or collection using a secondary select.
|Batch |Retrieve several entities or owner collections together using their identifiers.
|Subselect |Retrieve associated state using a subquery based on the query that loaded the owners.
|===

An individual select may satisfy eager or lazy timing. It is susceptible to the _N+1_ problem:
one query loads the owners, followed by many separate queries for their associated state.
It does not necessarily cause N+1; associated entities might already be loaded or available from a cache.
Batch and subselect fetching can reduce secondary queries without joining all associated rows into the owner query.
Join fetching makes the joined state available immediately.

Mappings define default timing and methods. Session settings supply defaults for certain optimizations;
query fetch joins, entity graphs, and fetch profiles customize an operation's plan.
A plan does not promise an exact number of SQL statements independent of context state, caches, dialect capabilities,
and other mapping requirements. Counts shown below describe the controlled examples.

[[fetching-fetch-annotation]]
==== Hibernate mapping fetch methods

`org.hibernate.annotations.Fetch` selects a mapping-level method using `org.hibernate.annotations.FetchMode`:

`SELECT`:: Use a secondary select, with timing determined by the association mapping.
`JOIN`:: Join the associated state when loading the owner directly. This implies eager loading,
  even if the association declares `fetch=LAZY`.
`SUBSELECT`:: Use a secondary subquery for grouped loading. Hibernate supports this for collections and to-one associations;
  see <<fetching-fetchmode-subselect>> for their behavior.

Do not confuse this annotation with `jakarta.persistence.Fetch`, which customizes an attribute in a named entity graph;
see <<fetching-graph-options>>.

[[fetching-lazy-basic]]
==== Lazy basic attributes and groups

Enhancement allows individual attributes or groups of attributes to be loaded on access.
Unlike an entity proxy, which delays loading the entity itself, attribute loading can defer selected state after the entity is initialized.
A lazy basic mapping needs enhancement for Hibernate to defer that attribute's loading.

Lazy basic attributes may be loaded together as a "lazy group".
By default, lazy basic attributes belong to the same group: accessing one loads the other basic attributes in that group.
Use `@LazyGroup` to assign them to separate groups.
To-one associations follow separate proxy and enhanced-reference loading rules; `@LazyGroup` is not a general way to control their initialization.
Lazy collections normally initialize independently.

==== Collections, pagination, and row multiplication
[[fetching-query-limitations]]

Joining a collection repeats the owner columns for each joined collection row.
Fetching several independent collections in parallel can multiply those rows into a large Cartesian product,
even when Hibernate returns each root entity only once. Fetching multiple bags in the same plan may raise
`MultipleBagFetchException`; see <<collections-bag>> for bag semantics.
Choose the collections needed by the operation, and consider batch or subselect fetching for the others.

Avoid applying offset/limit pagination to a query that fetches a collection.
Limiting joined SQL rows does not provide a complete page of owners with complete collections;
Hibernate may fetch all matching rows and apply the limit in memory.
// suppress inspection "AsciiDocLinkResolve"
The setting <<settings-hibernate.query.fail_on_pagination_over_collection_fetch,`hibernate.query.fail_on_pagination_over_collection_fetch`>>
can turn this usage into an error instead.

For a page of owners with a collection, first select the ordered page of owner identifiers without the collection fetch.
Then fetch the required state for those identifiers, without applying another collection-fetch limit.
An `IN` restriction does not preserve the identifier list's order: restore the intended ordering in the query or application.
The two operations do not create an atomic snapshot unless the transaction and database provide the necessary consistency.
See <<jpql-pagination>> for pagination APIs.

Collection fetch joins also complicate streaming and scrolling, since multiple rows may represent one owner.
See <<hql-api-incremental>> for query resource handling and the Query Language guide for fetch-join restrictions.

[[fetching-strategies-dynamic-fetching-entity-graph]]
=== Entity graphs

An entity graph describes an operation's attribute paths. It is rooted at an entity type;
subgraphs describe the state needed below a node.
Ordinarily, adding an attribute node requests eager state. A graph does not prescribe that all requested state
must come from one SQL join.

fetch graph:: Requested nodes override the default plan; unspecified attributes are treated as lazy,
  subject to mandatory state and the provider's ability to defer loading.
load graph:: Requested nodes override the default plan; unspecified attributes retain their mapped timing.

Explicit node options may request lazy state, and removing a node marks it for lazy loading even in a load graph.
Identifiers and required version state still identify the entity. Applying a graph does not unload state
already initialized in the persistence context.

==== Construction and named graphs

Construct a graph using `EntityManager.createEntityGraph(Entity.class)` or declare a named graph using
`@jakarta.persistence.NamedEntityGraph` and `@NamedAttributeNode`.
Retrieve a named graph using `getEntityGraph()`; use the overload accepting the root class for a typed result.

===== Modern and legacy syntax

The modern form places an attribute's subtype after a colon:

[source,text]
----
responsibleParty:Corporation(ceo)
responsibleParty(taxIdNumber), responsibleParty:Corporation(ceo), responsibleParty:NonProfit(sector)
----

For a graph rooted at `LegalEntity`, modern root-subtype paths may be written as:

[source,text]
----
:Corporation(ceo), :NonProfit(sector)
----

Legacy syntax places the subtype inside the parentheses:

[source,text]
----
responsibleParty(Corporation: ceo)
----

Repeated paths combine their requested nodes and subgraphs.
The deprecated link:{doc-javadoc-url}org/hibernate/cfg/GraphParserSettings.html#GRAPH_PARSER_MODE[`hibernate.graph_parser_mode`] setting selects the syntax:
`modern` uses the preferred syntax, while `legacy` remains the current default for compatibility.
The default is not changed merely because the setting is deprecated.
Modern root-subtype syntax requires modern mode.
Deprecated parse overloads which infer the root from an entity-name prefix in the text do not support modern mode;
pass the root class separately instead.

[[fetching-strategies-dynamic-fetching-entity-graph-merging]]
===== Combining graphs

`EntityGraphs.merge()` combines graphs of the same root type into a union of attribute paths and subgraphs.
When input graphs specify conflicting options on the same node, an option from a later input graph
replaces an earlier option of the same type. This applies to fetch timing, fetch methods, and batch sizes,
so input order matters when combining graphs with such overrides.
A later `FetchType.LAZY` option also clears the node's earlier subgraphs, so those subgraphs
are not retained in the combined graph.

[[fetching-strategies-dynamic-fetching-entity-graph-parsing-annotation]]
===== Named textual graphs

`@org.hibernate.annotations.NamedEntityGraph` declares a graph using text instead of attribute-node annotations.
It may appear on an entity class, package, or module. An entity class supplies the implicit root;
for a package or module declaration, specify `root` explicitly:

[source,java]
----
@org.hibernate.annotations.NamedEntityGraph(
    name = "Book.detail",
    root = Book.class,
    graph = "title,author(name)"
)
package com.example.model;
----

The annotation uses the selected parsing syntax, not always the legacy parser.
For package/module declarations, legacy compatibility permits an entity-name prefix in graph text when no root is supplied,
with a deprecation warning. Omitting both an explicit root and a resolvable legacy prefix fails;
modern mode requires an explicit root for these declarations.

[[fetching-strategies-dynamic-fetching-profile]]
=== Fetch profiles

A fetch profile is a named set of association overrides, not a graph rooted at one entity.
Its overrides apply wherever the affected association is encountered during a load influenced by that profile.
`@FetchProfile` declares the profile, and `@FetchProfileOverride` can contribute an override directly on an association.
Overrides specify both method and timing.

Enable a profile for the session using `enableFetchProfile()` and restore the previous activation state after the operation.
Queries and natural-id loaders provide operation-specific `enableFetchProfile()` and `disableFetchProfile()` controls.
`EnabledFetchProfile` may also be passed as a find option, but currently enables the profile on the session;
restore the previous activation state when using that form.

[[fetching-batch]]
=== Batch and subselect fetching

==== Batch fetching

Batch fetching groups otherwise separate loads for state already represented in the persistence context.
For entities, it groups eligible unloaded entity identifiers. For collections, it groups owner identifiers
for unloaded collections of the same role.

Use link:{doc-javadoc-url}org/hibernate/annotations/BatchSize.html[`@BatchSize`] on an entity type or collection mapping,
// suppress inspection "AsciiDocLinkResolve"
or set <<settings-hibernate.default_batch_fetch_size,`hibernate.default_batch_fetch_size`>> as the factory default.
`Session.setFetchBatchSize()` overrides the session default; a negative value inherits the factory default,
a value greater than one enables batching, and zero or one disables that default batching.
Explicit mapping or graph-node batch sizes can still govern particular associations.

[[fetching-fetchmode-subselect]]
==== Subselect fetching

Collection subselect fetching records the owner keys produced by a particular loading query.
Initializing one unloaded collection can initialize the same collection role for that recorded owner group,
not for every managed owner of that role from unrelated queries.
The secondary select uses a subquery based on the original owner restriction.
It does not simply run the application's owner-loading operation again.

=== Choosing and verifying a fetch plan
[[fetching-plan-selection]]

[cols="2,3,3",options="header"]
|===
|Use case |Starting point |Tradeoff to check
|One entity and a few to-one associations |Direct loading with a graph or joined associations |Required state, context/cache hits, and extra selects
|A bounded collection needed immediately |A fetch join or graph |Repeated owner columns and total joined rows
|Several independent collections |Fetch the principal paths and use batch/subselect loading for others |Cartesian multiplication and multiple-bag restrictions
|A page of owners with associated state |Page owner identifiers, then load their required state |Owner ordering, complete collections, and consistency between operations
|Opportunistic navigation across loaded owners |Lazy loading with batch fetching, or subselect groups from a suitable query |How much of each group is actually needed
|Read-only values for a screen or export |Scalar or DTO projection |Avoiding unnecessary entity/association materialization
|===

Measure both the number of statements and the number of rows transferred.
One very large joined result may cost more than several smaller queries; batching is not universally inferior to a fetch join or projection.
// suppress inspection "AsciiDocLinkResolve"
The <<settings-hibernate.max_fetch_depth,`hibernate.max_fetch_depth`>> setting bounds nested outer-join fetching,
but does not replace a deliberate operation-specific plan.

[[fetching-locking-interaction]]
==== Fetch plans and lock requests

A fetch plan selects state to retrieve; a lock request governs concurrency protection.
Applying an entity graph does not by itself lock the object graph.
`PessimisticLockScope.FETCHED` relates protection to state fetched by the locking operation;
see <<locking-jpa-query-hints,lock scope>> for the contract and examples. It is not a recursive lock of every reachable entity.

Lock requests can affect the available fetching methods and SQL statement count.
See <<fetching-batch>> for entity batch fetching and <<locking-LockMode>> for requesting locks.
<<locking-follow-on,Follow-on locking>> may issue acquisition statements after selection;
these statements acquire protection rather than initialize associations, so their count is distinct from an association-loading N+1 pattern.

An agreed <<locking-graph-root,graph-root coordination protocol>> is separate from an entity graph used for loading.
Choose the required state without assuming that eager loading or follow-on acquisition automatically provides the protocol's read/lock ordering.
A lock request does not refresh objects already held in the persistence context; see <<pc-refresh>> for reloading them.

==== Lazy state and explicit initialization
[[fetching-initialization]]

Hibernate represents unloaded associations using proxies, persistent collection wrappers, or enhanced attributes.
Navigating that state may issue SQL using the associated open persistence context.
After detachment or context closure, accessing still-unloaded state can raise `LazyInitializationException`.
Choose the required plan before leaving the context, or explicitly load the state while the context is available.
See <<pc-detach>> for detachment and <<BytecodeEnhancement>> for enhancement mechanisms.

Use `PersistenceUnitUtil.isLoaded(entity, attribute)` to inspect an attribute without deliberately initializing it.
The factory utility and Hibernate helpers offer the following checks; attribute-name checks avoid accessing an attribute merely to inspect its loading state.

`PersistenceUnitUtil.load(entity, attribute)` loads an attribute slot, such as a lazy enhanced field.
If that slot holds an associated proxy, initialize the proxy itself when its entity state is needed.
`Hibernate.isInitialized()` and `Hibernate.initialize()` are provider-specific alternatives for a proxy or collection.

Initializing a collection loads its contents, but does not recursively initialize every association on each element.

`EntityAgent` and Hibernate's `StatelessSession` do not keep an associated persistence context for automatic lazy loading.
Request required state using a graph or explicitly pass an association to `EntityAgent.fetch()`;

Use SQL inspection and <<statistics>> to measure loads, and <<caching>> to understand cache hits.
Statement counts should be collected with known initial context/cache state; fixture inserts and cleanup are separate work.
