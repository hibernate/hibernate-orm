[[flushing]]
=== Flushing
:example-dir-flushing: {core-project-dir}/src/test/java/org/hibernate/orm/test/flush
:flushing-extrasdir: extras

Flushing synchronizes pending persistence-context changes with the database using SQL inserts, updates, deletes, and collection operations.
It does not commit the transaction: flushed changes may still be rolled back. Conversely, committing a transaction does not synchronize pending state when automatic flushing is disabled.
See <<transactions,transactions>> for transaction boundaries and <<batch-jdbcbatch,batching>> for JDBC statement grouping.

[[flushing-explicit]]
==== Explicit synchronization

Call `EntityManager.flush()` or `Session.flush()` to synchronize pending state explicitly.
A transaction must be active, and a JPA context must be joined to it. An unsynchronized context must first join using `joinTransaction()`.
Outside an active transaction, or before joining it, automatic query flushing does not occur.
Calling `flush()` does not initialize every lazy association or reload managed objects.

[[flushing-modes]]
==== Context and query flush modes

Use `EntityManager.setFlushMode()` for Jakarta Persistence modes or `Session.setHibernateFlushMode()` for Hibernate modes.

[cols="1,1,3",options="header"]
|===
|Jakarta Persistence |Hibernate |Automatic synchronization
|`AUTO` |`AUTO` |Flushes on commit and before queries when needed to make relevant pending changes visible.
|`COMMIT` |`COMMIT` |Flushes on commit; Hibernate does not normally flush before queries with this effective mode.
|`EXPLICIT` |`MANUAL` |Requires explicit synchronization; pending state is not automatically flushed on commit.
|— |`ALWAYS` |Flushes on commit and before every query executed within an active transaction.
|===

Jakarta Persistence leaves query visibility under `COMMIT` unspecified. Do not rely on pending changes being visible to such a query.
These modes control flushing; they do not suppress inserts needed to obtain generated identifiers.
See <<identifiers-generators,identifier generation>> and <<flushing-settings,deferred identity inserts>>.

`Query.setQueryFlushMode()` controls synchronization before a particular query:

`DEFAULT`:: Uses the current context mode.
`FLUSH`:: Requests a flush before the query, even if the context normally defers synchronization.
`NO_FLUSH`:: Suppresses automatic flushing for that query, even if the context normally uses `AUTO` or `ALWAYS`.

A query override does not change the context mode or whether commit triggers flushing.
The older query-level `setFlushMode()` API is also supported; prefer `setQueryFlushMode()` when expressing a query-specific synchronization requirement.
For Hibernate query configuration, see <<hql,queries>>.

[[flushing-auto-triggers]]
==== Automatic query flushing at a glance

The following table assumes an active transaction, a joined context, and `QueryFlushMode.DEFAULT`:

[cols="2,2,2",options="header"]
|===
|Query |Context `AUTO` |Context `COMMIT`, `EXPLICIT`, or Hibernate `MANUAL`
|HQL/JPQL |Flushes when query spaces overlap pending changes. |Does not automatically flush before the query.
|Native SQL without synchronized spaces, JPA bootstrap |Flushes before execution. |Does not automatically flush before the query.
|Native SQL without synchronized spaces, native bootstrap |Does not automatically flush before the query. |Does not automatically flush before the query.
|Native SQL with synchronized spaces |Flushes when those spaces overlap pending changes. |Does not automatically flush before the query.
|===

Hibernate `ALWAYS`, or the query override `FLUSH`, requests flushing before query execution regardless of overlap.
`NO_FLUSH` suppresses query-triggered flushing. These distinctions depend on bootstrap and query configuration,
not on whether the same session is accessed through an `EntityManager` or `Session` variable.

[[flushing-always]]

[[flushing-settings]]
==== Execution planning and flush configuration

SQL execution order is determined by the action queue, not by the order of `persist()`, attribute changes, and `remove()` calls.
Hibernate provides two queue implementations, selected by the {doc-javadoc-url}org/hibernate/cfg/FlushSettings.html#FLUSH_QUEUE_TYPE[`hibernate.flush.queue.type`] setting:

* `graph` (the default) uses the graph-based action queue, which plans execution using dependency information such as foreign keys and unique keys.
* `legacy` is the traditional action queue implementation with fixed action ordering and legacy sorting behavior

The graph queue plans work using dependencies. Constraint cycles and the database's deferral capabilities can affect execution; the planner does not make every otherwise-invalid constraint change possible.
The following settings control batching and graph planning. See also the <<settings,configuration reference>>:

{doc-javadoc-url}org/hibernate/cfg/BatchSettings.html#STATEMENT_BATCH_SIZE[`hibernate.jdbc.batch_size`]::
	Specifies the maximum number of statements Hibernate will add to a JDBC batch before executing that batch.
	Set it at the factory level or override it for an individual `Session`. Values greater than one enable useful batching; see <<batch-jdbcbatch,JDBC batching>>.

{doc-javadoc-url}org/hibernate/cfg/FlushSettings.html#ORDER_BY_FOREIGN_KEY[`hibernate.flush.plan.foreignkey.order`]::
	Controls whether the graph-based flush planner orders operations using foreign-key dependencies.
	This setting defaults to `true`.
	Disabling it reduces the dependency information available to the planner and should generally only be useful for isolating planner behavior.

{doc-javadoc-url}org/hibernate/cfg/FlushSettings.html#ORDER_BY_UNIQUE_KEY[`hibernate.flush.plan.uniquekey.order`]::
	Controls whether the graph-based flush planner orders operations using unique-key dependencies.
	This setting defaults to `true`.
	Unique-key ordering helps avoid transient constraint violations when rows exchange or reuse unique values during the same flush.

{doc-javadoc-url}org/hibernate/cfg/FlushSettings.html#GRAPH_DEFER_IDENTITY_INSERTS[`hibernate.flush.queue.graph.defer_identity_inserts`]::
	Controls whether the graph-based action queue defers `IDENTITY` inserts into the normal flush plan.
	This setting defaults to `false`, preserving the legacy behavior where non-delayed `IDENTITY` inserts execute immediately so generated identifiers are available after `persist()`.
	When set to `true`, `IDENTITY` inserts are planned with the rest of the flush work and identifiers become available when the planned insertions execute.

See <<batch-jdbcbatch,JDBC batching>> for batch sizing and <<identifiers-generators,identifier generators>> for insertion and identifier availability.
