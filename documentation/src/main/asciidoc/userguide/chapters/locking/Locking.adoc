[[locking-basics]]
=== Locking concepts and transaction boundaries

Optimistic locking detects conflicting changes; pessimistic locking acquires database locks to prevent conflicting access while a transaction is active.
Both interact with database isolation, but neither replaces deliberate <<transactions,transaction boundaries>> nor validation of application invariants.
Hibernate uses database concurrency mechanisms and does not lock Java objects in memory.
These guarantees assume at least `READ_COMMITTED` transaction isolation; see <<transactions-concurrency,isolation and concurrency declarations>>.

Optimistic locking::
A version or comparison with previously loaded values detects that a row changed after it was read.
Automatic checks normally protect updates and deletes.
An entity that was only read (not mutated) is not automatically validated just because it has a version attribute; request an explicit optimistic lock when the operation depends on validating that read.
A conflict may be reported during flush or transaction completion, depending on the operation.

Pessimistic locking::
The database acquires locks that prevent conflicting concurrent updates or deletes to the locked rows until the transaction completes.
Ending application use of an entity or closing its persistence context does not define the lifetime of those database locks.
The effect on other readers depends on the database and isolation level; an exclusive write lock does not universally block ordinary snapshot reads.

The three pessimistic modes provide this protection in different ways:

* `PESSIMISTIC_READ` requests shared protection, allowing compatible shared locks from other readers. A stronger lock may be used when the database does not support shared locks.
* `PESSIMISTIC_WRITE` requests exclusive protection, serializing conflicting writers and locking requests. Ordinary snapshot reads may still proceed.
* `PESSIMISTIC_FORCE_INCREMENT` provides exclusive protection and immediately increments the version, causing subsequent optimistic checks using an earlier version to fail. It requires a versioned entity.

These guarantees concern the locked rows, not every row in an object graph or every insertion that could violate an application invariant.
See <<locking-LockMode,lock modes>> for the standard and Hibernate APIs and <<locking-jpa-query-hints,pessimistic lock scope>> for the rows included in a lock request.

[cols="1,2,2",options="header"]
|===
|Approach |Advantages |Throughput costs
|Optimistic locking
|Transactions can proceed concurrently without reserving access to rows when they are first read. This often provides better throughput when conflicts are uncommon.
|Conflicts are detected later and may discard substantial work. Frequent conflicts and retries can reduce throughput.
|Pessimistic locking
|Protection is acquired before performing dependent work. Under high contention, this can reduce wasted work and retries.
|Lock waiting and longer lock retention reduce concurrency. Contended rows serialize conflicting work, and deadlocks or lock timeouts may require retries.
|===

Neither approach always provides better throughput: contention, transaction duration, and the cost of retrying determine the tradeoff.
Optimistic locking also involves database locks when writing or validating; it is not lock-free.

Explicit transactional lock requests require an active transaction.
Stateful operations also enforce their managed-entity requirements; stateless operations work with detached instances.
A persistence context reuses managed identity and state, but this is not a database isolation guarantee.
See <<pc,Persistence Context>> for context lifetime and <<transactions-completion,transaction completion and failure handling>> for rollback and retries.

[[locking-LockMode]]
=== Lock modes and requesting locks

Jakarta Persistence's link:{jpaJavadocUrlPrefix}LockModeType.html[`LockModeType`] and Hibernate's link:{doc-javadoc-url}org/hibernate/LockMode.html[`LockMode`] provide these application lock modes:

[cols="1,1,3",options="header"]
|===
|`LockModeType` |Hibernate `LockMode` |Requested behavior
|`NONE` |`NONE` |No explicit lock requested.
|`READ`, `OPTIMISTIC` |`OPTIMISTIC` |Request version validation even when the entity is unchanged; timing depends on the session type, as described below.
|`WRITE`, `OPTIMISTIC_FORCE_INCREMENT` |`OPTIMISTIC_FORCE_INCREMENT` |Request version validation and increment even without an ordinary entity change; timing depends on the session type.
|`PESSIMISTIC_READ` |`PESSIMISTIC_READ` |Acquire shared database protection against conflicting writes; a stronger lock may be used when shared locks are unavailable.
|`PESSIMISTIC_WRITE` |`PESSIMISTIC_WRITE` |Acquire exclusive database protection against conflicting writes and locking requests.
|`PESSIMISTIC_FORCE_INCREMENT` |`PESSIMISTIC_FORCE_INCREMENT` |Acquire exclusive protection by immediately incrementing the version.
|===

Prefer the descriptive standard names `OPTIMISTIC` and `OPTIMISTIC_FORCE_INCREMENT` over their `READ` and `WRITE` aliases.


[NOTE]
====
Hibernate's `LockMode.READ` represents an entity read from the database in the current transaction and is accepted by native APIs.
It does not itself promise a transaction-long shared database lock or schedule explicit optimistic validation.
It is distinct from Jakarta Persistence's `LockModeType.READ`, which requests optimistic version validation.
Hibernate's `LockMode.WRITE` represents internal state after a write and is not valid for application lock requests.

`LockMode.UPGRADE_NOWAIT` and `LockMode.UPGRADE_SKIPLOCKED` modes remain available for native query lock-mode hints; for find/refresh operations, prefer the pessimistic mode plus the timeout option.
====

The optimistic modes and `PESSIMISTIC_FORCE_INCREMENT` require a versioned entity.
Ordinary pessimistic read/write requests can lock unversioned entities.
Force-increment support also depends on the version generator; do not assume a database-trigger-generated version supports every force-increment operation.

[[locking-session-lifecycle]]
==== Stateful and stateless timing

Explicit optimistic requests have different lifecycles in a stateful `Session` (`EntityManager`) and a `StatelessSession` (`EntityAgent`):

[cols="1,2,2",options="header"]
|===
|Request |Stateful session |Stateless session
|`OPTIMISTIC` |Schedule version validation before transaction completion, even for an unchanged entity. |Obtain immediate database protection retained until transaction completion.
|`OPTIMISTIC_FORCE_INCREMENT` |Schedule version validation and increment before transaction completion. |Validate and increment the version immediately.
|`PESSIMISTIC_FORCE_INCREMENT` |Validate and increment the version immediately. |Validate and increment the version immediately.
|===

Deferred stateful processing depends on the entity remaining managed.
Detaching the entity or clearing the context does not preserve a promise of validation or increment at completion.
A successful return from the request is not proof that deferred validation or transaction commit has succeeded.

Stateless optimistic protection must prevent concurrent modification until completion: a fresh version read or stable snapshot alone is insufficient.
Hibernate selects a suitable strategy from the <<locking-concurrency-baseline,resolved concurrency configuration>> and rejects the request if no strategy is established.
The SQL need not contain the same locking clause on every database.
See <<batch-stateless,stateless processing>> for the command-oriented lifecycle.

==== Requesting and upgrading locks

Use standard APIs where possible:

* `EntityManager.find()` loads an entity or obtains the requested lock for an already managed entity.
* `EntityManager.lock()` applies a lock to a managed entity without being a general refresh operation.
* `EntityManager.refresh()` reloads entity state and can request a lock at the same time.
* Query locking applies to entity results according to the query's lock mode and scope.

Typed `FindOption`, `LockOption`, and `RefreshOption` arguments carry lock modes, timeout, and scope.
Queries provide lock-mode controls and property/hint forms for the additional options.
Hibernate `Session` supports these standard APIs as well as its own lock-mode overloads.

Requesting a stronger mode can upgrade the lock for an already managed entity.
Requesting a weaker mode does not downgrade an existing stronger mode.
In particular, an `OPTIMISTIC_FORCE_INCREMENT` request after a pessimistic lock does not independently force a version increment.
For a versioned entity, requesting `PESSIMISTIC_FORCE_INCREMENT` after `PESSIMISTIC_READ` or `PESSIMISTIC_WRITE` upgrades the lock and immediately increments the version.
Repeating `PESSIMISTIC_FORCE_INCREMENT` when that mode is already held does not cause another increment merely because the request is repeated.
Choose the required mode before relying on its increment behavior.

Mode ordering and scope acquisition are separate concerns.
An `EXTENDED` pessimistic request can acquire collection-table and owned join-table locks even when the entity already holds an equal or stronger mode.
Repeating the request can be necessary after collection replacement or changes to the relevant managed state.
This acquisition retains the stronger entity mode and does not repeat a forced version increment solely to acquire scope.
`FETCHED` scope instead follows the locking operation's fetch plan; do not infer identical managed-state reacquisition behavior for every scope and operation.

[[locking-session-lock]]
==== Locking an already managed entity

A pessimistic read request asks for shared protection; its SQL and whether stronger protection is necessary depend on the dialect.
Lock acquisition checks and protects database rows but does not generally replace existing managed state.
Similarly, finding or querying an already managed entity can reuse that instance with its existing state.
Use <<pc-refresh,`refresh()`>> to reload state explicitly.
Refresh preserves existing pessimistic protection even when an equal or weaker mode is requested; depending on the dialect, this can require a locking read.
Reload visibility follows the database's current-read and snapshot rules, so repeatable-read isolation does not universally imply that refresh observes the earlier values.

[[locking-optimistic]]
=== Versioned optimistic locking

A <<domain-version-attributes,version attribute>> enables automatic checks when Hibernate updates or deletes an entity.
See that Domain Model discussion for mapping rules, supported types, initialization, and generation.
The previous version is included in the SQL predicate; a missing matching row indicates a stale version or a deleted entity.
For a numeric version, an update may use `where id = ? and version = ?` while assigning the next version.
A second transaction trying to write with the earlier version fails instead of silently overwriting the first transaction's changes.
Version checks do not reserve exclusive access throughout user think time; see <<long-conversations,conversations spanning multiple transactions>>.

Bulk link:{doc-query-language-url}#update[update] and link:{doc-query-language-url}#delete[delete] statements bypass these per-entity optimistic checks.
An ordinary bulk update does not increment versions automatically.
HQL `update versioned` increments the affected entities' versions, but does not automatically compare them with versions previously loaded by the application.
If a bulk mutation requires conflict detection, express the required conditions in its predicate and check the affected-entity count.

Explicit `OPTIMISTIC` locking additionally validates an unchanged versioned entity.
Use it when committing work depends on a read remaining valid, rather than assuming every entity read is checked automatically.

[[locking-optimistic-versionless]]
=== Versionless optimistic locking

`@OptimisticLocking` selects Hibernate's conflict-detection strategy:

`VERSION`:: The default version-attribute strategy.
`NONE`:: Disable optimistic checks, even when a version attribute is present.
`ALL`:: Compare eligible previously loaded column values in update/delete predicates.
`DIRTY`:: Compare eligible previously loaded values of dirty attributes for updates.

ALL and DIRTY require dynamic updates, normally enabled with <<pc-managed-state-dynamic-update,`@DynamicUpdate`>>, and cannot be combined with a `@Version` attribute.
Attributes mapped with <<domain-version-exclusions,`@ExcludedFromVersioning`>> do not participate in their comparisons.
These strategies compare row values rather than maintaining a separate version number.
They protect eligible mutations, not unchanged reads: `ALL` and `DIRTY` do not provide an equivalent to explicit `OPTIMISTIC` read validation on a versioned entity.

[[locking-pessimistic]]
=== Pessimistic scope, timeouts, and skip-locked behavior

Pessimistic read/write locking protects rows using the database's supported locking clauses or table hints.
Shared requests may use exclusive protection where shared locks are unavailable.
The dialect, query shape, and requested options determine how locking is acquired.
Unsupported combinations may fail; there is no universal guarantee of silent fallback preserving every requested behavior.
See the <<locking-query-combinations,query support comparison>> for direct and follow-on acquisition restrictions.

[[locking-jpa-query-hints]]
==== Lock scope

`PessimisticLockScope` controls which rows participate:

[cols="1,3",options="header"]
|===
|Scope |Rows included
|`NORMAL` |The entity's primary and secondary table rows, including its joined-inheritance rows.
|`EXTENDED` |Normal scope plus collection-table and owned association join-table rows. Referenced entity state is not automatically locked.
|`FETCHED` |Rows for relationships and collections fetched by the locking operation, including associated entity state as defined by the scope contract.
|===

Normal scope is the default.
Extended scope does not promise protection against every phantom insertion into a collection or join table.
Fetched scope follows the <<fetching-locking-interaction,fetch plan>> of the locking operation; it is not a recursive lock of everything reachable from the entity.
Dialect capabilities and mapping/query shape can require additional statements or limit support.

==== Lock acquisition timeout

Use `Timeout.milliseconds()` or `Timeout.seconds()` as typed options, or the standard `jakarta.persistence.lock.timeout` property/hint in milliseconds.
A lock timeout concerns waiting for a lock, not total query execution or transaction duration.
For queries, use `SelectionQuery.setLockTimeout(Timeout)` for lock acquisition and `setTimeout(Timeout)` for query execution.

[cols="2,1,2",options="header"]
|===
|Control |Unit |Purpose
|`setLockTimeout(Timeout)` or a typed find/lock/refresh `Timeout` option |Explicit in `Timeout` |Lock acquisition wait.
|`jakarta.persistence.lock.timeout` |Milliseconds |Lock acquisition wait.
|Query `setTimeout(int)` / `org.hibernate.timeout` numeric hint |Seconds |Query execution timeout.
|Query `setTimeout(Integer)` / `jakarta.persistence.query.timeout` |Milliseconds |Query execution timeout.
|Query `setTimeout(Timeout)` |Explicit in `Timeout` |Query execution timeout.
|`Transaction.setTimeout(int)` |Seconds |Transaction timeout, configured before beginning the transaction.
|===

The primitive `int` and boxed `Integer` query overloads use different units; prefer a typed `Timeout` to make the unit explicit.
An acquisition timeout is not a portable deadline for the complete selection and all follow-on statements.
See <<query-execution,query execution>> and <<transactions-timeouts,transaction timeouts>> for those separate controls.

==== No-wait and skip-locked options

`Timeouts.NO_WAIT` requests immediate failure when a conflicting lock cannot be acquired.
`Timeouts.SKIP_LOCKED` requests skipping already locked rows instead of waiting.
Their property/hint values are `0` and `-2`, respectively; `-2` is a Hibernate extension.
`Timeouts.WAIT_FOREVER` uses `-1` to request no acquisition timeout, subject to database settings and other timeouts.

Skip-locked is not a legal `lock()` option for an already managed entity; use a supported selection operation.

[NOTE]
====
On Sybase ASE, skip-locked `PESSIMISTIC_WRITE` selection uses `READPAST` with `FOR UPDATE` to retain exclusive row locks.
This requires the ASE server option `select for update` to be enabled and the selected tables to use `datarows` locking.
Hibernate does not enable the server option automatically.
When JDBC metadata access is available, Hibernate checks the option during bootstrap and rejects exclusive skip-locked requests if it is disabled or cannot be verified.
When bootstrapping without JDBC metadata, the application must ensure that the option is enabled.
ASE does not support `FOR UPDATE` with `DISTINCT`, `GROUP BY`, `HAVING`, aggregate functions, subqueries, or set operations such as `UNION`.
Hibernate rejects exclusive skip-locked HQL and Criteria queries with these shapes before executing SQL, including table-per-class polymorphic queries and full joins implemented using a union.
Use a supported query shape when exclusive skip-locked selection is required.
Skip-locked `PESSIMISTIC_READ` set queries use `READPAST` on each selected table and query-level repeatable-read isolation to retain shared locks.
====

[[locking-failures]]
==== Locking failures

Failure classification depends on the database failure and API exception conversion, not merely on the requested timeout:

[cols="2,3",options="header"]
|===
|Failure |Classification and handling
|Stale version or a required row missing during follow-on acquisition |A stale-state or optimistic conflict, commonly exposed as `OptimisticLockException` at a Jakarta Persistence boundary. A missing row is not successful acquisition or a lock timeout.
|Pessimistic acquisition failure aborting the transaction |`PessimisticLockException` at a Jakarta Persistence boundary; the transaction must be rolled back.
|Statement-level acquisition timeout |`LockTimeoutException` at a Jakarta Persistence boundary. This exception does not itself require Hibernate to mark the transaction rollback-only.
|Query execution timeout |Distinct from a lock timeout. `QueryTimeoutException` represents statement-level failure; a transaction-aborting failure may be exposed as a broader persistence exception.
|Unsupported locking request |A request or query-operation rejection, possibly converted at an API boundary. This is not evidence of contention or a stale version.
|===

Native causes may contain stale-state or JDBC locking exceptions; using a `Session` variable does not guarantee that only native exception types are thrown.
A failure during transaction completion may be wrapped in `RollbackException`; inspect the cause when diagnosing a deferred validation failure.

Hibernate marking a transaction rollback-only, the database aborting it, and the persistence context remaining reliable are separate questions.
Do not infer that a timed-out transaction remains usable merely because the exception does not itself require a rollback-only mark.
After a failure that leaves a stateful context unreliable, roll back and discard it before retrying the appropriate unit of work.
Stateless sessions do not automatically mark the transaction rollback-only after an exception, but the database may still abort it; rollback also does not restore detached Java object values.
See <<pc-exception-handling,exception handling>> and <<transactions-completion,transaction failure handling>>.

[[locking-graph-root]]
=== Coordinating access through a graph root

Applications can coordinate access to a graph of objects through an agreed graph root using either optimistic or pessimistic locking.
With optimistic locking, participating transactions capture the root's version before reading the graph state it protects and validate that version before successful transaction completion.
Graph writers advance the root's version within the transaction containing their graph changes, even when the root's own attributes are unchanged.
With pessimistic locking, participating transactions acquire a lock on the root before reading the graph state it protects: a shared lock for readers or an exclusive lock for writers, held until transaction completion.

Choose the <<fetching-locking-interaction,loading operation and fetch plan>> so that protected state is not read before the required coordination step.
Eager association loading and the selection phase of follow-on locking can retrieve that state before lock acquisition;
do not assume that requesting a root lock automatically establishes the protocol's required ordering.
State already read into the persistence context and transaction snapshots established before coordination must also be considered when choosing reads that satisfy the protocol.

This coordination requires all participating transactions to follow the same root-locking protocol.
Locking the root does not automatically lock, version, or validate every associated entity; the agreement makes the root the coordination point for graph access.
Neither approach automatically refreshes graph objects already loaded into the persistence context.
When existing managed state must be reloaded, see <<pc-refresh,refreshing entity state>>; acquiring or validating the root's lock does not make that state current.

[[locking-concurrency-baseline]]
=== Concurrency baseline and optimistic validation

Hibernate resolves a transaction concurrency baseline during bootstrap and uses it when selecting the current read needed to verify an explicit optimistic lock's version.
Resolution considers the bootstrap connection's isolation and database-specific configuration, including SQL Server's `READ_COMMITTED_SNAPSHOT` setting and TiDB's transaction mode.
It does not change connection isolation.

The `hibernate.transaction.concurrency` setting declares the baseline when it cannot be observed, especially when `hibernate.boot.allow_jdbc_metadata_access` is `DISALLOW`.
Its registered names are `READ_UNCOMMITTED`, `READ_COMMITTED`, `LOCKING_READ_COMMITTED`, `READ_COMMITTED_SNAPSHOT`, `REPEATABLE_READ`, `SNAPSHOT`, and `SERIALIZABLE`.
Names are interpreted by the dialect: `SNAPSHOT` is distinct from statement-level `READ_COMMITTED_SNAPSHOT`.
Programmatic configuration may instead supply a `TransactionConcurrency` instance constructed using `TransactionConcurrencies.builder()`.
An explicitly supplied instance bypasses concurrency resolution, probing, and validation; its accuracy and immutability are the caller's responsibility.
A known contradiction between a named declaration and observed behavior fails bootstrap.

With metadata access `ALLOW`, a failed concurrency query leaves the affected facts unresolved without discarding other JDBC metadata.
With `REQUIRE`, failure of a supported query fails bootstrap.
`DISALLOW` performs no JDBC access for concurrency resolution.
An unsupported query is not an execution failure and may be compensated for by a declaration.

All connections used by a factory must have consistent concurrency configuration.
The declaration does not configure a pool, replace `hibernate.connection.isolation`, or support session-specific overrides.
If neither an ordinary read nor a dialect current-read strategy establishes the required guarantee, Hibernate rejects the affected optimistic validation rather than relying on a potentially stale snapshot.

Stateless optimistic locking requires a read that retains row protection through transaction completion.
Hibernate uses a shared-lock or update-lock read, or an ordinary read when the resolved configuration already guarantees that protection.
A current read that provides only freshness, or a stable snapshot that permits concurrent modification, is insufficient for this purpose.
