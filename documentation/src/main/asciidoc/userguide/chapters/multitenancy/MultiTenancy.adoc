[[multitenacy]]
== Multitenancy
:example-dir-multitenancy: {core-project-dir}/src/test/java/org/hibernate/orm/test/multitenancy
:multitenancy-guide-examples: {example-dir-multitenancy}/guide/MultitenancyGuideTests.java

Multitenancy lets an application serve multiple tenants while distinguishing their data.
Hibernate supports tenant-specific connection routing, schema and credential selection, mapped tenant discrimination, and database row-level security where the dialect supports it.
See <<bootstrap>> for factory creation and <<database>> for general connection and pool configuration.

[[multitenacy-intro]]
=== Isolation approaches and choosing an integration

[[multitenacy-separate-database]]
==== Separate databases

image::images/multitenancy/multitenacy_database.png[align="center"]

Each tenant has a separate database.
A common arrangement uses a datasource or pool per tenant and a <<multitenacy-hibernate-MultiTenantConnectionProvider,tenant-aware provider>> to select the appropriate source.
The application controls provisioning and the lifecycle of those sources.

[[multitenacy-separate-schema]]
==== Separate schemas

image::images/multitenancy/multitenacy_schema.png[align="center"]

Each tenant has a separate schema in a shared database.
Use separate connection sources or a shared source with <<multitenancy-schema-mapper,schema selection>>.
Hibernate can manage JDBC schema switching through `TenantSchemaMapper`; a custom multitenant provider is not required for that approach.
Driver support for schema operations matters.

[[multitenacy-discriminator]]
==== Shared tables

image::images/multitenancy/multitenacy_discriminator.png[align="center"]

Tenants share tables, with a discriminator identifying the tenant that owns each partitioned row.
Hibernate handles tenant discrimination for supported mapped operations using <<multitenacy-hibernate-TenantId,`@TenantId`>>.
Applications do not need to hand-edit every ORM-generated SQL statement.
Native SQL and JDBC work have different boundaries; see <<multitenancy-direct-sql>> and <<multitenancy-rls>>.

[[multitenacy-approaches]]
.Isolation and integration choices
[cols="1,2,2",options="header"]
|===
|Approach |Typical integration |Application responsibilities
|Separate databases |`MultiTenantConnectionProvider` |Provision databases, route connections, and manage tenant sources
|Separate schemas |`TenantSchemaMapper` with ordinary connection access, or a custom provider |Provision schemas and use supported schema switching with connection-state cleanup
|Shared tables |`@TenantId`, optionally with database RLS |Map partitioned data and design suitable keys, constraints, and database policies
|Tenant-specific database users |`TenantCredentialsMapper` with a supporting provider |Provision users and grants; combine with schema selection or row discrimination as needed
|===

These mechanisms can be combined; selecting credentials does not itself partition rows.
A factory uses shared mappings and a dialect/capability model.
Its tenant databases and schemas must be compatible with that model: selecting a tenant does not select a different mapping or SQL dialect.

[[multitenacy-hibernate]]
=== Selecting a tenant and session lifetime

Choose the tenant when creating a session or entity manager, or configure a resolver to supply a default.
An existing session keeps its tenant across transactions and calls to `clear()`.
Changing application tenant context does not retarget that session; open a new session or persistence context to work for another tenant.
See <<pc,Persistence Context>> and <<transactions>> for their separate lifetimes.

[[multitenacy-hibernate-TenantId]]
=== Shared-table mappings with @TenantId

Map the tenant attribute of partitioned data using link:{doc-javadoc-url}org/hibernate/annotations/TenantId.html[`@TenantId`].
The attribute may be inherited, and field or property access may be used according to the entity's mapping.
All `@TenantId` attributes in one factory must have a consistent Java type.

====

When inserting an entity through the persistence APIs, Hibernate generates the tenant value from the session tenant.
For a nonidentifier tenant attribute such as `Document.tenant`, an ordinary tenant's supplied nonnull value is rejected if it differs from the session tenant.
A root tenant may supply another tenant value for such an attribute.
Tenant attributes belonging to a composite identifier have different generation behavior; see <<multitenancy-identifiers>>.
The tenant attribute is not an application-controlled way to transfer an existing row to a different tenant.

[[multitenancy-direct-sql]]
==== ORM operations and direct SQL

Hibernate's supported tenant-aware ORM operations include mapped queries, identifier loading, and entity mutations.
Bulk updates and deletes expressed in HQL or Criteria also apply the mapped tenant restrictions.
See <<query-mutations>> for execution and persistence-context considerations.

HQL `insert ... values` and `insert ... select` statements do not invoke the entity's `@TenantId` value generator or its supplied-value validation.
Include the tenant attribute in the insertion target list and supply an appropriate tenant value explicitly.
Tenant restrictions on a mapped source of an `insert ... select` limit the source rows; they do not generate or validate the tenant value assigned to the target rows.
Deployed database policies and constraints may impose additional checks; see <<multitenancy-rls>>.

Native queries, stored procedures, JDBC callbacks, and user-written SQL are not automatically rewritten to add tenant predicates.
Custom loaders or custom mutation SQL must also be reviewed for their tenant restrictions; do not assume arbitrary custom SQL inherits the restrictions of generated SQL.
Use explicit restrictions or appropriate deployed database policies for these paths.
See <<sql>>, <<database-jdbc-work>>, and <<multitenancy-rls>>.

This mapping permits both tenants to use the same local `id` with different tenant components.

==== TenantCredentialsMapper

link:{doc-javadoc-url}org/hibernate/context/spi/TenantCredentialsMapper.html[`TenantCredentialsMapper<T>`] selects database credentials for a tenant.
Configure `hibernate.multi_tenant.credentials_mapper` with an instance, class, or class name, use the factory-builder integration, or supply it through a BeanContainer.
This can be combined with schema selection or row discrimination.

[[multitenancy-credentials-example]]
====
[source,java,indent=0]
----
include::{multitenancy-guide-examples}[tags=multitenancy-credentials]
----

Register this mapper with `property("hibernate.multi_tenant.credentials_mapper", credentials)`.
`lookupPassword()` represents the application's credential source; the executable fixture uses synthetic credentials to verify routing, not actual tenant database users.
The ordinary provider must support `getConnection(user, password)` and the datasource must honor those credentials.

[[multitenacy-hibernate-MultiTenantConnectionProvider]]
=== Custom multitenant connection providers

link:{doc-javadoc-url}org/hibernate/engine/jdbc/connections/spi/MultiTenantConnectionProvider.html[`MultiTenantConnectionProvider<T>`] obtains and releases tenant-specific connections.
Pair `getConnection(tenantId)` with `releaseConnection(tenantId, connection)` and preserve the tenant's routing and connection state.
`getAnyConnection()` and `releaseAnyConnection()` supply representative non-tenant-specific access, typically for bootstrap metadata.
This is not a request to scan every tenant database.
See <<database-bootstrap-metadata>> for metadata controls and their limits.

Configure `hibernate.multi_tenant_connection_provider` with an instance, implementation class, or class name; register the service directly; or resolve it through a configured BeanContainer.
A datasource setting alone does not enable this service or automatically select the JNDI multitenant implementation.
When this service is configured, Hibernate uses it instead of ordinary connection-provider selection.

[[multitenancy-jndi]]
==== JNDI datasource routing

To use link:{doc-javadoc-url}org/hibernate/engine/jdbc/connections/spi/DataSourceBasedMultiTenantConnectionProviderImpl.html[`DataSourceBasedMultiTenantConnectionProviderImpl`], select it explicitly using `hibernate.multi_tenant_connection_provider`.
It expects tenant datasources beneath a common JNDI namespace and a string `hibernate.connection.datasource` naming either a representative datasource or the base JNDI Context.
For a Context, also configure `hibernate.multi_tenant.datasource.identifier_for_any` to identify the representative tenant.
See <<jndi>> and the provider's Javadocs for lookup assumptions.

There is a legacy fallback when the multitenant-provider key is explicitly present with a null value and `hibernate.connection.datasource` is a string.
Do not rely on a datasource setting alone to select this path; explicit provider selection is clearer.

[[multitenancy-rls]]
=== Row-level security

Database row-level security (RLS) supplements Hibernate's ORM tenant restrictions with policies enforced by the database.
The incubating `hibernate.multi_tenant.rls_enabled` setting defaults to `true` where the dialect supports the required capabilities and the `@TenantId` mapping qualifies.
Unsupported databases still use Hibernate's mapped tenant restrictions; the setting does not add RLS support to a dialect.

For eligible physical-table tenant-column mappings, Hibernate contributes policy DDL to schema tooling and establishes database-side tenant context on acquired connections.
A noncolumn mapping, view, or unsupported capability must not be assumed to receive equivalent policy DDL.
If a credentials mapper is configured and the dialect supports it, policies may instead obtain tenant identity from the database user.
That requires compatible user/tenant values and the appropriate users and grants.

[IMPORTANT]
====
Policies must actually be deployed. If Hibernate does not manage schema creation, arrange equivalent policy deployment through your schema-management process.
Enabling a setting alone does not retrofit policies into an existing schema.
Database roles and privileges matter: a bypass role may see data that an ordinary role cannot.
====

Unlike ORM predicate generation, deployed database policies can also constrain native SQL and JDBC work.
This query has no tenant predicate; the existing RLS integration tests verify that installed policies restrict its results for an ordinary tenant role:

[[multitenacy-hibernate-caching]]
=== Caching and tenant-specific session options

Hibernate's default tenant-aware cache keys distinguish tenants.
Database primary keys, persistence-context identity, and cache keying are separate concerns; a tenant-aware cache key does not change table constraints.
Keep sessions scoped to their selected tenant, and verify that custom cache keys/providers preserve the required tenant separation.
See <<caching>> for provider requirements, consistency, and invalidation rather than assuming every cache configuration is interchangeable.
Schema provisioning and cache eviction have separate responsibilities.
