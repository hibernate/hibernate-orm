[[BytecodeEnhancement]]
=== Bytecode Enhancement
:example-dir-enhancement: {core-project-dir}/src/test/java/org/hibernate/orm/test/pc

Enhancement adds interception and state-tracking code to persistent classes.
It supports lazy attribute loading and supplements <<pc-dirty-checking,dirty checking>>.
See <<tooling-enhancement,enhancement tooling>> for build-time and runtime configuration.

[[BytecodeEnhancement-lazy-loading]]
==== Lazy attribute loading

Enhancement allows individual attributes or groups of attributes to be loaded on access.
Unlike an entity proxy, which delays loading the entity itself, attribute loading can defer selected state after the entity is initialized.
A lazy basic mapping needs enhancement for Hibernate to defer that attribute's loading.

Lazy basic attributes may be loaded together as a "lazy group".
By default, lazy basic attributes belong to the same group: accessing one loads the other basic attributes in that group.
Use `@LazyGroup` to assign them to separate groups.
To-one associations follow separate proxy and enhanced-reference loading rules; `@LazyGroup` is not a general way to control their initialization.
Lazy collections normally initialize independently. See <<fetching,fetching>> for association and collection loading.

[[BytecodeEnhancement-dirty-tracking]]
==== In-line dirty tracking

Enhanced classes record attribute writes, allowing Hibernate to identify changed attributes without comparing every value.
Internally mutable values still require comparison against their snapshots: mutation inside a `Date`, array, or mutable document need not call an entity setter.
Hibernate combines enhanced tracking with these comparisons according to the mapping's mutability information.
See <<pc-dirty-checking,dirty checking>> and <<basic-mapping-composition-mutability,mutability plans>>.

[[BytecodeEnhancement-client]]
==== Client enhancement

Optional client enhancement rewrites direct accesses to persistent fields into calls to Hibernate's generated field readers and writers.
This allows client writes to participate in dirty tracking and client reads to trigger lazy loading.
It does not make the client a managed class or add managed-class interfaces or state.

NOTE:: Managed classes may themselves access persistent fields of other managed objects.
When client enhancement is enabled, it also processes those accesses, after managed enhancement of the class.
Generated accessor methods are excluded from client rewriting.

Client enhancement is optional and disabled by default. See <<tooling-enhancement,enhancement tooling>> for build-tool options.
The deprecated `enableExtendedEnhancement` name remains an alias;
an explicitly supplied `enableClientEnhancement` value takes precedence, including false.
Tool file sets and class-name filters still apply. Target classes must be selected for managed enhancement in the same invocation,
or already have compatible Hibernate enhancement. Unenhanced dependency classes are not automatically enhanced.

Containers may request `HibernatePersistenceProvider.getClientClassTransformer(PersistenceUnitInfo, Map)` and install the returned Jakarta `ClassTransformer`.
Targets must already have compatible managed-class enhancement from tooling, or the container must arrange it before those classes are defined.
A client may still be loaded before a target scheduled for managed enhancement; generated accessors need not be present in the original class resources.
A container can therefore use runtime client enhancement with runtime managed enhancement disabled when tooling has already enhanced the targets.
Without prior or scheduled managed enhancement, there is no client enhancement work to perform.
This Hibernate entry point anticipates the proposed Jakarta Persistence client-transformer API.
It neither registers a transformer nor consumes the managed-class transformer's registration.

Client enhancement uses the existing enhancer's mapping recognition; listing an XML-only mapped class does not by itself make it eligible.
It does not intercept reflection or method handles. Identifier accesses, static fields, nonpersistent fields, and final-field writes remain unchanged.

[[BytecodeEnhancement-dirty-tracking-optimizations]]
==== Internal performance optimizations

Enhancement also supplies hooks for maintaining persistence-context state efficiently.
These internal optimizations do not change entity identity, transaction boundaries, or the need to synchronize pending changes.
