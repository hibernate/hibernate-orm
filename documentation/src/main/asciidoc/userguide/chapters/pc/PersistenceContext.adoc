[[pc-fundamentals]]
=== Persistence-context fundamentals

A persistence context tracks entity instances and their pending changes.
Both `jakarta.persistence.EntityManager` and `org.hibernate.Session` provide this context.
Within a context, an entity type and identifier identify a single managed representation.
Repeated lookups return that representation, which may already contain unflushed changes;
a lookup is not a request to <<pc-refresh,refresh>> its state from the database.

[IMPORTANT]
`EntityAgent` and Hibernate's `StatelessSession` operate without a persistence context:
they do not provide managed identity or automatic dirty checking. See <<batch-stateless-session-example,stateless processing>>.

An entity instance has one of the following states in relation to the persistence-context:

`new` or `transient`:: Not associated with a context and not yet persistent. An assigned identifier alone does not make an instance persistent.
`managed` or `persistent`:: Associated with the context. Its database row might not exist yet if insertion is pending.
`detached`:: Previously persistent, but no longer associated with this context.
`removed`:: Associated with the context and scheduled for removal from the database.

The persistence-context lifetime and <<transactions,transaction>> lifetime are distinct:

* *Container-managed, transaction-scoped context:* normally ends when its associated transaction completes.
* *Container-managed, extended context:* can span multiple transactions; its lifetime is controlled by the container, typically through the owning stateful session bean.
* *Application-managed context:* lasts until the application closes it and may participate in multiple transactions during that lifetime.

See <<bootstrap-standardized-container,container bootstrap>>, <<bootstrap-standardized-app,application bootstrap>>,
and <<long-conversations,long conversations>> for their configuration and usage.

A context is not thread-safe. Do not share an `EntityManager` or `Session` between concurrent threads.
It holds references to managed objects, so use <<pc-detach,detachment and clearing>> when controlling memory during <<batch-session-batch,batch processing>>.

[[pc-by-multiple-ids]]
==== Finding multiple entities

Jakarta Persistence provides `findMultiple()` and `getMultiple()` for loading a list of identifiers.
By default, results follow identifier order. `findMultiple()` represents a missing entity with a null list element;
`getMultiple()` throws `EntityNotFoundException` if any requested entity is missing.
A single method call may execute multiple database requests, depending on batching and dialect capabilities.

Hibernate accepts additional loading options through `Session`, including:

* `ReadOnlyMode` - whether loaded entities should be marked <<pc-read-only,read-only>>.
* `LockMode` (`LockModeType`) - the <<locking-LockMode,lock mode>> to apply.
* `Timeout` - the timeout for a <<locking-pessimistic,pessimistic lock>>.
* `Locking.Scope` (`PessimisticLockScope`) - the <<locking-jpa-query-hints,scope of pessimistic locking>>.
* `Locking.FollowOn` - whether to acquire locks through <<locking-follow-on,additional queries>> when needed.
* `CacheMode` (`CacheStoreMode` / `CacheRetrieveMode`) - how to use the <<caching-management,second-level cache>>.
* `BatchSize` - how many identifiers should be loaded from the database at once
* `SessionCheckMode` - whether to look into the persistence context to check entity state
* `RemovalsMode` - if `SessionCheckMode` is enabled, how removed entities should be handled
* `OrderingMode` - whether the results should be ordered according to the order of the passed identifiers

[[pc-cascade]]
=== Cascading operations and orphan removal

Cascading propagates an operation from an entity to its associated entities.
The Jakarta Persistence `CascadeType` enumeration defines these operations:

`ALL`:: includes all the cascade operations listed below.
`PERSIST`:: cascades the entity persist operation.
`MERGE`:: cascades the entity merge operation.
`REMOVE`:: cascades the entity remove operation.
`REFRESH`:: cascades the entity refresh operation.
`DETACH`:: cascades the entity detach operation.

Cascading propagates an operation; it does not determine <<associations,association ownership>>.
For example, `REMOVE` propagates removal of the parent to its children, while `orphanRemoval=true` removes a child when it is dissociated from its owner.
See <<associations-one-to-many-bidirectional,bidirectional one-to-many associations>> and <<collections-bidirectional-bag-orphan-removal-example,orphan removal>> for examples.

[NOTE]
====
Without the `@OnDelete` annotation, the `@OneToMany` association relies on the `cascade` attribute to propagate the `remove` entity state transition from the parent entity to its children.
However, when the `@OnDelete` annotation is in place, Hibernate prevents the child entity `DELETE` statement from being executed while flushing the Persistence Context.

Database cascades and operation cascades have different effects on in-memory state.
With `@OnDelete(action=CASCADE)` alone, child entities deleted by the database are not automatically marked removed in the context or evicted from the <<caching,second-level cache>>.
Combining it with `cascade=REMOVE` lets Hibernate load and mark the children removed and evict their cache entries, while the database executes the child-row deletion.
The foreign key must actually declare the action; configure it through <<schema-generation,schema tooling>> or the schema migration used by the application.

[[pc-dirty-checking]]
=== Dirty checking and update behavior

During flushing, Hibernate determines which managed values have changed.
Snapshot-based dirty checking compares current state with the state recorded when the entity was loaded or last synchronized.
<<BytecodeEnhancement-dirty-tracking,Enhanced dirty tracking>> records attribute writes and reduces that comparison work.
Hibernate still checks internally mutable values, such as `Date` or a mutable document value, according to their <<basic-mapping-composition-mutability,mutability plans>>.

[[pc-read-only]]
==== Read-only entity state

Use `Session.setDefaultReadOnly(true)` for entities loaded subsequently, `Session.setReadOnly(entity, true)` for a managed instance,
or query/loading options such as `setReadOnly(true)` and `ReadOnlyMode.READ_ONLY` for selected results.
Setting the default does not change entities already managed. A query option does not replace the read-only status of an existing managed instance.

Hibernate does not dirty-check ordinary properties of a read-only entity for updates.
Changes to collections may still be synchronized and may increment its version; cascaded operations are also not disabled.
Read-only state is therefore not a prohibition on all writes.

Read-only state differs from <<mutability-immutable,`@Immutable`>>, which is a mapping-level declaration,
from <<flushing-manual,manual flushing>>, which controls synchronization timing,
and from database transaction read-only settings. See <<transactions,transactions>> for transaction boundaries.
When making a read-only instance modifiable again, do not expect changes made while it was read-only to be detected automatically;
refresh it first if those changes should be discarded.

[[pc-rowid]]
==== Row-id locators for updates and deletes

`@RowId` enables a database row-id column or pseudo-column as a locator for entity updates and deletes, where supported by the dialect.
For example:

[source,java]
----
@Entity
@RowId
class Product {
    @Id Long id;
    @Version int version;
    String name;
}
----

The entity identifier still defines persistence-context identity and association references.
The row-id changes how Hibernate locates a row for mutation; it does not replace `@Id` or remove optimistic-lock checks.
When the row-id is available, statements for the entity's identifier table may use predicates like these (shown using Oracle's `ROWID` spelling):

[source,sql,opts=novalidate]
----
update Product set name=?, version=? where ROWID=? and version=?
delete from Product where ROWID=? and version=?
----

Other mapped tables, such as secondary tables, retain their own key predicates.
If the dialect does not support row-id locators, `@RowId` is ignored and Hibernate uses the primary key.
Even on a supporting dialect, the primary key is used when the row-id is unavailable.
Hibernate obtains the locator when loading the entity; availability immediately after insertion depends on the dialect and generated-value retrieval support.
The annotation's optional name is mainly needed for explicitly declared row-id columns; dialects with implicit pseudo-columns determine the name themselves.
See <<identifiers-rowid,`@RowId` mapping>> for the mapping example.

<<batch-bulk-hql,Bulk mutations>> and SQL executed outside Hibernate can change database rows without updating managed instances.
Flush pending changes before a bulk mutation when they must be included, then refresh affected entities or clear the context before relying on their state.

[[pc-detach]]
=== Detachment, clearing, and merging

Closing a context, clearing it, or detaching an instance ends automatic dirty checking for those instances.
Serialization produces a detached copy without detaching the original managed instance.
Detached objects may be edited, but their changes are not automatically synchronized. Use <<pc-merge,merge>> to copy their state into a context.

==== Detaching entities and clearing the context

`detach()` removes an entity from the context; Hibernate's `evict()` is a synonym.
Detachment cascades only through associations configured with <<pc-cascade-detach,`DETACH`>>.
Detachment stops automatic dirty checking of the instance; it does not cancel every insertion or deletion already queued.
Flush first when pending changes must be preserved.
Detachment does not undo SQL already executed in the current transaction.

[[pc-merge]]
==== Merging detached data

`merge()` copies the incoming state into a managed instance and returns that instance.
The managed target may already exist in this context; otherwise Hibernate loads or creates it.
The incoming detached instance remains detached. Use the returned instance for subsequent managed changes.
Merge also accepts new instances, whose managed copies are persisted according to merge and cascade semantics.

[[pc-merge-gotchas]]
===== Multiple representations of the same entity

By default, Hibernate throws `IllegalStateException` when merging a parent entity which has references to two detached child entities `child1` and `child2` (obtained from different sessions), and `child1` and `child2` represent the same persistent entity, `Child`.

The configuration property `hibernate.event.merge.entity_copy_observer` controls how Hibernate will respond when multiple representations of the same persistent entity ("entity copy") is detected while merging.

The possible values are:

disallow (the default):: throws `IllegalStateException` if an entity copy is detected
allow:: performs the merge operation on each entity copy that is detected
log:: (provided for testing only) performs the merge operation on each entity copy that is detected and logs information about the entity copies.
This setting requires DEBUG logging be enabled for `org.hibernate.event.internal.EntityCopyAllowedLoggedObserver`

In addition, the application may customize the behavior by providing an implementation of `org.hibernate.event.spi.EntityCopyObserver` and setting `hibernate.event.merge.entity_copy_observer` to the class name.
When this property is set to `allow` or `log`, Hibernate will merge each entity copy detected while cascading the merge operation.
In the process of merging each entity copy, Hibernate will cascade the merge operation from each entity copy to its associations with `cascade=CascadeType.MERGE` or `CascadeType.ALL`.
The entity state resulting from merging an entity copy will be overwritten when another entity copy is merged.

[WARNING]
====
Because cascade order is undefined, the order in which the entity copies are merged is undefined.
As a result, if property values in the entity copies are not consistent, the resulting entity state will be indeterminate, and data will be lost from all entity copies except for the last one merged.
Therefore, the *last writer wins*.

If an entity copy cascades the merge operation to an association that is (or contains) a new entity, that new entity will be merged (i.e., persisted and the merge operation will be cascaded to its associations according to its mapping),
even if that same association is ultimately overwritten when Hibernate merges a different representation having a different value for its association.

If the association is mapped with `orphanRemoval = true`, the new entity will not be deleted because the semantics of orphanRemoval do not apply if the entity being orphaned is a new entity.

There are known issues when representations of the same persistent entity have different values for a collection.
See https://hibernate.atlassian.net/browse/HHH-9239[HHH-9239] and https://hibernate.atlassian.net/browse/HHH-9240[HHH-9240] for more details.
These issues can cause data loss or corruption.

By setting `hibernate.event.merge.entity_copy_observer` configuration property to `allow` or `log`,
Hibernate will allow entity copies of any type of entity to be merged.

The only way to exclude particular entity classes or associations that contain critical data is to provide a custom implementation of `org.hibernate.event.spi.EntityCopyObserver` with the desired behavior,
and setting `hibernate.event.merge.entity_copy_observer` to the class name.
====

[TIP]
====
Hibernate provides limited DEBUG logging capabilities that can help determine the entity classes for which entity copies were found.
By setting `hibernate.event.merge.entity_copy_observer` to `log` and enabling DEBUG logging for `org.hibernate.event.internal.EntityCopyAllowedLoggedObserver`,
the following will be logged each time an application calls `EntityManager.merge( entity )` or +
`Session.merge( entity )`:

- number of times multiple representations of the same persistent entity was detected summarized by entity name;
- details by entity name and ID, including output from calling toString() on each representation being merged as well as the merge result.

The log should be reviewed to determine if multiple representations of entities containing critical data are detected.
If so, the application should be modified so there is only one representation, and a custom implementation of `org.hibernate.event.spi.EntityCopyObserver` should be provided to disallow entity copies for entities with critical data.

Using optimistic locking is recommended to detect if different representations are from different versions of the same persistent entity.
If they are not from the same version, Hibernate will throw an `OptimisticLockException`, possibly wrapping a Hibernate `StaleObjectStateException`. See <<locking,locking>>.
====

[[pc-to-one-restrictions]]
==== Restrictions on to-one associations

`@SQLRestriction` and `@Filter` may also be declared on a `@ManyToOne` or `@OneToOne` field or getter:

[source,java]
----
@ManyToOne(fetch = FetchType.LAZY)
@SQLRestriction("active = true")
Person approver;

@ManyToOne(fetch = FetchType.LAZY)
@Filter(name = "activePerson", condition = "active = :active")
Person reviewer;
----

The filter must have a corresponding `@FilterDef` with an `active` parameter.
Enable it and set its parameter before loading the owner:

[source,java,opts=novalidate]
----
session.enableFilter("activePerson").setParameter("active", true);
----

The conditions apply to the target entity through the annotated association, including associations
mapped using `@JoinTable` and inverse one-to-one associations. Applicable conditions on the target entity
and the association are combined using `AND`. Association filters apply whenever enabled, regardless of
`@FilterDef.applyToLoadByKey`. Entity-level filters retain their usual load-by-key rules.
Filter default conditions and explicit `@SqlFragmentAlias` declarations work as for collections.
Use explicit aliases for filters referring to other tables of a target mapped with `JOINED` inheritance
or `@SecondaryTable`. SQL restrictions qualify mapped columns from these tables automatically.

An excluded target is represented as null, even if the target is already managed or cached.
Other associations and direct lookups may still return the same target. Hibernate preserves the stored
foreign key and join-table row when unrelated fields change or null is assigned to an already hidden
association. Assigning a new nonnull target replaces the reference. A hidden target is not orphan-removed.
Merge assumes that the detached source was loaded under the same filters and parameter values.

Changing filters does not reinterpret already loaded associations. Refresh or reload the owner to obtain
a new view. These predicates affect loading, not validation of newly assigned targets.
Native result mappings require an additional visibility query when the association has an applicable restriction.

[[pc-exception-handling]]
=== Exception handling

After a persistence or flush failure that leaves the context unreliable, roll back the transaction and discard the `EntityManager` or `Session`.
Do not continue using that context or attempt to repair it by clearing it.
For application-managed contexts, ensure closure with a `finally` block or try-with-resources; container-managed contexts follow their container lifecycle.

Not every query-result exception implies a damaged context.
For example, `NoResultException` and `NonUniqueResultException` report result cardinality and do not themselves mark the transaction for rollback.
Follow the exception's documented transaction semantics; do not generalize these exceptions to JDBC, optimistic-lock, or flush failures.
See <<transactions,transactions>> and <<locking,locking>> for transaction and lock handling.

Rollback restores database transactional state, but does not restore the values of Java objects or their generated identifiers.
Discard or reload affected objects before starting another unit of work.

Hibernate and Jakarta Persistence expose unchecked exceptions. Hibernate may convert failures into Jakarta Persistence exceptions at API boundaries;
using a `Session` variable does not guarantee that only Hibernate exception types will be thrown.

Hibernate wraps the JDBC `SQLException`, thrown while interacting with the database, in a
https://docs.hibernate.org/orm/{majorMinorVersion}/javadocs/org/hibernate/JDBCException.html[`JDBCException`].
In fact, Hibernate will attempt to convert the exception into a more meaningful subclass of `JDBCException`. The underlying `SQLException` is always available via https://docs.hibernate.org/orm/{majorMinorVersion}/javadocs/org/hibernate/JDBCException.html#getSQLException()[`JDBCException.getSQLException()`]. Hibernate converts the `SQLException` into an appropriate JDBCException subclass using the
https://docs.hibernate.org/orm/{majorMinorVersion}/javadocs/org/hibernate/exception/spi/SQLExceptionConverter.html[`SQLExceptionConverter`]
attached to the current `SessionFactory`.

By default, Hibernate combines an optional dialect-specific delegate supplied by the
https://docs.hibernate.org/orm/{majorMinorVersion}/javadocs/org/hibernate/dialect/Dialect.html#buildSQLExceptionConversionDelegate()[`buildSQLExceptionConversionDelegate`] method
with standard delegates that inspect JDBC exception subclasses and SQLState codes.
The dialect delegate is consulted first when present; the standard delegates provide fallback conversion.

The standard `JDBCException` subtypes are:

ConstraintViolationException::
	indicates some form of integrity constraint violation.
DataException::
	indicates that evaluation of the valid SQL statement against the given data
	resulted in some illegal operation, mismatched types, truncation or incorrect cardinality.
GenericJDBCException::
	a generic exception which did not fall into any of the other categories.
JDBCConnectionException::
	indicates an error with the underlying JDBC communication.
LockAcquisitionException::
	indicates an error acquiring a lock level necessary to perform the requested operation.
LockTimeoutException::
	indicates that the lock acquisition request has timed out.
PessimisticLockException::
	indicates that a lock acquisition request has failed.
QueryTimeoutException::
	indicates that the current executing query has timed out.
SQLGrammarException::
	indicates a grammar or syntax problem with the issued SQL.
