[[query-execution]]This chapter describes the common APIs for executing selections and mutations.
Use HQL or JPQL for query strings, <<criteria,Criteria>> for Java-based construction,
<<QuerySpecification,query specifications>> for iterative composition, or <<sql,native SQL>> for handwritten database SQL.
<<stored-procedures,Procedure calls>> have their own execution model.
The link:{doc-query-language-url}[Query Language guide] describes general language syntax and semantics;
<<query-language>> covers specialized functions.
For an introductory walkthrough, see link:{doc-introduction-url}#queries[Executing queries].

[[query-api]]
=== Selection and mutation contracts

The standard `EntityHandler` contract, shared by `EntityManager` and `EntityAgent`, creates executable queries and statements.
`EntityManager` executes operations in a persistence context; `EntityAgent` operates on detached entities.
Hibernate implements these contracts using `Session` and `StatelessSession` respectively.
Execution options involving managed state, such as read-only loading and automatic flushing, apply to a persistence context.

|===
| Operation | Standard contract | Hibernate contract | Execution

| Selection | `TypedQuery<T>` | `SelectionQuery<T>` | `getResultList()`, `getSingleResult()`, `getSingleResultOrNull()`
| Mutation | `Statement` | `MutationQuery` | `execute()`
| Mixed or legacy usage | `Query` | `Query<T>` | Selection methods or `executeUpdate()`
|===

Prefer typed selections and dedicated mutation statements.
The older `Query` contract combines selections and mutations; use it when an existing API requires it.
Hibernate's `Query<T>` extends the standard typed-query API and exposes provider-specific controls.

[[jpa-query-api]]

`createQuery(hql, Result.class)` creates a `TypedQuery<Result>`.
`createStatement(hql)` creates a `Statement` for an insert, update, or delete.

[[hql-getting-started]]
=== Creating queries and statements

HQL and Criteria selections use the same execution API. [[jpql-api-named-query-example]]Named queries may be declared using annotations or registered with the factory.
[[hql-api-named-query-example]]Hibernate provides corresponding typed creation methods for named selections and mutations.


A query may be provided to Hibernate as either:

* an _inline query_: the text of the query is passed as a string to the session at runtime, or
* a _named query_: the query is specified in an annotation or XML file, and identified by name at runtime.

A `Query` object is obtained from the `EntityManager` or Hibernate `Session` by calling `createQuery()` or `createNamedQuery()`.

The API for actually executing the query is the same in both cases, as we're about to see <<query-execution,below>>.

* `Query#getResultList()` is useful when the query might return zero, or more than one result.
* `Query#getSingleResult()` is only for cases where the query always returns exactly one result.
  It throws an exception when zero or many results are returned by the database.

* `Query#getResultStream()` exposes a stream; see <<hql-api-incremental>> for Hibernate resource handling.

[[query-result-shapes]]
==== Entities, scalar values, tuples, and DTOs

The result class describes what each result represents.
An entity selection returns entity instances, managed when loaded through an `EntityManager`.
A scalar selection returns a value; multiple selections may be represented by `Object[]`, `Tuple`, or a DTO with a matching constructor.
DTO instances are not managed entities.
See link:{doc-query-language-url}#select-new[HQL instantiation], <<criteria-typedquery>>, and <<sql-dto-query>> for construction and mapping details.

[[hql-api-result-transformers]]
=== Query result transformers

A program may hook into the process of building the query results by providing a `org.hibernate.query.ResultListTransformer` or `org.hibernate.query.TupleTransformer`.

See the https://docs.hibernate.org/orm/{majorMinorVersion}/javadocs/org/hibernate/query/TupleTransformer.html[TupleTransformer] and https://docs.hibernate.org/orm/{majorMinorVersion}/javadocs/org/hibernate/query/ResultListTransformer.html[ResultListTransformer] Javadocs for additional details.

A `TupleTransformer` transforms each row; a `ResultListTransformer` transforms the assembled result list.
These provider-specific hooks are also available to native SQL queries.
Use standard constructor or programmatic result mappings where they express the required result shape.

[[query-mutations]]
=== Executing mutations

A mutation statement executes an insert, update, or delete against the database and requires an active transaction.
For HQL and Criteria mutations, `Statement.execute()` and Hibernate's `MutationQuery.execute()` return the affected-entity count;
legacy `Query.executeUpdate()` serves the same purpose. Native SQL mutations return database row counts.
With multi-table inheritance, affected-entity counts need not equal the number of affected database rows.

Bulk HQL and Criteria mutations do not update entity instances already held in the persistence context or invoke entity lifecycle callbacks.
Flush pending changes when appropriate before the mutation, and clear or refresh affected managed state afterward.
Clearing also detaches other managed entities; do not discard unflushed changes.
See <<pc>> and <<flushing>> for persistence-context synchronization.

[[batch-bulk-hql-update-delete]]
==== Update and delete execution

Updates and deletes are polymorphic and may affect multiple tables.
A bulk update does not increment the entity version by default; HQL's `update versioned` form requests a version change.
See link:{doc-query-language-url}#update[Update statements] and link:{doc-query-language-url}#delete[Delete statements].

[[batch-bulk-hql-insert]]
==== Insert execution and conflict handling

HQL supports both insert-values and insert-select statements.
These are database mutations, rather than calls to `persist()` for individual entities.
See link:{doc-query-language-url}#insert[Insert statements] for assignment and id-generation rules.

On MySQL and MariaDB, conflict handling uses `on duplicate key`, which cannot select a particular conflict constraint.
With multiple unique constraints, results may differ from those on databases with an explicit conflict target.
Their JDBC affected-row counts also distinguish inserted and updated rows; consult the driver and database documentation when interpreting them.

[[batch-bulk-hql-strategies]]
==== Bulk mutation strategies

When a bulk mutation involves multiple tables, Hibernate has to issue individual DML statements to the respective tables.
Since the mutation itself could have an effect on the conditions used in the statement, it's generally not possible
to simply execute parts of the DML statement against the respective tables. Instead, Hibernate has to temporarily remember
which rows will be affected, and execute the DML statements based on these rows.

Usually, Hibernate will make use of local or global temporary tables to remember the primary keys of the rows.
For some databases, currently only PostgreSQL and DB2, a more advanced strategy (`CteMutationStrategy`) is used,
which makes use of DML in CTE support to execute the whole operation in one SQL statement.

The chosen strategy, unless overridden through the `hibernate.query.mutation_strategy` setting, is based on the
Dialect support through `org.hibernate.dialect.Dialect.getFallbackSqmMutationStrategy`.

[[batch-bulk-hql-strategies-non-temporary-table]]
===== Non-temporary table bulk mutation strategies

The strategies outlined above depend on the creation of temporary tables, which Hibernate creates on startup if they don't already exist. At present this process is not integrated in the schema management tooling, and this requires that the user have the required permissions to alter the database schema.

If the Hibernate session user lacks these permissions, you will need to either:

 * alter your schema through a different user with more permissions, to add a global temporary table named HTE_<root entity table name>, which contains all columns of all tables involved in the entity hierarchy. +
This will allow insert, update and delete in HQL for multi-table entities.

* OR configure Hibernate ORM to use the (badly-performing) inline strategy (for _mutations_ only!):

[source,xml]
----
<property name="hibernate.query.mutation_strategy"
          value="org.hibernate.query.sqm.mutation.internal.inline.InlineMutationStrategy"
/>
----

[IMPORTANT]
====
We strongly recommend the use of the first option, i.e. manually adding the temporary tables, because the inline strategy is set to be removed in a future release. Also, there is no equivalent strategy for inserts.

Additionally, automatic creation of temporary tables should be deactivated. This is done by setting the

`hibernate.query.mutation_strategy.global_temporary.create_tables` and `hibernate.query.mutation_strategy.global_temporary.drop_tables`

*or*

`hibernate.query.mutation_strategy.persistent.create_tables` and `hibernate.query.mutation_strategy.persistent.drop_tables`

properties (depending on the default strategy for the dialect) to `false`
====

[[query-options]]
=== Execution options

Options may be supplied through standard APIs, provider-specific setters, or query hints.
Timeout and fetch-size units differ: the standard `jakarta.persistence.query.timeout` hint is in milliseconds,
while Hibernate's `setTimeout(int)` uses seconds; JDBC fetch size is a driver hint measured in rows.
Typed standard options such as `Timeout`, `QueryFlushMode`, and `ReadOnlyMode` avoid string hints where supported.

Jakarta Persistence defines some standard hints with the prefix `jakarta.persistence`, but most hints are provider specific.
Using provider-specific hints limits your program's portability to only a small degree.

|===
| Hint name | Interpretation | Equivalent Hibernate API

| `jakarta.persistence.query.timeout` | The query timeout, in milliseconds. | `Query#setTimeout()`
| `jakarta.persistence.fetchgraph` | An `EntityGraph` to be interpreted as a _fetchgraph_, as defined by the Jakarta Persistence specification.
| See <<chapters/fetching/Fetching.adoc#fetching,Fetching>>.
| `jakarta.persistence.loadgraph` | An `EntityGraph` to be interpreted as a _loadgraph_, as defined by the Jakarta Persistence specification.

| `org.hibernate.cacheMode` | The `CacheMode` to use. | `Query#setCacheMode()`
| `org.hibernate.cacheable` | `true` if the query is cacheable. | `Query#setCacheable()`
| `org.hibernate.cacheRegion` | For a cacheable query, the name of a cache region to use. | `Query#setCacheRegion()`
| `org.hibernate.comment` | A comment to apply to the generated SQL. | `Query#setComment()`
| `org.hibernate.fetchSize` | The JDBC fetch size to use. | `Query#setFetchSize()`
| `org.hibernate.flushMode` | The query's `QueryFlushMode`. Hibernate also accepts legacy `FlushMode` and `FlushModeType` values and converts them to a query flush mode.
Prefer the typed standard query flush controls where applicable.
| `Query#setQueryFlushMode()`
| `org.hibernate.readOnly` | `true` if newly loaded entities should be marked as read-only.
| `Query#setReadOnly()`
|===

[TIP]
====
For named queries, query hints may be specified using the `@QueryHint` annotation.

[[hql-api-execution]]
==== Advanced control over query execution

When working directly with a Hibernate `Session`, the interface `org.hibernate.query.Query` is used to control the execution of the query.

Whereas we needed to specify some information using query hints when working with the Jakarta Persistence API, here we have typesafe setters:

|===
| `Query#setTimeout()` | Sets the JDBC-level query timeout.
| `Query#setFetchSize()` | Sets the JDBC-level fetch size.
| `Query#setCacheable()` and `setCacheRegion()` | Control query caching.
| `Query#setCacheMode()` | Overrides the session-level cache mode.
| `Query#setQueryFlushMode()` | Controls whether this query triggers flushing. Flushing is covered in detail in <<chapters/flushing/Flushing.adoc#flushing,Flushing>>.
| `Query#setLockMode()` | Sets the requested lock mode. Locking is covered in detail in <<chapters/locking/Locking.adoc#locking,Locking>>.
| `Query#setReadOnly()` | Overrides the session-level default for read-only state. The concept of read-only state is covered in <<chapters/pc/PersistenceContext.adoc#pc,Persistence Contexts>>.
| `Query#setComment()` | Adds a comment to the generated SQL.
| `Query#addQueryHint()` | Add a hint to the generated SQL.
|===

[IMPORTANT]
====
`addQueryHint()` allows specification of a hint intended for the database query planner.
A hint is added directly to the generated SQL according to `Dialect#getQueryHintString()`.

On the other hand, `setHint()` refers to the Jakarta Persistence notion of a query hint, a hint that targets the provider (Hibernate).
This is a completely different concept.
====

For complete details, see the https://docs.hibernate.org/orm/{majorMinorVersion}/javadocs/org/hibernate/query/Query.html[Query] Javadocs.

[[hql-query-plan-cache]]
=== Query compilation and plan caching

Hibernate caches HQL interpretations and reusable execution plans to avoid repeating compilation work.
Criteria queries already represent a query tree; they are not parsed as HQL strings.
Criteria plan caching and query-tree copying have separate controls.

See the generated settings for <<settings-hibernate.query.plan_cache_enabled,`hibernate.query.plan_cache_enabled`>>,
<<settings-hibernate.query.plan_cache_max_size,`hibernate.query.plan_cache_max_size`>>,
<<settings-hibernate.criteria.plan_cache_enabled,`hibernate.criteria.plan_cache_enabled`>>, and
<<settings-hibernate.criteria.copy_tree,`hibernate.criteria.copy_tree`>>.
The older `hibernate.query.plan_parameter_metadata_max_size` setting no longer controls a separate parameter-metadata cache.

Plan caching does not cache query results. See <<caching-query>> for result caching and
<<statistics-query-plan-cache>> for plan-cache measurements.
