[[QuerySpecification]]
== Programmatic query specifications
:example-dir-query-guide: {core-project-dir}/src/test/java/org/hibernate/orm/test/query/criteria

The `org.hibernate.query.specification` package supports iterative customization of a base query.
Use a specification to add restrictions, sorting, fetching, or projections before creating an executable query.
Unlike an executable query, a specification is not tied to a particular session.
These APIs are incubating; consult the link:{doc-javadoc-url}org/hibernate/query/specification/QuerySpecification.html[Javadocs] for their contracts.

[[query-specification-sources]]
=== Starting a specification

|===
| Base | Selection factory | Mutation factory

| Root entity | `SelectionSpecification.create(Entity.class)` | `UpdateSpecification.create(Entity.class)`, `DeleteSpecification.create(Entity.class)`
| HQL | `SelectionSpecification.create(Entity.class, hql)` | `MutationSpecification.create(Entity.class, hql)`
| Criteria | `SelectionSpecification.create(criteriaQuery)` | `MutationSpecification.create(criteriaUpdate)` or `create(criteriaDelete)`
| Typed reference | `SelectionSpecification.create(typedQueryReference)` | `MutationSpecification.create(statementReference)`
|===

A selection specification returns a single root entity, possibly with fetched associations.
Additional restrictions and ordering apply to that root.
Use <<query-specification-projections,projection specifications>> for other result shapes.
The HQL factory for mutation specifications accepts update and delete statements, not insert statements.
These facilities complement <<criteria,Criteria queries>>; they do not replace the full Criteria API.

[[SelectionSpecification]]
=== Selection specifications

`restrict()` adds a restriction expressed using `Restriction` and the static metamodel.
`sort()` appends ordering, while `resort()` replaces the existing ordering.
After customization, `createQuery(EntityHandler)` obtains an executable `SelectionQuery` associated with the given `Session` or `StatelessSession`.

[[query-specification-augmentation]]
=== Fetching and augmentation

`fetch()` adds an association path represented by `org.hibernate.query.restriction.Path`.
`augment()` accepts a callback with the builder, Criteria query, and root for additional Criteria customization.
When changing `where()` or `orderBy()` inside the callback, remember that these Criteria methods replace the existing clause.
See <<fetching>> for fetching behavior and <<criteria-extensions>> for `CriteriaDefinition`.

[[MutationSpecification]]
=== Mutation specifications

A mutation specification restricts the target of an update or delete.
`UpdateSpecification` also supports assigning attribute values; `DeleteSpecification` constructs a delete directly from an entity type.
Execution uses a `MutationQuery` and follows the transaction and managed-state rules in <<query-mutations>>.

[[query-specification-projections]]
=== Projections, counts, and existence tests

`createProjection()` creates a projected selection based on the specification.
Each selected attribute produces an `Element` for typed access to the corresponding item of an `Object[]` result.
The projection retains a reference to the base specification, so later customization of the base also affects the projection.
`createCountProjection()` and `createExistsProjection()` provide scalar count and existence results.
Remove unnecessary ordering from a specification used for a count projection, since ordering by a non-aggregated attribute can produce invalid SQL.
The example clears ordering before counting and restores it before projecting the titles.

[[query-specification-validation]]
=== Validation, Criteria conversion, and references

`validate(CriteriaBuilder)` checks a specification without executing it.
`buildCriteria(CriteriaBuilder)` produces a Criteria object; subsequent changes to that object are not reflected in the specification.
`reference()` exposes a typed query or statement reference that can be used as the base of another specification or passed to the standard query-creation API.

[[query-specification-execution]]
=== Execution and pagination

Set execution options and parameter values on the executable query returned by `createQuery()`.
For offset pagination, a `SelectionQuery` accepts a `Page` through `setPage()`.
See <<jpql-pagination>> and <<query-key-pagination>> for offset and key-based pagination,
and <<query-options>> for other execution controls.
