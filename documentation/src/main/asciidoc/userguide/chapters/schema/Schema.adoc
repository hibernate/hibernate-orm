[[schema-generation]]
== Schema Tooling
:example-dir-schemagen: {core-project-dir}/src/test/java/org/hibernate/orm/test/schema
:example-dir-schemagen-resources: {core-project-dir}/src/test/resources
:schema-guide-examples: {example-dir-schemagen}/guide
:schema-guide-resources: {example-dir-schemagen-resources}/org/hibernate/orm/test/schema/guide
:extrasdir: extras

Hibernate's schema tooling can create database objects from mappings, export DDL scripts,
validate an existing schema, and perform supported schema alterations.
Mapped objects include tables, columns, constraints, indexes, sequences, and configured auxiliary objects.
Historically, this tooling has been called _HBM2DDL_.
For explicit tenant-schema targeting and provisioning responsibilities, see <<multitenancy-provisioning>>.

Generation, validation, and migration serve different purposes.
Generation creates objects from the current mappings; validation checks supported aspects of existing objects.
Hibernate can execute schema creation and alteration commands against a database or write them to script files for later execution.
For schema evolution across application versions, consider dedicated schema versioning tools such as Flyway or Liquibase.
Versioned migrations record how the schema and its data evolve and can express changes beyond those Hibernate can infer from mapping metadata.

Generated SQL depends on the dialect, mappings, naming strategies, and configuration.
The SQL examples in this chapter illustrate H2 output unless another database is identified.

See <<settings-schema>> for schema-tooling settings and <<naming>> for naming strategies.

[[schema-generation-actions]]
=== Selecting schema actions

Jakarta Persistence defines separate settings for the database and script targets:

* `jakarta.persistence.schema-generation.database.action` controls operations executed against the database.
* `jakarta.persistence.schema-generation.scripts.action` controls commands written to DDL scripts.

Both targets default to no action. Configuring a script target does not, by itself, execute its commands against the database.
Hibernate also supports `hibernate.hbm2ddl.auto`, which selects automatic database operations during factory startup
and, for `create-drop`, factory shutdown.

[cols="3,2,2",options="header"]
|===
|Operation |Jakarta Persistence action value |`hibernate.hbm2ddl.auto` value
|No action |`none` |`none`
|Create without an initial drop |`create` |`create-only`
|Drop |`drop` |`drop`
|Drop and recreate |`drop-and-create` |`create`
|Drop and recreate at startup, then drop at shutdown |Not a standard action |`create-drop`
|Validate existing mapped objects |Not a standard action |`validate`
|Apply supported schema alterations |Not a standard action |`update`
|===

The two settings interpret `create` differently.
Hibernate's `hibernate.hbm2ddl.auto=create` first drops the mapped objects and then creates them.
The standard Jakarta Persistence `create` action creates objects without first dropping them.
A drop or recreation operation can destroy data in the affected objects.

Hibernate accepts additional action values through its schema tooling; those values are provider extensions.
See link:{doc-javadoc-url}org/hibernate/tool/schema/Action.html[Action] for the complete list.
For example, Hibernate also supports population, truncation, and generator synchronization;
see <<schema-generation-programmatic>> for explicit operations.

==== Defaults and precedence

An explicit standard database action takes precedence over `hibernate.hbm2ddl.auto`, including an explicit `none`.
When a standard script action other than `none` is selected and no standard database action is supplied,
Hibernate does not fall back to `hibernate.hbm2ddl.auto` for database execution.
Configure both targets explicitly when both are wanted, rather than relying on a mixture of standard and legacy defaults.

Schema-action selection happens after settings from the bootstrap sources are combined.
See <<bootstrap>> for persistence-unit configuration and property overrides.

==== Validation and update

`validate` checks supported aspects of the mapped database objects, such as tables, columns, compatible column types,
and sequence definitions. It does not establish complete equivalence between the mappings and the database,
and does not repair discrepancies. Additional validation of indexes and unique keys is controlled by
`hibernate.tooling.schema.index_validation` and `hibernate.tooling.schema.unique_key_validation`.

`update` applies supported schema alterations inferred from the current mappings and database metadata.
It does not infer arbitrary data transformations or reliably interpret a removed column and an added column as a rename.
It is not a replacement for a versioned migration history. Neither `validate` nor `update` is a portable Jakarta Persistence action.
Hibernate can also write the inferred alterations to a script without executing them; see <<schema-generation-alteration-scripts>>.

----
====

The standard `scripts.create-target` and `scripts.drop-target` properties accept a `Writer`
or a string containing a file URL, for example `Path.of("create.sql").toUri().toString()`.
Use fully qualified property names beginning with `jakarta.persistence.schema-generation.`.
Hibernate defaults to appending to script files.
Set `hibernate.hbm2ddl.schema-generation.script.append=false` to overwrite creation and drop script files instead.
This setting applies to both file-URL targets and Hibernate's filesystem-path target extension.
A caller-supplied writer uses the truncation or append mode selected when it was opened.
A caller-supplied writer has its own lifecycle; close it when it is no longer needed.

Generation still needs a target dialect even when commands are written only to scripts.
Hibernate may obtain database information through a connection.
For offline generation, explicitly configure the dialect and disable JDBC metadata access using
`hibernate.boot.allow_jdbc_metadata_access=false`; see <<database-dialect>>.
The standard `jakarta.persistence.database-product-name` and product-version properties are another way
to supply database information. Supply enough information to select the intended dialect and version.

==== Exporting schema alterations

Hibernate also accepts `update` for `jakarta.persistence.schema-generation.scripts.action`.
This is a Hibernate extension, not a standard Jakarta Persistence action.
It compares the mappings with the existing database metadata and writes supported alterations to the
`jakarta.persistence.schema-generation.scripts.create-target`.
Set the database action to `none` to generate the script without executing the alterations.

[[schema-generation-script-files]]
=== DDL sources and initial data

==== Choosing creation and drop sources

The target specifies where commands go; the source specifies where they come from.
`jakarta.persistence.schema-generation.create-source` and `jakarta.persistence.schema-generation.drop-source`
select independently among:

[cols="1,3",options="header"]
|===
|Source value |Commands used
|`metadata` |DDL derived from the ORM mappings.
|`script` |Commands from the configured source script.
|`metadata-then-script` |Mapping-derived DDL followed by source-script commands.
|`script-then-metadata` |Source-script commands followed by mapping-derived DDL.
|===

Supply the source scripts using `jakarta.persistence.schema-generation.create-script-source`
and `jakarta.persistence.schema-generation.drop-script-source`.
Each accepts a `Reader` or a string identifying a script URL.
Without an explicit source selection, a configured source script implies `script`; otherwise the source is `metadata`.
Thus, supplying a script alone does not automatically combine it with mapping-derived DDL.
Choose the combined source explicitly when both are needed, and choose an order that respects object dependencies.

Prefer `jakarta.persistence.sql-load-script-source` for SQL that populates the schema.
It accepts a `Reader` or a string identifying a script URL.

Hibernate's deprecated `hibernate.hbm2ddl.import_files` setting accepts a comma-separated list of resource names,
processed in list order. Prefer the standard load-script property for new configuration.
Hibernate also looks for `/import.sql` on the classpath when no legacy import-file list is supplied.
Use `hibernate.hbm2ddl.skip_default_import_file=true` to skip this implicit file; explicitly configured scripts still apply.
The standard and legacy properties can both contribute load commands, so avoid configuring the same data twice.

==== Script parsing and execution options

Hibernate's default script extractor expects one complete SQL statement per line.
For statements spanning multiple lines, select `hibernate.hbm2ddl.import_files_sql_extractor=multi-line`;
terminate statements with semicolons. The extractor applies to source scripts as well as load scripts.
A script is parsed by Hibernate, not by a database command-line client: client-specific commands and delimiter directives
may require a custom `SqlScriptCommandExtractor` or an external execution tool.

`hibernate.hbm2ddl.charset_name` selects the charset for script files, and `hibernate.hbm2ddl.delimiter`
selects the delimiter appended to generated script commands.
Set `hibernate.hbm2ddl.halt_on_error=true` to stop automatic schema tooling on an execution error;
otherwise Hibernate generally logs command failures and continues.
Failure does not guarantee that earlier DDL is rolled back. Database transaction and DDL behavior vary.

Mapping a table to a named database schema does not necessarily create the schema itself.
`jakarta.persistence.create-database-schemas=true` requests namespace creation during applicable database schema operations.

`validate()` checks the existing mapped objects. It does not change them.
`populate()` executes the configured initial-data scripts against an existing schema without first clearing its tables.
Repeated population may fail if the data already exists.
Hibernate's `truncate()` clears mapped tables, resets associated generators, and reloads configured initial data.
This differs from dropping and recreating the schema.

`SessionFactory.getSchemaManager()` returns Hibernate's extended `org.hibernate.relational.SchemaManager` contract.
Additional operations include `truncateTable()`, which does not repopulate the table,
`resynchronizeGenerators()`, which aligns supported sequence and table generators with imported identifier values,
and schema/catalog targeting through `forSchema()` and `forCatalog()`.
Population does not automatically resynchronize generators; request that separately when externally inserted identifiers require it.
See link:{doc-javadoc-url}org/hibernate/relational/SchemaManager.html[the Hibernate SchemaManager API].

These operations do not update objects already held in an entity manager or automatically invalidate all cached entity data.
Run them at a deliberate lifecycle boundary, close or clear affected persistence contexts, and evict affected cache regions when needed.
See <<pc>> and <<caching>>.
For integrations requiring lower-level control, see link:{doc-javadoc-url}org/hibernate/tool/schema/spi/SchemaManagementTool.html[SchemaManagementTool].

==== Indexes

`@Index` declares an index through table mapping annotations.
Its `columnList` specifies database column names and can include `ASC` or `DESC` ordering.
An index is distinct from a unique constraint; setting `unique=true` requests uniqueness as well.
Its physical representation depends on the dialect.
