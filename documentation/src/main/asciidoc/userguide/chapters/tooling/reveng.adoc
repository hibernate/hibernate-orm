[[tooling-reveng]]
=== Reverse-engineering reference

Reverse engineering reads an existing database schema via JDBC and generates various artifacts
from it.  This is useful for bootstrapping a Hibernate project from a legacy database, or for
regenerating model sources as a schema evolves. Generated sources are an input to application
development, not a database migration or an automatic merge of application edits. Keep generated
output in a dedicated directory and account for replacement of manually edited files.

:tooling-reveng-examples: {root-project-dir}/tooling/hibernate-reveng/src/test/resources/guide
:tooling-reveng-java: {root-project-dir}/tooling/hibernate-reveng/src/test/java/org/hibernate/tool/reveng/guide

See the tool-specific discussions (<<tooling-gradle-reveng,Gradle>>, <<tooling-maven-reveng,Maven>>
and <<tooling-ant-reveng,Ant>>) for details on integrating reverse engineering into those environments.


[[tooling-reveng-exporters]]
==== Exporters

The following artifacts can be generated from a database schema:

Java entity classes:: Annotated Jakarta Persistence entity classes.
Data Access Objects (DAOs):: DAO classes providing basic CRUD operations.
`hbm.xml` mapping files:: Hibernate XML mapping files.
`hibernate.cfg.xml`:: A configuration file listing the generated mappings.
DDL scripts:: SQL schema creation and drop scripts.
HTML documentation:: An HTML report describing the database schema.
Custom FreeMarker templates:: User-defined templates for arbitrary code generation.

Which exporters are available and how they are configured depends on the build tool.
See <<tooling-gradle-reveng-tasks,Gradle tasks>>, <<tooling-maven-reveng-goals,Maven goals>>,
or <<tooling-ant-reveng-exporters,Ant exporters>> for specifics.


[[tooling-reveng-connection]]
==== JDBC connection settings

Reverse engineering connects to the database using settings from a `hibernate.properties` file:

[source,properties]
----
hibernate.connection.driver_class=org.h2.Driver
hibernate.connection.url=jdbc:h2:./guide
hibernate.connection.username=sa
hibernate.connection.password=
hibernate.default_schema=PUBLIC
----

For the build examples, create a disposable H2 database at this URL containing a simple table:

[source,sql]
----
create table BOOK (ID bigint not null primary key, TITLE varchar(255));
----

The relative database URL is resolved from the build's working directory. Generation does
not create this input schema. Do not use a catalog/schema filter that excludes the tables
you intend to inspect.

The JDBC driver must be available on the classpath (typically declared as a project dependency).
The location of the properties file is configured in the build tool plugin -- see
<<tooling-gradle-reveng-properties,Gradle>>, <<tooling-maven-reveng-common-params,Maven>>,
or <<tooling-ant-reveng-configurations,Ant>> for details.


[[tooling-reveng-config]]
==== Reverse-engineering XML

An optional XML configuration file can be used to customize how the database schema is interpreted.
The file uses the `hibernate-reverse-engineering` document type:

[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE hibernate-reverse-engineering SYSTEM
    "https://hibernate.org/dtd/hibernate-reverse-engineering-3.0.dtd">

<hibernate-reverse-engineering>
    <!-- configuration elements go here -->
</hibernate-reverse-engineering>
----

The path to this file is configured via the build tool plugin (e.g. `revengFile` in Gradle and Maven,
`revengfile` attribute on `<jdbcconfiguration>` in Ant).


[[tooling-reveng-schema-selection]]
===== Schema selection

Without explicit schema selections, reverse engineering uses `hibernate.default_catalog`
and `hibernate.default_schema`, when configured, to limit table discovery. For example,
the <<tooling-reveng-connection,JDBC properties above>> limit discovery to the `PUBLIC`
schema. With neither setting configured, discovery uses the JDBC driver's behavior
for unspecified catalog and schema patterns.

Use `<schema-selection>` elements to explicitly select catalogs, schemas, or tables.
These selections replace the initial selection derived from the default catalog
and schema settings:

[source,xml]
----
include::{tooling-reveng-examples}/hibernate.reveng.xml[tags=guide-schema-selection]
----

With standard JDBC metadata discovery, `match-catalog` selects an exact catalog name,
while `match-schema` and `match-table` accept SQL `LIKE` patterns: `%` matches any
sequence of characters and `_` matches one character. For example,
`match-table="PROD%"` selects table names starting with `PROD`. Do not assume catalog
wildcards are portable across JDBC drivers.


[[tooling-reveng-type-mapping]]
===== Type mappings

The `<type-mapping>` element overrides how SQL types are mapped to Hibernate types:

[source,xml]
----
include::{tooling-reveng-examples}/hibernate.reveng.xml[tags=guide-type-mapping]
----

Each `<sql-type>` element supports the following attributes:

`jdbc-type`:: The JDBC type name (e.g. `VARCHAR`, `INTEGER`, `NUMERIC`). Required.
`hibernate-type`:: The Hibernate type to use. Required.
`length`:: Match only columns with this length.
`precision`:: Match only columns with this precision.
`scale`:: Match only columns with this scale.
`not-null`:: Match non-nullable columns (`true`) or nullable columns (`false`).

Mappings are grouped by JDBC type and length. An exact length bucket is selected when
present; otherwise the unspecified-length bucket is used. Within that bucket, the first
matching mapping wins, so put precision/scale-specific entries before a general entry.
An exact-length bucket with no matching entry does not fall back to the unspecified-length
bucket. Do not assume arbitrary sorting by the number of attributes.


[[tooling-reveng-table-filter]]
===== Table filters

`<table-filter>` elements control which tables are included or excluded, and can assign
a package name to the generated classes:

[source,xml]
----
include::{tooling-reveng-examples}/hibernate.reveng.xml[tags=guide-table-filter]
----

The first matching filter decides whether a table is included. Here, audit tables
are excluded before the `PROD_.*` rule assigns a package to product tables. The final
rule includes all remaining tables. Without that final rule, an unmatched table is
excluded if any inclusion filter is present; with only exclusion filters, unmatched
tables are included.

The `match-catalog`, `match-schema`, and `match-name` attributes use case-sensitive,
limited wildcard matching: exact text, `.*` for any value, `PREFIX.*`, `.*SUFFIX`, or
`.*CONTAINS.*`. These are not general Java regular expressions. For example, `PROD_.*`
matches a name starting with `PROD_`; arbitrary character classes and alternation are not supported.


[[tooling-reveng-table]]
===== Per-table configuration

The `<table>` element provides fine-grained control over individual tables:

[source,xml]
----
include::{tooling-reveng-examples}/hibernate.reveng.xml[tags=guide-table]
----

The `<table>` element supports the following attributes:

`name`:: The table name. Required.
`catalog`:: The catalog name.
`schema`:: The schema name.
`class`:: The Java class name to use instead of the default derived name.

The `<primary-key>` child element controls identifier generation. It accepts a `property` attribute
for the property name, and nested `<key-column>` and `<generator>` elements.

The `<column>` child element overrides individual column mappings. It accepts `name` (required),
`property`, `type`, and `exclude` attributes.

The `<foreign-key>` child element customizes association mappings for a specific foreign key
constraint. It accepts `constraint-name` and `foreign-table` attributes, and can contain
`<many-to-one>`, `<set>`, `<one-to-one>`, and `<inverse-one-to-one>` child elements to control
the generated association properties.


[[tooling-reveng-detection]]
==== Detection settings

The build tool plugins expose several boolean settings that control how relationships and special
columns are detected:

`detectManyToMany`:: When `true`, pure link tables (tables whose primary key consists entirely of
two foreign keys and no other columns) are mapped as `@ManyToMany` associations instead of generating
an entity for the link table. Default: `true`.

`detectOneToOne`:: When `true`, foreign keys that are also the primary key of their table are mapped
as `@OneToOne` associations. Default: `true`.

`detectOptimisticLock`:: When `true`, columns named `VERSION`, `TIMESTAMP`, or `DBTIMESTAMP` with
appropriate types are mapped as `@Version` properties. Default: `true`.

These settings are configured in the build tool plugin.  See
<<tooling-maven-reveng-common-params,Maven>> or <<tooling-ant-reveng-configurations,Ant>> for details.


[[tooling-reveng-custom-strategy]]
==== Custom strategies

For programmatic control over reverse engineering, implement the
`org.hibernate.tool.reveng.api.core.RevengStrategy` interface. This interface provides callbacks
for customizing class names, property names, type mappings, association handling, and more.

The following example extends the supplied `DelegatingStrategy` helper, delegating to the
configured strategy and changing only class naming and temporary-table exclusion. This helper
is in an internal package; its use couples the implementation to Hibernate tooling versions.
The strategy interface itself is `org.hibernate.tool.reveng.api.core.RevengStrategy`:

[source,java,indent=0]
----
include::{tooling-reveng-java}/GuideStrategy.java[]
----

Configure the class using `revengStrategy` in Gradle/Maven or `reversestrategy` in Ant.
A public constructor accepting `RevengStrategy` preserves the configured delegate, including
XML overrides. A public no-argument constructor is also accepted, but cannot accept that
delegate; prefer the delegating constructor when combining a strategy with XML configuration.

Key methods available for override:

`tableToClassName`:: Controls the entity class name for a given table.
`columnToPropertyName`:: Controls the property name for a given column.
`columnToHibernateTypeName`:: Controls the Hibernate type mapping for a column.
`excludeTable`:: Returns `true` to skip a table entirely.
`excludeColumn`:: Returns `true` to skip a specific column.
`isManyToManyTable`:: Returns `true` if a table should be treated as a many-to-many link table.
`isOneToOne`:: Returns `true` if a foreign key represents a one-to-one relationship.
`getTableIdentifierStrategyName`:: Controls the identifier generation strategy for a table.
`foreignKeyToCollectionName`:: Controls the property name for a collection association.
`foreignKeyToEntityName`:: Controls the property name for a many-to-one association.
