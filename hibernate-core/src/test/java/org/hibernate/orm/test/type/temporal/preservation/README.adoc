= Type-specific temporal preservation tests

The seven typed suites cover new direct-enabled handling and matched fallback
conversion. They mirror the organization of the legacy temporal tests while leaving
those tests focused on explicit-conversion compatibility.

The tests assert resolved handlers, SQL forms and preservation parts independently,
then compare ORM writes against JDBC reads and independent JDBC writes against ORM
reads. Domain assertions retain offsets and zone identity, with explicit precision
expectations and fixed-offset ZonedDateTime COLUMN reconstruction. Unsupported
mappings/values and corrupt tuples are real rejection assertions.

Live profiles explicitly admit H2, PostgreSQL/PostGIS/EDB, and Oracle; PostgreSQL
Dialect inheritance alone does not admit Spanner PostgreSQL or unknown subclasses.
Before runtime bootstrap, a separate provisioning connection discovers the server
version. Both metadata modes use that version, and a conflicting explicit live
version fails setup. The metadata-disabled runtime provider remains guarded and
must record no bootstrap connection attempts. Setup drops only fixture-owned
objects and creates them separately, including on Oracle versions before 23.

== Running profiles

Ordinary test execution covers E0 under the default UTC Gradle JVM. For named
profiles use the standalone task; it avoids JUnit's launch schema cleaner for
cross-process rows:

[source,shell]
----
./gradlew :hibernate-core:temporalPreservationMatrix -Pdb=h2 -Ptest.threads=1 \
  -PtemporalMatrixProfile=E3 -PtemporalTestJvmTimeZone=America/Denver \
  -PtemporalTestJdbcTimeZone=America/Los_Angeles
----

[cols="1,2,2",options="header"]
|===
|Profile |Writer/reader JVM |Writer/reader session
|E0 |UTC / UTC |UTC / UTC
|E1 |Denver / Denver |UTC / UTC
|E2 |Tokyo / Tokyo |Tokyo / Tokyo
|E3 |Denver / Denver |UTC / Tokyo
|E4 |Denver / Denver |Tokyo / UTC
|E5 |Denver / Tokyo, separate launches |UTC / Tokyo
|E6 |Tokyo / Denver, separate launches |Tokyo / UTC
|===

Use full ZoneIds America/Denver and Asia/Tokyo with temporalTestJvmTimeZone.
E3-E6 use temporalTestJdbcTimeZone=America/Los_Angeles; E0-E2 leave it unset.
The profile sets and verifies the actual writer/reader connection zones independently.
temporalTestSessionTimeZone, when supplied, initializes connections before those
phase-specific overrides. These settings do not request domain adjustment.

For E5/E6 run temporalMatrixPhase=write, followed by temporalMatrixPhase=read,
against the same dedicated database. For H2 use a shared file-backed
temporalMatrixUrl rather than an in-memory database. The reader verifies persisted
writer JVM/process identity and validates schema only after releasing its boot guard.
Run phases serially. temporalMatrixMetadata accepts both (default), true or false;
temporalMatrixType selects one of the seven type names. Default phase is both.

== Scope and diagnostics

E0 uses the complete historical/offset/finite-range catalog and negative cases.
Other profiles retain representative/overlap/seasonal inputs; E3/E4 add precision
carry cases. All profiles include historical fallback regression coverage.
Null persistence/updates and fresh-session reads have caches disabled.

GuardedConnectionProvider is lazy and non-pooling. Metadata-disabled boot rejects
and counts every connection acquisition through SessionFactory construction,
including caught attempts. Schema is provisioned separately; the guard opens for
live execution. Driver identity is configured at boot and recorded from runtime
metadata after release. No preinitialized DialectContext supplies the Dialect.

TP_CASE records resolutions, successful samples and expected rejections; TP_BOOT
and TP_ENV record bootstrap and actual runtime environment. Standalone execution
produces this inventory rather than JUnit XML counts. Distinct physical connections
are held open together and checked by server-side session IDs.

Precision expectations follow the selected driver's execution behavior rather than
pre-binding canonicalization. COLUMN stores the original/adjusted auxiliary offset;
regional read adjustment resolves the final extracted instant. Finite SQL/carrier
ranges are required; date/timestamp infinity sentinels are excluded. H2/PostgreSQL/Oracle live support is explicit; SQL Server live verification remains deferred.

== EDB range characterization

`EdbTemporalCharacterizationTests` runs only against EDB. It records timestamp
expressions across statements/transactions, the actual type of natural `date` and
`pg_catalog.date`, session-local `edb_redwood_date` modes, and typed LocalDate
binding/extraction for candidate bounds, neighboring dates, BCE/CE controls and
infinity sentinels. Run it separately with the EDB driver and pgJDBC against the
same server. Its observations are evidence for reviewing the finite-range contract;
a successful test does not certify every candidate as supported. Unsupported modes
and rejected values are recorded explicitly. Connections, temporary tables and
compatibility setting changes are confined to the test transactions.

EDB shares PostgreSQL session SQL, but `providerDialect` retains its separate
identity in `TP_CASE` output and child-process environments. Its LocalDate matrix
uses the common finite interval `-4712-01-01` through `+294276-12-31`, independently
of production constants. EDB 17.4 / EDB JDBC 42.7.3.5 typed probes established these
endpoints with `edb_redwood_date` on/off and explicit `pg_catalog.date`; the latter
can store wider values but does not widen the default handler contract. Neighboring
out-of-domain dates and Java infinity sentinels remain rejection cases. Ordinary
PostgreSQL retains its wider DATE maximum. pgJDBC-on-EDB verification remains
separate; a PostgreSQL or H2 pass is not live EDB evidence.
