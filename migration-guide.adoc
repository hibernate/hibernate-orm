[[metadata-serialization]]
=== Metadata serialization

Hibernate may now archive a factory-ready boot mapping and restore it in
another compatible service environment.  Enable capture while building the
mapping with `hibernate.boot.metadata_serialization.enabled=true`, then use
`org.hibernate.boot.serial.MetadataSerialization` to create or read a
`MetadataArchive`.

`MetadataArchive#restore(StandardServiceRegistry)` returns `RestoredMetadata`,
which exposes the restored `Metadata` for inspection and may build a
`SessionFactory` directly.

The archive is a trusted build artifact, not an interchange format for
untrusted input.  Producer and consumer must use the same Hibernate ORM version
and a compatible mapping environment.  Service-loaded function contributors
are replayed during restoration, while instance-only customizations without a
declarative representation make the mapping ineligible for serialization.

[[api-changes]]
== Changes to API

This section describes changes to contracts (classes, interfaces, methods, etc.) which are considered https://hibernate.org/community/compatibility-policy/#api[API].

[[legacy-xml-formats]]
=== Legacy Hibernate XML formats

Support for legacy `hbm.xml` mapping documents has been removed.  Applications
must migrate these mappings to annotations, standard Jakarta Persistence
`orm.xml`, or Hibernate's extended `orm.xml` format.  A document using the
legacy Hibernate mapping DTD or XSD is rejected during bootstrap.

The related `org.hibernate.boot.jaxb.hbm.spi` model and the legacy
`org.hibernate.boot.model.source.spi` mapping-source hierarchy were removed.
They have no replacement extension contract.

The legacy `hibernate.cfg.xml` configuration format has also been removed.
Move persistence-unit declarations to `META-INF/persistence.xml`, and move
settings to `persistence.xml`, `hibernate.properties`, or the programmatic
bootstrap entry point.

The method signatures `Configuration#configure()` and
`StandardServiceRegistryBuilder#configure()` remain, but their overloads always
throw `UnsupportedOperationException`.  The `org.hibernate.boot.cfgxml.spi`
package was removed.

The following bootstrap-only settings were removed:

* `hibernate.cfg_xml_file`;
* `hibernate.orm_xml_files`;
* `hibernate.hbm_xml_files`; and
* `hibernate.loaded_classes`.

Declare managed classes and mapping files through `persistence.xml` or the
corresponding methods of `PersistenceConfiguration` or
`HibernatePersistenceConfiguration`.

Reverse-engineering tooling no longer generates `hbm.xml` mappings or
`hibernate.cfg.xml`.  Generate annotated entity classes instead.

[[legacy-identifier-generators]]
=== Removed legacy identifier generators

The following deprecated contracts in `org.hibernate.id` were removed:

* `AbstractUUIDGenerator`;
* `UUIDGenerator`;
* `UUIDGenerationStrategy`;
* `UUIDHexGenerator`;
* `GUIDGenerator`; and
* `ForeignGenerator`.

For UUID identifiers, use `@UuidGenerator`, or use
`@GeneratedValue(strategy = GenerationType.UUID)`.  `GenerationType.AUTO` also
selects UUID generation for a UUID-typed identifier.  If an application
requires the exact database-side or hexadecimal behavior of `GUIDGenerator` or
`UUIDHexGenerator`, implement a custom generator explicitly.

Replace `ForeignGenerator` shared-primary-key mappings with `@MapsId`.
The legacy strategy names `uuid`, `uuid.hex`, `uuid2`, `guid`, and `foreign`
are no longer recognized.

[[bootstrap-api-changes]]
=== Bootstrap API and integration changes

Hibernate ORM 9 replaces the public staged bootstrap workflow with direct
bootstrap entry points backed by one internal pipeline.

==== Removed staged bootstrap APIs

The former workflow

[source,text]
----
MetadataSources
    -> MetadataBuilder
    -> Metadata
    -> SessionFactoryBuilder
    -> SessionFactory
----

has been removed, including:

* `org.hibernate.boot.MetadataSources`;
* `org.hibernate.boot.MetadataBuilder`;
* `org.hibernate.boot.SessionFactoryBuilder`;
* `Metadata#getSessionFactoryBuilder()`;
* `Metadata#buildSessionFactory()`.

There is no one-for-one replacement for constructing and mutating intermediate
builders.  Configure a supported bootstrap entry point and build the
`EntityManagerFactory` or `SessionFactory` directly.

Preferred entry points are:

* standard Jakarta Persistence bootstrap through `jakarta.persistence.Persistence`;
* container bootstrap using `jakarta.persistence.spi.PersistenceUnitInfo`;
* programmatic bootstrap using `jakarta.persistence.PersistenceConfiguration`
  or `org.hibernate.jpa.HibernatePersistenceConfiguration`.

`HibernatePersistenceConfiguration` now accepts managed class names, package
names, mapping resources, mapping files represented by `File`, `Path`, `URI`,
or `URL`, and JAR URLs.  These operations replace the corresponding source
collection use cases of `MetadataSources`.

`org.hibernate.cfg.Configuration` remains available as a native compatibility
facade.  It adapts its accumulated sources, settings, and customizations to the
same bootstrap pipeline and builds the `SessionFactory` directly.

For an archived boot model,
`org.hibernate.boot.serial.RestoredMetadata#buildSessionFactory()` is the
supported transition to a `SessionFactory`.

The `Configuration(MetadataSources)` constructor,
`Configuration#getXmlMappingBinderAccess()`,
`Configuration#addXmlMapping(Binding)`, and `Configuration#addJar(File)` were
removed with the old source collector.  Prefer the corresponding
`HibernatePersistenceConfiguration` mapping-source methods.  A retained
`Configuration` may still add annotated classes, packages, resources, files,
URLs, streams, and mapping directories through its supported methods.

[[user-type-creation-context]]
==== UserType creation context

`UserTypeCreationContext#getBuildingContext()` and `getServiceRegistry()` have
been removed, as announced by their 9.0 removal notices. Custom types continue
to receive member metadata through `getMemberDetails()` and mapping parameters
through `getParameters()` during construction and initialization.

Extensions calling either removed method must be updated and recompiled;
previously compiled calls are not binary compatible. There is no general
replacement context or service-registry accessor. If a custom type needs another
boot-time value or capability, report that requirement so a focused extension
contract can be considered.

==== Removed broad integration hooks

`AttributeBindingContext`, `EntityBindingContext`, and
`EmbeddableBindingContext` no longer expose `getMetadataBuildingContext()`.
Binders retain their categorized mapping inputs and mutable destination mapping
objects. There is no replacement general context or service-registry accessor.
Extensions calling the removed methods must be updated and recompiled; those
calls are not binary compatible.

`@TenantId` binding is now an internal mapping operation and no longer carries
an `@AttributeBinderType` marker. Tenant mapping, filtering, and value generation
remain supported, including tenant attributes inside embeddables. Custom binder
annotations on the same member continue to run.

Broad hooks tied to the removed staged builders have also been removed.
Integrations should use the narrow contract matching the actual contribution:

[cols="2,3", options="header"]
|===
| Removed hook
| Migration

| `MetadataBuilderContributor`
| Use `TypeContributor`, `FunctionContributor`, a supported programmatic
customization, or another focused integration SPI.
The `hibernate.metadata_builder_contributor` setting was removed with this
contract.

| `MetadataBuilderInitializer`
| There is no broad replacement.  Use focused contributors or supported
entry-point customizations.

| `MetadataSourcesContributor`
| Use `AdditionalMappingContributor` for the retained late mapping-contribution
boundary.

| `MetadataBuilderFactory` and `MetadataBuilderImplementor`
| There is no replacement.  Mapping resolution is owned by Hibernate's
bootstrap pipeline.

| `SessionFactoryBuilderFactory`, `SessionFactoryBuilderService`, and
`SessionFactoryBuilderImplementor`
| Use bootstrap settings and supported entry-point customizations for factory
options.  Use the service-loadable `SessionFactoryProducer` only when replacing
factory construction itself.

| `org.hibernate.jpa.boot.spi.Bootstrap`,
`EntityManagerFactoryBuilder`, and `PersistenceConfigurationDescriptor`
| Use the standard Jakarta Persistence entry points.  Hibernate's provider
implementation is not a staged bootstrap SPI.
|===

Code which previously used a broad builder hook for several unrelated tasks
should split that integration across the corresponding focused SPIs.  Do not
replace removed builder dependencies with dependencies on
`org.hibernate.boot.pipeline.internal` or
`org.hibernate.boot.serial.internal`.

==== Identifier-generator metadata

`org.hibernate.boot.model.IdentifierGeneratorDefinition` was replaced by
`IdentifierGeneratorRegistration`.  A registration records the resolved
generator family, implementation class, name, and immutable parameters instead
of retaining only a strategy string.

Consequently, `Metadata#getIdentifierGenerator(String)` was replaced by:

* `Metadata#getIdentifierGeneratorRegistration(String)`; and
* `Metadata#getIdentifierGeneratorRegistrations()`.

[[spi-changes]]
== Changes to SPI

This section describes changes to contracts (classes, interfaces, methods, etc.) which are considered https://hibernate.org/community/compatibility-policy/#spi[SPI].

[[binding-extension-spi]]
=== `AttributeBinder` and `TypeBinder`

The incubating custom binding SPIs now operate at an explicit
semantic-to-materialized boundary.  Their callback signatures have changed.

An `AttributeBinder` previously implemented:

[source,java]
----
void bind(
        A annotation,
        MetadataBuildingContext buildingContext,
        PersistentClass persistentClass,
        Property property);
----

It must now implement:

[source,java]
----
void bind(A annotation, AttributeBindingContext context);
----

`AttributeBindingContext` provides the read-only categorized domain model and
the concrete `AttributeApplication`, together with the mutable
`PersistentClass` and `Property`.  Its
`getMetadataBuildingContext()` method is a deprecated compatibility escape
hatch and should not be used by new binders.

A `TypeBinder` previously implemented separate methods receiving a
`MetadataBuildingContext` and either `PersistentClass` or `Component`.  It now
overrides one or both typed callbacks:

[source,java]
----
void bind(A annotation, EntityBindingContext context);
void bind(A annotation, EmbeddableBindingContext context);
----

The methods are default methods which report a standard unsupported-placement
error.  Implement only the entity or embeddable placements supported by the
custom annotation.  An embeddable binder is invoked for each concrete
embeddable usage.

The read-only categorized and declaration/usage/application contracts used by
these contexts are in `org.hibernate.boot.mapping.spi`.  Do not replace the
removed `MetadataBuildingContext` parameter with dependencies on
`org.hibernate.boot.mapping.internal`.

`MappingRole` and `DeclarationRole` moved from `org.hibernate.mapping` to
`org.hibernate.boot.mapping.spi`, alongside the contracts which expose them.

[[additional-mapping-contributor-spi]]
=== `AdditionalMappingContributor`

The `AdditionalMappingContributor#contribute()` signature no longer exposes
`InFlightMetadataCollector`, `ResourceStreamLocator`, and
`MetadataBuildingContext`.  It now receives:

* `AdditionalMappingContributions`, the write-side collector;
* `ProcessedMappings`, an immutable view of mappings processed before the
  contributor runs; and
* `AdditionalMappingContributorContext`, which exposes the Models context,
  class loading and resource lookup, dialect, and type configuration.

Use `ProcessedMappings#getEntityBinding()` to inspect an existing entity by
its Hibernate entity name.  Use `AdditionalMappingContributions#getDatabase()`
only for relational contributions which genuinely require direct database
model access.

[[integrator-spi]]
=== `Integrator` and SessionFactory-owned components

The `Integrator` lifecycle callbacks now use the same narrow context:

[source,java]
----
void integrate(
        Metadata metadata,
        Integrator.Context context,
        SessionFactoryImplementor sessionFactory);

void disintegrate(
        SessionFactoryImplementor sessionFactory,
        Integrator.Context context);
----

`Integrator.Context` exposes `ManagedBeanRegistry`, `ClassDetailsRegistry`,
and `ModuleDetailsRegistry`.  It replaces the
former `BootstrapContext` argument to `integrate()` and the former
`SessionFactoryServiceRegistry` argument to `disintegrate()`.

The SessionFactory child service registry and its contribution infrastructure
were removed, including:

* `SessionFactoryServiceRegistry`;
* `SessionFactoryServiceRegistryBuilder`;
* `SessionFactoryServiceRegistryFactory`;
* `SessionFactoryServiceContributor`;
* `SessionFactoryServiceInitiator`; and
* `SessionFactoryServiceInitiatorContext`.

`SessionFactoryImplementor#getServiceRegistry()` now returns the standard
registry used to build the factory.  Components requiring a SessionFactory are
owned directly by the factory and are exposed through focused contracts.

Use `ServiceContributor` for services which belong in the standard registry.
For factory-owned components, use the corresponding Java service:

[cols="2,3", options="header"]
|===
| Factory-owned concern
| Integration

| Event listeners
| Register them from an `Integrator` using
`SessionFactoryImplementor#getEventListenerRegistry()`.

| Native-query interpretation
| Provide a Java service implementation of `NativeQueryInterpreter`.

| Cache facade construction
| Provide a Java service implementation of `CacheFactory`.

| Per-session extensions
| Provide Java service implementations of `ExtensionIntegration`.
|===

`CacheFactory#buildCache(SessionFactoryImplementor)` was replaced by
`CacheFactory#buildCache(CacheConstructionContext)`.  The construction context
exposes the owning `SessionFactoryImplementor` and the immutable set of
`DomainDataRegionConfig` instances prepared from the resolved mapping.

`CacheImplementor#prime(Set<DomainDataRegionConfig>)` was removed.  A
`CacheFactory` implementation must consume the region configurations while
building the cache and return a fully initialized `CacheImplementor`.

The old `CacheInitiator`, `NativeQueryInterpreterInitiator`, and
`ExtensionIntegrationServiceInitiator` adapters were removed with the child
registry.

[[bean-validation-bootstrap-spi]]
=== Bean Validation bootstrap

`BeanValidationIntegrator` is no longer an `Integrator`.  It is retained as a
deprecated compatibility holder, while Hibernate now coordinates Bean
Validation through `BeanValidationPlan` so relational constraints and runtime
callbacks run at their respective construction boundaries.

Constants used by the integration moved to `BeanValidationSettings`.
`ActivationContext#getServiceRegistry()` now returns the standard
`ServiceRegistry`, and `ActivationContext#getSessionFactoryOptions()` exposes
the options needed during the relational phase, before a `SessionFactory`
exists.

[[generator-spi]]
=== Generator lifecycle

`IdentifierGenerator` no longer extends `ExportableProducer`.  A custom
identifier generator which contributes sequences, tables, or other schema
objects must now implement `ExportableProducer` explicitly.  Generators which
do not contribute schema objects no longer acquire that capability merely by
implementing `IdentifierGenerator`.

Generator creation, configuration, exportable registration, and initialization
are coordinated as one lifecycle.  Custom generators must not assume that a
new instance will be created separately for schema export and runtime use.
Container-managed generators retain the managed reference through factory
construction.

`GeneratorCreator` is retained only as a deprecated compatibility alias for
the internal `GeneratorDescriptor` contract.  Integrations should continue to
define generator behavior through supported generator annotations and
`Generator` implementations instead of depending on boot-model descriptor
types.

[[boot-model-spi-removals]]
=== Boot-model implementation SPIs

The following implementation-oriented boot contracts were removed or narrowed
with the staged metadata builder:

* `MetadataBuildingOptions` and its delegating implementation;
* `MetadataBuildingProcess`;
* `LocalMetadataBuildingContext`;
* `SecondPass`;
* `XmlMappingBinderAccess`; and
* the `org.hibernate.boot.models.spi.GlobalRegistrations` model and its
  registration DTOs.

The legacy `org.hibernate.mapping.Resolvable` second-pass marker was also
removed without replacement.

There is no supported replacement callback for adding arbitrary second-pass
work or mutating Hibernate's in-flight collector.  Use a focused contributor
or custom binder at its documented phase boundary.

`BootstrapContext` was narrowed to bootstrap-wide services and infrastructure.
It no longer exposes `MetadataBuildingOptions`, the function registry,
builder-registered SQL functions, auxiliary database objects, converters,
cache-region definitions, the Jandex view, or the ad-hoc basic-type registry.
Use the corresponding focused contributor or bootstrap setting instead of
treating `BootstrapContext` as a general-purpose mapping collector.

`MetadataImplementor#getMetadataBuildingOptions()` was likewise removed.
Its replacement, `getMappingResolutionOptions()`, exposes an internal pipeline
type and is not a supported integration point.  Integrations should obtain
configuration through their focused SPI context or the standard service
registry.

`org.hibernate.boot.spi.MappingDefaults` was renamed to
`GlobalMappingDefaults`.  This distinguishes persistence-unit defaults from
the effective defaults applied in a narrower mapping context.


[[action-queue-checkpoint-spi]]
=== `ActionQueue` speculative-flush checkpoints

The incubating `ActionQueue.clearFromFlushNeededCheck(int)` method has been
replaced by an opaque checkpoint and restore contract:

[source,java]
----
ActionQueueCheckpoint checkpoint();
void restore(ActionQueueCheckpoint checkpoint);
----

An `ActionQueueCheckpoint` belongs to the queue instance which created it and
does not expose the queue's internal list or graph representation.  Queue
implementations must preserve all work registered before the checkpoint.  Work
registered afterward is retained when it represents durable persistence-context
state, including entity inserts, entity deletes, orphan removals, and orphan
collection removals.  Flush-derived entity updates and ordinary collection work
may be discarded only while their source state remains intact and can reproduce
equivalent work during a later required flush.

Collection mutation registration now uses the queue-neutral
`addCollectionMutation(CollectionMutationInput)` method.  The collection-specific
`addAction(CollectionRecreateAction)`, `addAction(CollectionRemoveAction)`,
`addAction(CollectionUpdateAction)`, and
`addAction(QueuedOperationCollectionAction)` overloads have been removed from
the incubating `ActionQueue` SPI.  Queue implementations may lower the semantic
input to these legacy action forms internally, but they are no longer the common
registration vocabulary.

Collection mutation interpretation, including semantics-specific delta
production, is now associated with `CollectionSemantics` through the new default
`getCollectionMutationInterpreter()` method.  Custom semantics remain source
compatible and use the conservative compatibility interpreter unless they
override this association.  `PersistentCollection` likewise has new default
methods for exposing queued commands, a mutation generation, and the
post-snapshot initialization step.

Custom collection wrappers which apply queued commands during
`afterInitialize()` should instead retain them until
`afterInitializationSnapshot()`.  Hibernate captures the database-loaded state
between these calls and then applies and clears queued commands, ensuring that an
initialized collection has no queued commands while its snapshot still represents
the persisted comparison baseline.  Wrappers derived from
`AbstractPersistentCollection` inherit this sequencing automatically.


[[logical-physical-name]]
=== LogicalName and PhysicalName

Hibernate now defines `LogicalName` and `PhysicalName` for use during its bootstrap and metamodel processing, in place of `Identifier`, to represent the logical and physical name of database objects and types.

`LogicalName`:: The name of an object or type as indicated by mapping or determined by the effective `ImplicitNamingStrategy`.  `LogicalName.isExplicit()` tells whether the name was explicit in the mapping, as opposed to determined by `ImplicitNamingStrategy`.
`PhysicalName`:: The corresponding, actual name of the database object after processing via the effective `PhysicalNamingStrategy`.

The split fixes confusion and some bugs from cases where Hibernate was unsure whether an `Identifier` was logical or physical.


[[naming-stratergies]]
=== Naming Strategies

Both the `ImplicitNamingStrategy` and `PhysicalNamingStrategy` SPI have been revamped in this release.

1. Account for `LogicalName` and `PhysicalName`
2. New, richer input objects
3. More complete set of callbacks

==== ImplicitNamingStrategy

`ImplicitNamingStrategy` is now defined to always return a `LogicalName`, rather than `Identifier`.
Its "input objects" have also changed to provide richer information.

The out-of-the-box implementations have been consolidated.  There are 2 supported implementations.

`ImplicitNamingStrategyJpaCompliantImpl` ("default", "jpa"):: The default.  This implementation follows the Jakarta Persistence requirements to the letter.
`StandardImplicitNamingStrategy` ("hibernate"):: Mostly follows "jpa" naming, except 2 cases -
1. Embedded paths - Given a path `home.address.city`, Jakarta Persistence requires a column named `city`.  `StandardImplicitNamingStrategy` produces home_address_city`.  If using standard Jakarta Persistence naming, it is important to given explicit names in these cases to avoid collision.  See <<implicit-naming-paths>> for additional information.
2. Association-table names - `ImplicitNamingStrategyJpaCompliantImpl` combines the owning and target table physical names; `StandardImplicitNamingStrategy` combines their logical names.  This can differ when using a custom `PhysicalNamingStrategy`.  For example, if providing a `PhysicalNamingStrategy` which prepends `t_` to all table names and given an association for `Person.passport` with logical tables `Person` and `Passport` -
  * `ImplicitNamingStrategyJpaCompliantImpl` will produce a logical table name of `t_Person_t_Passport`, which the custom `PhysicalNamingStrategy` will then produce `t_t_Person_t_Passport`
  * `StandardImplicitNamingStrategy` however will use the 2 logical names producing a logical name of `Person_Passport`, which the custom `PhysicalNamingStrategy` will then produce `t_Person_Passport`

[NOTE]
In the association-table case, without a custom `PhysicalNamingStrategy` both `ImplicitNamingStrategy` implementations will create the same association-table name : `Person_Passport`.

3 legacy implementations have been deprecated:

`ImplicitNamingStrategyLegacyJpaImpl` ("legacy-jpa"):: Historical implementation for the older Java Persistence specification which in some cases had bugs and in others were superseded by Jakarta Persistence naming requirements.
`ImplicitNamingStrategyLegacyHbmImpl` ("legacy-hbm"):: Historical implementation from `hbm.xml` days.
`ImplicitNamingStrategyComponentPathImpl` ("component-path"):: Generally the same as `StandardImplicitNamingStrategy` with some minor differences.

These deprecated strategies remain available during the deprecation period. Selecting one, including a subclass, emits deprecation warning HHH90000046. Migrate to "hibernate" or "jpa" after comparing resolved schema names. "hibernate" now supplies "component-path"’s embedded naming behavior, but its association-table composition uses logical dependency names, so replacing "component-path" with "hibernate" is not guaranteed to preserve every schema name.

To preserve an existing schema -

* make affected mapping names explicit and verify the result under the configured physical strategy, if one, or
* copy the appropriate `ImplicitNamingStrategy` implementation locally, or
* otherwise provide a custom `ImplicitNamingStrategy` which returns the expected names.

`ImplicitNamingStrategy` also defines support for additional naming cases.  In all of these cases, Hibernate used to internally determine the implicit names.  The default implementation for these hooks is the same as existing naming.

Column names::

* Tenant-id column name
* Entity discriminator column nme
* Embeddable discriminator column name
* Aggregate container column name
* Collection identifier (ID_BAG) column name
* Soft-delete indicator column name
* Timezone column name

Constraint names::

* <<primary-key-naming,Primary-key name>>
* <<foreign-key-naming,Foreign-key name>>
* <<unique-key-naming,Unique-key name>>
* <<index-naming,Index name>>

Type names::

* <<enum-type-naming>>
* <<array-type-naming>>

[[implicit-naming-paths]]
=== Complete attribute paths for implicit naming

Naming inputs now retain the full owner-relative attribute path for embedded identifiers
and collections declared inside embeddables. Under `StandardImplicitNamingStrategy`
and `ImplicitNamingStrategyComponentPathImpl`, an embedded identifier `id.region`
produces `id_region` instead of `region`. Collection column examples include
`home_tags`, `home_tags_ORDER`, `home_labels_KEY`, and `home_links_target_pk`,
rather than their terminal-path equivalents. Entity-valued map keys likewise receive
the full collection path.

Custom strategies receive these complete paths too. JPA continues to use terminal
names, and explicit names remain unchanged. IdClass attributes directly declared on
the entity do not acquire an artificial `id` prefix. To preserve affected existing
schema names, explicitly name the columns or customize the implicit strategy.


[[enum-type-naming]]
=== ENUM type naming

When the underlying Dialect and database support named enum types, the new `ImplicitNamingStrategy.determineEnumName()` and `PhysicalNamingStrategy.toPhysicalEnumName()` methods will be called to determine the exported enum type name.

This is only supported for Oracle and PostgreSQL at the moment.

[[array-type-naming]]
=== ARRAY type naming

When the underlying Dialect and database support named array types, the new `ImplicitNamingStrategy.determineArrayName()` and `PhysicalNamingStrategy.toPhysicalArrayName()` methods are used to determine naming for the exported array type.

The corresponding generated HQL and Criteria function names are unchanged.

This is only supported for Oracle at the moment.

[[struct-type-naming]]
=== STRUCT type naming

The new `PhysicalNamingStrategy.toPhysicalStructName()` can be used to convert a logical STRUCT name to a `PhysicalName`.

Currently `@Struct.name()` is required, so implicit-naming is not relevant.  However, we are considering relaxing that requirement and allowing implicit-naming of STRUCT types.


[[primary-key-naming]]
=== Primary-key naming

`ImplicitNamingStrategy.determinePrimaryKeyName` maybe be used to produce primary-key names.  It receives a `PrimaryKeyNamingInput` containing only the table's logical and physical names. Its interface default uses the physical table name: up to twelve characters followed by `_pk`, retaining quoting.  The selected logical PK name then passes through `toPhysicalPrimaryKeyName`.

Entity, dependent-table, and collection PKs created through model binding share this algorithm. This replaces their inconsistent internal alias, UK-hash, and absent names; set-collection PKs no longer invoke implicit UK naming. Custom strategies may override the PK callback. The fifteen-character limit is only the supplied default, not a limit on custom or physically transformed names.

The primary-key naming is mapping-model only currently.  The built-in table exporters do not export the primary-key name.  Custom exporters could choose to do so, and future versions of Hibernate might decide to as well.  An explicitly named unique-key covering the primary-key still supplies its exported name, through the unique-key physical hook. This now works consistently when it is the table's only unique-key as well as when multiple unique-keys are declared. The existing last-eligible-declaration selection is preserved.


[[foreign-key-naming]]
=== Foreign-key naming

`ImplicitNamingStrategy.determineForeignKeyName()` accepts `ForeignKeyNamingInput`
and `ImplicitNamingContext`, and returns a non-null `LogicalName`.  The built-in algorithm now lives in the interface default.

The input exposes logical and physical table/column dependencies, actual local-to-target
column pairs (including primary-key references), and whether the resolved reference targets
the primary-key. Inline-view dependencies expose a logical identity without a physical table name;
this does not make their foreign keys exportable.

The legacy foreign-key hash recipe is unchanged. A corrected table lookup can change names where
schema-distinct tables share a physical object name: each FK now uses its own logical
table identity instead of whichever table last overwrote the unqualified reverse lookup.
Existing database constraints are not automatically renamed.

Audit helper tables which previously omitted logical-name registration now retain their
creation names for foreign-key naming inputs. With a transforming physical naming strategy, their
foreign-key hashes may change from the former physical-table-name fallback to the known logical
creation name. Explicitly registered table aliases retain their existing selection.

[[unique-key-naming]]
=== Unique-key naming

`ImplicitNamingStrategy.determineUniqueKeyName` takes `UniqueKeyNamingInput` and
`ImplicitNamingContext`, returning a non-null `LogicalName`. The input exposes the
selected table and ordered columns with both logical and physical names. Its interface
default retains the existing `UK` hash recipe and configured schema charset.

The physical unique-key callback runs once for each surviving naming decision, preserves requested quoting, and must return a non-null result.  Discarded inferred unique-keys and unnamed unique-keys absorbed into a PK do not invoke unique-key naming.

Column references follow the shared <<constraint-column-resolution,column-resolution sequence>>.

Duplicate explicitly named `@UniqueConstraint` declarations on the same table now
fail with `AnnotationException` instead of merging their columns (HHH-20918). This
also applies when their column lists are identical or match the primary key. The error
identifies the constraint name, table, and both declaration locations, including the
class/member, containing annotation, and zero-based `uniqueConstraints` array position.
Use a single `@UniqueConstraint` with all intended columns for a composite constraint;
remove redundant declarations, or give independent constraints distinct names.
Unnamed declarations and name reuse on different tables are unaffected by this check.
See https://hibernate.atlassian.net/browse/HHH-20918[HHH-20918].

Independent constraints with different columns whose
names collide through implicit or physical naming now cause a mapping error instead of
silently becoming one composite UK.

Unique indexes represented as UK constraints use this lifecycle and these naming
hooks; see <<index-naming>>.

Uniqueness inferred from an owning `@OneToOne`, declared by basic `@Column(unique=true)`,
or required for a non-ID `@Changelog.ChangesetId` now receives its constraint name during
boot through `ImplicitNamingStrategy` and `PhysicalNamingStrategy`.
Previously these paths could bypass both strategies and generate a `UK_` name during
schema export. That fallback omitted MD5 padding and could assign identical names to
unrelated constraints. It has been removed.

The built-in implicit strategy now uses the normal `UK` hashing recipe for these cases;
custom implicit and physical UK naming callbacks are honored. Already strategy-named
unique constraints retain their existing default naming behavior. Dialect rules governing
whether uniqueness is rendered inline, as a named constraint, or as an index are unchanged.

Names for affected constraints may change; see
https://hibernate.atlassian.net/browse/HHH-20916[HHH-20916].

Schema creation now honors finalized unique-key names wherever the dialect supports
named uniqueness, including names supplied by custom implicit and physical strategies.
Single-column uniqueness uses a named table constraint instead of an anonymous inline
clause where supported. Dialect-specific nullable-key suppression and unique-index
representation remain in force.

An explicitly named unique-key covering the primary-key may supply its exported name;
see <<primary-key-naming>> for the absorption rules.

Previously anonymous unique-key clauses may have database-assigned names that differ from the
names now emitted by Hibernate. Review generated migration scripts against actual
constraint names; existing database constraints are not automatically renamed.

Temporal period-start additions retain their previous exclusion from unique-key naming inputs
while remaining part of the constraint. Inferred aggregate-collection unique-keys also retain
their existing member-column behavior. Both are deferred investigations; this change
does not claim to correct aggregate unique-key membership or rename temporal keys.

[[index-naming]]
=== Index naming

`ImplicitNamingStrategy.determineIndexName()` accepts `IndexNamingInput` and
`ImplicitNamingContext` and returns a non-null `LogicalName`. `ImplicitIndexNameSource`
and `ImplicitConstraintNameSource` and their source-based subclass helpers are removed.
The interface default preserves the existing `IDX` hash over the logical table name
and sorted source term spellings. Order, direction, uniqueness, `type`, and `using`
do not enter that default hash, though custom strategies can inspect them.

Each column term exposes resolved logical/physical names plus its original reference
spelling. Expression terms carry opaque SQL, not identifiers. Explicit names bypass
implicit naming; physical index naming applies once and cannot remove requested quoting.

Column references and expression parsing follow the shared
<<constraint-column-resolution,column-resolution rules>>.

Repeated explicit `@Index` names on the same table now fail with both declaration
locations, even for identical definitions or unique indexes represented as UKs. Generated
or physical-name collisions between different definitions also fail instead of merging.
For example, `(first, second)` and `(second, first)` still have the same default hash:
give them distinct explicit names or supply a custom naming strategy. Equivalent unnamed
index declarations are deduplicated before naming.

Collection and join-table `@Index(unique=true)` now use the same dialect representation
policy as entity tables. When represented as a UK, they use the callbacks, default names,
and export rules described under <<unique-key-naming>> rather than index naming and export.
This may change both
schema object representation and generated names; different custom physical UK/index
strategies can also change explicitly named objects. Review schema migration scripts.
Explicit index `type`, `using`, expressions, ordering, and SQL options are retained as
appropriate for the dialect-selected representation.


[[constraint-column-resolution]]
=== @Index and @UniqueConstraint column resolution

Hibernate 9.0 defines the following resolution sequence for both `@Index.columnList`
and `@UniqueConstraint.columnNames`, including collection and association join tables.
Index ordering keywords (`ASC` or `DESC`) are removed before resolving the reference.

. An unquoted `\{key}` or `\{element}` marker selects the collection role directly,
bypassing column lookup. These forms are valid only in collection/join-table declarations.
. Otherwise, resolve the logical column name first.
. If no logical column matches, resolve the existing physical column name.
. If neither column lookup matches, an entity primary/secondary-table declaration may
resolve an attribute path relative to its declaring entity. Collection/join-table
declarations do not infer unprefixed attribute paths.

The first match wins: logical names take precedence over physical names, and column
names take precedence over entity attribute paths. Actual mapped columns are reused;
physical naming is not invoked again. Unknown references fail at boot, even for explicitly
named constraints or indexes. Applications relying on placeholder columns must correct
those references. See https://hibernate.atlassian.net/browse/HHH-20917[HHH-20917]
for the unique-constraint placeholder-column correction. Where a collection/join-table
reference previously matched a different physical column, it now selects the logical match.

Entity paths such as `summary.text` must explicitly name enclosing embeddables; bare
`text` does not search them. Collection roles use `\{element}` for the element/map value
and `\{key}` for the map key, with optional embeddable paths such as
`\{element}.address.city` or `\{key}.code`. The key marker does not select an owner FK
or list index. Owner FK columns remain addressable by column name.

Each attribute/role reference must identify one actual column on the declaring table.
A whole entity-valued role may select its single local FK column, but paths into the
associated entity are rejected. Multi-column values, formulas, inverse associations
without local columns, and references to other tables are rejected.

Quote the entire identifier to reference a literal marker-shaped column instead of a role:

[source,java]
----
@Index(columnList = "`{element}.city`")
@UniqueConstraint(columnNames = "`{element}.city`")
----

Parenthesized index expressions remain SQL expressions, not attribute/role references.
Use physical column names inside those expressions. Entity and collection/join-table
index lists now share parsing for `ASC`/`DESC`, parenthesized expressions, nesting,
and quoted commas. Malformed lists fail with declaration locations. Corrected expression
parsing can change generated names for previously misparsed definitions.

Source term spelling remains the default index-hash input, so switching from a column
reference to an attribute or role path can change an implicitly generated index name.
Unique-key hashing continues to use resolved column dependencies, not path spellings.
Review schema migration scripts when changing reference forms.

Collection association `@JoinTable` declarations containing only indexes or unique
constraints are now retained even when their table name and join columns are implicit.
These declarations were previously ignored, so their constraints/indexes now participate
in validation and schema generation.

[[behavior-changes]]
== Changes in Behavior

This section describes changes in behavior that applications should be aware of.

[[collection-remove-create-callback-order]]
=== Collection remove/create callback order

When moving a collection between owners or roles requires both removal of its old
state and creation of its new state, Hibernate now invokes the collection-remove
interceptor hook before the legacy collection-recreate hook.  The corresponding
Hibernate collection events and semantic mutation completion are likewise
remove-first.  Integrations must not retain the previous assumption that the
recreate interceptor hook runs before the remove hook.

[[collection-mutation-lifecycle-timing]]
=== Collection mutation lifecycle timing

Collection post-events, cache handling, successful statistics, and queued-operation
finalization are now tied to semantic collection-mutation completion instead of to
the last row operation produced during decomposition.  This ensures that grouped,
reordered, and batched row work completes the correct collection lifecycle and that
failed physical work suppresses successful completion handling.

A collection mutation which produces no SQL now completes directly after its
semantic work is sealed; Hibernate no longer creates a SQL-shaped no-op solely to
carry its post-event.  Consequently, applications must not rely on a global order
between pre/post collection events for unrelated collections.  Each mutation's
pre-event still precedes its post-event, and a post-event still follows all physical
work belonging to that mutation.

[[collection-owner-update-callback-timing]]
=== Collection owner update callback timing

Jakarta Persistence owner update callbacks are coordinated once per owner and flush.
When entity and non-inverse collection work both contribute to an applicable owner
update, one `@PreUpdate` callback is invoked and one `@PostUpdate` callback is delayed
until all contributing entity and collection post-events have been delivered.
Collection create or remove work associated with owner insert/delete lifecycle does
not by itself establish update-callback applicability.

[[implicit-list-semantics]]
=== `List` attributes use list semantics

A persistent attribute declared as `java.util.List` now uses LIST semantics by
default.  When an owned collection has no explicit `@OrderColumn`, Hibernate
uses an implicit order column.

The `hibernate.mapping.default_list_semantics` setting and
`MappingSettings#DEFAULT_LIST_SEMANTICS` were removed.  To map a Java `List` as
an unordered bag, annotate the attribute with `@org.hibernate.annotations.Bag`.

As before, inverse collections such as `@OneToMany(mappedBy = "...")` and
`@ManyToMany(mappedBy = "...")` do not gain an implicit persistent order.  Use
an explicit `@OrderColumn` where that mapping placement supports one.

[[quoted-entity-names]]
=== JPA entity names may not be quoted

The value of `@Entity(name = "...")` is a logical entity name, not a database
identifier.  Hibernate now rejects entity names enclosed in identifier quote
markers.  Remove the quotes from the entity name and use `@Table`, `@Column`,
or the corresponding XML mapping when a database identifier requires quoting.

[[global-generator-scope]]
=== Identifier-generator names are always persistence-unit scoped

Hibernate no longer supports entity-local scoping for explicitly named
`@SequenceGenerator`, `@TableGenerator`, and custom generator declarations.
Explicit generator names are always scoped to the persistence unit, and two
different declarations may not use the same explicit name.

The `hibernate.jpa.compliance.global_id_generators` setting and the related
`JpaCompliance` and `HibernatePersistenceConfiguration` methods were removed.
There is no setting which restores local named-generator scope.

An unnamed generator declaration is implicitly named using the owning JPA
entity name.  Different entities may therefore each declare an unnamed
generator without colliding.

Applications which formerly overrode a mapped-superclass generator by
redeclaring the same local name should instead give each concrete generator a
unique explicit name and reference it from `@GeneratedValue`.

[[generic-jpa-metamodel-types]]
=== Specialized generic types in the JPA metamodel

JPA criteria paths and metamodel attributes inherited from a generic mapped
superclass now expose the Java type resolved for the concrete entity usage.
For example, an association declared as `T` by a mapped superclass and
specialized as `Customer` by an entity now reports `Customer.class` from
`TupleElement#getJavaType()` instead of `Object.class`.

The static metamodel classes generated by `hibernate-processor` now represent
the same specialization.  Given, for example:

[source,java]
----
@MappedSuperclass
class Base<T> {
    T value;
}

@Entity
class Customer extends Base<UUID> {
    // ...
}
----

the generated `Customer_` class declares its own `value` field typed for
`Customer` and `UUID`.  That field intentionally hides the same-named field
in `Base_`, which continues to represent the generic declaration.  In
simplified form, the generated model is:

[source,java]
----
abstract class Base_ {
    static volatile SingularAttribute<Base, Object> value;
}

abstract class Customer_ extends Base_ {
    static volatile SingularAttribute<Customer, UUID> value;
}
----

Both fields are populated independently at runtime.  The same handling applies
to a concrete embeddable which specializes a generic mapped superclass, and
mapped-superclass attributes inherited by embeddables are now populated.

Applications should regenerate their static metamodel sources when upgrading.
Normal references such as `Customer_.value` now obtain the specialized type,
but code which reflects on generated metamodel classes, inspects declaring
classes, or assumes that the attribute field is declared only by the generic
superclass must account for the new hiding field.  Code which worked around
the previous raw or `Object` result should remove the workaround and use the
specialized metamodel type.


[[jdbc-resource-release-autocommit]]
=== JDBC resource release in autocommit mode

When no transaction is active (autocommit), Hibernate now correctly releases the connection after statement
execution if the configured `ConnectionReleaseMode` is set to `AFTER_TRANSACTION`.
Previously, with `DELAYED_ACQUISITION_AND_RELEASE_AFTER_TRANSACTION` connection handling mode, JDBC resources
and the physical connection were held until an explicit call to `afterTransaction()` or closing the session,
even though in autocommit mode each statement is effectively its own transaction.

This change ensures that JDBC connections are promptly returned to the pool after each statement when there
is no active transaction, preventing potential resource leaks.

As a consequence, accessing LOB locators (i.e. `java.sql.Blob` or `java.sql.Clob` typed attributes) outside of
an active transaction will no longer work and result in an exception on most dialects.
Previously this appeared to work only because the connection happened to remain open; however, there were no
transactional isolation guarantees — the data read from the LOB could have already been modified by another
transaction.

Note that this only affects entity attributes mapped as `java.sql.Blob` or `java.sql.Clob`, since these types
rely on a JDBC locator that requires a live connection. Attributes mapped as `byte[]` or `String` are always
eagerly materialized when the result set is read, and are not affected by this change. Similarly, some dialects
that always use materialized LOB access are also unaffected.

Applications that use `Blob` or `Clob` typed attributes must access them within an active transaction:

[source,java]
----
// Before (assuming no active transaction, may have accidentally worked, but with no isolation guarantees):
session.get(MyEntity.class, id);
entity.getData().getBinaryStream(); // may now fail — connection already released

// After (correct):
session.getTransaction().begin();
session.get(MyEntity.class, id);
entity.getData().getBinaryStream(); // works — connection held by the transaction
session.getTransaction().commit();
----

[[inverse-list-null-elements]]
=== Null elements of inverse indexed lists

A null element of an inverse `@OneToMany` list mapped with `@OrderColumn` again leaves a gap in the order
column, so that the element is read back as null and the elements after it keep their list positions.

Since 6.2 the order column was instead written compacted, and a list persisted as `[a, null, b]` was stored
with the index values `0,1` rather than `0,2` and loaded back as `[a, b]`, silently shifting the elements
after the null. Applications that came to rely on that compaction — for example by treating the reloaded list
size as the number of non-null elements — will now see the null elements preserved across a round-trip, as
they were through 5.x and 6.1.

Element collections are unaffected: a null element of an `@ElementCollection` list has never been persisted,
and such lists still load back without it.

[[default-orm-xml-discovery]]
== Default XML mapping discovery

Persistence-unit bootstrap discovers `META-INF/orm.xml` in the persistence-unit
root and archives referenced by its `jar-file` declarations. A same-named resource
in another archive is no longer included merely because the application classloader
can see it. List such a mapping explicitly using `mapping-file` to include it.
Explicit mapping resources may still be located anywhere on the application classpath.

`exclude-unlisted-classes` does not disable default XML mapping discovery.
Container-provided class/package/module inventories remain authoritative; Hibernate
loads XML mappings without repeating program-element scanning. If no root or
referenced archives are supplied, no ambient classpath search is performed.

[[xsd-changes]]
== Changes in XSD

This section describes changes in XML Schema Descriptors

The legacy `hbm.xml` and `hibernate.cfg.xml` schemas are no longer supported or
distributed.  Use the Jakarta Persistence schemas for `orm.xml` and
`persistence.xml`, or Hibernate's extended `mapping.xml` schema for
Hibernate-specific mapping features.

The ORM 9 extended mapping schema also adds `mutable` to basic and identifier
mappings, and adds the Jakarta Persistence 4.0 persistence-unit lifecycle
callbacks `post-create` and `pre-close`.
