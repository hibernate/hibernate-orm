[[to-one-association-restrictions]]
== Restrictions on to-one associations

`@SQLRestriction` and `@Filter` may now be declared directly on `@ManyToOne` and `@OneToOne`
associations, including associations mapped using join tables.
Restrictions apply to the target through that association, consistently across eager and lazy fetching.
An excluded target is represented as null while its stored reference is preserved during unrelated updates.
Association filters apply whenever enabled, independently of `@FilterDef.applyToLoadByKey`.
See the link:{userGuideBase}#pc-to-one-restrictions[user guide] for examples and
the link:{migrationGuide}#filtered-to-one-associations[migration guide] for the update and merge semantics.

[[schema-if-exists]]
== Schema DDL uses `IF EXISTS` / `IF NOT EXISTS`

Schema management DDL now uses `CREATE SCHEMA IF NOT EXISTS` and `DROP SCHEMA IF EXISTS` for dialects which support these clauses, avoiding warnings when a schema already exists or has already been dropped.

Supported dialects: PostgreSQL, CockroachDB, H2, HSQLDB, SAP HANA, and SQL Server (DROP only, version 13+).

[[formula-one-to-one-associations]]
== Formula-based one-to-one associations

A `@OneToOne` association whose join mixes physical `@JoinColumn`s with `@JoinFormula`s (via
`@JoinColumnOrFormula`/`@JoinColumnsOrFormulas`, or the equivalent `<one-to-one>` mapping XML) is
now recognized and bound as a true one-to-one association instead of falling back to a logical
many-to-one. For each physical join column that is also part of the owner's primary key, Hibernate
infers `insertable=false, updatable=false`, since the identifier mapping already owns that column's
value. See the link:{userGuideBase}#associations-one-to-one-formulas[user guide] for details and examples.

[[map-key-formula]]
== Formula-based map keys

The new `@MapKeyFormula` annotation specifies a native SQL expression used to read the key of a
`java.util.Map`, instead of storing the key in a `@MapKeyColumn`. Since the key is derived from the
expression, it is never written to the database:

[source,java]
----
@OneToMany(mappedBy = "parent")
@MapKeyFormula("upper(code)")
Map<String, Child> children;
----

The `<map-key-formula>` element of mapping XML, which was previously ignored, now has the same effect.
Mappings which declare it no longer fall back to the default `<attribute>_KEY` column.
See the link:{userGuideBase}#collections-map-key-formula[user guide] for details and examples.

[[embeddable-patterns]]
== Embeddable patterns in HQL

An embedded attribute may now be explicitly destructured to a tuple by listing the names of fields of the embeddable class:

[source,hql]
----
from Person p
where p.address(street, city, zip) = (:street, :city, :zip)
----

Unlike a direct comparison of an embedded attribute with a tuple, the result of this comparison does not depend on the order in which the fields of the embeddable class are enumerated.
[[bootstrap]]
== SessionFactory bootstrap orchestration

ORM 9.0 introduces a new internal SessionFactory bootstrap pipeline which makes
the major bootstrap products explicit and shared across entry points.

At a high level, the pipeline resolves bootstrap settings, normalizes source
contributions, prepares available mapping resources, categorizes the domain
model, resolves mapping metadata, resolves SessionFactory settings, and then
builds the `SessionFactory` / `EntityManagerFactory`.  It also limits the number
of bootstrap entry points and centralizes the handling based on that pipeline -

* Jakarta Persistence SE bootstrap with `(Hibernate)PersistenceConfiguration`
* Jakarta Persistence SE bootstrap with `Persistence`
* Jakarta Persistence EE bootstrap with container and `PersistenceUnitInfo`
* Hibernate native bootstrap with `Configuration` footnote:recommentation[Consider migrating to `(Hibernate)PersistenceConfiguration`]
* Hibernate native bootstrap with `MetadataSources`, `SessionFactoryBuilder`, etc. footnote:recommentation[]

The end-user impact of this pipeline specifically is small - basically some
historical bootstrap entry paths are compatibility paths rather than the
canonical pipeline.  However, it is fundamental to most of the new features
listed here.



== ORM 9 Model-Binding Pipeline

Part of the work done for <<bootstrap>>, and building on top of dropping support for
`hbm.xml` mappings, is deep changes to how Hibernate performs model binding.  The reasons
and goals for this are numerous - from functionality to correctness to performance...

Below are a few of the new capabilities beyond the historical model binding path.


=== Discriminated association binding

The new model-binding path supports a few `@Any` / `@ManyToAny` capabilities
that are not handled by the historical annotation binder:

`@Any` key Java type inference for basic target identifiers::
When `@AnyKeyJavaClass` is omitted, the new binder can infer the any-key Java
type from explicit `@AnyDiscriminatorValue` target entities, provided each
target uses the same basic identifier Java type.
+
Historically, Hibernate required the any-key type to be supplied explicitly with
`@AnyKeyJavaType`, `@AnyKeyJavaClass`, or the XML-oriented key type setting.

Default implicit discriminator strategy::
When an `@Any` or `@ManyToAny` mapping declares no explicit
`@AnyDiscriminatorValue` mappings and no `@AnyDiscriminatorImplicitValues`, the
new binder uses Hibernate's full entity-name implicit discriminator strategy.
+
Historically, implicit discriminator resolution had to be requested explicitly
with `@AnyDiscriminatorImplicitValues`.
