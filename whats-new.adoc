[[to-one-association-restrictions]]
== Restrictions on to-one associations

`@SQLRestriction` and `@Filter` may now be declared directly on `@ManyToOne` and `@OneToOne`
associations, including associations mapped using join tables.
Restrictions apply to the target through that association, consistently across eager and lazy fetching.
An excluded target is represented as null while its stored reference is preserved during unrelated updates.
Association filters apply whenever enabled, independently of `@FilterDef.applyToLoadByKey`.
See the link:{userGuideBase}#pc-to-one-restrictions[user guide] for examples and
the link:{migrationGuide}#filtered-to-one-associations[migration guide] for the update and merge semantics.

[[schema-if-exists]]
== Schema DDL uses `IF EXISTS` / `IF NOT EXISTS`

Schema management DDL now uses `CREATE SCHEMA IF NOT EXISTS` and `DROP SCHEMA IF EXISTS` for dialects which support these clauses, avoiding warnings when a schema already exists or has already been dropped.

Supported dialects: PostgreSQL, CockroachDB, H2, HSQLDB, SAP HANA, and SQL Server (DROP only, version 13+).

[[formula-one-to-one-associations]]
== Formula-based one-to-one associations

A `@OneToOne` association whose join mixes physical `@JoinColumn`s with `@JoinFormula`s (via
`@JoinColumnOrFormula`/`@JoinColumnsOrFormulas`, or the equivalent `<one-to-one>` mapping XML) is
now recognized and bound as a true one-to-one association instead of falling back to a logical
many-to-one. For each physical join column that is also part of the owner's primary key, Hibernate
infers `insertable=false, updatable=false`, since the identifier mapping already owns that column's
value. See the link:{userGuideBase}#associations-one-to-one-formulas[user guide] for details and examples.

[[flexible-constructor-enhancement]]
== Bytecode enhancement with Java 25+ flexible constructors

Bytecode enhancement now supports entities whose constructors use Java 25+ flexible constructor
bodies (https://openjdk.org/jeps/513[JEP 513]), where field writes occur before `super()`.
Field accesses on `this` before `super()` are emitted as raw `PUTFIELD`/`GETFIELD` (since
`INVOKEVIRTUAL` is illegal on `uninitializedThis`), with dirty tracking deferred to after the
`super()` call. Field accesses on other fully-initialized objects are enhanced normally.

If the enhancer encounters an unrecognized bytecode pattern in a constructor before `super()`, it
fails by default. Set `lenientConstructorTracking` to `true` in your build plugin configuration
(Gradle, Maven, or Ant) to fall back to skipping enhancement for the affected constructor instead.
See link:{versionDocBase}/javadocs/org/hibernate/bytecode/enhance/spi/EnhancementOptions.html#doLenientConstructorTracking()[`EnhancementOptions.doLenientConstructorTracking()`].
